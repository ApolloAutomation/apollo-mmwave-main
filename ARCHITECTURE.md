# Architecture

This document is for a maintainer new to the `apollo_mmwave` repository. It describes what the integration is, how the Python and TypeScript halves fit together, where data flows at runtime, and which values are tuning knobs. It cites functions, classes and constants by name rather than by line number, because names are the stable reference.

## Overview

`apollo_mmwave` is a Home Assistant custom integration (installed through HACS, `hacs.json`) for Apollo Automation mmWave radars: MSR-1 and MSR-2 (LD2410 chip), R PRO-1 (LD2412 plus LD2450) and MTR-1 (LD2450 only). It does not talk to hardware. The ESPHome integration already exposes the radar's sensors; this integration adds drawn occupancy zones on top of the LD2450 X/Y target sensors (with ignore zones, an exit-aware hold time, a zone map that lights zones and numbers and trails the live targets, and an opt-in, administrator-only movement history the map replays), a tuning dashboard for the gate radars, an empty-room auto-calibration of the gate thresholds, a setup card that checks either radar's settings, status and control cards for the LD2450 itself, a slider lock that keeps a scroll from moving the gate radar's sliders, a Device card on every tab, and a support file behind Home Assistant's Download diagnostics.

It has two halves that ship as one HACS package:

- The Python backend in `custom_components/apollo_mmwave/`. It owns a config entry, a persisted zone store (`.storage/apollo_mmwave.zones`), a persisted calibration store (`.storage/apollo_mmwave.calibration`), a movement store (`.storage/apollo_mmwave.movement`, which exists only while some radar has movement history on and has recorded something), the `apollo_mmwave.update_zone` service and the three gate-calibration services (`calibrate_gates`, `cancel_calibration`, `restore_gate_thresholds`), one `sensor` and one `binary_sensor` entity per zone, six websocket commands, the Lovelace resource registration, the config entry diagnostics (the support file), and the Apollo mmWave dashboard, which it creates only when an administrator asks.
- The TypeScript/Lit frontend in `frontend-src/`. Vite compiles it into two self-contained ES module bundles that are committed under `custom_components/apollo_mmwave/www/` (`apollo-radar-tuning.js` and `apollo-radar-zone-map-card.js`, `const.py` `JS_BUNDLES`).

The backend serves the committed bundles itself at `/apollo_mmwave/<bundle>?v=<manifest version>` and registers them as Lovelace module resources and extra JS URLs (`frontend.py` `async_register_frontend_assets`). Users therefore install one repository and get the cards, the strategy and the backend together. The `www/` folder is a committed build output, not a scratch directory (`frontend-src/vite.config.ts`), and CI fails if it is stale (see Build, test and CI).

Display text spells the product "R PRO-1". The ESPHome model ids `R-PRO-1-W` / `R-PRO-1-ETH` and the `r-pro-1` model prefix keep their hyphens, because the registry match depends on them.

## Runtime data flow

### Device entity to integration to storage to presence sensors

1. The ESPHome device exposes LD2450 target sensors named `sensor.<base>_ld2450_target_<n>_x` / `_y` (R PRO-1) or `sensor.<base>_target_<n>_x` / `_y` (MTR-1). `resolve_target_pairs` (`ld2450.py`) scans the entity registry for one device, matches `TARGET_X` / `TARGET_Y` and returns `[{x, y}]` pairs sorted by target number, skipping disabled entities. `async_track_target_pairs` (`ld2450.py`) installs a per-device cache in `hass.data["apollo_mmwave"]["ld2450_pair_cache"]`. Its entity registry listener acts only on target sensors: it returns unless the event's `entity_id`, or the `old_entity_id` a rename reports, is a `sensor.` id whose object id matches `TARGET_X` or `TARGET_Y` (`_is_target_sensor`). For such an event it invalidates every cached device whose pairs name either id, plus the entity's current device when that one is cached, and sends one `SIGNAL_ZONES_UPDATED` per invalidated device. This integration's own zone entities live on the radar device but never pass the filter, so creating or renaming a zone does not republish that device's zones a second time. When setup runs before Home Assistant has finished starting, a one-shot `EVENT_HOMEASSISTANT_STARTED` listener invalidates every cached device and re-fires the signal for each, so pairs resolved before ESPHome registered its entities are resolved again. Ahead of the target-sensor filter, the listener handles one case for this integration's own entities: an `update` event that carries `old_entity_id` (HA sends it only for an entity id change) for one of them with a device sends `SIGNAL_ZONES_PAYLOAD` with that device id and returns: the card lights a zone by its presence entity id, so a renamed id must reach it, and only the websocket forwarders listen, because the platforms and the recorder have nothing to redo and HA is removing and re-adding the renamed entity at that moment, which a platform sync must not race. A zone rename changes only the registry `name`, so it still pushes exactly once.
2. At setup, zones can enter the store from the migration paths (`async_migrate_legacy`, `async_import_zone_mapper`, `_promote_resolvable_orphans` in `migration.py`, and the v1 to v2 rekey in `store.py`). After setup, zones enter the store only through the service. `handle_update_zone` (built by `_build_update_zone_handler` in `__init__.py`) runs the body, `update_zone`, under one `asyncio.Lock` per handler, so calls run one at a time (see the `movement_history` save at the end of this step). `update_zone` resolves the device via `_resolve_target_device`, then `_call_changes_something` refuses calls that would change nothing. A call counts when it carries a device-wide field (a `rotation_deg` that survives `_sanitize_rotation`, `input_units`, a `display_units` that `_display_units_change_something` accepts, `clear_entities`, a non-empty `entities`, or `mirror_x` or `movement_history`, where `true` always counts and `false` only while the flag is stored, `_flag_changes_something`), or a `zone_id` together with `delete: true`, a `shape` (including `none`), or a `name` or zone setting for a zone the store already holds (`_zone_part_changes_something`, which reads `store.devices` and never the minting `store.device()`; `_zone_settings_change` counts `zone_type: ignore` and a `hold_s` above 0 on an existing zone even when already stored, `detect` only on an ignore zone and `hold_s: 0` only on a zone with a hold). `zone_type` or `hold_s` without a `zone_id` is ignored with a warning, and on a missing zone it is refused with the "does not exist" warning. So `{device_id, zone_id}`, `{device_id, zone_id, data}` without a shape, and a rename of a missing zone are refused with "carried nothing to change": no store entry is created, nothing is saved, and neither the signal nor the bus event fires. A refused zone part does not drop the device-wide part of a mixed call (`{zone_id: 7, name, rotation_deg: 90}` with no zone 7 still stores the rotation). `display_units` `m` or `ft` always counts, even when it is the unit already stored (as `input_units` does), while `auto` counts only when the device has a saved unit to forget; that check reads `store.devices`, so `auto` for a radar with no store entry creates none. The card adds `input_units` to every geometry, rename and rotation write, so those calls always count; its m / ft switch sends `display_units` alone, which counts on its own. The handler also warns about data sent without a shape, geometry sent without a `zone_id`, and a name given to a zone that does not exist. It then fetches `store.device(device_id)` (`store.py`), applies `rotation_deg`, `input_units` and `display_units` (`_apply_device_settings`; `auto` pops the stored key), `mirror_x` and `movement_history` (`_apply_device_flags`: true stores `True`, false pops the key) and tracked pairs (`_apply_entity_pairs`), then either deletes, renames and applies `zone_type` and `hold_s` to the stored zone (`_apply_zone_settings`: `ignore` and a hold above 0 are stored, `detect` and 0 pop the key), or normalizes geometry through `_normalize_zone_payload` into whole millimeters. The geometry branch reads the existing zone first and rebuilds the zone dict on every write, carrying over its `name`, `zone_type` and `hold_s` (`_carry_zone_settings`) before the call's own settings apply, so a redraw, an Undo, Clear All and `shape: none` never drop a zone's type or hold. Every mutating path ends in `_notify_zones_updated`, which schedules a debounced write (`ZoneStore.async_delay_save`, `SAVE_DELAY_SECONDS` in `store.py`), sends the dispatcher signal `SIGNAL_ZONES_UPDATED` with the device id, and fires the public bus event `apollo_mmwave_zone_updated`. After it, the geometry branch writes the registry names (`_update_registry_names`; both platforms register a new zone's entities inside that dispatch, so a name on the creating call reaches them, X01), except on the creating call with the default `Zone N` that Add Zone sends, which would read "Zone 1 - Zone 1". That call, and a creating call with no name, clears the zone's generated registry names instead (`_clear_generated_names`, since 2.4.0b3, J9): Add Zone takes the lowest free id, and Home Assistant restores a deleted entity's registry name and entity id when the same unique id registers again, so a new zone 1 came back as "Zone 1 presence - Couch". A name `_is_generated_name` does not recognize, one the user typed, stays, and so does the restored entity id, which no public API prevents. `_update_registry_names` itself takes the default `Zone N` for a clear, because the zone list's Save sends it for a cleared field and for a row nobody touched: it writes the bare bases over a generated name and skips an entity whose registry name is None. A call that turns `movement_history` off awaits `store.async_save()` before the notify: the zone store is saved at once, before the zone signal and so before the movement history is deleted, because `_reconcile` can start removing the movement file inside that signal (Home Assistant starts the background task eagerly). A crash between the two writes can never bring recording back. That save is the body's only await, and the lock is for it: a call run inside it, such as a second administrator turning history back on, would set the flag again before the signal, which would then keep the history the first call was to delete, or would send its own zone signal before the off state is on disk.
3. `async_setup_zone_platform` (`zone_entities.py`) runs `_sync_entities` once at platform setup and again on every `SIGNAL_ZONES_UPDATED`. It diffs `store.devices[*]["zones"]` against a `ZoneEntityTracker` and creates a `ZonePresenceBinarySensor` (`binary_sensor.py`) and a `ZoneCoordsSensor` (`sensor.py`) for each missing `(device_id, zone_id)`, skipping entries the user disabled. It does nothing while the entry is unloading (`tracker.unloading`).
4. `ZonePresenceBinarySensor.async_added_to_hass` calls `_track_coordinate_entities`, which resolves pairs via `effective_target_pairs` (`ld2450.py`: the stored `entities` list if the key is present, else the cached auto-detected pairs), de-duplicates the X/Y entity ids (pairs may share an entity) and subscribes `async_track_state_change_event` once per id. A state change runs `_handle_coordinate_update`, which only schedules one `_flush_evaluation` with `hass.loop.call_soon` (held in `_pending_eval`; further events are ignored while it is pending, and it is canceled in `async_will_remove_from_hass`). The flush runs `_evaluate_and_write`. A target's X and Y are two entities written one after the other, so evaluating on each write tested a point no target occupied (new X, old Y) and could pulse presence on and off. The coalescing removes that pulse when both writes land in one event-loop turn. The LD2450 of an R PRO-1 on firmware 26.10.21.1 writes each axis about once a second (1.0 to 1.15 s), with Y usually about 0.45 s after X in a turn of its own and sometimes in the same instant, so since 2.4.0b3 presence also pairs the two writes across turns (B10). Each entity keeps a `targets.ReadingPairer` (`_pairer`), and `masked_readings` hands it every slot's reading with the evaluation's time in whole ms. An axis written alone waits up to `TARGET_PAIR_MS` (550 ms) for the other axis's write while the slot's last whole reading stands in, so a zone beside a walking path never reads the new X with the old Y. An axis written twice before the other moves alone, and a move along one axis counts once `TARGET_PAIR_MS` has passed, through a per-entity timer (`_schedule_pair_expiry` at `ReadingPairer.due()`), because Home Assistant writes nothing for the axis that did not change. That applies to zones with no hold too. The first half of a 0/0 vanish or appearance is passed on unpaired, for the hold's own filter. The pairer resets when the tracked id list changes (a slot is a position in it) and is dropped (`_drop_pairing`) for an ignore zone, an offline radar and a zone with no usable shape. In the review's simulation of walk-ins at that cadence, a zone turned on at the same moment as in 2.4.0b2 in 65% of runs and 0.45 s later in the rest, never more than 0.55 s later and never earlier. The movement recorder pairs by the same `targets.AxisPairing`, and the card's trails and Coverage by `TRAIL_PAIR_MS` (`trails.ts`), which `tests/test_contracts.py::test_presence_the_recorder_and_the_trails_pair_x_and_y_alike` keeps equal to `TARGET_PAIR_MS`; it also checks that neither `binary_sensor.py` nor `movement.py` keeps a `*_PAIR_MS` of its own. The hold's rules are tuned for that cadence (see `hold.py`). Zone changes and the initial evaluation stay synchronous. `_evaluate_and_write` reads the zone from `store.zone()` and the device dict from `store.devices.get()` (neither mints an entry) and picks one of three writers: an ignore zone (`zone_type_of`) gets `_write_ignore` (off, available, `{zone_type: "ignore"}`, no hold, even while the radar is offline); a radar that `targets.radar_offline` reports offline gets `_write_offline` (unavailable and off, hold dropped, X09); every other zone gets `_write_detect`. The readings come from `targets.masked_readings`: `iter_slot_points` walks the effective pairs, keeping each pair's index as its slot, and `read_point` parses both states, drops a missing, `unknown`, `unavailable` or non-finite value, drops the exact `(0, 0)` idle-slot sentinel (tested on the raw readings) and converts each reading to millimeters by its own entity's unit (`reading_unit_factor`): `SENSOR_UNIT_FACTORS[unit_of_measurement]` when that attribute is a Home Assistant length unit, else `INPUT_UNIT_FACTORS[input_units]` (default 1.0, `fallback_factor`). X and Y are converted separately. ESPHome reports the targets in millimeters, but Home Assistant set to US customary units gives a new `distance` sensor reported in millimeters (or centimeters) a suggested unit of inches (meters become feet and kilometers miles), and a user can pick any length unit per entity, so the state is in whatever unit the attribute names. A unit change on its own is an attribute-only `state_changed`, which the subscription also receives, so presence re-evaluates. Each point is then rotated by the device's `rotation_deg` (`build_point_rotator`; a stored value that is not a finite number, such as a hand-edited `"inf"`, means no rotation) and dropped when it falls inside any of the radar's ignore zones. Without a hold (`hold_s` 0), any remaining whole reading inside the shape (`targets.shape_tester`) sets `is_on`, as before 2.4.0 but for the pairing, and the entity has no attributes. With a hold, `HoldTracker` (`hold.py`) decides from the inside and outside readings and the entity publishes `held` (see `binary_sensor.py`). Who is inside is decided by each whole reading, while rule 2's reports come from the latest write, stamped when it landed (`Reading.written`, `written_at`): an axis written alone is a real report, often the last one before the radar loses a walker. A target lost while its write waited (`ReadingPairer.lost`) is stepped through the hold once more with that write, so a held zone reads it as the person's last report; a zone with no hold never reads it. Without that, the review's bed sit case fell from 94.2% to 73.3% held.
5. `ZoneCoordsSensor.extra_state_attributes` (`sensor.py`) publishes `shape`, `data`, the effective `entities` list, `rotation_deg` (when set) and `name` (when not empty), plus `zone_type: "ignore"` and `hold_s` only when they are not the defaults, reading through `store.devices.get()` and `store.zone()`; its state is the zone id. Both entities rewrite state on `SIGNAL_ZONES_UPDATED` for their device.

### Device entity to websocket to cards

1. The zone map card's `setConfig` (`frontend-src/src/zone-map/card.ts`) requires `device_id` and calls `_connectZones`, which hands off to `connectZones` (`frontend-src/src/zone-map/api.ts`). That subscribes first (`subscribeZones`, command `apollo_mmwave/zones/subscribe`), then reads once (`fetchZones`, command `apollo_mmwave/zones/get`), drops the read if a push already arrived, and retries with `RETRY_DELAYS_MS` while the backend answers `not_loaded` or HA's `unknown_command` (`isNotLoaded`). HA answers `unknown_command` on a fresh boot: the websocket is up from the start, and this integration registers its commands only when its entry sets up. `connectZones` also re-opens both when `subscribeEntryLoads` sees this domain's config entry reach state `loaded`; HA's `config_entries/subscribe` is not admin-gated in any supported version, so every viewer gets this recovery. `connectZones` serializes overlapping opens through a promise queue (`requestOpen`), so a reload burst or a retry landing on an entry update cannot leave an orphan server-side subscription. When `setConfig` is called with a different `device_id`, `_resetDeviceState` disposes the subscription and clears zones, tracked entities, the undo snapshot, any shape in progress (`_resetDrawingState`), cone angle, lock, and the saved and picked map units; `_connectZones` tags each connection so payloads from a superseded connection are dropped. On supported Home Assistant (2026.8.1 and later) the card editor preview and a regenerated view or section build a fresh element instead of calling `setConfig` again, so a live retarget comes only from a parent that reassigns `config` on the same `hui-card` or a wrapper card that calls `setConfig` directly.
2. On the server, `ws_get_zones` and `ws_subscribe_zones` (`websocket.py`) both pass `_answerable` (`not_loaded` if the store is gone, `not_found` if the device id is not in the device registry) and answer with `_payload`, built from `store.devices.get(device_id)`: `zones` (string ids; each zone dict is copied, never mutated, its `zone_type` and `hold_s` normalized through `zone_type_of` and `zone_hold_s`, so a hand-edited value reads as the default and is left out, and `presence_entity_id` added from the entity registry, null while the presence entity is not registered), `entities` (null means never configured, `[]` means cleared), `rotation_deg`, `label`, `input_units` (null means millimeters), `display_units` (the map unit an administrator saved, `m` or `ft`; null means the card follows Home Assistant's unit system), `mirror_x` and `movement_history` (always booleans, `device_flag`) and `suggested_entities` (a fresh `resolve_target_pairs`). The subscription's `_forward` listens to `SIGNAL_ZONES_UPDATED` and to `SIGNAL_ZONES_PAYLOAD` (the websocket-only re-push after a presence entity id rename) and pushes a new payload for the matching device; its teardown disconnects both. One zone edit (create or rename) produces exactly one push, and a zone's creation push already carries its presence entity id, because both platforms register their entities inside the dispatch, before the forwarder runs (probed on HA 2026.10; a test pins it). A subscription ends on any of three paths (the client's `unsubscribe_events`, the connection closing, the config entry unloading). Its `_teardown` is a no-op the second time and leaves `connection.subscriptions` alone, because HA iterates that dict to run every teardown when the connection closes.
3. The card applies each payload in `_applyZoneConfig` (`card.ts`), in this order: `_applyZones`, `_applyRotation`, `_applyMirror`, `_applyDisplayUnits`, `_applyTrackedEntities` (which redraws the offline note), the movement history flag (`movement_history === true`), label, title, `_applyAutoLock`, the zone buttons and manager, `_renderAdminControls`, `_refitGrid`, the unit switch, the help line and `drawGrid`. `_applyZones` splits drawable zones from the zone list, which is the union of the YAML `zones:` seed and the store's ids: per id a non-blank stored name wins, else the YAML name, else `Zone N`. Geometry writes carry no name, so a YAML-named zone that gets drawn keeps showing its YAML name. It also builds `_zoneMeta` for every payload id, geometry-less zones included: the presence entity id (a string or null), the type (`ignore` only when exactly that) and the hold (a finite integer from 1 to 3600, else 0). The meta never goes on `this.zones`, whose entries `_upsertZone` and `_performUndo` rebuild as `{id, shape, data}`. `_applyRotation` sets the cone angle and slider from the store's `rotation_deg`, applying null as 0; the YAML `cone.angle_deg` is only the slider's double-click reset target. `_applyMirror` reads `mirror_x === true`, invalidates both render caches when it changes (no refit: the extents do not change) and, on every call, sets the cone slider's direction and the flip checkbox, because `render()` rebuilds both from the template. `_applyDisplayUnits` keeps the payload's `display_units` when it is `m` or `ft` and null otherwise. `_applyTrackedEntities` uses `entities` when it is an array and `suggested_entities` when it is null. Last, `_refitGrid` fits a grid the YAML does not set to the new zones, rotation and unit, and the unit switch and the help line under the map are redrawn (`_renderUnitSwitch`, `_renderInfo`). Until the first payload arrives, the entity status line reads "Waiting for this radar's configuration."
4. Live targets: `set hass` builds `_trackedStatesKey` (each tracked pair's X and Y entity ids plus both state strings and both `unit_of_measurement` attributes, since a unit change moves a target without changing its number) and `_zoneStatesKey` (each zone's presence entity id, its state and whether its `held` attribute is true), and paints only when either key differs from the one it last painted from; the first assignment with a canvas always paints. A change of the tracked key first runs `_onTargetsChanged(_now())` (trails, coverage, the offline note, the Walk panel), so a presence flip with no target movement repaints without adding a trail point. While a replay shows (`_replayShowing`: the History panel is open and its series has loaded) the replay timer is the only painter, so a push only updates state. The draw after a push stays synchronous, with no `requestAnimationFrame`, because the card tests count those draws. A push that changes no tracked target or zone state leaves the canvas alone; zones, rotation, draw mode, lock, theme and config repaint through their own paths. `drawGrid` reads the canvas scale once per frame (`_frameScale`, which dot radii, trail widths, readouts, markers and the label gap of `_getGridRenderState` and `_rangeLabel` use, so a frame calls `getBoundingClientRect` once) and draws, in order: the cells (the history heatmap while a replay shows with Heatmap on, else live coverage when it is on), first so no grid, ring or range label is tinted by them; the grid lines, axes and labels, after which `_placeMapNotes` moves the notes clear of the x labels, the cone (`drawDeviceCone`) and its range caption (`_rangeLabel`); the zones (`drawZones({lit})`, lit from the replay while one shows, else from presence); the shape in progress (`_drawInProgress`, rebuilt from stored state so any repaint keeps it on screen) and the Walk preview; the trails, then the dots (the replay's while one shows, else live); the Walk corner markers; the size readouts of the shape in progress and of Walk (`_drawInProgressReadout`, `_drawWalkReadout`), after everything else, so no ring, trail or dot runs through them; and finally it stamps `_lastDrawAt`. The live dots come from `_currentTargets` (extracted from the old `_drawTrackedTargets`), which reads `hass.states[pair.x].state` and `hass.states[pair.y].state`, skips near-zero raw readings, converts each reading to millimeters by its own entity's unit (`_readingUnitFactor`: `SENSOR_LENGTH_UNITS[unit_of_measurement]` when that is a Home Assistant length unit, else the multiplier of the card's YAML `input_units`); `_toMap` then rotates each point by the cone angle. The conversion is the backend's `targets.read_point` rule, so a target drawn inside a zone is one its presence sensor counts. See "Zone map live view, Walk and history" for the drawing itself.
5. Writes go the other way: `endDrawing` or `finishPolygon` produce a payload, `updateHomeAssistantShape` wraps it, and `_saveZoneUpdate` appends `input_units` (unless called with `withInputUnits: false`) and calls `hass.callService("apollo_mmwave", "update_zone", request, undefined, false)`. The fifth argument (`notifyOnError = false`) turns off HA's own "Failed to perform the action" toast, so a rejected save shows only the card's "Could not save: <reason>" toast, the same convention as the calibrate card's `callService` helper. A success toast means HA accepted the call, not that the store took it: a call for a radar that left the device registry is logged and ignored by the backend but still answers success. The backend path above then pushes the result back over the subscription. The m / ft switch (`_chooseDisplayUnit`) writes `{device_id, display_units}` this way, with no success toast and with `withInputUnits: false`, because the switch says only that it shows the map in a unit and `input_units` would also rescale presence for target sensors without a length unit. It writes only when `hass.user.is_admin` (`_isAdmin`); for anyone else, or a `hass` with no user, it changes that page's view and calls nothing, because the service would refuse them. The writes added in 2.4.0 take the same path, also with `withInputUnits: false`: the zone list's Type and Hold selects call `_saveZoneSetting(zoneId, {zone_type} or {hold_s})` once per change, which adds `shape: "none", data: null` for a zone only the YAML names (so the call creates it) and keeps the choice in `_zoneSettingPending` (`{value, seq}` keyed `<zone id>:<setting>`, cleared by `_resetDeviceState`) until its save settles, so a rebuild from an earlier save's echo still shows the newest choice (`_zoneMetaLine`); only the newest save settles its select, a refused one rebuilding the rows from the store, and an older save settles nothing; the flip checkbox writes `{device_id, mirror_x}`, applied at once and reverted on a refusal; the movement history checkbox writes `{device_id, movement_history}`, and turning it off waits for the inline confirm. Walk's Finish goes through the drawing paths: `_commitZoneShape` (the commit `endDrawing` uses) for a rect and `finishPolygon` for a polygon. Only an administrator gets these controls enabled; anyone else sees the selects and the flip disabled and no Walk or movement history controls.
6. The tuning cards do not use the websocket. `ApolloLd2410DistanceCard.shouldUpdate` (`frontend-src/src/cards/distance-card.ts`) calls `resolveRadar` (`frontend-src/src/cards/resolution.ts`), memoized on `config`, `hass.entities` and `hass.devices`, which calls `resolveEntitiesDetailed` and `resolveProfile` (`frontend-src/src/entities.ts`). A base-name fallback resolution (a `device_base_name`-only config, or a `device_id` whose entities are not in `hass.entities` yet) also depends on `hass.states`: `ResolvedRadar` records `fallbackBase` and the `detectProfile(hass, fallbackBase)` result as `fallbackDetected`, and the cache is reused only while a fresh detection agrees. An R PRO-1 card resolved before its LD2412 engineering-mode switch reached the states therefore moves from LD2410 ids to LD2412 ids on the tick the switch appears. Registry-resolved configs (the strategy's normal case) record no `fallbackBase`. Each card then re-renders only for the slots its chart reads (`DISTANCE_CHART_SLOTS` or `GATE_ENERGY_CHART_SLOTS`, flattened once per resolution by `watchResolved` and checked by `drawnStatesChanged`). `render` reads `hass.states` through `distanceModel` (`frontend-src/src/charts/distance-chart.ts`) or `gateEnergyModel` (`frontend-src/src/charts/gate-energy-chart.ts`).

### Card to service to job to websocket

1. The calibrate card (`frontend-src/src/cards/calibrate-card.ts`) subscribes to `apollo_mmwave/calibration/subscribe` for its device and calls `apollo_mmwave.calibrate_gates` with `{device_id}` plus its `calibration` block (`startCalibration` in `calibration/api.ts`). It never awaits that call for its UI: progress arrives over the subscription, which is why a job survives the browser closing.
2. `handle_calibrate_gates` (`calibration.py`) looks the calling user up (the only await of the pre-flight), then runs every check and the registration with no await between them, so two calls cannot both register a job for one device: `_single_device_id`, `_preflight_calibrate` (`calibration_running`, `no_gate_entities`, `engineering_mode_missing`, `device_offline`, `background_correction_running`, `thresholds_not_numeric` over every threshold the chip is sent with the writes, which is all 28 on the LD2412 and both numbers of every written gate on the LD2410 (its message only counts them; the ids are in the `entity_ids` placeholder and a warning log line), `margin_zero`, `not_allowed`; each a `ServiceValidationError` whose translation key is in `translations/en.json`), then `_launch` registers the `CalibrationJob` in `hass.data["apollo_mmwave"]["calibration_jobs"]` keyed by device id, starts `job.run()` as an entry background task, fires `apollo_mmwave_calibration_started` and returns `job.public_state()`, or, with `wait: true`, shields `job.done.wait()` and returns `job.result_payload()`.
3. `CalibrationJob.run()` delegates to `_prepare`, `_sample`, `_compute`, `_apply` and `_verify`, with `_finish` as the finally. Every timed phase is driven by one `async_track_time_interval(TICK_S)` tick and `asyncio.Event`s the tick sets, so tests drive it with `async_fire_time_changed`; the only `asyncio.sleep` calls are `WRITE_SPACING_S`, `VERIFY_SETTLE_S` and `RESTORE_READBACK_S`. `_prepare` hard-saves the `interrupted` marker (phase `engineering`) before `switch.turn_on` when the switch is off, waits for it to read `on` within `ENGINEERING_CONFIRM_TIMEOUT_S` (`engineering_mode_not_confirmed`), then runs the settle countdown and the energy warmup side by side; sampling starts on the first tick at which both hold, and `no_energy_data` fires `ENERGY_WARMUP_TIMEOUT_S` after the switch read `on` even mid-countdown. `_sample` takes one read of every energy sensor per tick (`samples` counts ticks; a state-change listener only raises the per-entity `event_peak`), counts ticks with the radar-target and moving-target sensors on, and the liveness guards fail the job with `engineering_mode_lost` (switch `off` for `ENGINEERING_LOST_TICKS` ticks) or `background_correction_started`. `_compute` runs `calibration_math.compute_channel` per gate channel and adds the `unused`, `skipped`, `off` and `gates_off` rules. `_apply` fails `no_gate_data` before touching the device when no gate collected `MIN_SAMPLES` readings, presses the LD2412 query-params button (`sub_phase: "refresh"`), re-checks that every threshold the chip will be sent is numeric, captures the current values (the snapshot, every `old` and the skip rule all come from this one read, and a cell's `unchanged` is recomputed from it), pushes once the plan and `writes_total` are known, takes no snapshot or marker at all when every value is already within tolerance, otherwise hard-saves the snapshot (`snapshot_failed` otherwise, and nothing is written), hard-saves the marker with phase `applying`, then writes gate by gate, move then still, skipping values within `VERIFY_TOLERANCE` of the capture, `WRITE_SPACING_S` apart; `device_offline`, `write_failed` and `not_allowed` stop it while keeping `writes_done`, `writes_total` and `snapshot_id` so the card can offer Undo. `_verify` presses the LD2412 button again, waits `VERIFY_SETTLE_S` and compares every written number numerically; mismatches and unreadable states go to `unverified` and the outcome becomes `partial`.
4. `_finish` runs on every exit path, including task cancellation from an unload or HA stop (`asyncio.CancelledError` is mapped to `cancelled_by_shutdown` and re-raised only after the restore attempt; a second cancellation during the restore is tolerated). It removes the tick and the listener, turns the switch off only if the job turned it on (bounded by `SHUTDOWN_RESTORE_TIMEOUT_S`, every exception logged at warning), reads the switch back, settles the marker (`_settle_marker`: everything is cleared when the switch reads `off`; a shutdown keeps the phase it was in so the banner can offer Undo after the restart; a finish the job reached itself clears the write phase and keeps the engineering fact, with `left_on` set when the turn-off was not echoed), persists `last_result` with a delayed save when the store is still in `hass.data`, removes the job from the registry, dispatches `SIGNAL_CALIBRATION_UPDATED`, fires `apollo_mmwave_calibration_finished` and sets `job.done`.
5. Only three device write shapes exist, all `blocking=True` with the service call's context: `number.set_value {entity_id, value}`, `switch.turn_on` / `turn_off {entity_id}` and `button.press {entity_id}`.
6. `ws_subscribe_calibration` (`websocket.py`) answers null, pushes `calibration_payload(hass, device_id)` at once, then forwards every `SIGNAL_CALIBRATION_UPDATED` for the device; `_calibration_loaded` requires both calibration keys in `hass.data` (`not_loaded` otherwise) and the forwarder re-checks them before every push. `restore_gate_thresholds` reuses the same job with `kind: "restore"`: the shared pre-flight plus snapshot resolution (ids re-resolved through `unique_id`, ids that left the registry or are disabled reported in `missing` and left out of the offline, numeric and permission checks), a redo snapshot with reason `restore`, the same paced writer and verification, and no engineering-mode touch.

### Device entity to movement history to the card

1. An administrator turns the flag on (`update_zone` `movement_history: true`, from the card's Configure checkbox or an automation). `MovementHistory._reconcile` (`movement.py`, the instance at `hass.data["apollo_mmwave"]["movement"]`, `DATA_MOVEMENT`) runs on `SIGNAL_ZONES_UPDATED` and starts one `_Recorder` for a radar whose zone-store entry has the flag and whose device is in the registry. Nothing is recorded, and no file is created, for a radar without the flag.
2. The recorder subscribes to the radar's effective pair ids, coalesces the writes of one loop turn with `call_soon` as presence does, and on each flush reads `targets.masked_readings`, so it sees exactly what presence sees: a target inside an ignore zone is invisible to it, and a slot that enters one gets a gone marker. An R PRO-1 often writes Y about 0.45 s after X, in a turn of its own, so one flush can see half a move, and each slot pairs its writes by the rule presence uses (`_SlotState.split`, a `targets.AxisPairing`, and `TARGET_PAIR_MS`): an axis written alone waits up to 550 ms for the other axis's write, an axis written twice before the other moves alone until the other is written (so a radar that reports several times a second keeps two points a second), and only a whole reading is recorded, so no point pairs a new X with an old Y; a move along one axis is stamped 550 ms after its write. It records a point when a slot appears, after a move of `MOVEMENT_MIN_MOVE_MM` at most every `MOVEMENT_MIN_INTERVAL_MS` (a move that comes too soon, or waits for its other axis, waits for the tick, which records wherever the target is by then), and every `MOVEMENT_HEARTBEAT_MS` while the slot stays, because a value that repeats is never written and jitter under 50 mm is no move; a gone marker when the slot loses its target bypasses the floor. The half-vanish filter is the hold's (`hold.half_vanished`, and `HALF_VANISH_MAX_S` as `MOVEMENT_HALF_VANISH_MAX_MS`): the first half of a vanish, or of an appearance in a slot that read 0/0, is held back however many flushes run before the second half lands, for up to that bound while it stays unchanged, and the slot's last good reading stands in for it, so a heartbeat still records the person and an appearance records nothing until it is whole. The floor, the heartbeat, the pair window and that bound run on `time.monotonic()` (`_mono_ms`); the wall clock (`_now_ms`) only stamps the records and detects a step back, so a clock step back of up to `MOVEMENT_CLOCK_STEP_MS`, whose records `_record` stamps at the last time, no longer holds the floor and the heartbeat back. One timer per radar (`_schedule_tick`, from each slot's `due()`) runs only while a slot is present or holds a reading back: at the floor of a pending move, else the next heartbeat, either one no sooner than the reading is whole, or at the moment a held-back reading counts. Points are integer millimeters in the raw sensor frame: unit converted, not rotated, not mirrored.
3. `MovementHistory` keeps each radar's records in packed arrays (`_Columns`), schedules one delayed save per dirty period (`MOVEMENT_SAVE_DELAY_S`), prunes to 24 hours on a retention timer even while nothing new arrives, trims a radar back to `MOVEMENT_MAX_POINTS` once it passes the cap by `MOVEMENT_PRUNE_SLACK`, and removes the file instead of saving it when no radar has records left (see `movement.py` and the movement storage schema under Contracts).
4. The card shows **History** only to an administrator with the flag on. Opening it, or changing the range, sends `apollo_mmwave/movement/get {device_id, since}` (`fetchMovement`, administrators only on the server too) and gets the packed columns with the server's `now`; `history.ts` `decodeMovement` turns them into per-slot series and the card replays them (see "Zone map live view, Walk and history"). **Clear history** sends `apollo_mmwave/movement/clear {device_id}`, which empties that radar, keeps the flag and keeps recording. Turning the flag off stops the recorder and deletes the radar's records, saved within `MOVEMENT_CLEAR_SAVE_DELAY_S`.

## Backend modules

### `__init__.py`

`async_setup_entry` loads the store. When `ZoneStore.async_load` returns `False` (no file, or a payload that is not an object), it runs `async_migrate_legacy` and then `async_import_zone_mapper` and saves once after both, so a fresh install writes the file once and a failed import leaves no half-populated file behind. It then runs `async_migrate_unique_ids`, stores the `ZoneStore` at `hass.data["apollo_mmwave"]["store"]`, creates `MovementHistory(hass, store)` (`movement.py`), awaits its `async_load` and stores it at `hass.data["apollo_mmwave"]["movement"]` (`DATA_MOVEMENT`), installs the LD2450 pair cache, calls `movement.async_start()` and registers the movement teardown (`_movement_teardown`: pops `DATA_MOVEMENT` and returns `movement.async_stop()`), registers `update_zone` with `UPDATE_ZONE_SERVICE_SCHEMA` and, right after it, the zone teardown (`_teardown`: removes the service, pops the store and returns `store.async_save()`). It continues with the websocket commands, the `async def` teardown returned by `async_setup_calibration` (`calibration.py`), the platforms (`PLATFORMS = [binary_sensor, sensor]`) and the frontend assets. Setup and reloads never create, rewrite or delete a dashboard, and there is no options update listener, so no options change (the flow's own saves included) can set off dashboard work.

`async_migrate_entry` moves entries from 2.2.5 and earlier (config entry minor version 1) to minor version 2 (`ENTRY_MINOR_VERSION`), before their first setup. It drops the old `auto_create_view` option and records which dashboard the entry owns in `dashboard_id` and `dashboard_url_path`, writing nothing to Lovelace: with that option on (or absent, its old default), `frontend.async_find_legacy_dashboard` returns the id of a row on url path `apollo-mmwave` whose own stored config is exactly `{"strategy": {...}}` with our type (keys the user typed under `strategy` included), and otherwise the entry owns none (both None). A taken-over dashboard, one with more than a `strategy` key, a row with no config and a YAML dashboard on the path are not adopted, and with the option off nothing is, so a strategy dashboard the user built there is left alone (X03). `dashboard_devices` is kept. The migration always returns True. When the dashboards cannot be read (the collection is unreachable or the lookup raised), `async_find_legacy_dashboard` logs a warning and raises `DashboardsUnreadableError`, and the migration returns without updating the entry: it keeps minor version 1 and `auto_create_view`, owns no dashboard meanwhile, and the next setup looks again. Unknown is never recorded as none.

Every teardown is an `entry.async_on_unload` hook. Home Assistant runs the hooks newest first, after `async_unload_entry` returns `True`, and starts a coroutine a hook returns as a task that the unload waits for (up to 10 s). On unload the order is therefore: calibration teardown (which then waits on running jobs), websocket subscriptions closed, zone teardown (service removed, store popped, store flushed), movement teardown (`DATA_MOVEMENT` popped, every recorder stopped with gone markers for its open slots, and a final write only when a save was scheduled: the records when any are left, else the file removed; the zone teardown has popped `DATA_STORE` by then, so `MovementHistory` keeps its own zone-store reference), LD2450 pair cache. Because the zone teardown is a hook, a setup that fails after the service was registered (platform forwarding, frontend assets) no longer leaves `update_zone` or a stale store behind: HA runs the hooks for a failed setup and never calls `async_unload_entry` for it. A failed platform unload skips the hooks, so the service and store stay. `async_unload_entry` itself only unloads the platforms. The calibration websocket commands guard on their own keys because the zone store can be gone while the calibration teardown is still waiting on a job. `async_remove_entry` removes the dashboard the entry recorded (`async_remove_dashboard`: by id, and only while its config is still our strategy; an entry that owns none touches no dashboard), then the Lovelace resource rows (`async_remove_lovelace_resources`, skipped while another non-ignored Apollo mmWave entry remains), removes the zone store through the live instance in `hass.data` when there is one (which cancels a pending delayed save that would otherwise write the file back about 2 s later; a fresh `ZoneStore` otherwise), removes the calibration file through a fresh `CalibrationStore`, and last awaits `async_remove_movement_store` (`movement.py`): when an unload failed and left the movement history running, it shuts that instance down without saving first (its recorders would otherwise write the file back within a minute) and removes the file through its `Store`, which also cancels a pending delayed write; otherwise it removes the file through a fresh `Store`. Either way it then deletes every `apollo_mmwave.movement.corrupt.*` copy.

The service side:

- `_device_id_from_call` accepts `device_id` as a string or a one-item list (the shape a `target:` block produces) and refuses multi-device targets. `_device_is_registered` is applied on every path, so an unknown or stale device id never reaches the `store.device()` setdefault.
- `_resolve_target_device`: when a call carries both `device_id` and `location`, `device_id` wins and `location` is ignored without the deprecation warning. The schema comment that says "Exactly one" is inaccurate; the schema requires at least one.
- Deprecated `location`: `_device_id_for_label` slug-matches the value against stored `label` fields first (the first device in store order wins), then against `aliases`, so either name a rename left behind reaches the radar and a device's own label beats another device's alias on a tie. `_device_id_for_deprecated_location` warns once per run via the `hass.data` flag `_DATA_LOCATION_WARNED` and refuses a label whose device has left the registry.
- `display_units` (`m`, `ft` or `auto`) is the unit the zone map card shows one radar's map in, for every viewer. It is display only: geometry stays millimeters and presence never reads it. `auto` removes the stored key, so the card follows Home Assistant's unit system again, and is never stored itself (`DISPLAY_UNITS_AUTO`).
- Zone settings and device flags (2.4.0): `zone_type` (`detect` or `ignore`, `ZONE_TYPES`) and `hold_s` (0 to `HOLD_S_MAX`, 3600) are zone settings and need `zone_id`; `mirror_x` and `movement_history` (`cv.boolean`) are device-wide like `display_units`. `_hold_seconds` refuses a boolean before `vol.Coerce(int)`, which would read `true` or YAML `on` as a 1 s hold; a float is still truncated, as for `zone_id`. Defaults are never stored: `detect` and `hold_s: 0` pop the zone keys and `false` pops the device key, so a call that only sends a default for a radar or zone that has none is refused as "carried nothing to change". The logic lives in helpers (`_zone_settings_in_call`, `_zone_settings_change`, `_apply_zone_settings`, `_carry_zone_settings`, `_apply_device_flags`, `_flag_changes_something`) so `update_zone`, the body `handle_update_zone` runs under its lock, stays under ruff's branch, return and statement limits. Turning `movement_history` off also deletes that radar's history (`MovementHistory._reconcile`).
- `_normalize_entities`: an empty `entities` list means "no change", never "erase", because a card calling the service before it had loaded used to wipe people's tracked pairs. `clear_entities: true` is the only way to empty the list, and it takes precedence over `entities` in the same call (`_apply_entity_pairs`).
- Rename: `_update_registry_names` writes the registry `name` as `Zone {n} - {zone_name}` / `Zone {n} presence - {zone_name}` (or the bare base when the name is empty) and only when `_is_generated_name` says the current name is still generated, so user-typed names survive. Both zone entities use `has_entity_name`, so before a rename their friendly names are "<radar name> Zone N" and "<radar name> Zone N presence". The explicit registry name replaces the whole friendly name, so a renamed zone's entities lose the radar prefix ("Zone 1 - Couch"), and a rename to "" writes the bare base, which is still explicit, so the prefix does not come back. Since 2.4.0 the geometry branch renames after `_notify_zones_updated`, by which time both platforms have registered a new zone's entities, so a name sent on the call that creates the zone reaches the registry too (X01); the default `Zone N` that Add Zone sends is skipped. Since 2.4.0b2 the default `Zone N` is a clear on every call: the zone list's Save sends it for a cleared field and for a row nobody touched, so `_update_registry_names` writes the bare base over a generated name, as for an empty name, and skips an entity whose registry name is None, which was never named and has nothing to clear; it never writes "Zone 1 - Zone 1". Delete removes both registry entries via `_remove_zone_entities`.
- Numbers: `_coerce_float` treats inf, nan, ints too large for a float and any magnitude above `_MAX_SAFE_INT` (2**53 - 1, JavaScript's `Number.MAX_SAFE_INTEGER`) as non-numeric. The bound is a serialization limit, not a geometry range: HA writes the store, websocket replies and recorder rows with orjson, which refuses ints outside 64 bits, and one such value used to make every later zone store write fail for every radar. A rect with such a bound clears with `WARN_RECT_NON_NUM`, an ellipse with `WARN_ELLIPSE_INVALID`, and a polygon drops that point. `_sanitize_rotation` goes through `_finite_float` instead: inf and nan are ignored (a rotation-only call then changes nothing), while a huge finite angle still clamps to 180.
- Geometry: each normalizer rebuilds a clean dict, so only the shape's own keys are stored (`x_min`, `x_max`, `y_min`, `y_max` for a rect; `cx`, `cy`, `rx`, `ry` for an ellipse; `points` for a polygon) and extra caller keys in `data` are dropped. Before 711f65b the rect and polygon paths kept them, which let an oversized extra value break every store write. Polygons with more than `POLYGON_MAX_POINTS` points are truncated with `WARN_POLY_TRUNCATING` (the slice runs before malformed points are filtered), not rejected; the card caps them too. A polygon clears with `WARN_POLY_INSUFFICIENT` when fewer than `POLYGON_MIN_POINTS` points arrive or `points` is not a list, and with `WARN_POLY_MALFORMED` when enough arrive but fewer than 3 parse as `{x, y}` numbers (for example `[x, y]` lists). A drawable shape sent with `data` omitted or null is stored as `{shape, data: null}` and logs `WARN_ZONE_NO_GEOMETRY`; `shape: none` is the quiet, documented clear. The warnings name "zone N on device '<device_id>'", and the `_normalize_*` helpers take the device id. There is no branch for an unsupported shape: the schema's `vol.In(list(SUPPORTED_SHAPES))` rejects it first.

The module also holds `_zone_entity_unique_ids` (used by the rename and delete paths, and by `websocket._payload` to look up each zone's presence entity id) and `get_store`, which `binary_sensor.py`, `sensor.py`, `zone_entities.py` and `websocket.py` import lazily, as `websocket.py` does `_zone_entity_unique_ids`. `__init__.py` imports `movement.py` at module level, as it does the package's other modules, so nothing is imported on the event loop later (`tests/test_imports.py` enforces it).

### `config_flow.py`

`ApolloMmwaveConfigFlow` has `VERSION = 1` and `MINOR_VERSION = ENTRY_MINOR_VERSION` (2). `async_step_user` shows two boxes, `create_dashboard` and `dashboard_admin_only` (`DEFAULT_CREATE_DASHBOARD` and `DEFAULT_DASHBOARD_ADMIN_ONLY`, both True), with a description that says what the dashboard is, that it is created once (if the first box stays ticked) and is never recreated or changed on its own, that removing the integration removes it unless the user took control of it, and where the Community dashboards picker is. On submit, with the first box ticked, it calls `async_create_dashboard(require_admin=...)` right there, then creates a single entry with `unique_id = "apollo_mmwave"`, empty `data` and `options = {dashboard_id, dashboard_url_path}` (`_ownership`): the new row's id and `apollo-mmwave`, or None for both when the box was unticked or nothing was created. A failed create (collection unreachable, url path taken, a write error) is a warning in the log and never blocks the setup. Neither box is stored. It aborts with `already_configured` when an entry exists (single instance is enforced in code, not through the manifest).

`ApolloMmwaveOptionsFlow.async_step_init` asks `async_dashboard_owned` whether the recorded row is still ours (`_owned`: True, False, or None when the collection cannot be read). It shows a menu: `add_dashboard` and `dashboard_devices` while the entry owns none, `dashboard_devices` and `remove_dashboard` while it owns one. With None it skips the menu and goes to `dashboard_devices`, keeping the recorded ownership. `add_dashboard` is a form with only `dashboard_admin_only` and a description of what it creates; Submit calls `async_create_dashboard` with the stored `dashboard_devices` and records the new row. `remove_dashboard` is a form with no fields that says what will be deleted; Submit calls `async_remove_dashboard` on the recorded row. `dashboard_devices` is a `DeviceSelector` filtered to `integration=esphome`, `manufacturer=ApolloAutomation` and `model in MMWAVE_MODELS`; While the entry owns a dashboard, or might (`_owned` None), Submit writes the selection into that row with `async_set_dashboard_devices` and stores it only if the write lands; owning none, Submit only stores it. `async_set_dashboard_devices` logs a warning when the collection is unreachable, so the form's error has a reason in the log. Each step finishes through `_save`, which keeps the current options, applies the step's change and, when `_owned` is False and a row is recorded, forgets it (both keys None): a dashboard the user deleted or took control of is never recreated or written to. An entry with no record keeps none, so a 2.2.5 entry whose migration could not read the dashboards yet can still adopt its old dashboard at a later start. A failed create, delete or write shows `dashboard_not_created`, `dashboard_not_removed` or `dashboard_not_updated` on the form and changes no option. HA's device filter compares `model` exactly, so `MMWAVE_MODELS` lists every firmware variant and must stay in step with the lower-cased prefixes in `frontend-src/src/profiles.ts` `APOLLO_MODELS`; `tests/test_config_flow.py::test_mmwave_models_match_frontend_prefixes` and `frontend-src/test/registry-detection.test.ts` check both directions. The `update_zone` service's own `device_id` selector stays unfiltered on purpose, so DIY hardware remains selectable. `ApolloMmwaveOptionsFlow` has no constructor and reads the entry through the base `OptionsFlow.config_entry` property; `async_get_options_flow` keeps HA's `config_entry` parameter but does not forward it. The flow does its dashboard work itself, before it saves, and saving the options sets off nothing else.

### `store.py`

`ZoneStore` wraps a `_MigratingStore` with key `apollo_mmwave.zones` and `STORAGE_VERSION = 2`.

Loading: `async_load` returns `False` when no file exists, and also when the file's `data` is not an object (logged at ERROR with its type); setup then takes the missing-file path and saves over it. Inside a well-formed payload, a `devices` or `orphans` value that is not an object is logged at ERROR and read as empty (`_section`) while the rest still loads; absent or null reads as empty without a log. Each entry goes through `_parse_entry(raw, device_id)`: int zone ids (`_parse_zones`), plus an allow-list of keys (`zones`, `entities`, `rotation_deg`, `label`, `aliases`, `input_units`, `display_units`, `mirror_x`, `movement_history`); anything else is dropped. The two flags are kept only when the raw value `is True`, so absent means off. `_parse_zones` keeps each zone dict verbatim, so a zone's `zone_type` and `hold_s` load with no change; the readers below normalize them. `aliases` keeps only its string items and is dropped when none are left. `input_units` is restored only when it is a string that is a key of `INPUT_UNIT_FACTORS`; any other value is dropped and the device reads as millimeters. `display_units` is restored only when it is `m` or `ft` (`DISPLAY_UNITS`); any other value is dropped and the card follows Home Assistant's unit system. `entities` (any list) and `rotation_deg` are carried verbatim (a string `'15'` loads as `'15'`). A zone value may be the empty placeholder `{}` from the legacy migration, which means no geometry. Every drop is logged at WARNING with its key: an entry that is not an object, a `zones` value that is not an object (null excepted), a zone key that is not a zone number, and a zone definition that is not an object. The log line is the only trace, because `_data_to_save` dumps the live dicts verbatim and the next save makes every drop permanent. A file that is not valid JSON is handled by HA's `Store`, which renames it to `.corrupt`. `ZoneStore` passes no `max_readable_version`, so HA's `Store` raises `UnsupportedStorageVersionError` for a file whose major version is above 2 before `_async_migrate_func` runs: a downgrade after a future version bump fails entry setup and leaves the file untouched. The `old_major_version > 1` branch only covers a version 2 file with another minor version, whose data passes through unchanged.

Migration: `_async_migrate_func` rekeys v1 `locations` (display names) into v2 `devices` (HA device ids) using `resolve_device_id` (public because `migration.py` shares it: tracked entity first, then the device name slug), retaining unresolvable entries under `orphans`. A v1 payload or `locations` value that is not an object is logged at ERROR and read as empty. When two v1 locations resolve to the same device (a mid-life rename), `_merge_location` folds them first writer wins per zone id and logs a WARNING only for a true id-level conflict; an empty `{}` placeholder does not count as a writer, so a real definition from a later location replaces it silently and a placeholder arriving after a real zone is skipped. Scalars (`entities`, `rotation_deg`) stay first writer. `_record_location` is the one helper all four merge paths use (`_merge_location`, `async_migrate_legacy`, `async_import_zone_mapper`, `_merge_promoted_orphan`): the first name becomes `label` and each later, different name is appended to `aliases`. Like `label`, `aliases` is never used to build an identifier.

Access: `device()` is a `setdefault` and the only accessor that mints an entry; it is for write paths only (the `update_zone` handler calls it after `_call_changes_something`). `zone()` reads through `devices.get()`, so `store.zone()` for an unknown device returns None and stores nothing, and every other reader uses `store.devices.get()`. Three pure readers, which every backend reader of the 2.4.0 keys uses because a hand edit can hold anything: `zone_type_of(zone_def)` is `"ignore"` only for a dict whose `zone_type` is exactly that, else `"detect"`; `zone_hold_s(zone_def)` is an int (not a bool) or a finite float above 0, truncated and capped at `HOLD_S_MAX`, and 0 for anything else; `device_flag(entry, key)` is true only when the value `is True`. `STORAGE_VERSION` stays 2 with no minor bump. Going back to 2.3.0, its allow-list drops `mirror_x` and `movement_history` at its next save, and a zone's `zone_type` and `hold_s` stay until 2.3.0 rewrites that zone (a redraw, Undo, Clear, Clear All or `shape: none` rebuilds the dict with shape, data and name only), ignored until then.

### `migration.py`

Three one-way upgrade paths run from setup. `async_migrate_legacy` rebuilds zones from the RestoreEntity attributes of pre-1.2 sensors whose unique id is `apollo_mmwave_<slug>_zone_<n>`, resolving once per location; it keeps an empty placeholder for a zone with no shape so the entity is recreated, puts an unresolvable location in `orphans` with a warning, and skips a restored `rotation_deg` that cannot be rounded (such as `"inf"`) instead of raising out of setup. `async_import_zone_mapper` does the same for the standalone `zone_mapper` platform, except that it skips zones whose restore attributes carry no `shape`, and a location that matches no device is skipped with a warning rather than kept as an orphan; the import is read-only with respect to that integration and counts defined zones (`_defined_zone_count`), so filling a placeholder counts as an import. Neither saves the store; `async_setup_entry` does, after both. Both run only when `ZoneStore.async_load` returns `False`.

`async_migrate_unique_ids` runs on every setup. It promotes orphans that now resolve (`_promote_resolvable_orphans`, folding into an existing entry through `_merge_promoted_orphan`, which also records the orphan's location as label or alias), then builds the slug-to-device bridge first writer wins: every device's `label` in store order, then every device's `aliases` (so a label always wins a tie), then the locations promoted in this run. That is the same precedence as `_device_id_for_label`, so a pre-2.0 entity and a `location:` automation for one name land on one device. It then rewrites pre-2.0 unique ids matching `_OLD_UID` to `<device_id>_zone_<n>[_presence]`. When the new unique id is already taken, the old entity is left in place and a warning names it as stale; that warning repeats on every setup until the stale entity is deleted.

### `zone_entities.py`

`ZoneEntityTracker` keeps exactly one entity per `(device_id, zone_id)` per platform and is built with the config entry. It retries any add the platform refuses (`add_to_platform_abort`, for example an entity id that is still taken) on the next `SIGNAL_ZONES_UPDATED`, and `ZoneEntityMixin.async_will_remove_from_hass` sends one extra signal only while such a refused attempt is pending (`has_aborted`). On the supported Home Assistant versions (2026.8.1 and 2026.10.0) registry removal appears to finish eagerly, so a delete followed by an immediate redraw should cause no refused add and no extra signal (unverified, X58); the module docstring still describes that race. A zone whose entity or device the user disabled is skipped (`is_disabled`) and its earlier aborted attempt is dropped (`ZoneEntityTracker.discard`), so `has_aborted` reports only refusals a retry can still fix. While the entry is `ConfigEntryState.UNLOAD_IN_PROGRESS` (`tracker.unloading`), `_sync_entities` returns early and the removal-time signal is skipped: HA resets the platforms before it runs the entry's on-unload callbacks, so the dispatcher subscription is still live while entities leave, and a re-add then would land on a reset platform bound to the old `ZoneStore`. Only that state counts, because the first sync runs during `SETUP_IN_PROGRESS`. `tests/test_zone_entities.py` pins the real-platform paths.

### `targets.py`

Shared by presence and the movement recorder, so the two can never read a target differently. The shape testers, the rotator and the unit factor moved here from `binary_sensor.py` in 2.4.0, with their TODO markers (X13 on `_coerce_float`, X59 on `_LINE_INTERSECTION_EPSILON`), and unchanged except for one guard: `_point_in_ellipse` holds nothing when a radius squares to 0, where a hand-edited radius below about 1.5e-154 used to raise `ZeroDivisionError` inside every evaluation of the radar (masking runs each ignore zone's test inside every zone's), and the card's division gives Infinity or NaN there, which nothing is inside either. Shape testers: `_point_in_rect` and `_point_in_ellipse` (inclusive on every boundary) and `_point_in_polygon` (an even-odd ray cast toward +x, at least `POLYGON_MIN_POINTS`; a point exactly on a non-horizontal edge counts as a crossing and one on a horizontal edge does not, so whether a polygon boundary point reads inside depends on the edge), in `SHAPE_TESTERS` (was `_SHAPE_TESTERS`). `shape_tester(zone_def)` returns one only for a dict whose `shape` is a string key of `SHAPE_TESTERS`: a hand-edited list shape is unhashable, and a bare `.get()` would raise inside every evaluation of every zone of the radar. Rotation (`build_point_rotator`, was `_build_point_rotator`) uses `x' = x cos t + y sin t`, `y' = -x sin t + y cos t`. The module has its own `_coerce_float` without the finite and size guard of the one in `__init__.py`, so `build_point_rotator` checks finiteness itself. `reading_unit_factor(state, fallback)` (was `_reading_unit_factor`) is the per-entity unit rule, and `fallback_factor(store, device_id)` the device's `INPUT_UNIT_FACTORS[input_units]` or 1.0. `pair_ids(pairs)` lists the unique X/Y string ids in list order. `read_point(hass, x_id, y_id, fallback)` returns None when either state is missing, `unknown`, `unavailable` or not a number, when the reading is the exact `(0, 0)` sentinel, or when a value is not finite once converted to millimeters (a huge reading in a large unit overflows), else both readings in millimeters in the raw sensor frame; rejecting non-finite floats changes no presence result, because nan and inf were never inside a bounded shape. `iter_slot_points` yields `(slot, x_mm, y_mm)`, the slot being the pair's index in the list, kept for skipped pairs so the numbering never shifts. `masked_readings(hass, store, device_id, pairs)` rotates each point and drops it when any of the radar's ignore zones (`zone_type_of` ignore with a usable `shape_tester`) contains it, returning `hold.Reading(slot, raw, map)` items; with no ignore zone that costs one empty list per evaluation. `radar_offline(hass, pairs)` is true when the pair list has ids, at least one of them has a state, and every state there is `unavailable`: all ids missing, or an empty list, is not offline, and `unknown` is a live state. `tests/test_binary_sensor.py` imports `build_point_rotator` from here.

Since 2.4.0b3 it also holds the X/Y pairing that presence and the recorder share. `TARGET_PAIR_MS` (550 ms) is the one wait: above the 0.40 to 0.50 s the R PRO-1 takes from an X write to its Y, below the 0.62 s from a Y to the next X, so a lone Y never pairs with the next reading's X. `AxisPairing` follows one slot's writes (`follow(previous, raw, at)`, times in ms): an axis written alone waits (`lone_axis`, `lone_at`) until the other axis is written or `TARGET_PAIR_MS` passes, an axis written twice before the other moves alone (`solo_axis`) until the other changes, so a radar that reports several times a second keeps every report along one axis, and `whole(at)` and `whole_at()` say whether and from when the reading counts. It was the recorder's `_SlotState.pair` in 2.4.0b2. `ReadingPairer` keeps one `_PairedSlot` per slot for one reader: the last reading seen and when a write changed it, the last whole reading, which stands in while an axis waits, the pairing, and `half`, set when `hold.half_vanished` reads the latest reading as half of a vanish or of an appearance from 0/0, which is passed on as it is and waits for nothing. `pair(slot, raw, at)` returns the reading to use, `written_at(slot)` when the latest write landed (None for a half), `keep(slots)` forgets the slots with no reading now and returns those whose latest write had not counted yet, `due()` the first moment a waiting reading counts, and `reset()` forgets every slot. `masked_readings(hass, store, device_id, pairs, pairing=None)` takes an optional `(pairer, now_ms)`: each slot is paired before it is masked, so the point between a target's two writes cannot vanish into an ignore zone either. A whole reading that differs from the latest write carries that write as `Reading.written` (raw and map), every paired reading carries `written_at` in seconds, and the slots gone since the last pass while a write waited land, masked the same way, in `pairer.lost`. The recorder calls it without a pairer and pairs in its `_SlotState.split`, next to its own half-vanish handling.

### `hold.py`

Pure: no Home Assistant import, and `now` is passed in (seconds of `time.monotonic()`), so `tests/test_hold.py` tests it with plain values. `Reading` is one target (slot, raw reading, rotated map point, and `carried`, set on the copy of the slot's last good reading that stands in for a half-vanished one). Since 2.4.0b3 it also carries `written`, where the target's latest write puts it (raw and map) while that write waits for the other axis's and `raw` and `map` keep the whole reading before it, and `written_at`, when that write landed in seconds of `time.monotonic()`; `latest` and `report_t(now)` read them. `Occupant.first` and `update` take their reports from `latest` at `report_t`, so the motion rule 2 reads includes an axis written alone, while who is inside is still decided by the whole reading. The numbers are tuned for the LD2450 of an R PRO-1 on firmware 26.10.21.1, which writes each axis about once a second (1.0 to 1.15 s), Y usually about 0.45 s after X and sometimes in the same instant, writes nothing for a value that repeats, and reports a lost target as `unknown` on both axes at once; `tests/test_binary_sensor.py` drives the real entity that way (`_report_at_radar_cadence` with inch states, and `_lose`) in six phases of that period, with Y 0.45 s after X or both together. `half_vanished(prev, raw)` is true when exactly one coordinate of `raw` is exactly 0.0 and that coordinate of `prev` was not, or, with no `prev` (the slot read 0/0, or nothing), whenever exactly one coordinate is 0.0. On firmware that empties a slot as 0/0, a target that vanishes writes X = 0 and Y = 0 as two writes, and one that appears writes its X and Y the same way, which sometimes land in separate loop turns; the point between, (0, old y), (old x, 0), (x, 0) or (0, y), is nobody's position: it would fake motion and, as an outside target, could release a hold. Firmware 26.10.21.1 never empties a slot that way, so on it the rule mainly guards real readings of exactly 0 (one-decimal inches read 0.0 within about 1.3 mm of an axis line). `HoldTracker.usable(readings, now)` applies it: a flagged reading is replaced by a copy of the slot's last good reading (`_good`) marked `carried`, or dropped when the slot has none, as for an appearance; the same raw reading stays flagged (`_flagged`, with when it was first flagged) for `HALF_VANISH_MAX_S` however many evaluations other writes start in between, and after that counts as someone on an axis line; any other reading clears the flag and becomes the slot's good reading. A slot with no reading forgets both, `_last_raw` keeps every raw reading for the next evaluation, and `flag_expiry()` says when the oldest flag would count as real, which presence turns into a timer. The filter applies to hold accounting and, through the same function and bound, to the recorder, never to presence with `hold_s` 0. A carried reading sets `carried_since` on the occupant it stands for, leaves the rest of them as it was and creates nobody; the evaluation that empties the zone sets `empty_since` to the earliest `carried_since` (else now), so rule 1's radius, rule 2's freshness and the deadline count from the first half of a vanish.

`Occupant` follows one person inside: when they were first seen inside, the last evaluation that found them inside (`last_t`), their map point and raw reading, `reports` (each change of their reading, with its time, map point and raw reading, kept for `HOLD_MOTION_WINDOW_S`; `seen_t` is the newest) and `carried_since`. Motion comes from those reports only, never from evaluations, which any target's write starts. `moving_at(t)` is false when the last report is older than `HOLD_MOTION_FRESH_S` (a value that repeats is never written, so someone who sat down can go seconds without a report, and their last step would otherwise read as motion forever), true for someone seen inside for under `HOLD_FIRST_SEEN_S` (so a ghost blip that vanishes mid-zone holds it), and otherwise `_walking()`. That measures the step from the latest report at least `HOLD_ANCHOR_STEP_S` before the last one to the last one, so each step spans a whole report of both axes: no such report within `HOLD_MOTION_WINDOW_S` is too sparse to measure (the safe side: hold), a step under `HOLD_MOVE_MIN_MM` is not walking, a step at `HOLD_BRISK_MM_PER_S` or faster is, and any other step needs the one before it, measured the same way and inside the same window, to be `HOLD_MOVE_MIN_MM` or more too. The LD2450 was measured jumping 467 mm in its last report before it lost a still target: one slower step that follows none, so it holds. `exit_margin_mm(t)` is `HOLD_EXIT_MARGIN_MM` plus the last step's speed times the time from `seen_t` to `t` plus `HOLD_AXIS_LAG_S` (the most by which the axis the last report did not write can be older, from a Y write to the next X), capped at `HOLD_EXIT_MARGIN_MAX_MM`, or `HOLD_EXIT_MARGIN_MM` with no step to measure. `exit_path(t)` is where they may have walked to, as (map, raw) points: the last report, then, when `_walking()` holds for their last reports, a point every `HOLD_EXIT_SAMPLE_MM` on along that step's direction, out to `exit_margin_mm(t) - HOLD_EXIT_MARGIN_MM`. Map points move along the map step and raw points along the raw step, so the view's edge is measured in the raw frame under any `rotation_deg`, and points 100 mm apart come within 50 mm of any edge the way on crosses, a polygon's included, whose edge distance is unsigned. So only an edge ahead gets the speed term: in every direction, it would read someone lost walking into a room, within 1.5 m of the doorway behind them or a wall beside them, as walked out. Someone moving only by the first-seen rule gets the last report alone, whatever their last step, jitter or a walk in to sit down, as in 2.4.0b1. 2.4.0b2 followed a first-seen person's last step whenever it was `HOLD_MOVE_MIN_MM` or more, and so read someone lost as they sat down within about a second of walking in as walked out by the edge ahead of them. `edge_distance_mm` is a map point's distance to the zone's edge (rect: the nearest side; ellipse: radial, which overstates on long ellipses and so errs toward holding; polygon: the nearest segment), and `coverage_edge_distance_mm` a raw point's distance to the edge of the LD2450's default view (`COVERAGE_RANGE_MM`, `COVERAGE_HALF_FOV_DEG`; 0 outside it).

`HoldTracker.step(now, inside, outside, shape, data)` is one evaluation and returns whether the zone reads on. With anyone inside, the occupants are rebuilt from the inside readings and the pending people are dropped (someone inside again ends a hold). The evaluation that empties the zone sets `empty_since`, records the slots of its outside readings in `tracked_slots`, matches people to outside readings first (rule 1) and keeps the rest pending unless they exited (rule 2, decided once from the state at `empty_since`: `moving_at(empty_since)`, and a point of `exit_path(empty_since)` within `HOLD_EXIT_MARGIN_MM` of the zone's edge or of the view's edge); later evaluations only look for people outside. Rule 1 (`_match`) pairs people and unused outside readings nearest first over every pair, during the first `HOLD_REACQUIRE_WINDOW_S`, within `HOLD_REACQUIRE_BASE_MM` plus `HOLD_REACQUIRE_MM_PER_MS` for each ms since `empty_since` and for each ms from the person's `seen_t` to `empty_since` (at most `HOLD_REPORT_AGE_MAX_S`, never negative): at a report about once a second, a walker's last report inside can be a second old when a report outside empties the zone. That radius, up to 7.3 m at 3 s, is only for the person's own slot or a slot that had no reading when the zone emptied; a slot in `tracked_slots`, a target already tracked elsewhere then (another person, a still object, a ghost), counts only within `HOLD_REACQUIRE_BASE_MM`. The radar suite's rule, which 2.4.0b1 followed, gives every target the growing radius; 2.4.0b2 narrowed it because a still object the R PRO-1 tracked all night ended every hold. Each outside slot accounts for one person once per empty period (`used_slots`). Only the occupants of the last occupied evaluation are carried, so a still person lost while someone else stays inside is forgotten (the radar suite's behavior too; carrying them is an open question for the maintainer). `deadline(hold_s)` is `empty_since + hold_s` while anyone is pending. With a hold, an evaluation costs O(targets), at most 9 distance pairs for rule 1, and once per emptying the edge distances of at most 13 points a person.

At that cadence the tests hold a still person with about 40 mm of jitter until `hold_s` (mid-zone, 0.7 m from the zone's edge and 0.7 m short of the 6 m range, and at the last two also when the last report jumps the measured 467 mm toward the edge), turn the zone off within 3 s of walking out into view at 0.8 and 1.0 m/s and as soon as a 1.4 m/s walker with X and Y together is outside, turn it off within 1 s of the loss after 3 m of walking out of view at the 6 m range, at the 60 degree line or through a doorway in the zone's far edge, and hold someone who walked in through that doorway and was lost 1.8 m inside, or 0.5 or 1 s after sitting down 1.75 m inside. A shorter walk out of view often holds: in a simulation at the same cadence (120 runs a case), 2 m at 1.0 m/s released within 1.5 s of the loss in 94 to 99% of runs, 2 m at 1.4 m/s in 62 to 75%, and 1.5 m at 1.0 m/s in 50 to 58%. A still person whose last report jumps across the zone's edge reads as stepping out, so 0.3 m from the edge, with the jump in a random direction, the zone held in 68 to 80% of runs. In 2.4.0b3's run of the review's simulation (a 1 m/s walk in, lost 0.5 s after sitting down), a couch zone held in 96.7% of runs with Y after X (2.4.0b2: 76.7%) and 86.7% with X and Y together (2.4.0b1: 100%), and a bed zone in 94.2% (2.4.0b2: 81.7%). The cost is in slow transits: 0.6 m/s through 1 to 1.5 m of a zone and out of view at 6 m released within 1.5 s of the loss in 43 to 48% of runs (2.4.0b2: 55 to 100%). Applying the flat margin to everyone moving only by the first-seen rule, walkers included, would bring the couch back to 2.4.0b1's numbers, but it also lowers 1.0 m/s transits, so it was left out.

### `binary_sensor.py`

`ZonePresenceBinarySensor` has unique id `{device_id}_zone_{n}_presence`, name `Zone {n} presence`, device class occupancy, and is linked to the radar's device entry. It reads targets through `targets.py` and keeps `_evaluate_and_write(self, *, write=True)`, `_handle_coordinate_update`, `_flush_evaluation` and `_evaluate_presence()` with their 2.3.0 names and signatures, because tests patch and call them; `_evaluate_presence` still means "a live, unmasked target is inside right now". `_evaluate_and_write` picks `_write_ignore`, `_write_offline` or `_write_detect` (see Runtime data flow). With `hold_s` 0, `_write_detect` drops any hold and is the 2.3.0 rule with no attributes. With a hold it splits `HoldTracker.usable(readings, now)` into inside and outside, runs `HoldTracker.step`, releases at once when the deadline has passed (a late timer, or `hold_s` lowered), publishes `held` (always present while the zone has a hold) and schedules one `async_call_later` at the deadline (`_schedule_hold_expiry`, a `HassJob` with `cancel_on_shutdown=True`, rescheduled only when the deadline moves); `_hold_expired` drops the pending people and evaluates again. A second timer of the same kind runs at `HoldTracker.flag_expiry()` while a half-vanished reading is flagged (`_schedule_flag_expiry`; `_flag_expired` evaluates again), because readings change only with a write: a target standing still on an axis line, with nothing else writing, needs it to be counted. The `SIGNAL_ZONES_UPDATED` handler compares `_hold_fingerprint()` (JSON of the zone's shape, data and type, the device's `rotation_deg` and `input_units`, the tracked pairs, and the sorted id, shape and data of the radar's ignore zones) with the last one and drops the hold when it changed, then re-tracks and evaluates as before. A name, another detect zone's edit, `display_units`, `mirror_x` and `movement_history` keep a hold; a `hold_s` change keeps it and reschedules from `empty_since`, and 0 releases at once. The fingerprint is seeded in `async_added_to_hass` before the first evaluation, so the first signal after a reload (which gets no STARTED nudge) compares against real data. `async_will_remove_from_hass` also cancels both timers (zone deletion, unload), and `_drop_hold` cancels both with the hold. Since 2.4.0b3 each entity also pairs its targets' writes (see Runtime data flow): `_pairer` (a `targets.ReadingPairer`), `_paired_ids` (the tracked ids it pairs for; another list resets it in `_track_coordinate_entities`) and a third timer of the same kind at `ReadingPairer.due()` (`_schedule_pair_expiry`, `_unsub_pair`, `_pair_due`; `_pair_expired` evaluates again), because a move along one axis brings no second write. `_write_detect` reads `_readings(now_ms)` with the pairer, and `_step_hold` runs one hold evaluation; while `_pairer.lost` holds a target gone with its write still waiting, it first steps the hold once with those readings added. `_drop_pairing` resets the pairer and cancels its timer for an ignore zone, an offline radar and a zone with no usable shape, and `async_will_remove_from_hass` cancels it with the others. Hold state lives in memory only and is not restored after a restart or reload; a restart or any radar reconnect passes through offline, which drops every hold on that radar. Each `_write_*` helper exists to keep the functions under ruff's limits.

### `target_units.py`

ESPHome reports an LD2450's Target X and Y in mm, and Home Assistant on US customary units shows a new distance sensor in inches by its own pick, the suggested unit in the entry's `sensor.private` options. Apollo mmWave reads any length unit (`targets.reading_unit_factor`), so this is about what people read: the radar's built-in zone corners stay in mm. `async_track_target_units(hass)` (registered in `async_setup_entry` after `async_track_target_pairs`, torn down with the entry) does two things. A listener on `EVENT_ENTITY_REGISTRY_UPDATED` only looks: a `create` of an ESPHome target sensor (`ld2450._is_target_sensor`) whose `created_at` is at most `TARGET_UNITS_FRESH_S` (60 s) old adds its registry id to a pending set, and a `Debouncer` (`TARGET_UNITS_DELAY_S`, 2 s, not immediate) decides them later, silently. Never inside the create event, which fires before the entity has its registry entry and listens for updates, so it would keep showing inches until a reload; a deleted entity that comes back keeps its old `created_at` and its options, so it is never new. Then `async_at_started` runs one pass over every ESPHome target sensor once Home Assistant has started, when automations and scripts are loaded, and raises one persistent notification (`TARGET_UNITS_NOTIFICATION_ID`) naming the sensors it switched, radar by radar, why, and how to go back.

Both use `_decidable` and `_verdict`. Not decided at all: anything but an ESPHome target sensor with a distance device class on an Apollo LD2450 model (`apollo_radars` names `ld2450`), or one that already has a decision. Not decided yet: a disabled sensor, or one whose `sensor.private` has `refresh_initial_entity_options` (Home Assistant recomputing after a unit system change). Kept: a unit picked in the sensor's settings (`options["sensor"]["unit_of_measurement"]`), a suggestion of mm or none (a metric install), or a sensor something names (`_Users`: `automations_with_entity` and `scripts_with_entity`, a substring search of every automation's and script's `raw_config` for templates, and of the `data`, `options` and subentry data of every other integration's config entry for UI helpers; YAML template entities, dashboards and outside tools stay invisible). Otherwise switched. A switch merges `unit_of_measurement: "mm"` into the sensor's own options with `async_update_entity_options`, as the sensor's settings dialog does, and never writes `sensor.private`, the radar, Distance, Speed, Resolution, Angle or a number. Every decision, kept ones too, is written to the entity's own options under `apollo_mmwave` (`OPTION_TARGET_UNITS`: `TARGET_UNITS_MM` or `TARGET_UNITS_KEPT`), so it survives a lost store, a downgrade, a rename and a restore, and a sensor is never looked at again: a sensor kept because an automation reads it stays when the automation goes, and a metric install that moves to US customary units with "update units" keeps its inches. The log names each switch at info level, never a reading. Each switch costs about three registry events per sensor (ours, the decision and Home Assistant's precision rewrite), and each re-pushes the radar's zones through `ld2450._registry_updated`.

The Radar setup card's tap goes through `target_unit_rows(hass, device_id)` (the paired X and Y in X1, Y1 ... Y3 order with `unit` from the state, `picked`, `convertible`: distance device class and a `SENSOR_UNIT_FACTORS` unit, and `used_by`: the automations and scripts that name it), `switchable(rows)` (convertible, not picked, not mm) and `async_show_in_mm(hass, entity_ids)`, which switches and records them whatever the device. `UNIT_WORDS` mirrors the card's; `tests/test_contracts.py` keeps the two equal. `tests/test_target_units.py` covers both paths, a real `SensorEntity` reading mm once switched, presence and a hold across a live switch, the commands and the diagnostics.

### `movement.py`

The opt-in movement history. Nothing in it logs a target position, a movement record or a movement payload at any level: log lines name device ids and counts only, and `tests/test_movement.py::test_movement_never_logs_positions` runs a session at DEBUG to check it.

`_Columns` holds one radar's records in `array` columns, about 18 bytes a record in memory: `t` (`q`, epoch ms, non-decreasing so `bisect` works), `dt` (`I`, ms since the previous record, `dt[0] == 0`, kept so encoding is a copy), `s` (`h`, the slot, or `-1 - slot` for a gone marker), and `x` and `y` (`h`, mm in the raw sensor frame, 0 on gone markers). `encode()` packs each column with `tobytes()` (a byte-swapped copy on a big-endian host) and standard base64 and caches the result until the columns change; `window(since_ms)` builds the `get` answer from slices and C-level copies, never a per-record Python loop; `decode(raw)` accepts only an `n` and a `t0` of the right types and four strings that decode to exactly `n * 4`, `n * 2`, `n * 2` and `n * 2` bytes, and rebuilds `t` with `itertools.accumulate` (about 8 ms per full radar, once at load).

`_Recorder`, one per registered radar with the flag, is described under Runtime data flow. Its `_SlotState` per slot remembers whether the slot's last record is a point, that record's wall-clock stamp (`last_t`), monotonic time (`last_mono`) and position, a pending move, the last raw reading seen (`seen_raw`, for `half_vanished`), the last reading not held back (`good_raw`, which stands in for one that is), the reading held back as the first of two writes and since when (`half_raw`, `half_since`), and the pairing state, `split`, a `targets.AxisPairing` (since 2.4.0b3 the class presence uses; it replaced `lone_axis`, `lone_at`, `solo_axis`, `pair` and `whole`, and `MOVEMENT_PAIR_MS` with them). `split.follow` follows which axes changed, `split.whole` says whether the reading waits for no axis's write, and `due` says when the tick has something to record, no sooner than `split.whole_at()`. A flush whose clock is more than `MOVEMENT_CLOCK_STEP_MS` behind the newest slot stamp clears the slot state first, and a new pair list closes every open slot with a gone marker and resubscribes (`retrack`), because a slot's meaning may change with the list.

`MovementHistory`, one per config entry:

- `async_load` reads `Store(hass, 1, "apollo_mmwave.movement", private=True, atomic_writes=True)`, which keeps the default `serialize_in_event_loop=True`: encoding a full radar takes about 1 ms, so the data function reads the live arrays on the loop with no copies. A missing file and a corrupt one both load as nothing: HA's `Store` renames a corrupt file to `apollo_mmwave.movement.corrupt.<time>`, logs an error and raises a repair ("restore from backup"), and a read error warns and starts empty. It then deletes every `.corrupt.*` copy, which holds positions that nothing else would ever delete (an executor glob on that exact prefix), drops radars whose flag is off, radars no longer in the device registry, malformed radars (with a warning that names the device id only), records older than 24 h and records more than 60 s in the future, and closes each open slot with a gone marker at the later of its last record and `min(saved_at, now)`, because nobody is known to be there after the downtime. A file that existed with nothing left is removed; anything dropped or added marks the history dirty.
- `async_start` connects `SIGNAL_ZONES_UPDATED`, and the device registry's create and remove events for a device the zone store knows, to `_reconcile`, listens once for `EVENT_HOMEASSISTANT_STOP`, and reconciles every flagged device. `_reconcile` starts or re-tracks a recorder for a registered radar with the flag; otherwise it stops the recorder (gone markers) and, when the radar has records, deletes them and saves soon. A radar removed from HA therefore loses its history while its zone-store entry and flag stay (X08), so the same device id restored later records again.
- `payload(device_id, since_ms, now_ms)` and `count(device_id)` never trim, save or schedule anything, so a `get` and a diagnostics download write nothing. `clear(device_id)` removes that radar's records, resets the recorder's slots (no gone marker for a cleared point), saves soon only when something was removed, and flushes once, so a target in view is recorded again at once.
- `trim` runs the cheap checks first: past `MOVEMENT_MAX_POINTS` plus `MOVEMENT_PRUNE_SLACK` it drops the oldest back to the cap, and once the oldest record is `MOVEMENT_PRUNE_BATCH_MS` past 24 h it drops everything older than 24 h. `_record` keeps time moving forward in the columns, which bisect and the unsigned deltas need: a step back of up to `MOVEMENT_CLOCK_STEP_MS` (an NTP correction) stamps the record at the last time, and a bigger one (a board without a clock booting before NTP, a manual change) first drops that radar's records newer than now, which no window could show, with one warning.
- Saving: `Store.async_delay_save` is a trailing debounce, so calling it per point would push the write out for as long as anyone moves. `_mark_dirty` schedules once per dirty period (`MOVEMENT_SAVE_DELAY_S`), and `_data_to_save` clears that flag, prunes every radar to 24 h and packs `{saved_at, devices}`. `_save_soon` (a clear, a flag off, a removed radar) writes within `MOVEMENT_CLEAR_SAVE_DELAY_S`. Whenever no radar has records left, the file is removed instead of saved (`_remove_file_soon`; `Store.async_remove` also cancels a pending delayed write), with its corrupt copies. A retention timer at the oldest record's time plus 24 h plus `MOVEMENT_PRUNE_BATCH_MS` prunes and saves, or removes the file, even while nothing new is recorded, so points on disk are at most 24 h plus about 11 minutes old (the prune batch plus the save delay). It is event driven, not polling: it fires at most once per batch while history exists.
- Stop and unload: HA's stop does not unload entries, so `_on_stop` closes every slot with a gone marker (a replay never shows someone frozen across the downtime), then cancels the retention timer, and leaves a pending delayed save to HA's final write. `async_stop`, the unload hook, is `async_shutdown(save=True)`: listeners off, recorders stopped, then the retention timer off, and an awaited save, or the file removal, only when a save was scheduled. The timer goes after the recorders because their gone markers start it again when none is set; left running, an unloaded history's timer would prune its stale copy a day later and save it, or remove the file, over the history of the next setup. Entry removal uses `save=False`, which sets `_removed` first so nothing writes from then on, and `async_remove_movement_store` then removes the file (see `__init__.py`).

While the integration is disabled nothing runs, so the file keeps what it had until the next start prunes it. The file lives only under `.storage`, never under `/config/www` or any other path served without authentication.

### `gates.py`

`resolve_gate_entities` classifies one device's enabled registry entries into `GateEntities`: per-gate `move_threshold`, `still_threshold`, `move_energy` and `still_energy` maps keyed by the digit `GATE_RE` captures (a disabled gate leaves a hole rather than shifting its neighbors), the engineering-mode switch, the LD2410 max move/still gate numbers, the LD2412 min/max gate numbers, the radar-target and moving-target binary sensors, the LD2412 background-correction button and status, and the query-params button of either chip (`_ld2412_query_params` on the R PRO-1, `_query_params` on the MSR firmware) (`_SCALAR_PATTERNS`, first writer wins per slot as in `ld2450.py`). The profile is `ld2412` when any object id contains `_ld2412_`, else `ld2410`; `None` is returned when no gate slot matched (an MTR-1). `number_bounds` reads a number's `min`, `max` and `step` with 0/100/1 fallbacks, `numeric_state` returns a finite float or `None` (through `finite_float`, which `calibration.py` and `calibration_store.py` share), and `is_offline` treats a registered entity with no state object the same as `unavailable`. It is the Python twin of `entities.ts` (see Contracts).

### `calibration.py` and `calibration_math.py`

`calibration.py` holds the algorithm's timing, headroom and verification constants (each a module-level name so tests patch it there; `MIN_SAMPLES`, `SPIKE_ABS` and `SPIKE_RATIO` live in `calibration_math.py` and `MAX_SNAPSHOTS` in `calibration_store.py`, are deliberately not re-exported, and must be patched on those modules), the three service schemas (`CALIBRATE_GATES_SCHEMA`, `CANCEL_CALIBRATION_SCHEMA`, `RESTORE_GATE_THRESHOLDS_SCHEMA`, all `extra=vol.PREVENT_EXTRA`), the pre-flights, `CalibrationJob`, `calibration_payload` and `async_setup_calibration`. Setup loads the store, installs the jobs dict, registers the services with `SupportsResponse.OPTIONAL`, subscribes a synchronous `EVENT_HOMEASSISTANT_STOP` listener that only sets `cancel_requested` (HA core cancels every background task before it fires the event) and returns the `async def` teardown: a closing flag set before its first await (so `calibrate_gates` and `restore_gate_thresholds` are refused as not loaded while it waits, as they are while HA is stopping), cancel requests on every job, a bounded wait for their finally (`asyncio.wait_for` over a `gather`, skipped when no job runs), service removal, listener removal, a final save that logs rather than raises, then the two `hass.data` keys (and the closing flag) are popped last so no job can persist into a store the entry no longer owns. `calibration_math.py` is the pure half: `Bounds`, `Margins`, `ChannelSamples`, `ChannelResult` and `compute_channel` (the peak is the ceiling of the largest tick or event value; the proposal is `peak + max(margin, peak * margin_pct / 100)` rounded up to the step and clamped to the range; `off` at the top of the range; `spike` when the tick maximum is both `SPIKE_ABS` above and `SPIKE_RATIO` times the nearest-rank 95th percentile; `no_data` under `MIN_SAMPLES` ticks, whatever the event peak). It is tested directly with plain tuples.

### `calibration_store.py`

`CalibrationStore` wraps a `Store` with key `apollo_mmwave.calibration`, version 1, as its own file so `store.py` and its allow-list stay untouched and an older build ignores it. Per device it keeps up to `MAX_SNAPSHOTS` snapshots newest first (`add_snapshot`, `discard_snapshot`, `snapshot`, `snapshots_summary`), the `last_result`, and the `interrupted` marker (`set_interrupted`, `clear_interrupted`, `interrupted`). `_parse_device` drops malformed snapshots one at a time and reads a missing `left_on` as `False`; a missing file is empty, an unreadable one logs a warning and starts empty. `async_save` is awaited directly for the snapshot and the marker because both exist to survive a crash, and it raises when the write failed: HA's `Store` catches `WriteError` and `SerializationError` and only logs them, so `_ReportingStore` records the error from `_async_write_data` for `async_save` to raise (during an HA stop the save defers to the final-write stage, still before the process exits, and cannot be checked); results use `async_delay_save`. `snapshot` and `snapshots_summary` skip a snapshot without values, so one can never hide a real one from Undo.

### `websocket.py`

`async_register` registers `apollo_mmwave/zones/get`, `apollo_mmwave/zones/subscribe`, `apollo_mmwave/calibration/get`, `apollo_mmwave/calibration/subscribe`, `apollo_mmwave/movement/get` and `apollo_mmwave/movement/clear` (`TYPE_MOVEMENT_GET`, `TYPE_MOVEMENT_CLEAR`) on every config entry setup; registration is a keyed assignment that replaces the previous handlers rather than stacking them, and the commands are never unregistered (HA has no API for it). It returns a teardown that closes this entry's subscriptions, zone and calibration alike (`_subscriptions`); the hook order above runs it before the zone teardown pops the store, and each zone forwarder re-checks `DATA_STORE` as a safety net. Zone and calibration reads are open and writes are admin-only. None of the zone or calibration commands requires admin, and that is deliberate: the Apollo mmWave dashboard is admin-only only when the administrator leaves that box ticked (those made before 2.2.6 are not), the card can sit on any dashboard, the zone card cannot draw without the zone commands, and the same geometry, rotation and tracked pairs are already readable by every user through the zone sensors' attributes. The one zone write, `update_zone`, is an admin service (see below), so a non-admin user sees the zones but cannot change them. It is also why calibration progress goes over a subscription rather than a custom bus event. `tests/test_websocket.py::test_non_admin_users_can_read_and_subscribe` pins it. The two movement commands are the exception, and both require admin (`@websocket_api.websocket_command`, then `@websocket_api.require_admin`, then `@callback`, HA core's order, as in `config/area_registry.py`): movement history is where people were, which no zone sensor exposes, so its reads stay with administrators as its writes do. A non-admin gets `unauthorized` for any valid request; HA validates the command schema before the wrapper runs, so a malformed request gets `invalid_format` whoever sends it. `_movement_answerable` then answers `not_loaded` ("Apollo mmWave is not loaded.") when `DATA_MOVEMENT` or `DATA_STORE` is gone and `not_found` for a device that is not in the registry. Neither command mints a zone-store entry, and a radar whose flag is off answers `enabled: false` with no records instead of an error. `test_movement_get_requires_admin` and `test_movement_clear_requires_admin` in the same file pin the split. `_payload` copies each zone dict before it adds the 2.4.0 keys (see Runtime data flow), so a payload never mutates the store. Zone ids and `peaks` gate keys are stringified in the payloads. The calibration commands use `_calibration_answerable`, built on `_calibration_loaded`, which needs both `calibration_store` and `calibration_jobs` in `hass.data` (`not_loaded` otherwise): the zone teardown can pop the zone store while the calibration teardown is still waiting on a job, and a half-set-up entry can have the reverse. `ws_subscribe_calibration` sends the current payload right after its result, and its forwarder re-checks the keys before every push.

### `frontend.py`

`async_register_frontend_assets` is guarded by `hass.data["apollo_mmwave"]["assets_registered"]`, so it runs once per Home Assistant run; an integration reload skips the resource reconciliation too. It reads the manifest version for the `?v=` cache buster, registers each existing bundle as a static path with `cache_headers=True` (a missing bundle file is a warning; the cache duration itself is Home Assistant's `CACHE_TIME` in `homeassistant/components/http/static.py`, 31 days at the time of writing), adds it as an extra JS URL and reconciles the Lovelace resource collection (`_async_register_lovelace_resources`). The reconciliation keeps exactly one resource row per bundle: rows under `/apollo_mmwave/` are grouped by url with `?v=` stripped (`_base_url`), the row already at the current `?v=` is kept (else the first), it is repointed at the current url with type `module` when its url or type differs (a hand-added classic `js` row would throw on the bundle's top-level `export`), and every other row for that bundle and every row for a bundle no longer in `JS_BUNDLES` is deleted (`_async_remove_stale_resources`, listed under "removed" in the info log). Rows outside `/apollo_mmwave/` are never touched. The storage collection loads lazily, so the function loads it first through `async_get_info()` when its `loaded` attribute is false, as Home Assistant's own resource count does. A YAML-mode resource collection only produces a warning that ends with the urls to add by hand as modules and says to replace each row's url after an upgrade rather than add a second row. On entry removal `async_remove_lovelace_resources` loads the collection the same way and deletes every row under `/apollo_mmwave/` (`_async_remove_stale_resources` with no bundle still shipped), because nothing serves those files after the next restart; in YAML mode it only warns with the rows to delete by hand, and any failure is a warning that never stops the removal. The static paths and extra JS URLs stay registered for the rest of the run, so it sets `hass.data["apollo_mmwave"]["resources_removed"]` before it deletes anything (a delete that fails partway has already taken some rows), and the next `async_register_frontend_assets` in that run recreates the rows from the urls it kept in `resource_urls` before returning on the once-per-run guard.

Nothing in `frontend.py` writes a dashboard at setup. `async_create_dashboard(hass, require_admin, devices)` is called only from the config flow and the options flow's `add_dashboard` step: it creates the storage dashboard at url path `apollo-mmwave` (title, icon, `show_in_sidebar` True and `require_admin` as asked, written once and the user's from then on), saves `_desired_config(devices)`, and returns the row's id. It returns None with a warning that ends with `_PICKER_HINT` (Settings > Dashboards > Add dashboard > Apollo Radar Tuning, and the strategy type) when the collection is unreachable, when any dashboard (YAML or storage) or any row already holds the url path, which is left as it is, or when a write raises; if the row was created and its first `async_save` failed, `_async_roll_back_created_row` deletes it again so a retry starts clean.

Every later touch goes through `_async_our_row(hass, collection, dashboard_id, url_path)`, which returns the recorded row and its stored config only while the row exists under that id with that url path and the config is still ours (`_is_ours`: a `strategy` dict with our type). Lovelace derives a row's id from its url path, so the config check is what keeps a taken-over dashboard, or one the user made on the path after deleting ours, from being written to or deleted. The config is read only from the row's own storage dashboard: `_async_stored_config(hass, item)` returns None, which every caller treats as not ours, unless `hass.data[LOVELACE_DATA].dashboards[item["url_path"]]` has mode `storage` and `config["id"] == item["id"]`, so a stale row under a user's YAML dashboard on the same url path is never written to or deleted (deleting it would make Lovelace drop the YAML panel). `async_dashboard_owned` reports True, False or None (unreadable) for the options flow. `async_set_dashboard_devices` writes `_desired_config(devices, stored)`, which rewrites only `type` and `devices` and carries over any other key under `strategy` that the user typed into the raw config editor (such as `distance_unit`); it saves only when the config changes. `async_remove_dashboard` deletes the row through the collection, which makes Lovelace remove the panel and the stored config; it returns True when nothing of ours is left (deleted, nothing recorded, gone or no longer ours) and False when the collection is unreachable or the delete raised. `async_find_legacy_dashboard` is the read-only lookup `async_migrate_entry` uses (see `__init__.py`). Each of these catches every exception, logs it and returns its failure value, except `async_find_legacy_dashboard`, which raises `DashboardsUnreadableError` so the migration can tell "unknown" from "none". The dashboards collection is borrowed from HA's `lovelace/dashboards/list` handler (`_dashboards_collection`); that is the only working path on the pinned versions (2026.10.0, and 2026.8.1, the HACS floor), which keep the collection in a local inside lovelace's `async_setup`, and the `dashboards_collection` attribute check that runs first is forward compatibility only. `tests/test_frontend.py` covers every warning branch and the ownership checks, `tests/test_config_flow.py` the flows, and `tests/test_init.py` the migration and that setup, reloads and option changes write no dashboard (`record_dashboard_writes` in `tests/conftest.py`).

### `diagnostics.py`

`async_get_config_entry_diagnostics` builds the support file an administrator downloads from Settings > Devices & services > Apollo mmWave > three dots > Download diagnostics (HA's download view is `require_admin`). Home Assistant wraps the result with its own system details, the custom integrations and this manifest. The integration has no `manifest.json` dependency on `diagnostics`: HA finds the platform by its file and preloads it with the package (`loader.BASE_PRELOAD_PLATFORMS`), which is why `tests/test_imports.py` now imports every preloaded platform whose file exists, as HA's import executor does, before it checks that nothing else loads later.

Top level: `versions` (manifest and HA), `unit_system` (`hass.config.units.as_dict()`; a `length` of `mi` means the cards show feet), `entry` (title, state, version, minor version, the whole `options` dict and `dashboard_is_ours` from `async_dashboard_owned`: True, False or None when the dashboards cannot be read), `lovelace` (`resource_mode`, `served_urls` from `DATA_RESOURCE_URLS`, and `resource_rows`: url and type of every row under `/apollo_mmwave/`, or None when the collection has not loaded or cannot be read), `zone_store_loaded`, `calibration_store_loaded`, the zone store's `orphans`, and `devices`. A device gets a section when it is an Apollo radar in the registry (`apollo_radars`: manufacturer ApolloAutomation and a model starting with a `MODEL_RADARS` prefix) or when the zone store, the calibration store or `dashboard_devices` names it, which covers DIY radars and devices that left the registry; sections are sorted by name. Each holds the registry identity (name, name_by_user, manufacturer, model, model_id, sw_version, hw_version, disabled_by, the config entry domains) and `selected_for_dashboard`; `radars` (`expected` from the model, `gate_radar` from `resolve_gate_entities`, `ld2450` from the entities); `firmware` (the Apollo, ESPHome, LD2410, LD2412 and LD2450 version sensors, reported even when disabled, plus every `update` entity with `installed_version`, `latest_version` and `in_progress`); `wifi_signal`; `gate_radar` (profile, gate count, every move and still threshold state by gate); `ld2450` (Zone Type, Multi Target Tracking and `target_pairs` with `source` detected, configured or cleared, `tracked` and `detected`; None on a radar with neither an LD2450 nor configured pairs); `calibration` (exactly `calibration_payload`, what the calibrate card receives); `zone_store` (the store entry with string zone keys, which carries `mirror_x`, `movement_history`, `zone_type` and `hold_s` verbatim); `movement_history` (`{"enabled": <flag>, "points": <record count>}`, the count 0 when the movement store is not loaded, never a point); and `zone_entities` (this integration's own entities on the device). The top level also has `movement_store_loaded`. Every entity is reported as entity id, state, unit, device class, `registered` and `disabled_by` (`_entity`).

It is read only: no store save, service call, state write, dashboard write or resource write (`tests/test_diagnostics.py` checks each, the movement store's `async_save` and `async_delay_save` included; `MovementHistory.count` never trims, saves or schedules anything). `_target_pairs` reads `DATA_PAIR_CACHE` the way `effective_target_pairs` answers but never fills it, and the Lovelace resource collection is read only when its `loaded` attribute is true, because its first load can import resources from an old dashboard config and save files. Privacy is two nets. First, only the entities named above are read, and of the registry fields only the ones listed, so the device's `connections` (its MAC), `configuration_url` and identifiers, and the IP address, MAC, BT MAC and SSID sensors never reach the file. Second, `async_redact_data(result, TO_REDACT)` replaces any `access_token`, `bssid`, `bt_mac`, `configuration_url`, `connections`, `host`, `ip`, `ip_address`, `mac`, `mac_address`, `password`, `refresh_token`, `ssid`, `token`, `user_id` or `wifi_ssid` key anywhere in the result with `**REDACTED**`, for a value a later field or a verbatim-stored pair might carry. Device names and entity ids stay, by the owner's decision, although ESPHome's default names end in the last six hex digits of the MAC. `MODEL_RADARS` mirrors `APOLLO_MODELS` in `profiles.ts`; `tests/test_diagnostics.py::test_model_radars_match_the_frontend` keeps the two equal. There is no device-level diagnostics: the radar devices belong to the ESPHome entry, and the zone entities attach through `device_entry` without adding this entry to the device, so HA would never offer a per-device download.

### `services.yaml`, `translations/en.json`, `manifest.json`

`services.yaml` documents `update_zone`: `device_id`, deprecated `location`, `zone_id`, `shape`, `data`, `name`, `delete`, `input_units`, `display_units` ("Map Units", a select of `auto`, `m` and `ft`), `zone_type` ("Zone Type", a select of `detect` and `ignore`), `hold_s` ("Hold Time (seconds)", a box from 0 to 3600 in steps of 1 s), `mirror_x` ("Flip Map Left to Right") and `movement_history` ("Movement History"), both booleans, then `rotation_deg`, `entities`, `clear_entities`. Its texts say that `data` is read only together with `shape`, that `shape: none` clears a zone, how naming renames the entities (an empty name, or the default `Zone N`, clearing them), and the rotation sign; that `zone_type` is a mask in Home Assistant, not the LD2450 Zone Type setting of the R PRO-1 or MTR-1; when a hold ends early, with both release rules and their numbers, that the radar needs about two seconds of walking in the zone to see someone walk, and that a target already tracked elsewhere counts only within 0.6 m; and where movement history is kept, that backups include it and that the support file never does. Since 2.4.0b3 they also say that a creating call with no name or the default one clears the names left from an earlier zone of that number, that someone in the zone for under about 1.2 seconds walks out only within 0.3 m unless the radar saw them walk at 0.85 m/s or faster, and, for `mirror_x`, that the walk test needs the map turned the way the room is, as `MIRROR_HINT` says. The service description names `mirror_x` and `movement_history` among the device-wide fields. The `zone_id` selector's `max: 32` is a UI bound only. It also documents the three calibration services with their fields, defaults and selector ranges (which mirror the voluptuous schemas in `calibration.py`). `translations/en.json` carries the config and options flow strings and the `exceptions` block whose keys are the calibration pre-flight refusals; it has no entity block, because the zone entities take their names from `_attr_name`. The options flow's `dashboard_devices` text says the selection applies only while the Apollo mmWave dashboard is still generated. Both files follow the copy style (no em dash, "R PRO-1" in display text), which `tests/test_translations.py` enforces. `manifest.json` declares `config_flow: true`, dependencies `frontend`, `http`, `lovelace`, `websocket_api`, `integration_type: service`, `iot_class: local_push`, and the version.

## Frontend modules

### Detection and profiles (`register.ts`, `entities.ts`, `entity-index.ts`, `profiles.ts`, `ld2450.ts`, `ld2450-entities.ts`, `types.ts`, `index.ts`)

`index.ts` is the tuning bundle entry: it re-exports `CARD_VERSION` from `version.ts` (its own module since 2.4.0b3, so the zone map bundle can read it without the tuning entry; see Version check) and side-effect imports the distance, gate-energy, calibrate and setup cards and the strategy. `registerElement` (`register.ts`) defines an element immediately and re-asserts every pending definition once `home-assistant` or `hc-main` is defined, because HA's scoped-custom-element-registry polyfill replaces `window.customElements` after boot; `safeDefine` swallows any `define()` error without logging. `test/register.test.ts` boots the app through a model of @webcomponents/scoped-custom-element-registry 0.0.10 (the copy in HA frontend 20260930.2): its `define()` throws only on a tag or class collision in its own map and native-defines a stand-in only when the native registry lacks the tag, while `get()` and `whenDefined()` see only its own map. That stand-in is what resolves the native `whenDefined` held from before the swap; re-check the model if HA ships a different polyfill. `register.ts` also exports `registerCustomCard(type, name, description)`, which adds a card picker entry to `window.customCards` once per type with the repository link; the distance, gate-energy and setup cards use it, the calibrate card has its own once-per-type guard, and the zone map card pushes its entry unconditionally.

`profiles.ts` holds the chip tables: `LD2410_PROFILE` (9 gates g0..g8, MSR-2 naming) and `LD2412_PROFILE` (14 gates g00..g13, `ld2412_` naming), each with `maxBarLabels`, optional `maxBarTips` (only the LD2412 sets them, so its Min Gate row reads "gates below this one are ignored"; the default is `rangeLimitTip(label)`), `rangeLabels`, `gateSizeLabel`, `rangeTip`, `gateTip` (one shared `GATE_TIP`), `wikiUrl` and `entityMap(base)`. `rangeTip(gateDepth)` states one gate's depth (`gateDepthTip`; `cardMap` passes the same `aboutDistance` text the help card and the threshold rows use, so the note follows the gate size select when the user enabled it and the user's unit) instead of pointing at the gate size control, which ships disabled on every model, and says which sensor Radar Timeout holds on (`radarTimeoutTip`: Radar Target, or LD2412 Presence). It also holds `APOLLO_MODELS` (model prefix to profile and LD2450 flag), `apolloModelInfo`, `isEsphomeDevice`, `detectProfile` (probes each profile's engineering-mode switch id in `hass.states`) and `LD2410_FACTORY_THRESHOLDS`.

`entity-index.ts` exports `entitiesForDevice(hass.entities, deviceId)`, which groups `hass.entities` by `device_id` in one pass (registry order kept, so first-match-wins and tie-breaks are unchanged) and caches the result in a WeakMap keyed on the `hass.entities` object. `baseNameFromDevice`, `detectProfileFromEntities`, `entityMapFromDevice` (`entities.ts`), `isEsphomeDevice` (`profiles.ts`), `ld2450EntityIds`, `hasLd2450Device` (`ld2450.ts`) and the liveness fallback in `hasLiveRadarEvidence` (`strategy-core.ts`) read their device's list from it, so detection is linear in the registry size (a Proxy guard test in `test/strategy-regen.test.ts` counts enumerations). Like the `cards/resolution.ts` memo, it relies on HA replacing, never mutating, `hass.entities`: code and tests must build a new registry object rather than add, remove or re-home entries of one a helper has already read.

`entities.ts` turns registered entity ids into an `EntityMap` (`types.ts`). `baseNameFromDevice` strips `KNOWN_SUFFIXES` and takes the most common base; the LD2412 and LD2450 entries (`/_ld2412_(?!.*ld2412_).+$/`, `/_ld2450_(?!.*ld2450_).+$/`) strip from the last chip token, so a device named after its chip ("Office LD2412", entities `switch.office_ld2412_ld2412_engineering_mode`) keeps base `office_ld2412`. `classifyObjectId` matches `GATE_PATTERNS` then `SCALAR_PATTERNS` (the entity's domain must match the slot's). `entityMapFromDevice` builds a possibly sparse map, first match wins per slot. Gate arrays are indexed by gate number (0..8 on the LD2410, 0..13 on the LD2412), and on an LD2412 the `max_move_distance` / `max_still_distance` slots hold the max and min distance gate, so consumers label them through `RadarProfile.rangeLabels` / `maxBarLabels`, never by slot name. `resolveEntities` wraps `resolveEntitiesDetailed`, which adds the base-name fallback and the `config.entities` overrides and also returns `fallbackBase`. The fallback picks its chip with `resolveProfile(hass, config) ?? LD2410_PROFILE`, so the map and the card's profile share one precedence: concrete entity markers, then the registry model (`apolloModelInfo`), then `detectProfile(hass, base)`, then the LD2410 default. Overrides go through `withOverrides`: the four gate slots (`GATE_SLOTS`) take an override only when it is an array, so a YAML `move_threshold:` (null) or a single id string keeps the resolved list, while a scalar override applies as given and a null scalar hides that row. The LD2410 map has a `zone_occupancy` slot for the firmware's any-zone sensor (`_radar_zone_occupancy`, "Radar Zone Occupancy"), whose suffix the numbered `_radar_zone_<n>_occupancy` patterns never match and the reverse. `deviceInfoEntities(hass, deviceId)` resolves the Device card's whole-device entities (`DeviceInfoEntities`) from the device's own entities, skipping this integration's: the Apollo firmware version, the LD2410 "Radar Firmware Version" (`_radar_firmware_version`), the LD2412 and LD2450 firmware sensors, the firmware `update` entity, RSSI and ESP Reboot (`DEVICE_INFO_PATTERNS`, first match per slot). Each pattern names its domain, and the update slot takes the `update` domain only, because the firmware's "Firmware Update" template button (`button.<dev>_firmware_update`), which installs with no dialog, ends the same way. `ld2450.ts` exports `ld2450EntityIds`, `hasLd2450Device` and `zoneMapCard` (the zone map card config the strategy emits, with no `grid` or `grid_units`, so its map is fitted and in the viewer's units); it uses the same regexes as the backend for detection only.

`ld2450-entities.ts` resolves the LD2450's settings and live sensors on one device into an `Ld2450Entities` map (`ld2450Entities(hass, deviceId)`): Zone Type, Multi Target Tracking, Timeout, Bluetooth, Restart (R PRO-1 only), Factory Reset, the presence and target-count sensors, each target's distance, direction and speed (`targets`, `LD2450_TARGETS`) and each built-in zone's four corner numbers and three counts (`zones`, `LD2450_ZONES`). The two Apollo firmwares name them differently: the R PRO-1 puts "LD2450 " in front of every name because it also carries an LD2412 (`select.<dev>_ld2450_zone_type`), the MTR-1 mostly does not (`select.<dev>_zone_type`), keeps the prefix on a few ("LD2450 Bluetooth", "LD2450 Presence") and puts it last on one ("Factory Reset LD2450"). `PATTERNS` lists per slot the domain and the spellings in order of preference (`chip`, the prefixed one, first; then `bare`; `exact` for `factory_reset_ld2450`), each allowing HA's `_N` dedup tail, and a slot takes the device's entity whose object id matches the most preferred spelling, in registry order among equals. The base cannot be required, because an entity that is disabled by default keeps the id it was registered with after the device is renamed. The MTR-1's bare names (`timeout`, `zone_type`) are generic, so the lookup reads only the device's own entities (`entitiesForDevice`) and skips entities of this integration's platform. An object id that starts with the device's base (`baseNameFromDevice`) is matched whole after it (`rank` with `whole`: the spelling must match from the name's first character), so nothing in the base is taken for part of a name; matching every id by suffix read an MTR-1 named "Garage Zone 2" as having a `zone_2` token before every bare name, which lost its settings and filed its radar-wide counts as built-in zone 2's. Only an id that matches no pattern that way (one registered under another base, or any id when the base is unknown or wrong) is matched by its suffix, and then a bare match is rejected when the text before it ends in a token its spelling lists in `notAfter`: `ld2410` or `ld2412` for every bare name (`OTHER_CHIP_BEFORE`: `ld2412_timeout` is the R PRO-1's other radar), and also `zone_N` for the radar-wide still and moving counts (`ZONE_BEFORE`, `radarCount`: `zone_1_still_target_count` is a built-in zone's count). The whole-device ESP Reboot and Factory Reset ESP buttons match no spelling, and the chip's firmware version is left to `deviceInfoEntities`. Results are cached per `hass.entities` object and device id, relying on HA replacing the registry as `entity-index.ts` does. `builtInZoneNumberIds` lists the resolved corner numbers. `zonePresenceSensors(hass, deviceId)` lists this integration's zone presence sensors on the device (`ZonePresenceBinarySensor` is attached to the radar's own device entry): `binary_sensor.` entries of platform `apollo_mmwave`, or, when the frontend sends no platform, ids of the shape `binary_sensor.<device>_zone_<n>_presence[_N]`, sorted by zone number with registry order kept for renamed ids.

### Calibrate card (`cards/calibrate-card.ts`, `calibration/api.ts`, `calibration/model.ts`)

`ApolloRadarCalibrateCard` (element `apollo-radar-calibrate-card`, card picker name "Apollo Radar Auto-Calibrate") is a Lit element that takes `device_id`, `device_base_name`, `title` and a `calibration` block (`CalibrateCardConfig` in `types.ts`). It is a view of a backend job, never the job itself: it opens `apollo_mmwave/calibration/subscribe` for one device (`subscribeCalibration`), renders every pushed `CalibrationPayload`, and sends three service calls through one `callService` helper that passes `notifyOnError = false` so a `ServiceValidationError` is rendered once by the card and not again by HA's toast (`startCalibration`, `cancelCalibration`, `restoreThresholds`, plus `turnEngineeringMode` for the interrupted banner). The start call's promise is only watched for rejection; progress arrives over the subscription, which is why the job survives the browser closing. A rejection goes through `describeServiceError`: HA's websocket `call_service` sends a pre-flight `ServiceValidationError` as `{code: "service_validation_error", message: "Validation error: <text without its final period>", translation_domain, translation_key, translation_placeholders}`, so the card loads the exception translations (`hass.loadBackendTranslation("exceptions", domain)`) and renders `component.<domain>.exceptions.<key>.message` in the user's language, falling back to the message with the prefix dropped and the period restored. A `not_found` from a service call means the integration is unloaded (HA cannot find the service); only the subscription's `not_found` means an unknown device. A rejected start or Undo becomes the failed view ("Calibration failed: " / "Restore failed: ", with Try again and Close); a rejected Stop or "Turn it off" is shown inline in the running view or the banner, so it never replaces the running job or its result. For `thresholds_not_numeric` (the refusal's `translation_key`, read by `refusalKey`, or a failed job's `error.code`) the primary button is "Read settings from the radar" instead of Try again when the card knows the query-params button (`entities.query_params_button`, else the resolved map's `query_params`, and only while HA has its state): it calls `button.press` (`pressButton`), waits `READ_SETTINGS_WAIT_MS` (3 s) and then runs the same retry Try again would (same calibration or preview, same restore). Close, a new run, a device change and leaving the page drop a pending retry (`_readSettingsToken`); a rejected press is shown in the view. Without a known button the view keeps Try again and says where the button is. The button label, its progress line and the wait (`READ_SETTINGS_LABEL`, `READING_SETTINGS`, `READ_SETTINGS_WAIT_MS`) live in `calibration/model.ts`, which the calibrate card re-exports, so the gate setup checks share them without importing the card.

Subscription lifecycle: the device id comes from `resolvedDeviceId` (`cards/resolution.ts`: `config.device_id`, else the device of the first resolved entity in `hass.entities`); the card subscribes on the first `hass` with a device id, disposes in `disconnectedCallback`, resubscribes in `connectedCallback`, and on a device change disposes and reopens. Every open is tagged with a serial so a payload or a resolved unsubscribe from a superseded connection is dropped. It also listens to the websocket connection's `ready` and `disconnected` events and re-runs its own subscribe on every `ready`: `home-assistant-js-websocket` re-sends subscriptions on reconnect, but a re-subscribe refused with `not_loaded` (HA restarted and `apollo_mmwave` is not loaded yet, the normal order after the one restart that interrupted a job) is dropped silently. A `not_loaded` rejection is retried with `CALIBRATION_RETRY_DELAYS_MS` (copied from the zone API, not imported) while the card reads "Apollo mmWave is still loading...", then shows the Not loaded copy with a manual Retry (`_failOpen`). Unlike the zone API, it does not treat HA's `unknown_command` as not loaded. Neither `ready` nor `disconnected` fires on an integration reload, which closes the subscription server side without telling the client, so the card also watches `config_entries/subscribe` through `subscribeEntryLoads` (copied into `calibration/api.ts` from the zone API, once per connection) and reopens its subscription when an `apollo_mmwave` entry reports `loaded`. That feed is open to every user; the copy's doc comment still calls it admin-only. The engineering switch and the LD2412 background-correction status are read from live HA state first and from the payload's `entities` only when HA has no state: the backend pushes only from job code, so while no job runs the payload is as old as the last push. `shouldUpdate` re-renders on payload, local state or config changes, registry changes, and state changes of the engineering switch, the threshold numbers, the gate-range numbers, the radar-target sensor and the background-status sensor only.

State selection lives in `model.ts` (`nextLocalState`, `showsResultView`): the Done, Partial, Preview, Cancelled, Failed and Restored views render only while card-local `observedFinish` holds the id of a job this card watched reach a terminal status; a fresh mount with a stored `last_result` renders Idle with the footer and a "Show last result" toggle. Every terminal and failure view has a Close back to Idle, and the interrupted banner renders above all of them. "Try again" repeats the failed job: a calibration with the same `apply` the card saw on the job, a restore with the snapshot it was writing back (`restoreSource`: the result's `restored_from`, else the snapshot older than its redo snapshot), never the newest snapshot, which after the redo snapshot is the very values being undone. Everything else in `model.ts` is pure copy: `phaseLabel`, `phaseHeadline` (the headline's stable phase sentence, the only text in the running view's live region, so the per-second countdown is not announced) and `progress` for the running job, `resultRows`, `unusedFootnote` and `warningLines` for the result, `undoLabel` and `restoredLine` (what the snapshot holds, from `snapshotContents`: a calibrate snapshot holds the values from before it and each restore snapshot above it flips that, so the newest reads "Undo (restore your previous values)" or "Redo (put the calibrated values back)", falling back to the time when the calibrate snapshot has aged out; `undoTitle` keeps the time for the tooltip and `savedLine` shows it as text under the idle footer's button, since a tooltip never shows on a touch screen), `footerLine` (names a preview by the result's `apply`, a `cancelled_by_shutdown` failure as stopped by a restart, and says "Nothing was changed." when `writes_done` is 0), `idleSentence`/`durationText`, `isFactoryThresholds` (the `LD2410_FACTORY_THRESHOLDS` hint) and `canStart`/`canStop`. A gate channel whose threshold sits at its number's `max` (`thresholdMax`, fallback 100) never triggers, so it is off; calibration still sets it. Before a run the idle body names the in-use ones from live state (`liveGateLimits`, `offChannelsBeforeRun`, `offGatesLine`; the gate range mirrors `_gate_unused`, LD2410 G0 and G1 still are skipped as in `gate_off`, and so is a channel that `last_result`, an applied or partial calibration, set to the top itself, by its `gates_off` or a written cell at the max); after one, `resultRows` tags a cell "(was off)" when the result's `old` was at the max and `new` is below it, and `reenabledLines` adds one warning per such channel under applied and preview tables. The interrupted banner composes its lines from the marker's `phase` and `left_on` as independent facts plus the live switch state, so "Turn it off" disappears when the switch reads off without a store write. Since 2.4.0b3 the idle body (shown online, and under a Restored view) and the Done and Partial views end with `SIT_STILL_LINE` as a hint: raise Radar Timeout to 60 s or more if Radar Target turns off while someone sits still, and Undo. The LD2410 drops a very still person once their still energy stays under the threshold for longer than Radar Timeout, and a calibration sets each threshold 15 points or 35%, whichever is larger, above the empty room's peak.

Every render helper wraps its template in an element, because happy-dom 14 mis-cloned Lit child-part markers at a template root and inside `<svg>` (see Build, test and CI); the same reason is why `charts/gate-energy-chart.ts` keeps its SVG in a nested template.

### Setup card (`cards/setup-card.ts`, `cards/setup-checks.ts`)

`ApolloRadarSetupCard` (element `apollo-radar-setup-card`, `SETUP_CARD_TAG`, card picker name "Apollo Radar Setup") is a Lit element that takes `device_id`, `title` and `radar` (`SetupCardConfig` and `SetupRadar` in `types.ts`: `ld2450`, the default, or `gate`; the header defaults to "Radar setup" with "LD2450 · <device name>", or "<chip> · <device name>" in gate mode, under it). Without `radar` it checks the two LD2450 settings that decide whether the zone map can show anyone, and offers the fix; gate mode is described at the end of this section. Both are handed straight to the radar chip and Apollo firmware never sets them, so they are whatever the chip holds. Zone Type Detection makes the chip report only people inside its built-in zones (with all of them at 0, nobody, so the map never gets a dot) and Filter reports everyone except them; the zone map replaces those zones, so Disabled is recommended. Multi Target Tracking off tracks one person only.

The checks are pure functions of HA state in `setup-checks.ts`, which also holds every line of the card's copy. `setupStatus(hass, deviceId)` returns `no_device`, `nothing_to_check` (neither setting resolved on the device), `offline` (every checked entity is "unavailable" or has no state), `waiting` (no checked entity has a value other than "unknown", or Zone Type has none and nothing else needs fixing, so "Radar settings look good." always means Zone Type, when the device has it, was read), or `checked` with a list of `SetupProblem`s and `zoneTypeUnread` when those are Multi Target Tracking's while Zone Type is still unread; the card then adds "Waiting for the radar to report its Zone Type." under the warning. Zone Type is a problem whenever it is live and neither "Disabled" nor "unknown": Detection is a warning whose second sentence depends on `builtInZonesEmpty` (all of the resolved corner numbers read 0; false when any is missing or not a number, so the card never says "None are set" without reading them all) and carries a "Zone Type should be Disabled" hint; Filter and any option the card does not know are notes. Multi Target Tracking is a warning only while its switch reads "off": on the R PRO-1 the switch is disabled by default in the registry and so usually absent, and the chip's default is multi target, so there is nothing to say then. Each problem carries one `SettingFix`, `select.select_option {entity_id, option: "Disabled"}` (left out when the select's `options` attribute lacks "Disabled") or `switch.turn_on {entity_id}`. With more than one fix the card shows a single "Use recommended settings" button with a helper line built by `recommendedLine`, otherwise one button per problem.

The card never writes on its own: only a click calls the services, through the calibration `callService` helper with `notifyOnError = false`, every fix of the click at once (`Promise.allSettled`). The buttons are disabled and a progress line shows while the call runs; a rejection becomes the card's own error line (the fix's `failure` lead, else "Could not change <setting>", then ": <reason>" through `describeServiceError`, except that HA's `not_found` reads as "Home Assistant could not find this setting", because these are select and switch calls, not this integration's services). A device change bumps `_serial`, so a call that settles afterward is dropped, and the error line clears once the checks pass. `shouldUpdate` re-renders on config, registry or device changes, and on a `hass` tick only when a state that `watchedSetupIds` names changed (Zone Type, Multi Target Tracking and the corner numbers). `getStubConfig` picks the first device with an LD2450 (`hasLd2450Device`), else the first whose own entities give a gate profile (`detectProfileFromEntities`) with `radar: "gate"`.

Gate mode (`radar: "gate"`) checks the device's gate radar, the LD2410 or LD2412 its profile names, with the checks and copy in `cards/gate-setup-checks.ts`. The card resolves the entity map and profile through `resolveRadar` with `{type, device_id}`, so the MSR-1 and MSR-2 spellings both resolve and one config fits MSR-1, MSR-2 and R PRO-1. `gateSetupStatus(hass, deviceId, map, profile, job)` returns the LD2450 status shapes plus `checking`: `nothing_to_check` without a profile or when none of `gateCheckedIds` resolved, `offline` when none of them is live (`isLive`, exported from `setup-checks.ts` with `isRead`), `waiting` when none has a value yet, else `checked` with these problems, each with `setting`, `level`, `text`, `hint` and an optional `fix`:

- `engineering_mode` (a note) while Radar Engineering Mode reads `on` and `job` is `idle`; the fix is `switch.turn_off`. `job` comes from `CalibrationJobWatch` (`calibration/job-watch.ts`), which opens `apollo_mmwave/calibration/subscribe` with a smaller copy of the calibrate card's recovery (the `not_loaded` backoff with `CALIBRATION_RETRY_DELAYS_MS`, a reopen on the connection's `ready` and on the entry's `loaded` through `subscribeEntryLoads`) and keeps only `jobActivity(payload)`: `unknown` until the feed first answers, `running` while the payload has a job whose result is not stored yet (`last_result.job_id` differs; the job turns the switch back off before it stores the result), and `idle` otherwise, a refused feed included, since no job can run then. While the activity is `unknown` and the switch reads `on` with nothing else to report, the status is `checking`, so "Radar settings look good." never stands over a switch a job may own.
- `settings_unread` (a note) when a threshold, a range gate or the timeout reads `unknown`; the text names the groups ("gate thresholds", "detection range", "timeout"). The fix presses the query-params button only while that button is live, with the calibrate card's `READ_SETTINGS_LABEL` and `READING_SETTINGS` and `settleMs: READ_SETTINGS_WAIT_MS`: the card keeps the progress line (and every button disabled) until the problem clears or the wait runs out, then shows the fix's `noAnswer` line if it is still there. Without a live button the hint says to press Query Params on the device page.
- `zone_order` (a warning, LD2410 only) for zones that can never turn on, by the firmware's rules: Zone 1 counts from Start Zone 1 to End Zone 1, both inclusive, and each later zone from past the previous end to its own. `zone_reach` (a warning when a zone starts past the reach, a note when it only ends past it) uses the larger max gate times the gate size select's value when enabled, else `DEFAULT_GATE_SIZE_M` (0.75 m). Each bound is converted to cm from its own number's unit. Both are report only.
- `gate_range` (a warning, LD2412 only) when Min Gate (`max_still_distance` on the LD2412 map) is at or above Max Gate (`max_move_distance`). Report only.

Gate fixes are never combined into "Use recommended settings": each fixable problem keeps its own button. `shouldUpdate` watches `gateWatchedIds` (the checked ids plus the gate size select), and the job watch re-renders the card when the activity changes. The watch opens in `connectedCallback` and on `willUpdate`, reopens on a device or connection change, and closes in `disconnectedCallback` and outside gate mode.

In both modes the card also shows the page's version notice under its subtitle (`_renderVersionNotice`, see Version check): it starts a `watchVersion` in `connectedCallback`, hands it each `hass` in `willUpdate`, and closes it in `disconnectedCallback`. Since the card is on every tab of the dashboard, the notice reaches every tab.

### Version check (`version.ts`, `version-check.ts`)

`version.ts` holds `CARD_VERSION`, which both bundles carry since 2.4.0b3. `version-check.ts` compares it with the Apollo mmWave Home Assistant runs, read with Home Assistant's own `manifest/get {integration: "apollo_mmwave"}`. That answers from the manifest `async_get_integration` cached at startup, so it keeps the old version until a restart, and any signed-in user may send it (`tests/test_frontend.py::test_any_logged_in_user_reads_the_running_version`). `track(hass)` asks once when a card first hands in a connection and again on each of that connection's `ready` events, which is when a restart shows; the listener stays only while a card watches (`watching`), so the next card after the last one left asks again. `versionNotice(running, page, before)` compares the PEP 440 forms the manifest uses (`compareVersions`: a release ranks above its `a`, `b` and `rc` pre-releases) and returns a `reload` notice (`versionReloadLine`, a **Reload** button that calls `location.reload()`, then `VERSION_APP_LINE`) when the page is older, a `restart` notice (`versionRestartLine`, no button) when it is newer, a `reload` notice also when Home Assistant's answer has changed since the page's first one (`firstRunning`: a restart into another version, a downgrade included), and nothing for equal or unreadable versions. A rejected call, a missing `callWS` or an answer with no version reads as unreadable, and nothing throws into a card; `serial` drops an answer a newer check overtook. The bundle does not read its own `?v=`, which would take `import.meta`, kept out of both bundles by the "imports nothing" checks in `test/bundle-tuning.test.ts` and `test/bundle-zone-map.test.ts`.

Each bundle has its own copy of the module and asks for itself. Which card shows the notice is shared by both through one global list under `Symbol.for("apollo_mmwave.version_notice.v1")`: `watchVersion(onChange)` adds the card in start order, and its `notice` is the card's own bundle's notice only while no earlier entry has one, so a tab shows it once and a fresh bundle's card never hides an old bundle's notice. The two bundles can be different versions exactly when this matters, so that protocol must not change; a later version that needs another one uses another key. `close()` removes the card and repaints the rest, so the next one can take the notice over. The Radar setup card renders it in Lit; the zone map card, which has no Lit, builds it with `versionNoticeElement` (inline styles, a plain `button`) into an empty `#versionNotice` host under the title in all three of its templates (full, `view_only` and the load error), outside `.canvas-container` so the Reload button never sits under the map's own controls. Its `_renderVersionNotice` touches the DOM only when the notice changes, and `render()` resets `_versionShown` with the fresh host; `connectedCallback` starts the watch, `set hass` hands each `hass` in (`track` returns at once for a connection it knows, so the LD2450's pushes cost nothing), and `disconnectedCallback` closes it. The auto-registered resource URLs stay `?v=<version>` with no content hash: a hash in storage resource mode can run a bundle twice in a tab served before the restart, and the alternative, `no-cache` in place of the static path's 31-day `Cache-Control`, is open.

### Strategy (`strategy.ts`, `strategy-core.ts`, `panels/`)

`strategy.ts` registers `ll-strategy-dashboard-apollo-radar-tuning`, `ll-strategy-view-apollo-radar-tuning` and `ll-strategy-section-apollo-radar-tuning` and pushes a `window.customStrategies` entry once. All three share `shouldRegenerate`. Its fast path returns false when `hass.devices` and `hass.entities` are reference-equal and no entity crossed the live line (`availabilityChanged`, which uses `isLiveState` from `strategy-core.ts`: only "unavailable" or a missing state is offline, "unknown" is live; the device `online` flag uses the same predicate). Otherwise it first unwraps the legacy `{type, options: {...}}` strategy form exactly as HA does before `generate()` (exactly two keys, `options` an object; `isLegacyOptions`), because HA hands the hook the raw strategy object, then compares `radarDeviceKey`: per device a JSON array of device id, profile key, LD2450 flag, device name and base name, sorted and joined. Since 2.4.0 the key leaves out the online flag (X31), so a radar going online or offline no longer rebuilds every tab and drops a zone drawing in progress. `availabilityChanged` still sends a liveness crossing to the full key, so a device that only liveness puts in the set (no registry match) still enters and leaves it. The cost: a tab's help card keeps the offline note it was generated with until the page reloads, so a dashboard opened while radars reconnect after a restart says "offline" on a working radar. A `name_by_user` rename or an entity-id rename regenerates an open dashboard. Drawing a zone does not: the zone entities (`sensor.<slug>_zone_N`, `binary_sensor.<slug>_zone_N_presence`, platform `apollo_mmwave`) sit on the radar device, but their ids match no radar entity pattern and the liveness fallback in `hasLiveRadarEvidence` skips entities of that platform, so base, capabilities, liveness and the key are unchanged. `ApolloLd2410DashboardStrategy.generate` has two empty states: `EMPTY_VIEW` ("No Apollo mmWave devices found", auto-detection found nothing) and `STALE_SELECTION_VIEW`, used when the config has a non-empty `devices` list or a `device_id` and `generateViews` returns nothing. A selected device is rendered whenever it is in `hass.devices`, offline or not, so that result means every selected id is missing from the registry. The view and section strategies return empty sections or cards with no message.

`strategy-core.ts` does the work. `strategyDevices` takes `config.device_id` first (when both are set, only it is rendered and `devices` is ignored), then the `config.devices` selection (forced, shown even offline), else `detectRadarDevices`. `deviceFromId` combines the registry match (`apolloModelInfo`, applied only to an ESPHome device per `isEsphomeDevice`), the base name, liveness (`hasLiveRadarEvidence`: a recognized radar entity with a live state; when none is recognized, a registry-matched device falls back to any live entity of the device other than this integration's own), the profile (`detectProfileFromEntities`, then the registry model) and the LD2450 flag. That flag is device-scoped only (`hasLd2450Device` or the registry model's flag), so a gate-only MSR renamed to the same name as an R PRO-1 or MTR-1 never gets a zone map. `cardMap` builds entities cards from `panels/entity-rows.ts` (each filtered through `presentRows`), one history graph per tab (`historyCard`, rows from `panels/history.ts`), the two custom chart cards, the gate radar's Radar setup card and the calibrate card (both for every device with a gate-radar profile, online or not; the calibrate card gets `config.calibration` as its `calibration` block), a "Start here" help card, the zone map card, the LD2450 cards below and the Device card. The gate setup card is `{type: "custom:apollo-radar-setup-card", device_id, radar: "gate"}` (see Setup card), left out when none of `gateCheckedIds(m, profile)` exists in `hass.states`, as on an R PRO-1 built without the LD2412.

The help card (`helpCard`, `helpCardBody`) gives each kind of tab its own "Start here" list, and every kind, the "no radar data" card included, ends with `deviceLink`, a markdown link to `/config/devices/device/<device_id>` ("All settings for this device →"). A gate radar alone gets `gateSteps`: "Fix anything the Radar setup card flags." when the tab has the gate setup card (`HelpContext.gateSetup`), then calibrate, the two range gates on the Detection Range card with one gate's depth in the user's unit, Radar Timeout and the Gate Energy walk, then, while `radar_target` exists, `gateAutomations(anyZone)` (since 2.4.0b3: Radar Target for the whole room and a Radar Timeout of 60 s or more for someone who sits still, plus Any zone to ignore people past End Zone 3 while `zone_occupancy` exists, `HelpContext.anyZone`), then the wiki link. Radar Target needs no distance, while the zone sensors do, and the MSR firmware can hold a distance at unknown while the radar reports someone. The depth is `aboutDistance(gateSizeMeters(...))`: the gate size select's value when the user enabled it, else `DEFAULT_GATE_SIZE_M` (0.75), in feet when `hass.config.unit_system.length` is `mi` (`lengthUnit`). An R PRO-1 gets a sentence on what each radar is for, the same steps naming the chip ("the LD2412's Radar setup card"), a last step for the LD2450 that names its own setup card when the tab has one (`ld2450Setup`), and an "In automations" line that recommends LD2412 Presence while its `radar_target` exists, else `LD2450_AUTOMATIONS`. An MTR-1, online or not, gets three steps (two without the LD2450 setup card), the last of which says to reload the page before watching Zone presence, and `LD2450_AUTOMATIONS`. So does an R PRO-1 with none of the gate radar's entities (`HelpContext.gateRadar` false: no gate setup card and no `radar_target`), which keeps the LD2412 profile from its registry model (see Known limitations). No step names Gate Size, which ships disabled on every model. The device name goes through `markdownText`, which backslash-escapes every ASCII punctuation character, because Home Assistant renders markdown card content as a template first, so a name with `{{`, `{%` or `{#` would be evaluated and `*` or `[` would change the formatting. `OFFLINE_NOTE` follows for an offline device with a profile or an LD2450. It is written when the dashboard is generated, and since a liveness change no longer regenerates it (X31), it stays until the page reloads.

Gate-radar rows: `controlRows` lists Radar Engineering Mode, the LD2412 background correction pair, `RADAR_BLUETOOTH` ("Radar Bluetooth (HLK app)", the chip's own Bluetooth, not the device's proxy), `restartRadarRow` and `factoryResetRow`. The whole-device ESP Reboot is no longer on it. Both buttons come from `confirmRow`, whose `Row.confirm` makes `entityRow` build HA's special `button` row with `action_name` (the button text, "Restart" or "Reset") and a `perform-action` `button.press` tap action that carries a `confirmation`, so HA asks "Restart the <chip> radar? It stops detecting for a few seconds while it starts up." or "Reset the <chip> radar to its factory settings?" before pressing. Threshold rows are named by `gateName` ("G0 (at the sensor)", "G4 (about 3 m)", "G4 (about 10 ft)"; below 1 m two decimals, below 3 ft one), fixed when the dashboard is generated, so a changed gate size shows after a reload. Notes follow three cards: the profile's `rangeTip` under Detection Range, `zoneConfigNote(unit, anyZone)` under the LD2410 Zone Config (the boxes are template numbers in cm, which HA never converts; the back-to-back zones; what "Any zone" is for when `zone_occupancy` exists; and, since 2.4.0b3, Radar Target for the whole room in automations, because the zone sensors also need the distance) and `GATE_TIP` under the thresholds. Target / Occupancy (`occupancyRows`, ending with "Any zone") sets `state_color: true`.

Slider rows: `sliderRow` (`panels/entity-rows.ts`) builds a row with `slider: true`. `rangeRows` uses it for the two range gates (`max_move_distance` and `max_still_distance`: Max Move Gate and Max Still Gate on the LD2410, Max Gate and Min Gate on the LD2412) and `moveThresholdRows` and `stillThresholdRows` for every gate; Radar Timeout (0 to 900 s, which HA draws as a box) and the gate size select stay plain `row()`s. `cardMap` passes the Detection Range, Move Thresholds and Still Thresholds rows through `unlockBoxes(hass, presentRows(...))`, which drops the flag from a number whose state has a `mode` and is not a slider (`showsSlider`; a state without a mode keeps it, the safe side), and hands `entitiesCard` the device id. `entityRows(rows, lockDevice)` then writes each flagged row as `{type: "custom:apollo-radar-slider-row", entity, name, device_id}` and puts one `{type: "custom:apollo-radar-slider-lock-row", device_id}` right above the first of them, so Radar Timeout and Gate Size sit above the lock row and read as unlocked. The three cards stay `entities` cards with the same titles and columns. No other card (Controls, Zone Config, Target / Occupancy, the LD2450 cards, the Device card, anything on an MTR-1 tab) gets a slider row, and DIY LD2410 and LD2412 devices take the same path. `GATE_TIP` says the sliders start locked and where Unlock is.

`historyCard` makes one `history-graph` per tab with `hours_to_show: 24`, left out with no rows. `historyEntities(m, chip)` gives the gate radar's lines ("Detected", "Moving", "Still", "Any zone", "Zone 1" to "Zone 3"; "<chip> Presence", "<chip> Moving" and "<chip> Still" on a tab with two radars), and `ld2450HistoryEntities(l, zones)` adds "LD2450 Presence" (on every tab since 2.4.0b3, as LD2450 Live names it: it covers the radar's whole view, which a plain "Presence" beside the zones hid) and each `zonePresenceSensors` id with no name, so HA shows the zone's own name. `HistoryRow` is its own type (`entity`, optional `name`). The graph is "<chip> Occupancy History" on a gate radar alone and "Occupancy History" otherwise. Like Zone presence, a zone drawn since the page loaded joins it after a reload.

The Device card (`deviceCard`, `DEVICE_TITLE`) ends every tab. `deviceRows` (`panels/device-rows.ts`) turns `deviceInfoEntities` into rows: "Apollo firmware", "LD2410 firmware", "LD2412 firmware", "LD2450 firmware", "Firmware update" (a plain row, whose tap opens HA's own update dialog; the card never installs anything) and the restart, a `confirmRow` that `deviceRestart` names after what it takes down ("Restart device", "Restart device (both radars)" on an R PRO-1 with gate radar entities, "Restart device (also restarts the radar)" on an MTR-1 and on an R PRO-1 without the LD2412). A native `conditional` card with a `numeric_state` condition below `WEAK_WIFI_DBM` (-75) shows `WEAK_WIFI_NOTE`; an unavailable RSSI is not numeric, so the note stays hidden offline and follows the live signal without a regeneration. A markdown card with `deviceLink` and `SUPPORT_FILE_NOTE` (a link to `/config/integrations/integration/apollo_mmwave` and the Download diagnostics menu item) closes it, titled "Device" itself when no row resolved; more than one card goes in a `vertical-stack`.

`buildDeviceSections`, `deviceView` and `generateViews` lay the cards out as one sections view per device. Column 1 of a gate-radar tab is the help card, the gate setup card, the calibrate card, Controls, and the LD2410 Zone Config with its note, so the help's steps come before the cards they point at; then Distances, Detection Range and its tip; then Gate Energy, Move Thresholds and the gate tip; then the history and Still Thresholds. Target / Occupancy goes in column 2, or in column 1 when there is no Zone Config (the LD2412). `buildDeviceCards`, the flat list the section strategy uses, starts the same way. The Device card is appended to the last section, so it ends every tab. A device without a gate-radar profile but with a zone map leads with [help, setup, zone map], online or not, so an offline MTR-1 shows the "Offline right now" note above its map; a forced device with nothing detectable gets only the "no radar data available right now" help card and the Device card instead of an empty tab.

Since 2.4.0b3 the zone map's column is one section with `column_span: ZONE_MAP_COLUMN_SPAN` (2), because Home Assistant caps a view column at 500 px (`--column-max-width`), which left a fitted map about 36 px per meter on any screen. On an R PRO-1 it holds the Zone Map heading, the LD2450's setup card and the map, the last two with `grid_options: {columns: "full"}` (`fullWidth`; a card's default of 12 grid columns is half of a two-column section). On an MTR-1 the help card and the setup card share its first row at half width each, the help card filling the row when there is no setup card, above the full-width map. `deviceView` sets `dense_section_placement: true` on a view with a wide section, so on two columns Home Assistant moves the LD2450's cards up into the gap beside column 1 instead of leaving it empty; a tab with no wide section keeps Home Assistant's default placement. At Home Assistant's default of four columns an R PRO-1's first row is column 1, the two-column zone map and the LD2450's cards, and the LD2412's tuning fills the second row on purpose, so the view sets no `max_columns` (X36, settled). Phones, at one column, keep the section order, and Home Assistant narrows the wide section to the columns the screen has. The zone map card has no `getGridOptions`, so Home Assistant sizes it by its content and the card's own height cap applies (see Zone map).

For a device with an LD2450, `cardMap` resolves `ld2450Entities` for that device only and adds, besides the zone map: the Radar setup card (`{type: "custom:apollo-radar-setup-card", device_id}`, online or not like the calibrate card, and left out when neither Zone Type nor Multi Target Tracking exists in `hass.states`), "Zone presence" (`zonePresenceCard`: an entities card of the device's `zonePresenceSensors` with no row names, so HA shows each sensor's own name, which follows a zone rename; each row is a `conditional` row with `state_not: "unavailable"`, because a conditional reads a missing entity as "unavailable" and a deleted zone's sensor leaves `hass.states`, where a plain row would show HA's "Entity not available" warning until a reload; since 2.4.0 a detect zone's presence also reads `unavailable` while the radar is offline, so the rows hide then too (accepted and documented); the inner row repeats `state_color: true`, since the conditional row builds it from `row` alone; with no sensors, a markdown card that says to draw a zone and reload), "LD2450 Live" (`ld2450LiveRows`: LD2450 Presence, Moving Target, Still Target, Target Count and each target's distance and direction), "LD2450 Controls" (`ld2450ControlRows`: Zone Type, Multi Target Tracking, Radar Timeout, Radar Bluetooth (HLK app), Restart Radar and Factory Reset Radar, named like the gate radars' Controls rows and asking first the same way; the firmware version is on the Device card), `LD2450_TIMEOUT_NOTE` under it while the LD2450 timeout exists (it holds LD2450 Presence, not the drawn zones, which turn off as soon as nobody is in them unless they have a hold time in the zone list under Configure), and the built-in zones card (`builtInZonesCard`). Its Presence and the zone presence sensors also go to the tab's history. Rows go through `presentRows` like every other entities card, and Zone presence and LD2450 Live set `state_color: true`. The built-in zones card is a native `conditional` card on the Zone Type entity with `state_not: ["Disabled", "unavailable", "unknown"]`, wrapping a `vertical-stack` of a markdown note titled "Radar's built-in zones" and an entities card with a `section` row per zone (`builtInZoneRows`: X1, Y1, X2, Y2 and the three counts), so it appears and goes with the live state without a regeneration; it is left out when Zone Type or every zone row is missing. `buildDeviceCards` order ends with the zone heading, setup, zone map, zone presence, LD2450 Live, the history, LD2450 Controls, its note, built-in zones and the Device card. In `buildDeviceSections` the LD2450 setup card sits right above the zone map in the map's section. An R PRO-1 gets column 1, then [heading "Zone Map", LD2450 setup, zone map] and [zone presence, LD2450 Live, LD2450 Controls, its note, built-in zones], then its other three tuning columns, six in all, with one Radar setup card per radar. An MTR-1, online or not, gets [help, setup, zone map], [zone presence, LD2450 Live, history] and [LD2450 Controls, its note, built-in zones, Device]. Section order is also the phone's reading order, which is why help, setup and the map lead. These cards are built once per generation: drawing a zone or enabling a disabled entity leaves `radarDeviceKey` unchanged (see `shouldRegenerate` above), so a new zone's presence sensor or a newly enabled Multi Target Tracking row appears after a page reload, while the setup card and the conditional card follow live state. `generateViews` appends the device id to the view path when two devices share a base name, because HA opens the first view matching the URL.

### Tuning cards and charts (`cards/`, `charts/`)

`ApolloLd2410DistanceCard` (`cards/distance-card.ts`, element `apollo-radar-distance-card`) and `ApolloLd2410GateEnergyCard` (`cards/gate-energy-card.ts`, element `apollo-radar-gate-energy-card`) are Lit elements that take `device_id`, `device_base_name`, `entities`, `title` and `distance_unit` (`types.ts`; `distance_unit` is typed as `Uom`). Without a `title` they are titled after the resolved chip ("LD2412 Distances" / "LD2412 Gate Energy" on an R PRO-1, "LD2410 ..." on an MSR, matching the strategy's titles), and a device with no resolved profile keeps the LD2410 wording; the chart SVG aria-labels follow the same chip through the trailing `label` argument of `renderDistanceChart` and `renderGateEnergyChart`. `cards/resolution.ts` memoizes entity resolution (`resolveRadar`). `ResolvedRadar` carries `ids` (every resolved id, which drives a recomputed resolution's re-render check) and `radarIds` (`radarEntityIds`: the same minus the ESP Reboot button). Both cards decide "device not found" with `anyResolved(hass, radarIds)`, so a card pointed at a device with no gate radar (an AIR-1, an MTR-1, any ESPHome board whose only classified entity is ESP Reboot) says "Apollo mmWave: device not found. Check the card's device configuration." instead of rendering blank. Each card watches only the slots its chart reads: the distance card `DISTANCE_CHART_SLOTS` and the gate-energy card `GATE_ENERGY_CHART_SLOTS` (exported next to each renderer), flattened by `watchedIds` and cached per resolution by `watchResolved`. The gate is `drawnStatesChanged`: a resolution recomputed on the tick checks every id, a tick that flips the "device not found" decision re-renders, and otherwise only the watched ids count, so a gate-energy tick no longer redraws the distance card and the reverse. Registry replacements (and `hass.config` for the distance card) always re-render. A chart that starts reading a new slot must add it to its list; a Proxy guard test in `test/cards.test.ts` fails otherwise.

Both charts take the gate count from `gateRegisterCount` (`charts/geometry.ts`), the longest of the four gate arrays, so a disabled top-gate threshold entity (HA leaves disabled entities out of `hass.entities`, which shortens that one array) no longer drops a gate. `charts/distance-chart.ts` renders zones, detection/moving/still bars, gate bands and max-gate bars scaled to gate size times gate count; the two max rows take their tooltips from the profile's `maxBarTips` (the trailing `maxTips` argument of `renderDistanceChart`), `maxLabels` defaults to `LD2410_PROFILE.maxBarLabels`, and a max row is drawn only when its gate state is numeric. The distance chart renders nothing when `move_threshold` is empty. `charts/gate-energy-chart.ts` renders per-gate move/still energy with threshold markers, visible only while the engineering-mode switch is on. `GateEnergyModel.unavailable` is true only when that switch reads "unavailable": the dimmed plot then says "Radar unavailable / Waiting for the device to reconnect" and shows no button. While the switch reads off and `hass.callService` exists, the chart places a real HTML `<button class="overlay">` ("Turn on Radar Engineering Mode") over the plot area, inside a `position: relative` wrapper, which calls `switch.turn_on` through the calibration `callService` helper with HA's own error toast left on (the chart has nowhere else to show a failure) and catches the rejection; a real button is focusable and announced where an SVG element with an ARIA role inside `role="img"` is not. A bar whose energy exceeds its threshold is outlined in the threshold color (`stroke-width="2"`), and the legend says "outlined bar = above threshold" (it read "above threshold (detecting)" up to 2.4.0b2, which an outline alone does not mean). Since 2.4.0b3 `gateEnergyModel(hass, m, profile)` marks each gate's move and still channel in use or not with `calibration/model.ts` `gateInUse` over `liveGateLimits` (past Max Move Gate or Max Still Gate on the LD2410, outside Min Gate to Max Gate on the LD2412; an unread limit counts as in use): a channel the radar ignores draws its bar and triangle at `OUT_OF_RANGE_OPACITY` (0.3) and is never outlined, and the legend then adds "faded = outside the radar's range (ignored)". `verdictLine` gives the radar's own answer from Radar Moving Target and Radar Still Target, under the legend only while the mode is on and both read `on` or `off` ("The radar reports a moving target." and so on, `NO_TARGET_VERDICT` for neither), and `NEEDS_MOVEMENT_LINE` follows "The radar reports no target." while an in-range bar is outlined, on every chip but the LD2412, where that drop-out was not measured. `GATE_ENERGY_CHART_SLOTS` adds the two range gates and the two target sensors, and the card passes the profile key as the chart's fourth argument. In the distance chart, `DistanceBar.unreported` marks a row whose target sensor reads `on` while its distance reads `unknown`: it reads "distance unknown" (`UNREPORTED_TEXT`) instead of a 0 value, and its tooltip adds "The radar reports a target, but its distance reads unknown." There is deliberately no "turn it off" line or button on the chart: the calibration job turns the mode on for its listen, and that line would invite a click mid-run. The `.chart-legend` styles are exported as `chartLegendStyles` from `charts/gate-energy-chart.ts` and composed into the gate-energy card's `static styles`. `panels/entity-rows.ts` `controlRows` adds the LD2412's Start Dynamic Background Correction button and Background Correction Running status right after the engineering-mode row when the slots resolve. `charts/geometry.ts`, `charts/entity-read.ts` and `charts/unit-convert.ts` are pure helpers.

### Slider lock (`cards/slider-lock.ts`, `cards/slider-lock-rows.ts`)

HA's number row draws its slider with `ha-slider`, a Web Awesome slider (3.7 in HA 2026.8 to 2026.10) whose `#slider` is `touch-action: none` and sets the value on touch down. On a phone, a scroll that starts on a slider therefore changes the threshold instead of scrolling the page. The slider lock puts the gate radar's sliders behind a per-radar lock while keeping HA's own row.

The store, `slider-lock.ts`, is pure (it defines no element), so `strategy-core.ts` can import `SLIDER_ROW_TAG`, `SLIDER_LOCK_ROW_TAG` and `showsSlider`, a copy of HA's `showNumberSlider` (mode `slider`, or `auto` with (max - min) / step <= 256; the same in both supported frontends). It keeps one `RadarLock` per `device_id` in a module `Map` and saves nothing, so every page load starts locked (the zone map's Locked button, by contrast, is in localStorage). `setUnlocked(id, true)` does nothing for a radar no row watches (a stale toast action), resets the try counter and arms the relock timer, `RELOCK_AFTER_MS` (5 minutes); `noteSliderChange` arms it again. `expire` re-arms for the time left when a change moved the deadline, and returns without locking while `drags` holds a pointer (`dragStarted`, from the row's capture-phase pointerdown on an unlocked slider with the primary pointer's main button, the button Web Awesome drags with; `drags` maps each pointerId to its pointerType). Global listeners go in on the first watch or drag: window `pointerup` and `pointercancel` (capture) end a drag and, when the deadline passed during it, call `expire` one tick later, after Web Awesome's `change` (sent from its pointerup handler once `updateComplete` resolves) has re-armed the timer, so a drag that set a value never ends in a relock; window `contextmenu` (capture) ends every drag but a touch's the same way, because a context menu can take the mouse's pointerup (macOS opens it on the press of a ctrl-click, which Web Awesome takes for a drag), while a long press on a touch screen can open one under a finger that goes on dragging; document `visibilitychange` clears `drags` when hidden and runs `expire` on every radar when visible, as window `pageshow` does, because phone timers sleep in the background; window `scroll` stamps the time for `recentScroll` (HA dashboards scroll the window). `watchSliderLock` returns an unwatch. When a radar's last watcher leaves, the radar locks after `LEAVE_GRACE_MS` (2 s) and its entry is dropped, so leaving the tab or the dashboard locks it, while a strategy regeneration, which puts new rows in within milliseconds, keeps the state. `hui-root` keeps each tab's view and reattaches the same rows when the user comes back, so both rows `requestUpdate()` on every connect.

`ApolloRadarSliderRow` takes `entity`, `device_id` and any option of HA's number row (`SliderRowConfig`); `setConfig` throws without `entity` or `device_id`. It builds HA's row with `window.loadCardHelpers().createRowElement({color: "state", ...config})`, less `type` and `device_id` (`color: "state"` is what the entities card adds to a plain row; it leaves custom rows alone), hands it every `hass` in `shouldUpdate`, and re-renders itself only for its entity's state or `localize`. Without `loadCardHelpers`, or when it throws, the row shows a read-only name and value and nothing is locked. Locked means the radar is locked, HA's row is built and `showsSlider` holds for the state; an unavailable number keeps its range and mode, so it stays locked. The row then gets `.locked`: `.native { pointer-events: none }`, `--ha-slider-thumb-color` and `--ha-slider-indicator-color` set to `--secondary-text-color` (the track keeps its color, so the position stays readable), and an `aria-hidden` `.shield` over the whole row with `touch-action: pan-y` (then `pan-y pinch-zoom` where known) and explicit sides rather than `inset` for iOS 14. A vertical swipe that starts on the shield scrolls the page natively, the browser sends `pointercancel` and no click, and Web Awesome's own pointer and touch listeners never see it.

A try on a locked slider: pointerdown (primary, main button) records whether it landed in the slider zone (`_inSliderZone`: from 8 px before the `ha-slider`'s left edge, its right edge in a right-to-left language, read through HA's row's open shadow root; with no slider to measure the whole row counts, so the row stays locked and only the name tap is lost). A move of `DRAG_PX` (10 px) either way marks the gesture moved, and a mostly horizontal one in the slider zone is a try; a moved gesture never counts its click, and a mouse or pen move with no button down drops a gesture released elsewhere. A click in the name zone fires `hass-more-info`, as HA's row does; in the slider zone it is a try unless the window scrolled within `SCROLL_GUARD_MS` (300 ms). `_try` does nothing for a missing or unavailable entity. Otherwise `noteTry` answers `nudge` or `remind`: a second try within `REMIND_WITHIN_MS` (10 s), or any key press, reminds, at most once per `REMINDER_GAP_MS` (4 s, HA's shortest toast). The thumb and fill take `--warning-color` for `NUDGE_MS` (1.2 s), a bubbling `haptic` event ("light", or "warning" for a reminder) reaches the window, where HA's haptic mixin vibrates only while the user's Vibrate setting is on, and a reminder fires `hass-notification` with `REMINDER_TOAST`, `duration: 6000` and an Unlock action. Toast ids are `apollo-mmwave-sliders-<device_id>`, so an unlock, a lock and a reminder replace each other in place. Every watcher hears "try", so the radar's lock rows flash.

The keyboard and change checks are capture-phase listeners on the row's own `.row`, so they run before anything inside HA's row. While locked, a value key (arrows, Home, End, Page Up, Page Down) from a slider (an `ha-slider`, a `role="slider"` element or a range input in the composed path) is prevented and stopped before Web Awesome's keydown on `#slider`, and a non-repeat press is a keyboard try; Tab, Enter and Space pass, so focus moves and Enter on the name opens more-info. A `change` from a slider while locked stops before HA's row's `@change`, which calls `number.set_value`, and the row is built again so it shows the real value: whatever moved the slider, nothing is written. Unlocked, a slider's `change` calls `noteSliderChange`.

`ApolloRadarSliderLockRow` takes `device_id` and is laid out like an HA row: a lock icon (`--state-icon-color`, `--primary-color` when unlocked), "Sliders locked" over "A scroll cannot move them." or "Sliders unlocked" over "They lock again after 5 minutes without a change.", and an Unlock or Lock button whose `aria-describedby` points at that text (no `aria-pressed`, since the label names the action, and no live region, since three lock rows per radar would all speak). Unlock toasts `UNLOCKED_TOAST` and Lock `LOCKED_TOAST`; a relock after 5 idle minutes or after leaving is silent. A try flashes the button with a warning-colored ring (`flash-a` and `flash-b` alternate so the animation starts again; a steady ring with `prefers-reduced-motion`). It skips renders for `hass` alone.

What the rows rely on from HA, and what happens without it: `loadCardHelpers().createRowElement` (`ha-panel-lovelace.ts`; without it, the read-only fallback), the `ha-slider` tag (the name and slider split only), `--ha-slider-thumb-color` and `--ha-slider-indicator-color` (the gray look only), and the `hass-more-info`, `hass-notification` and `haptic` events. The lock itself, the shield and the capture checks, depends on none of them. Neither row calls `registerCustomCard`, so the card picker still lists four cards from this bundle.

### Zone map (`zone-map/card.ts`, `editor.ts`, `api.ts`)

`ZoneMapCard` (element `apollo-radar-zone-map-card`) is a plain `HTMLElement` with a canvas 800 px wide (`CANVAS_WIDTH_PX`, `setupCanvas`, sized by `_sizeCanvas`). It draws rect, ellipse and polygon zones in millimeters, Y-down, over live targets and a device cone, with a rotation slider (`_persistRotation`), an m / ft switch, a per-radar lock persisted in `localStorage` (`readStoredLock`) that gates drawing, Walk, the two one-gesture clears (X06) and the rotation slider, a single-level undo and a zone manager for rename, delete and add (`_renderZoneManager`, `_handleAddZone`). Lock precedence: `_applyAutoLock` runs once per page load (and again after `start_locked` is removed from a live config) and uses the `start_locked` config first, then the stored `localStorage` value, then "locked if the radar already has zones". `setConfig` derives every field from the defaults plus the keys present, so removing `grid`, `cone`, `show_undo`, `unit_label_size` or `start_locked` (or a sub-key of `cone`) from a live card reverts it to what a freshly added card uses (the fitted grid, `DEFAULT_CONE`, `DEFAULT_SHOW_UNDO`, `DEFAULT_UNIT_LABEL_SIZE`); a sub-key dropped from a YAML `grid` that still has a usable extent falls back to `DEFAULT_GRID` for that edge. `view_only` is read the same way: only `true` makes a view-only map (see "Zone map live view, Walk and history"), and anything else, or no key, is the editable card. The file is `@ts-nocheck` by design (see its header comment), so `tsc` does not check it.

Map unit: `_displayUnit` returns, in order, the unit this page's viewer picked on the switch (`_viewDisplayUnits`), the unit saved for the radar (`_storedDisplayUnits`, from the payload's `display_units`), a YAML `grid_units` the card knows (`_gridUnitsConfigured`, returned as written, so a hand-written card in mm or in draws as it did before the switch existed; a misspelled unit counts as absent), and last Home Assistant's unit system (`hass.config.unit_system.length === "mi"` gives `ft`, else `m`, the distance card's rule). Grid steps, labels, the help line and the cache keys all read it, and `set hass` calls `_displayUnitChanged` when it changes. The switch (`_chooseDisplayUnit`) sets the page's pick and saves it for the radar only for an administrator (see Runtime data flow), and its tooltips say so (`UNIT_SWITCH_TITLES`, set by `_renderUnitSwitch`, which `set hass` also calls when the viewer's admin flag changes): "Show this radar's map in feet for everyone" for an administrator, "Show the map in feet" for anyone else; the pick then stays the page's, for an administrator too, so a save from another page does not flip the map under someone who just chose. A device change forgets both the pick and the saved unit (`_resetDeviceState`). Feet labels read "4 ft" with a space; meters keep "2m".

Fitted grid: a card whose YAML has no `grid` with a usable extent (`_gridFromConfig` false) fits its extents to the radar's field of view as currently rotated (`_refitGrid`, `_fittedGrid`). `_sectorBox` takes the box around the cone with the arc pushed out by `FIT_MARGIN_FRACTION` of its range (the apex gets no margin: behind the radar is its wall), the box grows to take in every stored zone (`_zonePoints`), `_roundOut` moves each edge out to a whole grid step of the map's unit (1 m, or 2 ft at the 6 m range), leaving an edge within `FIT_EDGE_SLACK_MM` of a step on that step: the card saves zones in whole mm and a feet edge rarely is one (22 ft is 6705.6 mm), so without the slack a zone drawn to the edge grew the map a step when its save echoed back. The step depends on the span, so the rounding repeats until the step settles; when two steps take turns (rounding out to the larger can leave a span narrow enough for the smaller), the larger is used. `_fittedGrid` returns that step, `_refitGrid` keeps it with its unit in `_fitStep`, and `_computeGridMetrics` draws both axes at it (`_fittedStep`; a YAML grid, or a unit changed since the fit, picks a step per axis), so every edge lands on a grid line and X and Y never differ where float error put a step at exactly 40 px. Then `_shapeFit` grows the short side in whole steps until the height is between `FIT_MIN_ASPECT` (0.75) of the width and the width, toward the side the radar faces along that axis (so a wall-mounted radar stays on the edge it is mounted on) or evenly when it faces neither way. Facing ahead, a 120 degree, 6 m cone fits a grid about 12 m wide by 9 m deep. `_sizeCanvas` then gives a fitted grid a canvas 800 px wide and as tall as the grid's own shape, and sets the same `aspect-ratio` on `.canvas-container`, so a meter is as long across as down; a YAML grid keeps the square 800 by 800 canvas. Since 2.4.0b3 `_mapSizeRule` caps the container's width at `min(100%, calc(max(MAP_MIN_HEIGHT_PX, 100dvh - MAP_HEIGHT_ROOM_PX) * var(--zm-aspect)))` (with a `vh` line first for browsers without `dvh`) and centers it, on the full card and the map alone: the map is never taller than the screen less 200 px (Home Assistant's toolbar, the card's padding and title, and the chips under the map), a cap that never drops below 240 px, and the width gives way, not the height, so a meter stays as long across as down. A section of the usual width meets the cap only on a short screen; the dashboard's two-column section can meet it on a 1080p monitor. The grid refits when a payload arrives (`_applyZoneConfig`), when the rotation slider is released or reset (`_refitAndDraw` on `change` and double-click, never on every `input` step, which would resize the canvas under the dragging finger), and when the map's unit changes; it never refits while a shape is being drawn (`isDrawing`), because a drag holds its start point in canvas pixels. Every path that ends or drops a gesture calls `_refitAndDraw` (a rect or ellipse save in `endDrawing`, `finishPolygon` whether or not it saves, Escape, `cancelDrawing`, which the outside press, `mouseleave` and `touchcancel` reach, and a mode change in `_setDrawMode`), so a payload or unit change that arrived mid-gesture is fitted once it ends; the save's echo fits again too. The fitted canvas can be shorter than the five polygon buttons on a phone, so `#modeGroup` wraps into a second column through a CSS container query (`container-type: size` on `.canvas-container`, `max-height: calc(100cqh - 44px)`); browsers without container queries keep the single column.

Captions: with `unit_display` on, `_rangeLabel` draws "Radar range 6 m (20 ft), 120°" (`_rangeText`; feet first in feet mode) centered just past the arc on the line the radar faces, or just inside it, and leaves it out when it fits in neither place, as on a YAML grid that cuts the arc off. The help line under the map (`_renderInfo`, `#gridInfo`) gives the grid extents in the map's unit and ends with "Radar range: ..."; it is rewritten without rebuilding the card when the unit or the fit changes. Cone rings stay 1 m apart in meters and 4 ft apart in feet.

`getStubConfig` seeds no `grid` and no `grid_units` and sets `unit_display: true`, so a card added from the picker is fitted and in the viewer's units like the dashboard's cards (X42).

Drawing: only the primary mouse button and touch draw (`startDrawing` and `endDrawing` return when `e.button !== 0`). A touch gesture follows the finger that started it: `startDrawing` ignores a touchstart with more than one touch and records `changedTouches[0].identifier` as `_activeTouchId`; `_getPointFromEvent(e, touchId = this._activeTouchId)` reads that finger from `touches`, then `changedTouches` (a lifted finger is only there), and returns null when the finger is absent, the canvas has no layout box, or the point is not finite. `draw` and `endDrawing` ignore touch events whose `changedTouches` lack the tracked finger (`_carriesTrackedTouch`). Pointer moves only record `_cursorPoint` and call `drawGrid()`, which rebuilds every preview from state. A rect or ellipse drag is canceled by leaving `.canvas-container` (mouseleave), by a `touchcancel` that includes the tracked finger (`_cancelTouch`), by a press elsewhere in the card, and by an end point that is null; the rect branch of `endDrawing` also cancels when the rounded bounds have no area, mirroring the backend's strict `<` check in `_normalize_rect`. A polygon is a multi-click session: leaving the canvas or a `touchcancel` only drops the rubber-band line and keeps the placed vertices. It is canceled by Escape, by a mousedown or touchstart elsewhere in the card (`_outsideClickHandler`, a document capture listener added in `_attachGlobalListeners`), by locking the grid and by a real draw-mode change; Backspace and the Undo point button remove the last vertex (`_popPolyPoint`). `_outsideClickHandler` and the window `keydown` listener (`_onKeyDown`) read `event.composedPath()` because a document or window listener sees the target retargeted to the outermost shadow host; presses on the overlay buttons inside `.canvas-container` (Finish, Undo point, mode menu, lock, undo) do not cancel, and keys whose origin is an input, textarea, select or contenteditable element are left to that field. A double-click or double-tap finishes the polygon only when the second tap lands within `POLY_DOUBLE_TAP_SLOP_PX` (24 CSS px) of the last vertex and within 350 ms of it (`_isPolyFinishTap`); the finishing tap is never stored, and `finishPolygon` drops consecutive identical vertices, so a polygon with fewer than 3 distinct vertices is not saved. Since 2.4.0 it says why when a polygon was in progress (`_polyPoints.length > 0`): no selected zone toasts `SELECT_ZONE_TOAST` and fewer than 3 distinct points `POLY_TOO_FEW_TOAST`, and it still ends the polygon (X44). A double-tap finish with too few points toasts `POLY_TOO_FEW_TOAST` and keeps drawing. Both go through `_notifyThrottled` (each message at most once per 1500 ms, `_toastAt`). `startDrawing` adds no toast: it runs on every touchstart, so a toast there would fire on scroll attempts. `_setDrawMode` with the mode already active (including the call at the end of every `render()`: a theme flip, a same-radar `setConfig`, load-error recovery) leaves a shape in progress alone; only a real mode change (`_resetDrawingState`) or a retarget to another radar drops it. A gesture whose selected zone disappears mid-drag is dropped, and ellipse corners are clamped to the grid before the radii are derived.

Touch and the lock (X46, X06): touchstart, touchmove and touchend first offer the event to `_pinchTouch` (see Zoom and pan), then return when `_canvasPans()` holds and nothing is being drawn, read at event time, so the browser scrolls; otherwise they `preventDefault` and act as before, so a gesture already drawing still finishes or cancels normally. `_canvasPans()` is true while the map is locked, in Walk, or with no zone selected, since nothing can be drawn then and a new radar's map starts unlocked with no zones. `_updateCanvasTouchMode()` toggles the canvas class `pans` (`touch-action: pan-y`; up to 2.4.0b2 also `pan-y pinch-zoom`, which since 2.4.0b3 would let the browser zoom the page where two fingers now zoom the map) and runs from `updateLockVisual`, `_enterWalk`, `_exitWalk`, `_setSelectedZone` and `render()`. A tap on a panning map still gets the browser's synthesized mousedown, so a locked map shows the lock toast. Every lock reminder goes through `_remindLocked(message)`, which rings `#btnLock` (the `nudge` class for `LOCK_NUDGE_MS`) and toasts at most once per 1500 ms through the shared `_lastLockWarningTs`: `DRAW_LOCKED_TOAST` for a press on a locked map or the Walk button, `CLEAR_LOCKED_TOAST` for a chip double-click or Clear All while locked, and `CONE_LOCKED_TOAST` for the slider. `#clearBtn` stays enabled while locked, because a disabled button gets no click and touch shows no tooltip: it carries the class `locked-action` (dimmed, `cursor: not-allowed`) and `aria-disabled="true"`, set in `renderZoneButtons` and `updateLockVisual`, and its click handler reminds and returns. The lock button toasts `LOCK_ON_TOAST` and `LOCK_OFF_TOAST`. Undo, rename, Delete and Add stay ungated.

Zone manager: `_renderZoneManager` rebuilds every row on each payload, but first `_captureZoneNameDrafts` records each input whose value differs from the name its row was built with (`data-stored-name`, keyed by `data-zone-id`) and the focused input's selection; after the rebuild `_restoreZoneNameDrafts` puts those values back on the rows of zones still listed and restores focus (`preventScroll`) and `setSelectionRange`. Save looks the zone up in `zoneConfig` by id at click time. When `_zoneIsUnsaved(zoneId)` holds (a payload has arrived, its `zones` lacks the id, and `this.zones` holds no local geometry for it) Save sends `{device_id, zone_id, shape: "none", data: null, name}`, which creates a zone only the YAML named; otherwise, and always before the first payload, it sends the name-only `{device_id, zone_id, name}`. Delete is not undoable: it drops that zone's entries from the undo snapshot, so Undo cannot re-create the deleted zone or overwrite a zone added later under the freed id, while entries for other zones stay undoable. Add Zone takes the next free id and sends `{device_id, zone_id, shape: "none", data: null, name}`. Each row's first line stays label, name input, Save and Delete, which the tests find rows by; a fifth child, `div.zone-meta` (spanning the row, wrapping), holds the size (`span.zone-size`: `SIZE_PREFIX` and `formatSize`, or `NO_SHAPE_TEXT`), a Type select (`select.zone-type`, `TYPE_OPTIONS`) and a Hold select (`select.zone-hold`, `HOLD_OPTIONS`, plus a stored value outside the list as an extra option in sorted position). The selects carry `data-zone-setting` and `data-zone`, never `data-zone-id`, which the draft capture scans on inputs, and a focused select is focused again after a rebuild. A select is built from the newest choice whose save is still on its way (`_zoneSettingPending`, see Runtime data flow) rather than the stored value, so the echo of an earlier save cannot step it back under the next arrow key. Hold is disabled for ignore zones (`HOLD_IGNORE_TITLE`), and both are disabled for non-admins (`ADMIN_ONLY_TITLE`); `ZONE_SETTINGS_HINT` sits above the rows, followed for non-admins by the visible `ADMIN_ONLY_NOTE`, because a disabled select's `title` never reaches touch or keyboard users. `_renderZoneSizes()` rewrites only the size texts, on a unit switch and after each shape change.

`ZoneMapCardEditor` (`editor.ts`, element `apollo-radar-zone-map-card-editor`) edits `device_id`, `title`, `dark_mode`, `start_locked` and `view_only` using `ha-device-picker`, `ha-textfield` and `ha-selector`; `firstLd2450DeviceId` fills the `device_id` of `getStubConfig`, which never sets `view_only`, and neither does the strategy's `zoneMapCard()`. The `view_only` selector (`VIEW_ONLY_LABEL`, a boolean) comes after the lock selector and before the hint; `_commitViewOnly` writes `view_only: true` or deletes the key and emits nothing on an echo, and the lock selector hides while it is on, since a view-only map has no lock. `api.ts` is the typed websocket client described under Runtime data flow; 2.4.0 adds the zone payload's new fields, `MOVEMENT_GET`, `MOVEMENT_CLEAR`, `fetchMovement`, `clearMovement` and the `isMovementPayload` guard (types only; `history.ts` checks the column lengths).

### Zone map live view, Walk and history (`zone-map/copy.ts`, `presence.ts`, `geometry.ts`, `format.ts`, `trails.ts`, `cells.ts`, `walk.ts`, `history.ts`, `view.ts`, `snap.ts`)

The 2.4.0 features live inside the card, which still registers exactly two elements (the card and its editor, `test/bundle-zone-map.test.ts`), so every new control is plain DOM inside it, and their testable logic sits in pure typed modules under `src/zone-map/` (the `zone-map/card` bundle shim exports only `ZoneMapCard`). Every new string is an exported constant in `copy.ts`, covered by `test/copy.test.ts`. User strings (titles, zone names, ids) are never interpolated into HTML but set as `textContent` or `.value`; `copy.ts` constants may go into the template. The build target stays es2020 and Safari 14 with no polyfills, so none of `.at()`, `structuredClone`, `Object.hasOwn`, `findLast` or `toSorted`. Clocks: trails, coverage finality, the fade timer's frame gate and Walk read `performance.now()` through `_now()`; the toast throttles keep `Date.now()`; history uses the server's epoch ms from its payload.

- Lit zones: `drawZones({lit})` draws detect zones first and ignore zones last, sorted by id, each inside `ctx.save()` and `ctx.restore()` so no line dash leaks into the grid, a preview or the dots. A zone's look follows its presence entity's state: `on` fills `fillOn` (its palette hue at alpha 0.45) with a solid stroke, lineWidth 3; `off`, `unknown`, no state or no entity id fill `fillOff` (alpha 0.18) with the dash `[8, 6]`, lineWidth 2; `unavailable` is gray (`zoneUnavailableFillLight` and `zoneUnavailableStrokeLight`, or their `Dark` twins) with the dash `[4, 4]`. The hue (`zonePalette[(id - 1) % 5]`) still identifies the zone, and a presence state with `held: true` adds `HELD_SUFFIX` to the label, so a lit zone with nobody on the map explains itself. `_drawZoneLabel` measures the label with its suffix (`measureText`, else `LABEL_FALLBACK_EM_PER_CHAR` per character) and moves it in as far as it takes to stay on the canvas, 2 px from the sides and 12 px (half the 24 px font) from the top and bottom, centered on the canvas when it is wider. A zone whose canvas box misses the canvas gets no label, which only a YAML grid can cause (a fitted map takes in every zone): pulled onto the edge, its name would label whatever is drawn there. A polygon is filled by the even-odd rule (`ctx.fill('evenodd')`, the hatch included), the rule presence tests it by, so one that goes around an area twice is not filled where presence finds nobody. `_presenceEntityFor(zoneId)` takes the meta's `presence_entity_id`, else `presence.ts` `fallbackPresenceId` (a registry entry on this device with platform `apollo_mmwave` or none whose id matches `^binary_sensor\..+_zone_<id>_presence(?:_\d+)?$`, cached per `hass.entities` object), which covers a 2.3.0-shaped payload and a push that lacks the id. During a replay a lit set overrides presence.
- Ignore zones: a cached 12 by 12 px hatch pattern (`_hatchPattern(dark)`, one diagonal line in `ignoreHatchLight` or `ignoreHatchDark`), or a flat `ignoreFillLight` or `ignoreFillDark` when `createPattern` is missing, throws or returns null (some browsers, and the test contexts), a `[6, 4]` dash in `ignoreStrokeLight` or `ignoreStrokeDark`, and `IGNORED_SUFFIX` on the label. `_isIgnored(mx, my)` tests a map-frame point against the ignore zones with `geometry.ts` `pointInZone`, an exact port of the backend testers; `rotateToMap` ports the presence rotation.
- Numbered dots: `drawCurrentPosition(x, y, color, label, {hollow, numberColor})` draws a halo at 1.7 times the radius, the core, a white 3 px stroke and the number in bold, with a radius of `max(10, round(9 * _frameScale))`. Live dots pass the pair index + 1 (not parsed from entity ids, so live and replay agree) and `targetNumber[idx % 5]`: black on red, blue, green and amber, white on purple. A target inside an ignore zone is a hollow gray ring with a gray number, outlined in the canvas color (`lightCanvasBackground` or `darkCanvasBackground`, `strokeText` at 4 px times the frame scale), because the ring has no fill and the target's own gray trail runs under it. The radius is `_dotRadius()`, which the fade gate's halo uses too.
- Trails: `trails.ts` `TrailBuffer` keeps `TRAIL_MS` of raw-frame samples per slot. X and Y arrive as separate writes, and an R PRO-1 often writes Y about 0.45 s after X, so pushes are paired by coordinate. A push under `TRAIL_COALESCE_MS` after the slot's last sample replaces it, as the two writes of one loop turn do. A push that moved one coordinate leaves its sample waiting for the other (`pending`), and when the other moves within `TRAIL_PAIR_MS` of the sample's first push it completes the sample in place: `t` stays the first push's time and `tLast` is the merge's. A push that moves the same coordinate again, or both, appends, so a radar that reports several times a second keeps every sample. A slot's first sample, or the first after `gone`, with exactly one coordinate 0 waits too, because it may be the first write of a target appearing in a slot that read 0/0. A slot keeps its last reading after its samples age out, so a still target's next move is judged against where it stood. `takeFinal(now)` hands each sample out once, after it can no longer change: `TRAIL_COALESCE_MS` old, or `TRAIL_PAIR_MS` for a newest sample still waiting, so coverage counts only positions the radar reported, never the in-between point of a split update. On firmware that empties a slot as 0/0 the two writes of a vanishing target can land in separate pushes too, and the first leaves (0, old y) or (old x, 0), a point nobody stood at: when the next push shows that slot empty, `_onTargetsChanged` takes the sample back with `TrailBuffer.retract(slot)` while it is not yet final (`halfVanished` in `card.ts`, the rule of hold.py's `half_vanished` for a slot with a previous reading), so no trail runs out to x = 0 or y = 0 and coverage paints no cell there. It then calls `TrailBuffer.gone(slot, now)` for every slot that lost its reading. That takes back a newest sample still waiting for its other coordinate (pending, not yet taken, under `TRAIL_PAIR_MS` old): firmware 26.10.21.1 loses a target on both axes at once at any moment, so one lost between an X write and its Y left (new X, old Y), and coverage would count that cell and the trail end there. A target moving along one axis only loses its last step that way, as the movement recorder drops it too. Whatever the slot reads next starts a new run (`brk`). The live dot, drawn from the current states, can show a new X with the old Y for up to about 0.45 s. `_drawTrail` joins no sample with `brk` to the one before, breaks a trail at a silence over `TRAIL_GAP_MS`, counted from the previous sample's `tLast` (or `t`) to the next sample's `t`, and fades each segment by age; a trail is gray while its slot is inside an ignore zone. The fade timer (`_kickTrailTimer`, every `TRAIL_FRAME_MS`) runs only while the card is connected, has a canvas, has a trail to fade (`hasTrail`) and shows no replay, and only while a frame would change what the map shows (`_trailCanChange`: a slot whose target is gone still has a trail to fade out, or a sample from the last `TRAIL_MS` lies farther from its slot's newest sample than the dot's halo, 1.7 times `_dotRadius()`, in canvas px); it skips a frame a hass push already painted (`_lastDrawAt`). A still target's jitter stays under its own dot, so it repaints only on pushes, about twice a second, view-only cards included, while a walker's trail still fades about ten times a second. A new pair list clears the trails; coverage keeps its cells, which are positions, not slots.
- Coverage: `cells.ts` `CellGrid` bins positions into `CELL_MM` cells in the raw frame; `cellAlpha` maps a count to an alpha by log, and `bucketCells` groups the cells into ten alpha buckets so `_drawCells` paints one path per bucket, each cell's corners mapped through `_toMap` and `valueToPixels` (rotation and flip apply). The grid fills from `takeFinal` whether or not Coverage shows, counts targets inside ignore zones (it shows where the ghosts are) and lives in the page; only the toggle is kept, per radar, in `localStorage` (`apollo-mmwave.zone-map.coverage.<device_id>`).
- Size readout: `format.ts` formats lengths (`formatLength`: tenths of a meter, or a `decimals` argument, or feet and inches with the 12-inch carry), sizes (`formatSize`, joined by U+00D7, with the same `decimals`), `zoneSize` (rect, ellipse, and the polygon's bounding box) and hold times (`formatHold`). `_shapeFromDrag` is the math `endDrawing` saves, so `_drawSizeReadout` shows exactly the saved size, snapped (see Snapping), to 0.01 m while the snap is finer than 10 cm (`_readoutDecimals`, `snapDecimals`; the zone list stays at 0.1 m). It sits `READOUT_OFFSET_MOUSE_PX` above the pointer or `READOUT_OFFSET_TOUCH_PX` above a finger. Where that runs off the top of the canvas, as near the radar on a fitted map, a mouse pointer's goes as far below, and since 2.4.0b3 (J7) a finger's goes beside it at its height, its near edge `READOUT_BESIDE_TOUCH_PX` (44 CSS px) out, on the side with more room, instead of below under the fingertip. Walk's readout (`_drawWalkReadout`, `READOUT_OFFSET_TOUCH_PX` from the newest corner) takes the first of above, below, right and left that stays on the canvas `READOUT_CLEAR_CSS_PX` (4) clear of the earlier corners' rings and numbers and of the overlay buttons (`_clearReadoutSpot`, `_overlayBoxes`), else above. Both use the same plate, and `drawGrid` draws both readouts, `_drawInProgressReadout` and `_drawWalkReadout`, after the corner rings, the trails and the dots, so none of them runs through a readout's plate.
- Zoom and pan (2.4.0b3): `view.ts` is pure. A view is a zoom (`ZOOM_MIN` 1 to `ZOOM_MAX` 8) and the map point, in mm, at the canvas's center, in the map frame before the flip, so the same view shows the same part of the room flipped or not. The card keeps `_view` as it was last set (null is the whole map, and a view at 1x becomes null), unclamped: a same-radar `setConfig` fits the map around the YAML's cone for a moment before the store's rotation is laid back over it, and the view must not lose its place to that. `_applyView` lays it over the map's extents (the fitted or YAML grid) as `viewWindow(_view, map)`, clamped inside them (`clampView`), into `_viewXMin`, `_viewXMax`, `_viewYMin` and `_viewYMax`, and sets `pxPerX` and `pxPerY` to the 1x canvas px per mm (`_basePxPerX`, `_basePxPerY`) times the zoom, 0 before the first canvas. `valueToPixels` and `pixelsToValue` map through that window, mirrored while `_mirrorX` (a flipped map draws the window's xMax on the left), so the grid, cone, zones, drawing, hit tests, trails, Coverage, the dots, Walk, the replay, labels and readouts all follow the zoom with no code of their own. `_setView` carries a drag's start and pointer across in mm, so a shape keeps its corner on the map. `zoomAt(view, map, factor, at)` zooms around a map point that keeps its place on the canvas: + and − around the view's center by `ZOOM_STEP` (√2), and Ctrl or Cmd and the wheel (`_onWheel` on `.canvas-container`, not passive, `preventDefault` so the page does not zoom) around the pointer, one step per `WHEEL_PX_PER_STEP` (100 px) of travel, at most a step per event, 16 px a line for a line-mode wheel and a canvas height a page; a trackpad pinch in Chrome, Edge and Firefox arrives as many small Ctrl wheel events. Safari's `GestureEvent` is not handled. `viewAt(map, zoom, at, frac)` holds the map point a pinch or a drag started on at the same place under the fingers or the pointer. `fitView(map, box)` frames the zones' box with `FIT_ZONES_MARGIN_FRACTION` (0.1) of its longer side, at least `FIT_ZONES_MARGIN_MIN_MM` (300), up to `ZOOM_MAX`; `_fitTarget` is null with no zones, a fit at 1x or a view that already is the fit, and Fit then shows the whole map. `_renderZoomControls` runs on each frame, since a zone saved or deleted changes what Fit does next, and touches the DOM only when the zoom or Fit's next action changed (`readout.dataset.shown`): the readout (`zoomReadout`, hidden at 1x, `ZOOM_PAN_HINT` as its tooltip), + and − disabled at the ends, and Fit's label (`ZOOM_FIT_ZONES_LABEL` or `ZOOM_FIT_ALL_LABEL`), disabled at 1x with nothing to fit. The row (`#zoomControls`, `ZOOM_GROUP_LABEL`) sits over the lower right corner, 40 px up, above the unit switch, Undo and Lock. `followPoints(view, map, points, inset)` moves a zoomed view as little as it takes, zooming out only as far as it must, to keep Walk's targets `WALK_FOLLOW_INSET` (0.15) inside each edge (`_followWalker`, on each target change and on entering Walk, never during a gesture). The zoom resets to the whole map (`_resetView`, which also ends a gesture) on page load, another `device_id` (`_resetDeviceState`), a rotation that differs from the one the view was set at (`_viewAngle`, checked in `_applyRotation`; the slider's `input` and double-click reset it too) and a switch to `view_only`, whose template has no zoom row and which attaches no gesture listeners. The m / ft switch and a refit keep it.
- Gestures: Shift and the left button, or the middle button, start `_startMousePan` before any drawing (window `mousemove` and `mouseup` listeners, so a drag past the canvas's edge keeps going; the middle press is `preventDefault`ed against the browser's autoscroll), so a Shift drag no longer draws and a Shift double-click does not finish a polygon. Each touch handler offers the event to `_pinchTouch` first. A second finger starts a pinch (`_startPinch`) while the event is still cancelable, which it no longer is once the browser scrolls the page for the first finger, and while the first finger, if it is drawing, has moved no more than `PINCH_SLOP_CSS_PX` (10 CSS px); past that it is drawing and a second finger (a resting thumb, a palm) changes nothing, as before. A pinch drops a rect or ellipse in progress (`cancelDrawing`) but keeps a polygon's corners, then zooms by the fingers' distance against where they landed and pans with their midpoint (`_movePinch`, `viewAt`). Every touch until the last finger lifts belongs to the gesture (`{kind: 'pinched'}` once a pinching finger lifts), so the finger left behind draws nothing and places no corner. The pinch works on a panning canvas too (locked, Walk, no zone selected), which is why `pans` dropped `pinch-zoom`. The view-only canvas keeps `touch-action: pan-y; touch-action: pan-y pinch-zoom`, since it has no zoom of its own.
- Grid at a zoom: `_computeGridMetrics` picks the step at the zoomed px per mm, so a zoomed map gets lines every `GRID_MIN_SPACING_PX` or more at a finer step. A fitted grid takes the finer of its fitted step and `_chooseGridStep` at the zoom, one step for both axes and never coarser than the fit's: 1, 0.5, 0.2 and 0.1 m (`GRID_STEP_CANDIDATES.default`) or 2, 1, 0.5 and 0.25 ft (`GRID_STEP_CANDIDATES.ft`). Axis labels whose line is off the canvas run along the nearer edge (the top for x labels when y = 0 is above the canvas, the right for y labels when x = 0 is past it), and axis, ring and range labels that a zone's name would cover are left out (`_clearOfBoxes` over `_zoneLabelBoxes`), as are axis and ring labels under the buttons over the map (`_overlayBoxes({notes: false})`, from the frame's one read of the canvas box), which are see-through: on a zoomed map a y label read as "16 ft2x" beside the zoom readout. The offline note is not among them, because `_placeMapNotes` places it under the x labels.
- Snapping (2.4.0b3): `snap.ts` is pure. `snapStepMm(gridStepMm, family)` is the largest of the unit family's round snaps (mm 10, 20, 50, 100, 200, 500 and 1000 for meters; inches 1, 2, 3, 6, 12 and 24 for feet) no more than `SNAP_GRID_FRACTION` (0.1) of the grid step shown, or the finest under a step that fine: 100 mm at a 1 m grid, 2 in at 2 ft, 1 in at 1 ft and below. `snapMm` rounds to it counted from 0, where the grid lines count from. `_snapStep` takes the finer of a YAML grid's two steps. `_placeMm(px, free)` is where a drawn corner goes: on the snap, or under the pointer while Alt or Option was held at the last move or key (`_cursorFree`; `_onKeyDown` and `_onKeyUp` call `_setCursorFree`, which redraws at once, so a press or a release mid-drag needs no move). `startPoint` is placed at the press (`_placedPx`) and stays, a polygon's corners snap as they are tapped, and `_shapeFromDrag` and every preview use the same placement, so the readout, the preview and the save agree. Saves are whole mm, clamped onto the map, and a walked corner, the radar's own average, never goes through it.
- View only: `view_only: true` makes `_template()` return `_viewOnlyTemplate()` (title, version notice, canvas, offline note; a load error still shows the error template), `render()` attaches no canvas listeners and `connectedCallback` no global ones, `_onTargetsChanged` feeds trails only, and `getCardSize()` is 6. Switching a live card to view only drops a shape in progress, exits Walk and closes History.
- Offline note: `#offlineNote` (`OFFLINE_NOTE`, `role="status"`, top left over the canvas, no pointer events) shows while `_radarOffline()`, the card's twin of `targets.radar_offline`, holds; it touches the DOM only when the answer changes. It and the Replay badge (`.map-note`, `top: var(--zm-note-top, 4px)`) sit `MAP_NOTE_INSET_CSS_PX` below the map's top edge, or that far below the x labels when their row starts within `MAP_NOTE_INSET_CSS_PX` plus `MAP_NOTE_HEIGHT_CSS_PX` of that edge, as on a fitted map, where y = 0 is the top edge: each frame `_placeMapNotes` sets `--zm-note-top` on `.canvas-container` when it changes, and a render's new container gets it from the render's first frame.
- Walk: `walk.ts` `walkShape(corners, clamp, maxPoints)` turns map-frame corners into a rect (2 corners; `flat` under `WALK_MIN_CORNER_GAP_MM` on a side), a polygon (3 or more; `flat` under `WALK_MIN_AREA_MM2`) or `few`. A corner is `TrailBuffer.average(slot, _now(), WALK_AVERAGE_MS)`, time-weighted because HA reports changes only and a plain mean of the samples would lean toward the walk in, falling back to the current reading of a still target whose samples aged out. The samples are paired positions (see Trails), but the LD2450 updates each axis about once a second, so the first reading of where the walker stopped can come about 1.15 s after they stop, and a corner pressed 1 s after stopping lands about 0.4 m short: the hints (`WALK_HINT_START`, `walkHintNext`) ask for about 3 seconds of standing still before **Corner here**. Corners are kept in the raw frame, so they follow a rotation change. Walk ignores targets inside ignore zones, refuses a corner near the last one or back at the first, saves through `_commitZoneShape` or `finishPolygon`, and is not `isDrawing`, so the outside-press handler leaves its panel alone. Entering it closes History, which stays disabled until Walk ends, because opening it would hide the dot being walked.
- History: `history.ts` `decodeMovement` checks each column's byte length against `n` (a mismatch throws and shows `historyError`) and reads it through a little-endian `DataView` into per-slot series. `positionAt` interpolates between two records only when the next is a point within `REPLAY_INTERP_MAX_GAP_MS` and within the hold's plausibility bound (600 mm plus 1.6 mm per ms of the gap), so a slot swap never slides a dot across the room, and hides a slot after a gone marker or after `REPLAY_VISIBLE_MS` without records. `trailAt`, `heatCells` (dwell-weighted, capped at `HEAT_WEIGHT_CAP_MS` a point, so walking does not drown out where people stay) and `sparkBuckets` feed the replay trails, the heatmap and the 120-bucket sparkline (inline SVG built from numbers only). Each fetch takes a token from `++_historyReq`; closing the panel, `_resetDeviceState` and a websocket error bump it too, and an answer is applied only while its token is current and the panel is open for the same device, so a slow 24 h answer never replaces a later 1 h one or reopens a closed panel. The range ends at the payload's `now`, and a first answer that shows more than 60 s of clock skew is fetched once more with a corrected `since`. Play advances `t` every `HISTORY_FRAME_MS` at 1x, 10x or 60x and pauses at the end. Each replay frame first computes the dots (`positionAt` per slot, `_toMap`, `_isIgnored`) and lights every detect zone a dot outside the ignore zones is in, with the current shapes, then draws through the live paths. `#replayBadge` formats the time with `Intl.DateTimeFormat` in the Home Assistant locale (12 or 24 hours from `hass.locale.time_format`, the server's time zone when the profile asks for it), falling back to the browser default.
- Flip: `valueToPixels` and `pixelsToValue` mirror x while `_mirrorX`, and so does every place that bypassed them (the grid step in `_computeGridMetrics`, the cone rings and labels, `_rangeLabel`'s direction); the cache keys include the flag. Never `ctx.scale(-1, 1)` or a CSS `scaleX(-1)`, which would mirror text and pointer math. X tick labels keep their stored values, and the cone slider gets `direction: rtl` so it drags in screen direction. Since 2.4.0b3 `MIRROR_HINT` asks for the walk test with the map turned the way the room is, because at Cone rotation 180 a step to the right moves the dot left on an unturned screen and the radar is right (J8), and `CONE_MOUNT_HINT` under the slider says to mount the sensor first, since nothing on the radar tells the map how it is mounted.
- Admin gating: the template is built before the first `hass`, so `_renderAdminControls()` sets the Walk button, the Walk chip (`#btnWalkChip`, `_renderWalkChip`, since 2.4.0b3: an administrator's, hidden while Walk is on, and shown only on a `pointer: coarse` screen by the `.walk-chip` rule, where the 🚶 among the drawing modes is often missed; a press goes through `_enterWalk`, so a locked map says how to unlock), the flip checkbox's disabled state and title, the movement option and its checkbox, and the History chip afterward, and exits Walk and closes History when they are no longer allowed; `set hass` runs it again when the admin flag changes. Non-admins never call the movement commands. `.container.dark { color-scheme: dark; }` makes native checkboxes, selects and the scrubber follow the card's forced `dark_mode`, inputs take `accent-color` from the theme's primary color, every new toggle is a `button.zone-btn` chip with `aria-pressed`, and `.config-content.open` grew from 1200 px to 5000 px so the longer Configure does not clip.

## Contracts between frontend and backend

**Websocket commands** (`websocket.py`, `api.ts`): `apollo_mmwave/zones/get {device_id}` returns one payload; `apollo_mmwave/zones/subscribe {device_id}` returns null then pushes the same payload on every change (one push per zone edit). Error codes: `not_loaded` and HA's `unknown_command` (both retried by the zone card; `api.ts` exports `ERR_UNKNOWN_COMMAND`) and HA's `not_found` (terminal). The card's reload recovery also uses HA's `config_entries/subscribe`, which is not admin-gated in any supported version. None of the four zone and calibration commands requires admin; the two movement commands do (see Movement websocket commands below).

**Calibration websocket commands** (`calibration/api.ts`): `apollo_mmwave/calibration/get {device_id}` returns one payload; `apollo_mmwave/calibration/subscribe {device_id}` returns null, then immediately pushes the current payload, then every change. Error codes: `not_loaded` (retried by the calibrate card) and `not_found`; the calibrate card does not retry `unknown_command`. The payload (`CalibrationPayload`) is `{job: JobState | null, snapshots: [{id, taken_at, reason, count}], last_result: CalibrationResult | null, interrupted: InterruptedMarker | null, entities: EntitiesInfo | null}`, where `EntitiesInfo` names the radar's `query_params_button` (null when it has none); `JobState` carries `job_id`, `kind`, `status`, `sub_phase`, `elapsed_s`, `remaining_s`, `duration_s`, `settle_s`, `samples`, `peaks` (gate keys are strings on the wire), `writes_done`, `writes_total`, `apply`, `cancel_requested` and `engineering_mode_turned_on`; `CalibrationResult` is the backend's result payload (per-gate `move`/`still` channel results with `peak`, `p95`, `old`, `new`, `samples`, `written`, `confirmed`, `actual`, `flags`, `skipped`, plus `apply` (false for a preview, null on a restore), `changed`, `unchanged`, `writes_done`, `writes_total`, `unverified`, `gates_off`, `warnings` and `error`; a restore result has `gates: []` and adds `restored`, `missing` and `restored_from: {id, taken_at}`); `InterruptedMarker` carries `phase` and `left_on` as independent facts. `warnings`, `flags` and `error.code` are codes; `calibration/model.ts` owns every sentence. The card calls `apollo_mmwave.calibrate_gates` with `{device_id, ...calibration block, apply?: false}`, `apollo_mmwave.cancel_calibration {device_id}` and `apollo_mmwave.restore_gate_thresholds {device_id, snapshot_id?}` (without `snapshot_id` from every Undo button, because the newest snapshot is the one its label names; only "Try again" on a failed restore passes the id of the snapshot it was restoring), `switch.turn_on` / `switch.turn_off {entity_id}` for the chart overlay and the interrupted banner, and `button.press {entity_id}` on the query-params button for "Read settings from the radar". The setup card in gate mode opens the same subscription (`CalibrationJobWatch`, with the same `not_loaded` retry) and reads only whether a job runs; its own writes are `switch.turn_off` on Radar Engineering Mode and that `button.press`. The service schemas, the bus events, the `apollo_mmwave.calibration` storage file and the backend side of these commands are documented with the backend modules.

**Calibration services** (`calibration.py`, `services.yaml`; all `extra=vol.PREVENT_EXTRA`, all registered with `SupportsResponse.OPTIONAL`, all plain services rather than admin ones because each checks `POLICY_CONTROL` for the calling user on the entities the job writes): `apollo_mmwave.calibrate_gates {device_id: str | [str], duration_s?: 15..600 = 60, settle_s?: 0..120 = 15, margin?: 0..50 = 15, margin_pct?: 0..100 = 35, kind?: both | move | still = both, apply?: bool = true, wait?: bool = false}` returns `job.public_state()` when the job starts, or the result payload with `wait: true`; `apollo_mmwave.cancel_calibration {device_id}` returns `{cancelled: bool}` and is a no-op without a job; with one, the caller must be allowed to control every entity the job writes (`_job_entities`: the engineering mode switch and the planned thresholds, or a restore's targets), the check that job's pre-flight ran, or the call is refused with `not_allowed`; `apollo_mmwave.restore_gate_thresholds {device_id, snapshot_id?, wait?}`. `margin` and `margin_pct` may not both be 0 (checked in the pre-flight, not the schema). Pre-flight refusals are `ServiceValidationError`s with the translation keys `unknown_device`, `multiple_devices`, `calibration_running`, `no_gate_entities`, `engineering_mode_missing`, `device_offline`, `background_correction_running`, `thresholds_not_numeric`, `margin_zero`, `not_allowed` and `no_snapshot` (`translations/en.json` `exceptions`). Job failures are codes on `result.error` (`engineering_mode_not_confirmed`, `no_energy_data`, `engineering_mode_lost`, `background_correction_started`, `thresholds_not_numeric`, `snapshot_failed`, `device_offline`, `write_failed`, `not_allowed`, `cancelled_by_shutdown`, `unexpected`, and `no_gate_data`, which the original calibration spec did not list) with the sentences in `ERROR_MESSAGES` (`device_offline` and `write_failed` have reworded zero-write forms without the Undo clause), which the card shows verbatim after "Calibration failed: ".

**Calibration bus events and signal**: `apollo_mmwave_calibration_started {device_id, job_id, kind}` and `apollo_mmwave_calibration_finished {device_id, job_id, kind, status, outcome, changed, snapshot_id}` (`EVENT_CALIBRATION_STARTED`, `EVENT_CALIBRATION_FINISHED`). The internal dispatcher signal `apollo_mmwave_calibration_updated` (`SIGNAL_CALIBRATION_UPDATED`) carries the device id as its only positional argument and fires on every status or sub-phase change and once per tick, never more often.

**Calibration storage schema** (`calibration_store.py`): key `apollo_mmwave.calibration`, version 1, shape `{"devices": {<device_id>: {"snapshots": [{"id", "taken_at", "reason": "calibrate" | "restore", "job_id", "values": {<entity_id>: {"value", "unique_id", "platform"}}}], "last_result": <result payload> | null, "interrupted": {"job_id", "kind", "phase": "engineering" | "applying" | null, "started_at", "engineering_mode_turned_on", "snapshot_id", "left_on"} | null}}}`. Snapshots are newest first and capped at `MAX_SNAPSHOTS`; `unique_id` and `platform` let a restore re-resolve a renamed entity. `apollo_mmwave.zones` and `store.py` are untouched by the calibration feature.

**Payload** (`websocket.py` `_payload`, `api.ts` `ZoneConfig`): `{zones: {"<id>": {shape, data, name?, zone_type?, hold_s?, presence_entity_id} | {}}, entities: [{x, y}] | null, rotation_deg: number | null, label: string | null, input_units: string | null, display_units: string | null, mirror_x: boolean, movement_history: boolean, suggested_entities: [{x, y}]}`. Per zone, `zone_type` is present only as `"ignore"` and `hold_s` only from 1 to 3600 (both normalized with `zone_type_of` and `zone_hold_s`, so a hand-edited value reads as the default and is left out), and `presence_entity_id` is the presence entity's id from the registry, or null while it is not registered; the card's `ZoneDef` declares all three optional, so a 2.3.0-shaped payload still works (the card then finds the presence entity by its id pattern). `mirror_x` and `movement_history` are always present as booleans. The payload is pushed again, through the websocket-only `SIGNAL_ZONES_PAYLOAD`, when a presence entity's id is renamed. The server always sends `input_units` (null means millimeters), the unit for target sensors that have no length unit of their own, and `display_units` (`"m"`, `"ft"`, or null when no unit is saved and the card follows Home Assistant's unit system); the TypeScript interface declares both optional (`display_units?: DisplayUnits | null`). Zone ids are ints in the store and strings on the wire. A zone value of `{}` is the placeholder `migration._legacy_zone_definition` stores for a pre-1.2 zone whose restore data was lost; it means no geometry, `api.ts` `ZoneDef` declares `shape?` and `data?` optional to match, and the card lists such a zone (as `Zone N` or its YAML name) and draws nothing for it. `entities: null` means never configured (the card uses `suggested_entities`); `[]` means cleared.

**Service** `apollo_mmwave.update_zone` (`UPDATE_ZONE_SERVICE_SCHEMA` in `__init__.py`, `services.yaml`): registered with `async_register_admin_service`, so a call from a user who is not an administrator raises `Unauthorized` before anything is written (the card shows it as its "Could not save" toast), and calls with no user, such as automations, run (`tests/test_init.py::test_update_zone_is_admin_only`). at least one of `device_id` (str or one-item list) or deprecated `location`; when both are given, `device_id` wins and `location` is ignored without the deprecation warning. `zone_id` is an integer from 1 to 2**53 - 1 (`vol.All(vol.Coerce(int), vol.Range(min=1, max=_MAX_SAFE_INT))`), so 0 is refused, matching `services.yaml` ("1..N", selector min 1) and the card; a float is truncated (1.9 becomes 1). `shape` in `none`, `rect`, `ellipse`, `polygon`; `data` dict or null, read only together with `shape`. To clear a zone send `shape: none` (`data` omitted or null); `data: null` without a shape never cleared anything. `name` (an empty name, or the default `Zone N`, sets the entity names back to their bases; see Rename under `__init__.py`); `delete`; `rotation_deg` (coerced to float, then rounded and clamped to [-180, 180] by `_sanitize_rotation`; inf and nan are ignored, so the call carries no rotation); `input_units` in `INPUT_UNIT_FACTORS`; `display_units` in `m`, `ft` or `auto` (`m` and `ft` always count as a change, `auto` removes the saved unit and counts only while one is saved, so an `auto` with nothing saved is refused as "carried nothing to change" and creates no store entry); `entities` as `[{x: entity_id, y: entity_id}]`, where an empty list means no change; `clear_entities`, which wins over `entities`; `zone_type` in `detect` or `ignore` and `hold_s` from 0 to 3600 (booleans refused), both zone settings that need `zone_id`; `mirror_x` and `movement_history` (`cv.boolean`), device-wide. A default value counts only while a non-default is stored (`detect` on an ignore zone, `hold_s: 0` on a zone with a hold, `false` on a stored flag), and geometry writes carry a zone's type and hold over. Extra top-level keys are rejected. Coordinates that are not finite or exceed `_MAX_SAFE_INT` are treated as non-numeric (see `__init__.py`). Calls that would change nothing are refused with a warning and write, signal and fire nothing (`_call_changes_something`). Calls run one at a time, under the handler's `asyncio.Lock`. The card sends: `{device_id, zone_id, shape, data}` for geometry (`updateHomeAssistantShape`), `{device_id, zone_id, name}` for rename of a stored zone, `{device_id, zone_id, shape: "none", data: null, name}` for a new zone and for the rename of a zone only its YAML names, `{device_id, zone_id, delete: true}` for delete, `{device_id, rotation_deg}` for rotation (`_persistRotation`), `{device_id, display_units}` with `m` or `ft` from the unit switch, and only for an administrator (`_chooseDisplayUnit`), `{device_id, zone_id, zone_type}` or `{device_id, zone_id, hold_s}` from the zone list (with `shape: "none", data: null` added for a zone only its YAML names, `_saveZoneSetting`), `{device_id, mirror_x}` from the flip checkbox and `{device_id, movement_history}` from the movement history checkbox. `_saveZoneUpdate` adds `input_units` to the geometry, rename and rotation writes; the unit switch, the zone settings, the flip and the movement history writes leave it out (`withInputUnits: false`). It never sends `entities`, `clear_entities`, `location` or `display_units: auto`.

**Geometry**: integer millimeters, X to the radar's right, Y away from the radar. `rect {x_min, x_max, y_min, y_max}` with strict `x_min < x_max` and `y_min < y_max`; `ellipse {cx, cy, rx, ry}` with radii floored at 1 mm; `polygon {points: [{x, y}]}` with `POLYGON_MIN_POINTS` to `POLYGON_MAX_POINTS` points (`const.py`). The rotation formula is the same in `targets.py` (`build_point_rotator`), `card.ts` (`_toMap`) and `geometry.ts` (`rotateToMap`), and the shape tests in `targets.py` and `geometry.ts` (`pointInRect`, `pointInEllipse`, `pointInPolygon`, `pointInZone`) follow the same rules, so the card lights, hollows and replays exactly what presence counts, and `drawZones` fills a polygon by the same even-odd rule. Positive `rotation_deg` swings the device's facing direction toward its right (+X): 90 maps (x, y) to (y, -x), so a target straight ahead at (0, d) lands at (d, 0), and `drawDeviceCone` uses the same sign (the cone at +90 points to +X). Do not call it "clockwise": the card's canvas is Y-down, so on screen the motion looks counterclockwise. `services.yaml` `rotation_deg` and the `build_point_rotator` docstring carry the same sentence. The flip (`mirror_x`) is display only and never reaches this contract: stored geometry, presence, the recorder and Walk corners are never mirrored.

**Bus event** `apollo_mmwave_zone_updated` with data `{"device_id": "<ha device id>"}` (`EVENT_ZONE_UPDATED`, fired from `_notify_zones_updated`), only for `update_zone` calls that changed something. The internal dispatcher signal `apollo_mmwave_zones_updated` (`SIGNAL_ZONES_UPDATED`) carries the device id as its only positional argument; the LD2450 cache invalidation sends the signal without the bus event.

**Storage schema** (`store.py`): key `apollo_mmwave.zones`, version 2, shape `{"devices": {<device_id>: {"zones": {"<n>": {shape, data, name?, zone_type?: "ignore", hold_s?: 1..3600} | {}}, "entities"?: [...], "rotation_deg"?: int, "label"?: str, "aliases"?: [str], "input_units"?: str, "display_units"?: "m" | "ft", "mirror_x"?: true, "movement_history"?: true}}, "orphans": {<v1 location>: same}}`. A default is never stored: no `zone_type` means detect, no `hold_s` means no hold, and a missing flag means off (the tests pin exact zone dicts). The 2.4.0 keys need no version or minor bump; `store.py` lists what 2.3.0 does with them. `aliases` holds every other v1 or legacy location name that merged onto the device (the first name stays `label`). `input_units` is absent for millimeters and is restored on load only when it is a key of `INPUT_UNIT_FACTORS`. It only scales readings from target sensors with no length unit of their own; a sensor's own unit wins. `display_units` is absent when the card follows Home Assistant's unit system and is restored only when it is `m` or `ft`; it is display only, so presence detection and the zone sensors never read it. Version 1 files have `{"locations": {<display name>: {zones, entities, rotation_deg}}}`.

**Movement websocket commands** (`websocket.py` `TYPE_MOVEMENT_GET` and `TYPE_MOVEMENT_CLEAR`, `api.ts` `MOVEMENT_GET`, `MOVEMENT_CLEAR`, `fetchMovement`, `clearMovement`, `MovementPayload`): administrators only. `apollo_mmwave/movement/get {device_id, since?}`, where `since` is epoch milliseconds (`vol.All(vol.Coerce(int), vol.Range(min=0))`), answers `{enabled, now, since, retention_s, n, t0, dt, s, x, y}`. `now` is the server's epoch ms when the answer was built (the card uses it, never its own clock); `since` is the effective lower bound, the request's `since` clamped between 24 hours before `now` and `now` (24 hours before `now` when the request has none); `retention_s` is 86400; `n` is the record count and `t0` the first record's epoch ms (null when `n` is 0). `dt`, `s`, `x` and `y` are standard base64 (RFC 4648, padded) of the values packed little-endian: `dt` uint32, the ms since the previous record (`dt[0] == 0`, so `t[i] = t[i-1] + dt[i]`); `s` int16, the slot (the index in the radar's effective pair list, so the card's dot number is `s + 1`), or `-1 - slot` for a gone marker; `x` and `y` int16 mm in the raw sensor frame (unit converted, not rotated, not mirrored; 0 on gone markers). Decoded byte lengths are exactly `n * 4` and `n * 2`, and empty columns are `""`. Records are sorted by time across slots. For each slot, the last record before `since` comes first when it is a point within `MOVEMENT_CARRY_IN_MS` of `since`, so a still person shows at the window start and `t0` can be below `since`. A radar whose flag is off answers `enabled: false`, `n: 0`, `t0: null` and empty columns. The answer is built from array slices and `tobytes()`: at the cap (105,000 records) it is about 1.4 MB and takes about 1 ms to build on an M1 (`test_movement_get_at_the_cap_stays_under_2_mb`). `apollo_mmwave/movement/clear {device_id}` answers `{cleared: <records removed>}`; it empties that radar, keeps the flag and keeps recording. Errors: `unauthorized` for a non-admin, then `not_loaded` and `not_found` (see `websocket.py`). The card guards an answer with `isMovementPayload` (types only) and `history.ts` `decodeMovement` (byte lengths).

**Movement storage schema** (`movement.py`): key `apollo_mmwave.movement`, version 1, a private `Store` with atomic writes, shape `{"saved_at": <epoch ms>, "devices": {<device_id>: {"t0", "n", "dt", "s", "x", "y"}}}`, the same column encoding as `get` without the carry-in or `now`. Sizes, measured with HA's indented writer: about 13.3 bytes a record on disk, 1.33 MB per radar at 100,000 records (about 1.4 MB with the prune slack), and about 18 bytes a record in memory (about 1.9 MB per radar at the cap). Each save rewrites the whole file, so with someone always in view at the cap that is up to about 1.9 GB a day per radar at the 60 s save delay (300 s would write five times less and lose up to 5 minutes in a crash, an open question for the maintainer). Lifecycle: created only by a save that has records, so only after an administrator turned history on and a target was recorded; removed instead of saved, together with its corrupt copies, whenever a clear, a flag off, retention, a removed radar or a load leaves no radar with records; pruned on disk to 24 hours plus about 11 minutes by the retention timer; dropped per radar at load for a flag that is off, a device no longer registered, malformed columns, records older than 24 hours and records more than 60 s in the future; a corrupt file's `apollo_mmwave.movement.corrupt.*` copies deleted at load, at removal and whenever the file is removed; and the file removed with the config entry. Home Assistant backups include it, as they include all of `.storage`. 2.3.0 neither reads nor deletes it.

## Build, test and CI

The frontend is built and tested from `frontend-src/` (`frontend-src/package.json`):

```sh
cd frontend-src
npm ci              # installs exactly the lockfile, as CI does
npx tsc --noEmit    # type check src and test (tsconfig.json); zone-map/card.ts is @ts-nocheck
npm test            # vitest run (vitest.config.ts)
npm run test:bundles # the card, strategy and zone map suites against www/ (vitest.bundles.config.ts)
npm run build       # vite build && vite build --config vite.zone-map.config.ts
npm run watch       # watch:tuning and watch:zone-map side by side (Ctrl+C stops both)
```

The toolchain is Vite 8.3 (Rolldown bundles, Oxc transforms TypeScript), vitest 5, happy-dom 21, TypeScript 7.0 (the native `tsc`, used only to type check) and terser 5.51, all dev dependencies; `lit` (3.3) is the only runtime dependency and the only one that reaches the shipped bundles. CI builds on Node 22, so rebuild `www/` with a Node 22 toolchain to match the committed output. `npm run build` runs Vite twice on purpose (`vite.config.ts`): a single multi-entry build would hoist `src/register.ts` into a shared chunk that HA never fetches, so each bundle is built standalone and written to `../custom_components/apollo_mmwave/www/<name>.js` with `emptyOutDir: false`, `minify: "terser"` and `rolldownOptions.output.codeSplitting: false` (Rolldown's name for `inlineDynamicImports`). `npm run watch` keeps two separate Vite processes for the same reason; it uses POSIX shell job control (`a & b & wait`), so on Windows with npm's default `cmd.exe` run `npm run watch:tuning` and `npm run watch:zone-map` in two terminals. `build.target` is pinned to Vite 6's old default (`es2020`, `edge88`, `firefox78`, `chrome87`, `safari14`), because Vite 8's default (Safari 16.4, Chrome 111) leaves class static blocks in the output that iOS 15 Safari cannot parse. Oxc reads `experimentalDecorators` and `useDefineForClassFields: false` from `tsconfig.json`, so Lit's decorators compile to legacy `__decorate([...], Card.prototype, "hass", void 0)` calls and field initializers to constructor assignments, with no class field that would hide Lit's accessors. The two outputs, `apollo-radar-tuning.js` (from `src/index.ts`) and `apollo-radar-zone-map-card.js` (from `src/zone-map/card.ts`), are committed because the Python side serves exactly those filenames (`const.py` `JS_BUNDLES`) and HACS users never run npm. Any change under `frontend-src/src` must therefore be followed by a rebuild and a commit of `www/`. Up to 2.2.2 the bundles shipped unminified, comments included, because Vite 6's terser plugin skipped ES library output. Vite 8 runs terser on it, keeping `/* @__PURE__ */` annotations, and strips comments except lit's `@license` notices (kept by `rolldownOptions.output.comments: { legal: true }`) and comments inside template strings (CSS in the card styles), so most comment-only edits no longer change a bundle; rebuild anyway and let the bundle-sync step decide.

`vitest.config.ts` runs `test/**/*.test.ts` in happy-dom with `TZ=UTC` and `test/setup-canvas.ts` as a setup file, and allows `../custom_components/apollo_mmwave` in `server.fs.allow` because `test/registry-detection.test.ts` imports `config_flow.py` with `?raw` to check `MMWAVE_MODELS` and the `test/bundle-*.test.ts` files import the committed bundles from `www/`. Two Lit problems seen on happy-dom 14 shaped the tests: child-part markers at a template root and inside `<svg>` were mis-cloned, and a `<button>` reported `tabIndex` -1 unless it carried `tabindex="0"`. So render helpers keep their bindings inside an element, `charts/gate-energy-chart.ts` keeps its SVG in a nested template, the chart's overlay button carries `tabindex="0"`, and both chart renderers are asserted on their `TemplateResult` through `flat` in `test/template-markup.ts` rather than on the DOM (`test/distance-chart.test.ts`, `test/gate-energy-chart.test.ts`). `vitest.config.ts` notes that the problems were not re-checked after the move to happy-dom 20. A probe during the audit's documentation pass (happy-dom 20.14.6) rendered both charts' SVG children and a root-level child part into the DOM and gave a plain `<button>` `tabIndex` 0, so the workarounds look unnecessary now; they still work. Frontend coverage is not configured.

`vitest.bundles.config.ts` reuses that config for the suites that import `../src/cards/calibrate-card`, `distance-card`, `gate-energy-card`, `setup-card`, `slider-lock-rows`, `../src/strategy`, `../src/zone-map/card` or `editor` (it reads `test/` to find them, leaving out `test/bundle-*.test.ts`). An alias swaps each of those modules for the file at the same path under `test/bundle-shims/`, which exports the class the committed bundle defined (`shouldRegenerate` for the strategy), plus the source module's other exports for `calibrate-card`, `setup-card`, `slider-lock-rows` and `editor`. The setup file `test/bundle-shims/load-bundles.ts` loads both bundles into each suite's window before the suite imports anything and records the class each defined per tag, so a shim throws for a tag its bundle lost instead of handing out the class the source module registered in its place. Tests that need identity with a source module (an `instanceof` against a source class, a spy on a source module's export, a source object compared by reference) are listed in `SOURCE_ONLY` there, each with a one-line reason, and skipped by `testNamePattern`; card tests otherwise compare values only. Two examples: `cards.test.ts` "styles the gate-energy chart's legend from the chart module" and `strategy.test.ts` "stays one entry when the bundle is evaluated again" (`bundle-tuning.test.ts` evaluates the bundle twice instead). Helpers that only the sources export, such as the chart renderers in `charts/`, are still tested from the sources alone, and so is the slider lock store: `test/slider-lock.test.ts` imports only `cards/slider-lock.ts`, which defines no element, while `test/slider-lock-rows.test.ts` runs in both modes and, since the bundle's rows use the bundle's own copy of the store, drives the lock only through the rows. If a bundle test misses a file just added under `src/` (`test/bundle-sources.ts` reads the sources through `import.meta.glob`), delete `frontend-src/node_modules/.vitest-cache` and run it again.

The Python suite (`tests/`) needs Python >= 3.14.2. Locally, after `scripts/bootstrap`:

```sh
uv pip install -r requirements-test.txt   # test harness into the .venv bootstrap made
uv run --no-project pytest tests/         # or .venv/bin/python -m pytest tests/
```

Do not run `uv venv` after `scripts/bootstrap`: uv refuses an existing `.venv`, and `--clear` would discard ruff and pre-commit. `uv venv && uv pip install -r requirements-test.txt` is the clean-checkout form CI uses, and it installs no ruff. Coverage needs no extra install, because `pytest-homeassistant-custom-component` pins `pytest-cov` and `coverage`: append `--cov=custom_components/apollo_mmwave --cov-report=term-missing` (the `.coverage` file is gitignored). `requirements-test.txt` pins `pytest-homeassistant-custom-component` (which pins a matching `homeassistant`, 2026.10.0 at the time of writing) and `home-assistant-frontend`, needed because `manifest.json` depends on `frontend`. Keep the frontend's YYYYMMDD prefix aligned with the HA release; an exact match is not required, because the harness sets `skip_pip` and HA never checks the frontend requirement under test. A `.venv` created before a pin change keeps the old harness until `uv pip install -r requirements-test.txt` runs again (`scripts/bootstrap` alone does not upgrade it), so check `homeassistant` in `.venv` before trusting a local backend run. CI tests only 2026.10.0, and no job tests the `hacs.json` floor (2026.8.1). During the audit the local `.venv` happened to hold 2026.8.1 (REVIEW_REPORT X56), which is where the HA APIs the calibration feature relies on were checked against the floor. `pyproject.toml` sets `testpaths = ["tests"]` and `asyncio_mode = "auto"`. `tests/conftest.py` auto-enables custom integrations; fixtures register an ESPHome radar device with three target pairs, plus gate-radar fixtures for the calibration tests.

Linting:

```sh
scripts/bootstrap     # checks $PYTHON (default python) is >= 3.14.2, then "$PYTHON" -m venv .venv,
                      # pip install -r requirements.txt, pre-commit install; needs neither uv nor pipx
scripts/lint-check    # .venv/bin/ruff format . --check && .venv/bin/ruff check .
scripts/lint          # .venv/bin/ruff check . --fix-only, ruff format ., ruff check . (one pass leaves nothing for lint-check)
```

Use `PYTHON=python3.14 scripts/bootstrap` when `python` is not a suitable interpreter. Both lint scripts stop with ".venv/bin/ruff not found: run scripts/bootstrap first" when there is no venv ruff. The Python floor lives in `pyproject.toml` `requires-python` and in `scripts/bootstrap`, and `tests/test_scripts.py::test_bootstrap_floor_matches_requires_python` fails if they diverge; raise the devcontainer image tag with them (`tests/test_devcontainer.py`). Ruff is configured in `pyproject.toml` (`select = ["ALL"]`, target py314, test exemptions) and pinned by the single `ruff==` line in `requirements.txt`. `.pre-commit-config.yaml` runs `ruff check --fix --exit-non-zero-on-fix` and `ruff format` on staged Python files as `language: system` hooks, so ruff comes from the committing shell's `PATH` and commits need `.venv` active. The copy style for user-facing text (no em dash, "R PRO-1") is enforced by `tests/test_translations.py` for `translations/en.json` and `services.yaml` and by `frontend-src/test/copy.test.ts` for the frontend's profile tips, help cards, empty dashboards, card picker entries, the setup card's lines, the slider lock's copy and every export of `zone-map/copy.ts`.

CI (`.github/workflows/`):

- `lint.yml`: Python 3.14, uv, `uv venv` plus `uv pip install "$(grep -E '^ruff==' requirements.txt)"` (ruff only; the Home Assistant pin is exercised by the pytest job), then `scripts/lint-check`.
- `test.yml` job `pytest`: `uv venv`, `uv pip install -r requirements-test.txt`, `uv run --no-project pytest tests/ -q --cov=custom_components/apollo_mmwave --cov-report=term-missing`. The log ends with a per-module coverage table listing missed lines; no threshold is enforced, so a coverage drop never fails CI.
- `test.yml` job `frontend` (working directory `frontend-src`): `actions/setup-node` with Node 22 (npm cache keyed on `frontend-src/package-lock.json`), `npm ci`, `npx tsc --noEmit`, `npm test`, `npm run test:bundles`, then `npm run build` followed by `git status --porcelain -- ../custom_components/apollo_mmwave/www` and `test -z` on that output. The step fails when a fresh build modifies, deletes or adds any file under `www/`, including an untracked bundle a rename leaves behind (with `emptyOutDir: false`, `git diff` alone would not see it); the status lines are printed first so the log names the files out of sync.
- `validate.yml`: hassfest and HACS validation (`category: integration`, no checks ignored) on push to `main`, pull request, daily cron and manual dispatch. The HACS brands check passes on the local `custom_components/apollo_mmwave/brand/icon.png`; the action falls back to the home-assistant/brands list only when that file is missing.

`.github/dependabot.yml` asks for daily version updates for devcontainers (Features only, never the base image), GitHub Actions, pip and npm in `/frontend-src`. It ignores `homeassistant`, `pytest-homeassistant-custom-component` and `home-assistant-frontend`, which are bumped by hand in one commit (`homeassistant==` in `requirements.txt`, the harness release that pins the same HA, and a matching frontend); that also suppresses Dependabot security-update PRs for the two test pins, though alerts still appear in the Security tab. An npm bump that changes the built output (lit, vite, terser) fails the frontend job's bundle-sync step until `npm run build` is run and `www/` is committed on that PR, which is expected. A bundle change also needs a version bump (the `?v=` cache buster), so such a bump ships as a release: the Vite 8, TypeScript 7 and terser 5.51 bumps went out in 2.2.3, together with the setup-uv bump.

Local development uses `scripts/develop`, which sources `./.venv/bin/activate` when it exists (so the pinned `hass` runs from a plain shell; without a `.venv` it falls back to whatever `hass` is on `PATH`), creates `config/` with `hass --script ensure_config` when it is missing, and runs `hass --config config --debug` with `./custom_components` on `PYTHONPATH` and `config/configuration.yaml` (debug logging for `custom_components.apollo_mmwave`). The devcontainer (`.devcontainer.json`) uses the `mcr.microsoft.com/devcontainers/python:3.14` image, runs `scripts/setup` (bootstrap into `./.venv`) as its `postCreateCommand` and `scripts/motd` on start, and points VS Code's interpreter at `${containerWorkspaceFolder}/.venv/bin/python`, so `hass`, `ruff` and `pre-commit` come from that venv. `scripts/help` (printed by `scripts/motd`) lists each script with the text of its `# script/<name>:` header, so a new script needs that header (60 characters or fewer, or it is truncated).

## Known limitations

These were checked against the code at the end of the full audit (October 2026), and the 2.4.0 items were added with that release. `CHANGELOG.md` lists the user-facing ones under "Known limitations" in its "Upgrading to 2.0" notes, and `docs/configuration.md` mentions more of them next to the feature they affect. `REVIEW_REPORT.md` at the repository root records what the audit fixed and, under "Flagged and left alone", every item it deliberately did not fix (X01 to X61), each with a recommendation. Most flagged items also carry a `TODO(REVIEW_REPORT.md <id>)` comment at their code site (Python ones end the first line with `# noqa: FIX002, TD003`, because ruff `select = ["ALL"]` reports every TODO), and `grep -rn --exclude-dir=www "TODO(REVIEW_REPORT.md" custom_components frontend-src/src .github .pre-commit-config.yaml` lists them. The list below is the subset a maintainer is most likely to run into; the ids point at the full entries.

Zones, the store and `update_zone`:

- The card owns `input_units` in practice: `_saveZoneUpdate` sends its own YAML value on every geometry, rename and rotation write and the card never reads the payload's `input_units`, so a unit set through the service is overwritten by the next card save. Since 2.2.7 it only applies to target sensors with no length unit of their own, so this matters for DIY sensors only. `yd` is accepted by the backend (`INPUT_UNIT_FACTORS`) but absent from the card's `LENGTH_UNITS`, which normalizes unknown units to `mm` (X04). The store itself now keeps `input_units` across restarts and reloads.
- `zone_id: .inf` and a `rotation_deg` integer too large for a float raise `OverflowError` out of the service call instead of a validation error, because `vol.Coerce` catches neither; no state changes.
- A zone 0 created before `zone_id` gained its lower bound still loads and has entities, but neither the service nor the card can address it; remove it by editing `.storage/apollo_mmwave.zones` with Home Assistant stopped.
- Zones stored under a device id that left the registry for good (replaced hardware, or a radar re-added after HA's 30-day deleted-device retention) cannot be removed through `update_zone`, and their device-less entities are re-created with a warning on every setup (X08).
- `delete: true` for a zone the store does not hold still mints an empty store entry, saves, and fires the event (X15). A blank `name` is stored and pins the bare base as the registry name (X14). `location` is ignored silently when `device_id` is also given (X12), and labels that slugify alike resolve by store order with no warning (X16).
- The stored `label` is a one-time copy of the v1 display name: it is never refreshed after a device rename and is absent for devices first configured on 2.x, yet the payload sends it and the zone card uses it as its heading when the card has no `title` (X27).
- Configured `entities` pairs do not follow an entity id rename; presence then reads off with no log (X07).
- Zone presence reads `unavailable` while the radar is offline (X09, done in 2.4.0), and also after every Home Assistant restart until the radar connects, because the ESPHome placeholders are `unavailable` until then. An automation triggered by `to: "off"` without `from:` fires on that step from `unavailable` to `off`, and the dashboard's Zone presence rows hide meanwhile. Ignore zones stay `off` and available.
- Since 2.4.0b3 presence pairs a target's split X and Y writes (B10), which moves presence timing for every user: a zone can turn on or off up to `TARGET_PAIR_MS` (0.55 s) after the first of the two writes, about 0.45 s later than 2.4.0b2 in a third of the simulated walk-ins, and a move along one axis counts only 0.55 s after its write. When a target is lost between an X write and its Y, a held zone reads that X write (new X, old Y) once as the person's last report (`ReadingPairer.lost`); a zone with no hold never reads it. The live dot on the card is drawn from the current states, so it can still show the new X with the old Y for up to about 0.45 s.
- The hold is a position heuristic, tuned for the LD2450's cadence on an R PRO-1 (about one write of each axis a second). It needs about two seconds of walking in the zone to see someone walk, so a shorter walk out of view or through a doorway at the zone's edge, from a seat beside the door for example, often holds for the full hold time, and since 2.4.0b3 a slow walk (0.6 m/s) through 1 to 1.5 m of a zone and out of view releases at once in only 43 to 48% of simulated runs, the price of holding someone who sits down right after walking in; the radar's jump of about 0.5 m in its last report before it loses someone sitting still reads as stepping out when it lands outside the zone, so a seat within about 0.5 m of an edge can release early; a target in a slot that had no reading when the zone emptied, a ghost included, releases the hold within the growing rule 1 radius (up to 7.3 m at 3 s), while one already tracked elsewhere counts only within 600 mm, and a target picked up in the very evaluation that empties the zone counts as already tracked (rare on firmware 26.10.21.1); someone passing through the zone ends a hold; a still person lost while someone else stays inside is forgotten when that person leaves; two people swapping slots inside can read as motion for about a second, so a vanish near an edge then releases; a target seen for under 1.2 s that vanishes mid-zone holds the zone (an ignore zone over the ghost's source is the remedy); the exit rule assumes the LD2450's 6 m and 120 degree view, so where walls or the radar's own zone filter end the view earlier, away from the zone's edge, someone walking out there holds the zone for the full hold time; and a radar reconnect (a Wi-Fi blip) or a restart ends every hold, which is never restored.
- Movement history replays with today's zone shapes, rotation and flip, because it stores raw positions, not zone states. The cap of about 100,000 records per radar (up to 105,000 before the oldest are dropped back to 100,000) drops the oldest first, so a busy room keeps less than 24 hours (as little as about 4.6 h with three people moving all the time, at the floor's two points a second each; an R PRO-1 walk records about one a second). Up to about 60 s of history can be lost in a crash (the save delay). The file is in every Home Assistant backup, those that leave out the database included, and turning history off does not reach backups already made; a recorder exclude or purge does not touch it either. A busy radar at the cap rewrites about 1.3 MB a minute, which matters on SD cards.
- A pre-2.0 zone entity that cannot move to its new unique id logs the "is stale and can be deleted" warning on every setup and reload until it is deleted (X29).
- The retry details of `zone_entities.py` were flagged but not verified: a disabled entity is constructed on every signal before it is skipped, an add that raises inside HA instead of aborting is never retried, the removal nudge fires before HA frees the old state so a retry could get a `_2` entity id, and the module docstring describes a race the pinned HA cannot produce (X58).

Frontend registration and the dashboard:

- JS cache busting uses only the `manifest.json` `version` for the `?v=` query, with Home Assistant's long-lived cache header on the static path. A `www/` rebuild without a version bump is invisible to browsers that cached the old module. Since 2.4.0b3 the cards say when the page runs another version than Home Assistant (see Version check), but a rebuild under the same version reads as equal. A content hash in `?v=` was left out: in storage resource mode a tab served before the restart can then run a bundle twice until it reloads, and replacing the 31-day cache header with `no-cache` is the other open option.
- Ownership is the recorded id and url path plus a config that is still this strategy. Lovelace derives a row's id from its url path, so if the user deletes the integration's dashboard and builds a new one on `apollo-mmwave` whose config is exactly this strategy, the integration cannot tell it apart from its own: a device selection is written into it, and removing the entry, or the options flow's remove step, deletes it. Any other dashboard on that path is left alone.
- A dashboard made by 2.2.5 or earlier keeps `require_admin` False after the upgrade: adoption writes nothing, so it stays visible to every user until an administrator changes it in Settings > Dashboards.
- A deleted `/apollo_mmwave/` Lovelace resource row comes back only at the next Home Assistant restart, not on an integration reload, because the once-per-run asset guard also skips the resource reconciliation (X28).
- Editing a strategy view in the Home Assistant UI discards its cards; that is how Home Assistant treats strategy views. Use "take control" on the dashboard instead.
- Entities registered after the first detection do not add rows to an open dashboard, because they do not change `radarDeviceKey`. That includes a zone drawn since the page loaded, whose presence sensor joins the Zone presence card only after a reload (the empty card says so); a deleted zone's row hides itself at once, but once every listed zone is deleted the card shows its title over no rows, not the draw-a-zone hint, until a reload; and an entity enabled since then, such as the R PRO-1's Multi Target Tracking switch, which joins LD2450 Controls after a reload, or its chip firmware sensors, which join the Device card. The history's zone lines follow the same rule. The Radar setup cards, the built-in zones conditional card and the weak Wi-Fi note read live state and need no reload. Since 2.4.0 a radar's online/offline flip no longer changes the key (X31), so no tab is rebuilt and a drawing in progress survives; in exchange a tab keeps the offline note it was generated with until the page reloads, so a dashboard opened while radars reconnect after a restart says "offline" on a working radar.
- The view and section strategies render nothing, with no message, when no device matches (X30); with several devices the view strategy runs their sections together with no separator (X38). An R PRO-1's six sections (four tuning, the zone map with its setup card, and the LD2450 status and controls) exceed HA's default of four columns. Since 2.4.0b3 the zone map spans two, so the first row is column 1, the zone map and the LD2450 column, and the gate tuning wraps to the second on purpose (X36, settled; see Strategy). The two-column section with dense placement has not been checked on a real Home Assistant or in the apps yet.
- The MTR-1 firmware leaves most LD2450 names unprefixed ("Timeout", "Zone Type"), so `ld2450-entities.ts` reads them on the radar's own device only, after its base name, or by suffix for an id under another base. A second entity on the same device with such a name would be ambiguous, and the first in registry order wins. The base comes from `baseNameFromDevice`, the most common base among the device's entity ids; a device whose ids were renamed one by one to different bases falls back to suffix matching for the ids outside that base.
- The slider lock (see Slider lock) covers locked sliders only. Unlocked sliders behave like HA's own: a touch sets the value where it lands and cannot start a scroll, until the radar locks again (5 minutes without a change, or leaving the tab). On a locked slider, a gesture that starts sideways does not scroll the page (the shield is `pan-y`) and counts as a try. The lock is per page, not per user: every browser tab and device has its own, and a reload locks. A dashboard taken control of before 2.3.0 keeps plain number rows with no lock until the rows are added by hand (`docs/configuration.md` Card options). Locked sliders stay in the Tab order; their value keys go to the reminder toast. The zone map's Cone rotation slider (a native range input under Configure) is not behind this lock but behind the zone map's own: while `isLocked`, `_updateLockVisual` disables it and puts `pointer-events: none` on it (class `locked` on `#cone-controls`), its input, change and double-click handlers return without turning or saving, and `_watchLockedConeTries` treats a tap on its row, or a press that moves more than `CONE_TRY_PX` (10 px) mostly sideways, as a try: `_remindLocked(CONE_LOCKED_TOAST)` (`_remindConeLocked` before 2.4.0) outlines the Locked button for `LOCK_NUDGE_MS` and toasts at most once per 1.5 s, sharing `_lastLockWarningTs` with the drawing and clear reminders. A radar with no zones starts unlocked, so its slider is free. The gate tip under Move Thresholds says the sliders start locked even on a DIY build whose thresholds are all boxes.
- Restart Radar, Factory Reset Radar and the Device card's restart ask first through HA's button row (see Strategy). The LD2412's Start Dynamic Background Correction is still a plain button row that presses on one tap.
- The gate distances in the threshold row labels and the help card follow Home Assistant's unit system, not the strategy's `distance_unit` (which only the distance cards read), and are fixed when the dashboard is generated, so a gate size changed on the device shows after a reload.
- After a Home Assistant restart that interrupted a calibration, the calibrate card's interrupted banner can offer its own "Turn it off" beside the gate setup card's "Turn off Radar Engineering Mode". Both turn the same switch off; they were left separate.
- On an R PRO-1 tab both setup cards are titled "Radar setup"; only the line under the title ("LD2412 · <name>" or "LD2450 · <name>") and their place tell them apart.
- An invalid `distance_unit` ("CM", "feet") is ignored without a warning (X50).
- An R PRO-1 without the optional LD2412 still gets the LD2412 tuning cards. `APOLLO_MODELS` in `profiles.ts` maps every `r-pro-1` model to `LD2412_PROFILE`, and `deviceFromId` in `strategy-core.ts` falls back to that registry profile when `detectProfileFromEntities` finds no LD2412 entity. The help card and the Device card's restart follow the LD2450-only wording (`gateRadar` in `cardMap`), but the tab still shows an Auto-calibrate card that says the radar is offline with its buttons disabled (the backend's payload has `entities: null` because `resolve_gate_entities` finds no gate), "device not found" on both charts and no Controls card (ESP Reboot is on the Device card now), above a working zone map. The gate setup card is left out, because none of the settings it checks exists. `docs/configuration.md` tells users to use the zone map.

Zone map card:

- Reload recovery uses `config_entries/subscribe`, which every user can open. The bounded `RETRY_DELAYS_MS` retry covers a card that misses the entry's `loaded` event (for example when the entry finishes loading between the failed open and the feed subscribe, or when the feed is refused); once the retries run out without that event, the card stays on the "still not loaded" message until a page reload. The re-subscribe `home-assistant-js-websocket` sends after a websocket reconnect can be refused silently, leaving the card on stale zones (X48).
- The lock gates drawing, Walk, the rotation slider and, since 2.4.0, the two one-gesture clears (X06): Undo and the manager's Delete, Add and rename still write while the card says Locked. Since 2.4.0 a locked canvas lets a touch scroll the page (X46), and so does an unlocked one in Walk or with no zone selected; an unlocked canvas with a zone selected still takes every touch for drawing.
- Trails and Coverage live in the page, per viewer: another browser, a reload or a rebuilt card starts them empty, and only the Coverage toggle is remembered (per radar, in `localStorage`).
- Walk needs exactly one visible target outside the ignore zones, so a second person, or a fan or curtain no ignore zone covers, disables Corner here. Dot numbers follow the tracked pair order: the target number on Apollo radars, the list order for configured `entities`.
- The canvas backing store is a fixed 800 px wide with no `devicePixelRatio` scaling (blurry on HiDPI screens). A fitted grid gets a canvas of its own shape, but a YAML `grid` keeps the square canvas, so one whose X span differs from its Y span is drawn stretched (X39).
- Zone map cards added from the card picker before 2.3.0 carry the old stub's `grid` (-6000..6000 by 0..12000 mm) and `grid_units: mm` in their YAML, so they keep that square map until the user deletes both keys; an administrator's saved unit still wins over their `grid_units`.
- A non-administrator's m / ft pick is saved nowhere: it lasts until the card is rebuilt (a page reload or a dashboard regeneration).
- Clear All, and undo of a first draw, write `shape: none` for YAML-seeded ids the store never held, which creates entities for them (X43). A polygon finished with fewer than 3 distinct points, or with no zone selected, is still dropped, and since 2.4.0 a toast says why (X44).
- In ellipse mode a click, a tap or a perfectly straight drag still saves an ellipse with a 1 mm radius over the zone: the ellipse branch of `endDrawing` floors each radius at 1 (`Math.max(1, ...)`), while the rect branch drops a box with no area (F21). The fix agents reported it but left it out of scope; see REVIEW_REPORT.md "Recommended next steps".
- Before the first payload arrives, the cone is drawn at the YAML `cone.angle_deg` and then snaps to the stored rotation (cosmetic; the sensors are unaffected).
- The card picker entry is pushed without a once-per-type guard, so evaluating the zone-map bundle twice lists "Apollo Zone Map" twice.
- Zoom and snapping (2.4.0b3): Safari on macOS sends a trackpad pinch as `GestureEvent`, which the card does not handle, so there it is Cmd and the wheel or the buttons. Nothing in the card tells a desktop user about Alt or Option. The zone list reads sizes to 0.1 m while the drawing readout can read 0.01 m. A finger dragged off a zoomed canvas still extends the shape to the map's edge, past the part on screen. A zone label pulled onto the top edge can overlap the x labels when zoomed. `_enterWalk` does not check for a selected zone, so Walk starts without one and only Finish says "Select a zone first." The range caption is never left out, so on a zoomed map it can run under the unit switch. Where none of Walk's four readout spots is clear (on a phone's map, after a fourth corner near the drawing modes, for example), the readout falls back to above the newest corner, over earlier corners' numbers and partly under the 🚶 button.

Tuning cards and detection:

- If all four top-gate entities of a device are disabled, the longest gate array is still one short and the charts show one gate fewer; only the profile's register count could hold the axis, which was left out so DIY firmware with fewer gates keeps its own count.
- A resolved device with no gate entities renders nothing (X20). An offline device shows "0.0" distance bars on the 0.75 m default axis, and unavailable max and zone rows drop out and shrink the chart (X21).
- The chip markers stay unanchored: `/_ld2410_/` in `LD2410_MARKERS` and the inline `/_ld2412_/` in `detectProfileFromEntities` match any entity whose base holds the token, so a device named "My LD2410 Bench" counts its non-radar entities as LD2410 evidence. No tab or card comes from that alone, because liveness needs classified radar entities.
- `resolveProfile` calls `apolloModelInfo` without the `isEsphomeDevice` gate the strategy applies, so a hand-written card pointed at a network integration's copy of the radar device resolves a profile the strategy would reject.
- A `device_base_name`-only distance card on an MSR-1 builds MSR-2 entity ids for Bluetooth and Gate Size, so it draws gates at the 0.75 m default; `device_id` (which the generated dashboard always sets) avoids this (X24).

Calibration:

- The chart's one-click engineering mode and every calibrate card action need `hass.callService`, which every current HA frontend provides; without it the chart shows only the SVG text and the card's buttons stay disabled.
- Snapshot history lives for the integration's lifetime: `async_remove_entry` deletes `apollo_mmwave.calibration` along with the zone store, and only `MAX_SNAPSHOTS` are kept per device.
- The numeric pre-flight sees only enabled gate entities and Home Assistant's copy of their state; the LD2412 refresh before the capture, the read-back verification and Undo are the backstop for what it cannot see.
- The calibrate card offers only the newest snapshot as Undo (`undoLabel` names `snapshots[0]`, which is what `restore_gate_thresholds` picks without a `snapshot_id`); older snapshots are reachable through the service.
- `snapshotContents` tells Undo from Redo by assuming every restore wrote back the newest snapshot, which every card Undo and Redo does. A restore of an older `snapshot_id` through the service, a failed restore and its retry, or a hand edit between runs can make the label describe the wrong values; the button still restores exactly `snapshots[0]`.
- The "Restored the thresholds from 14:31" line names the result's `restored_from`; for a stored result without it, it infers the restored snapshot as the entry older than the redo snapshot in the payload's list, and drops the time when that entry is missing.
- The calibrate card does not treat HA's `unknown_command` as not loaded, so on a fresh boot it can show that error instead of the loading state until the entry's `loaded` event reopens the subscription; the zone API's handling of that code was not copied over.

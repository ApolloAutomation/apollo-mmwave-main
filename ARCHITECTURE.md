# Architecture

This document is for a maintainer new to the `apollo_mmwave` repository. It describes what the integration is, how the Python and TypeScript halves fit together, where data flows at runtime, and which values are tuning knobs. It cites functions, classes and constants by name rather than by line number, because names are the stable reference.

## Overview

`apollo_mmwave` is a Home Assistant custom integration (installed through HACS, `hacs.json`) for Apollo Automation mmWave radars: MSR-1 and MSR-2 (LD2410 chip), R PRO-1 (LD2412 plus LD2450) and MTR-1 (LD2450 only). It does not talk to hardware. The ESPHome integration already exposes the radar's sensors; this integration adds drawn occupancy zones on top of the LD2450 X/Y target sensors, a tuning dashboard for the gate radars, an empty-room auto-calibration of the gate thresholds, a setup card that checks either radar's settings, status and control cards for the LD2450 itself, a slider lock that keeps a scroll from moving the gate radar's sliders, a Device card on every tab, and a support file behind Home Assistant's Download diagnostics.

It has two halves that ship as one HACS package:

- The Python backend in `custom_components/apollo_mmwave/`. It owns a config entry, a persisted zone store (`.storage/apollo_mmwave.zones`), a persisted calibration store (`.storage/apollo_mmwave.calibration`), the `apollo_mmwave.update_zone` service and the three gate-calibration services (`calibrate_gates`, `cancel_calibration`, `restore_gate_thresholds`), one `sensor` and one `binary_sensor` entity per zone, four websocket commands, the Lovelace resource registration, the config entry diagnostics (the support file), and the Apollo mmWave dashboard, which it creates only when an administrator asks.
- The TypeScript/Lit frontend in `frontend-src/`. Vite compiles it into two self-contained ES module bundles that are committed under `custom_components/apollo_mmwave/www/` (`apollo-radar-tuning.js` and `apollo-radar-zone-map-card.js`, `const.py` `JS_BUNDLES`).

The backend serves the committed bundles itself at `/apollo_mmwave/<bundle>?v=<manifest version>` and registers them as Lovelace module resources and extra JS URLs (`frontend.py` `async_register_frontend_assets`). Users therefore install one repository and get the cards, the strategy and the backend together. The `www/` folder is a committed build output, not a scratch directory (`frontend-src/vite.config.ts`), and CI fails if it is stale (see Build, test and CI).

Display text spells the product "R PRO-1". The ESPHome model ids `R-PRO-1-W` / `R-PRO-1-ETH` and the `r-pro-1` model prefix keep their hyphens, because the registry match depends on them.

## Runtime data flow

### Device entity to integration to storage to presence sensors

1. The ESPHome device exposes LD2450 target sensors named `sensor.<base>_ld2450_target_<n>_x` / `_y` (R PRO-1) or `sensor.<base>_target_<n>_x` / `_y` (MTR-1). `resolve_target_pairs` (`ld2450.py`) scans the entity registry for one device, matches `TARGET_X` / `TARGET_Y` and returns `[{x, y}]` pairs sorted by target number, skipping disabled entities. `async_track_target_pairs` (`ld2450.py`) installs a per-device cache in `hass.data["apollo_mmwave"]["ld2450_pair_cache"]`. Its entity registry listener acts only on target sensors: it returns unless the event's `entity_id`, or the `old_entity_id` a rename reports, is a `sensor.` id whose object id matches `TARGET_X` or `TARGET_Y` (`_is_target_sensor`). For such an event it invalidates every cached device whose pairs name either id, plus the entity's current device when that one is cached, and sends one `SIGNAL_ZONES_UPDATED` per invalidated device. This integration's own zone entities live on the radar device but never pass the filter, so creating or renaming a zone does not republish that device's zones a second time. When setup runs before Home Assistant has finished starting, a one-shot `EVENT_HOMEASSISTANT_STARTED` listener invalidates every cached device and re-fires the signal for each, so pairs resolved before ESPHome registered its entities are resolved again.
2. At setup, zones can enter the store from the migration paths (`async_migrate_legacy`, `async_import_zone_mapper`, `_promote_resolvable_orphans` in `migration.py`, and the v1 to v2 rekey in `store.py`). After setup, zones enter the store only through the service. `handle_update_zone` (built by `_build_update_zone_handler` in `__init__.py`) resolves the device via `_resolve_target_device`, then `_call_changes_something` refuses calls that would change nothing. A call counts when it carries a device-wide field (a `rotation_deg` that survives `_sanitize_rotation`, `input_units`, a `display_units` that `_display_units_change_something` accepts, `clear_entities`, or a non-empty `entities`), or a `zone_id` together with `delete: true`, a `shape` (including `none`), or a `name` for a zone the store already holds (`_zone_part_changes_something`, which reads `store.devices` and never the minting `store.device()`). So `{device_id, zone_id}`, `{device_id, zone_id, data}` without a shape, and a rename of a missing zone are refused with "carried nothing to change": no store entry is created, nothing is saved, and neither the signal nor the bus event fires. A refused zone part does not drop the device-wide part of a mixed call (`{zone_id: 7, name, rotation_deg: 90}` with no zone 7 still stores the rotation). `display_units` `m` or `ft` always counts, even when it is the unit already stored (as `input_units` does), while `auto` counts only when the device has a saved unit to forget; that check reads `store.devices`, so `auto` for a radar with no store entry creates none. The card adds `input_units` to every zone and rotation write, so those calls always count; its m / ft switch sends `display_units` alone, which counts on its own. The handler also warns about data sent without a shape, geometry sent without a `zone_id`, and a name given to a zone that does not exist. It then fetches `store.device(device_id)` (`store.py`), applies `rotation_deg`, `input_units` and `display_units` (`_apply_device_settings`; `auto` pops the stored key) and tracked pairs (`_apply_entity_pairs`), then either deletes, renames, or normalizes geometry through `_normalize_zone_payload` into whole millimeters. Every mutating path ends in `_notify_zones_updated`, which schedules a debounced write (`ZoneStore.async_delay_save`, `SAVE_DELAY_SECONDS` in `store.py`), sends the dispatcher signal `SIGNAL_ZONES_UPDATED` with the device id, and fires the public bus event `apollo_mmwave_zone_updated`.
3. `async_setup_zone_platform` (`zone_entities.py`) runs `_sync_entities` once at platform setup and again on every `SIGNAL_ZONES_UPDATED`. It diffs `store.devices[*]["zones"]` against a `ZoneEntityTracker` and creates a `ZonePresenceBinarySensor` (`binary_sensor.py`) and a `ZoneCoordsSensor` (`sensor.py`) for each missing `(device_id, zone_id)`, skipping entries the user disabled. It does nothing while the entry is unloading (`tracker.unloading`).
4. `ZonePresenceBinarySensor.async_added_to_hass` calls `_track_coordinate_entities`, which resolves pairs via `effective_target_pairs` (`ld2450.py`: the stored `entities` list if the key is present, else the cached auto-detected pairs), de-duplicates the X/Y entity ids (pairs may share an entity) and subscribes `async_track_state_change_event` once per id. A state change runs `_handle_coordinate_update`, which only schedules one `_flush_evaluation` with `hass.loop.call_soon` (held in `_pending_eval`; further events are ignored while it is pending, and it is canceled in `async_will_remove_from_hass`). The flush runs `_evaluate_and_write`. A target's X and Y are two entities written one after the other, so evaluating on each write tested a point no target occupied (new X, old Y) and could pulse presence on and off. The coalescing removes that pulse when both writes land in one event-loop turn, which is how the ESPHome API normally delivers them, but not when they arrive in separate turns; there is no timed debounce. Zone changes and the initial evaluation stay synchronous. `_evaluate_presence` reads the zone from `store.zone()` and the device dict from `store.devices.get()` (neither mints an entry), picks a tester from `_SHAPE_TESTERS`, builds a rotator from the device's `rotation_deg` (`_build_point_rotator`; a stored value that is not a finite number, such as a hand-edited `"inf"`, means no rotation), and iterates `_iter_rotated_coordinates`. `_get_coordinate_pair` parses both states, drops `unknown`/`unavailable`, drops the exact `(0, 0)` idle-slot sentinel (tested on the raw readings) and converts each reading to millimeters by its own entity's unit (`_reading_unit_factor`): `SENSOR_UNIT_FACTORS[unit_of_measurement]` when that attribute is a Home Assistant length unit, else `INPUT_UNIT_FACTORS[input_units]` (default 1.0). X and Y are converted separately. ESPHome reports the targets in millimeters, but Home Assistant set to US customary units gives a new `distance` sensor reported in millimeters (or centimeters) a suggested unit of inches (meters become feet and kilometers miles), and a user can pick any length unit per entity, so the state is in whatever unit the attribute names. A unit change on its own is an attribute-only `state_changed`, which the subscription also receives, so presence re-evaluates. Any rotated point inside the shape sets `is_on`.
5. `ZoneCoordsSensor.extra_state_attributes` (`sensor.py`) publishes `shape`, `data`, the effective `entities` list, `rotation_deg` (when set) and `name` (when not empty), reading through `store.devices.get()` and `store.zone()`; its state is the zone id. Both entities rewrite state on `SIGNAL_ZONES_UPDATED` for their device.

### Device entity to websocket to cards

1. The zone map card's `setConfig` (`frontend-src/src/zone-map/card.ts`) requires `device_id` and calls `_connectZones`, which hands off to `connectZones` (`frontend-src/src/zone-map/api.ts`). That subscribes first (`subscribeZones`, command `apollo_mmwave/zones/subscribe`), then reads once (`fetchZones`, command `apollo_mmwave/zones/get`), drops the read if a push already arrived, and retries with `RETRY_DELAYS_MS` while the backend answers `not_loaded` or HA's `unknown_command` (`isNotLoaded`). HA answers `unknown_command` on a fresh boot: the websocket is up from the start, and this integration registers its commands only when its entry sets up. `connectZones` also re-opens both when `subscribeEntryLoads` sees this domain's config entry reach state `loaded`; HA's `config_entries/subscribe` is not admin-gated in any supported version, so every viewer gets this recovery. `connectZones` serializes overlapping opens through a promise queue (`requestOpen`), so a reload burst or a retry landing on an entry update cannot leave an orphan server-side subscription. When `setConfig` is called with a different `device_id`, `_resetDeviceState` disposes the subscription and clears zones, tracked entities, the undo snapshot, any shape in progress (`_resetDrawingState`), cone angle, lock, and the saved and picked map units; `_connectZones` tags each connection so payloads from a superseded connection are dropped. On supported Home Assistant (2026.8.1 and later) the card editor preview and a regenerated view or section build a fresh element instead of calling `setConfig` again, so a live retarget comes only from a parent that reassigns `config` on the same `hui-card` or a wrapper card that calls `setConfig` directly.
2. On the server, `ws_get_zones` and `ws_subscribe_zones` (`websocket.py`) both pass `_answerable` (`not_loaded` if the store is gone, `not_found` if the device id is not in the device registry) and answer with `_payload`, built from `store.devices.get(device_id)`: `zones` (string ids), `entities` (null means never configured, `[]` means cleared), `rotation_deg`, `label`, `input_units` (null means millimeters), `display_units` (the map unit an administrator saved, `m` or `ft`; null means the card follows Home Assistant's unit system) and `suggested_entities` (a fresh `resolve_target_pairs`). The subscription's `_forward` listens to `SIGNAL_ZONES_UPDATED` and pushes a new payload for the matching device; one zone edit (create or rename) produces exactly one push. A subscription ends on any of three paths (the client's `unsubscribe_events`, the connection closing, the config entry unloading). Its `_teardown` is a no-op the second time and leaves `connection.subscriptions` alone, because HA iterates that dict to run every teardown when the connection closes.
3. The card applies each payload in `_applyZoneConfig` (`card.ts`). `_applyZones` splits drawable zones from the zone list, which is the union of the YAML `zones:` seed and the store's ids: per id a non-blank stored name wins, else the YAML name, else `Zone N`. Geometry writes carry no name, so a YAML-named zone that gets drawn keeps showing its YAML name. `_applyRotation` sets the cone angle and slider from the store's `rotation_deg`, applying null as 0; the YAML `cone.angle_deg` is only the slider's double-click reset target. `_applyDisplayUnits` keeps the payload's `display_units` when it is `m` or `ft` and null otherwise. `_applyTrackedEntities` uses `entities` when it is an array and `suggested_entities` when it is null. Last, `_refitGrid` fits a grid the YAML does not set to the new zones, rotation and unit, and the unit switch and the help line under the map are redrawn (`_renderUnitSwitch`, `_renderInfo`). Until the first payload arrives, the entity status line reads "Waiting for this radar's configuration."
4. Live targets: `set hass` builds `_trackedStatesKey` (each tracked pair's X and Y entity ids plus both state strings and both `unit_of_measurement` attributes, since a unit change moves a target without changing its number) and calls `drawGrid` only when the key differs from the one it last painted from; the first assignment with a canvas always paints. A push that changes no tracked target state leaves the canvas alone; zones, rotation, draw mode, lock, theme and config repaint through their own paths. `drawGrid` draws the grid, axes and labels, the cone (`drawDeviceCone`) and its range caption (`_rangeLabel`), the zones, the shape in progress (`_drawInProgress`, rebuilt from stored state so any repaint keeps it on screen) and last `_drawTrackedTargets`, which reads `hass.states[pair.x].state` and `hass.states[pair.y].state`, skips near-zero raw readings, converts each reading to millimeters by its own entity's unit (`_readingUnitFactor`: `SENSOR_LENGTH_UNITS[unit_of_measurement]` when that is a Home Assistant length unit, else the multiplier of the card's YAML `input_units`), and rotates by the cone angle. The conversion is the backend's `_get_coordinate_pair` rule, so a target drawn inside a zone is one its presence sensor counts.
5. Writes go the other way: `endDrawing` or `finishPolygon` produce a payload, `updateHomeAssistantShape` wraps it, and `_saveZoneUpdate` appends `input_units` (unless called with `withInputUnits: false`) and calls `hass.callService("apollo_mmwave", "update_zone", request, undefined, false)`. The fifth argument (`notifyOnError = false`) turns off HA's own "Failed to perform the action" toast, so a rejected save shows only the card's "Could not save: <reason>" toast, the same convention as the calibrate card's `callService` helper. A success toast means HA accepted the call, not that the store took it: a call for a radar that left the device registry is logged and ignored by the backend but still answers success. The backend path above then pushes the result back over the subscription. The m / ft switch (`_chooseDisplayUnit`) writes `{device_id, display_units}` this way, with no success toast and with `withInputUnits: false`, because the switch says only that it shows the map in a unit and `input_units` would also rescale presence for target sensors without a length unit. It writes only when `hass.user.is_admin` (`_isAdmin`); for anyone else, or a `hass` with no user, it changes that page's view and calls nothing, because the service would refuse them.
6. The tuning cards do not use the websocket. `ApolloLd2410DistanceCard.shouldUpdate` (`frontend-src/src/cards/distance-card.ts`) calls `resolveRadar` (`frontend-src/src/cards/resolution.ts`), memoized on `config`, `hass.entities` and `hass.devices`, which calls `resolveEntitiesDetailed` and `resolveProfile` (`frontend-src/src/entities.ts`). A base-name fallback resolution (a `device_base_name`-only config, or a `device_id` whose entities are not in `hass.entities` yet) also depends on `hass.states`: `ResolvedRadar` records `fallbackBase` and the `detectProfile(hass, fallbackBase)` result as `fallbackDetected`, and the cache is reused only while a fresh detection agrees. An R PRO-1 card resolved before its LD2412 engineering-mode switch reached the states therefore moves from LD2410 ids to LD2412 ids on the tick the switch appears. Registry-resolved configs (the strategy's normal case) record no `fallbackBase`. Each card then re-renders only for the slots its chart reads (`DISTANCE_CHART_SLOTS` or `GATE_ENERGY_CHART_SLOTS`, flattened once per resolution by `watchResolved` and checked by `drawnStatesChanged`). `render` reads `hass.states` through `distanceModel` (`frontend-src/src/charts/distance-chart.ts`) or `gateEnergyModel` (`frontend-src/src/charts/gate-energy-chart.ts`).

### Card to service to job to websocket

1. The calibrate card (`frontend-src/src/cards/calibrate-card.ts`) subscribes to `apollo_mmwave/calibration/subscribe` for its device and calls `apollo_mmwave.calibrate_gates` with `{device_id}` plus its `calibration` block (`startCalibration` in `calibration/api.ts`). It never awaits that call for its UI: progress arrives over the subscription, which is why a job survives the browser closing.
2. `handle_calibrate_gates` (`calibration.py`) looks the calling user up (the only await of the pre-flight), then runs every check and the registration with no await between them, so two calls cannot both register a job for one device: `_single_device_id`, `_preflight_calibrate` (`calibration_running`, `no_gate_entities`, `engineering_mode_missing`, `device_offline`, `background_correction_running`, `thresholds_not_numeric` over every threshold the chip is sent with the writes, which is all 28 on the LD2412 and both numbers of every written gate on the LD2410 (its message only counts them; the ids are in the `entity_ids` placeholder and a warning log line), `margin_zero`, `not_allowed`; each a `ServiceValidationError` whose translation key is in `translations/en.json`), then `_launch` registers the `CalibrationJob` in `hass.data["apollo_mmwave"]["calibration_jobs"]` keyed by device id, starts `job.run()` as an entry background task, fires `apollo_mmwave_calibration_started` and returns `job.public_state()`, or, with `wait: true`, shields `job.done.wait()` and returns `job.result_payload()`.
3. `CalibrationJob.run()` delegates to `_prepare`, `_sample`, `_compute`, `_apply` and `_verify`, with `_finish` as the finally. Every timed phase is driven by one `async_track_time_interval(TICK_S)` tick and `asyncio.Event`s the tick sets, so tests drive it with `async_fire_time_changed`; the only `asyncio.sleep` calls are `WRITE_SPACING_S`, `VERIFY_SETTLE_S` and `RESTORE_READBACK_S`. `_prepare` hard-saves the `interrupted` marker (phase `engineering`) before `switch.turn_on` when the switch is off, waits for it to read `on` within `ENGINEERING_CONFIRM_TIMEOUT_S` (`engineering_mode_not_confirmed`), then runs the settle countdown and the energy warmup side by side; sampling starts on the first tick at which both hold, and `no_energy_data` fires `ENERGY_WARMUP_TIMEOUT_S` after the switch read `on` even mid-countdown. `_sample` takes one read of every energy sensor per tick (`samples` counts ticks; a state-change listener only raises the per-entity `event_peak`), counts ticks with the radar-target and moving-target sensors on, and the liveness guards fail the job with `engineering_mode_lost` (switch `off` for `ENGINEERING_LOST_TICKS` ticks) or `background_correction_started`. `_compute` runs `calibration_math.compute_channel` per gate channel and adds the `unused`, `skipped`, `off` and `gates_off` rules. `_apply` fails `no_gate_data` before touching the device when no gate collected `MIN_SAMPLES` readings, presses the LD2412 query-params button (`sub_phase: "refresh"`), re-checks that every threshold the chip will be sent is numeric, captures the current values (the snapshot, every `old` and the skip rule all come from this one read, and a cell's `unchanged` is recomputed from it), pushes once the plan and `writes_total` are known, takes no snapshot or marker at all when every value is already within tolerance, otherwise hard-saves the snapshot (`snapshot_failed` otherwise, and nothing is written), hard-saves the marker with phase `applying`, then writes gate by gate, move then still, skipping values within `VERIFY_TOLERANCE` of the capture, `WRITE_SPACING_S` apart; `device_offline`, `write_failed` and `not_allowed` stop it while keeping `writes_done`, `writes_total` and `snapshot_id` so the card can offer Undo. `_verify` presses the LD2412 button again, waits `VERIFY_SETTLE_S` and compares every written number numerically; mismatches and unreadable states go to `unverified` and the outcome becomes `partial`.
4. `_finish` runs on every exit path, including task cancellation from an unload or HA stop (`asyncio.CancelledError` is mapped to `cancelled_by_shutdown` and re-raised only after the restore attempt; a second cancellation during the restore is tolerated). It removes the tick and the listener, turns the switch off only if the job turned it on (bounded by `SHUTDOWN_RESTORE_TIMEOUT_S`, every exception logged at warning), reads the switch back, settles the marker (`_settle_marker`: everything is cleared when the switch reads `off`; a shutdown keeps the phase it was in so the banner can offer Undo after the restart; a finish the job reached itself clears the write phase and keeps the engineering fact, with `left_on` set when the turn-off was not echoed), persists `last_result` with a delayed save when the store is still in `hass.data`, removes the job from the registry, dispatches `SIGNAL_CALIBRATION_UPDATED`, fires `apollo_mmwave_calibration_finished` and sets `job.done`.
5. Only three device write shapes exist, all `blocking=True` with the service call's context: `number.set_value {entity_id, value}`, `switch.turn_on` / `turn_off {entity_id}` and `button.press {entity_id}`.
6. `ws_subscribe_calibration` (`websocket.py`) answers null, pushes `calibration_payload(hass, device_id)` at once, then forwards every `SIGNAL_CALIBRATION_UPDATED` for the device; `_calibration_loaded` requires both calibration keys in `hass.data` (`not_loaded` otherwise) and the forwarder re-checks them before every push. `restore_gate_thresholds` reuses the same job with `kind: "restore"`: the shared pre-flight plus snapshot resolution (ids re-resolved through `unique_id`, ids that left the registry or are disabled reported in `missing` and left out of the offline, numeric and permission checks), a redo snapshot with reason `restore`, the same paced writer and verification, and no engineering-mode touch.

## Backend modules

### `__init__.py`

`async_setup_entry` loads the store. When `ZoneStore.async_load` returns `False` (no file, or a payload that is not an object), it runs `async_migrate_legacy` and then `async_import_zone_mapper` and saves once after both, so a fresh install writes the file once and a failed import leaves no half-populated file behind. It then runs `async_migrate_unique_ids`, stores the `ZoneStore` at `hass.data["apollo_mmwave"]["store"]`, installs the LD2450 pair cache, registers `update_zone` with `UPDATE_ZONE_SERVICE_SCHEMA` and, right after it, the zone teardown (`_teardown`: removes the service, pops the store and returns `store.async_save()`). It continues with the websocket commands, the `async def` teardown returned by `async_setup_calibration` (`calibration.py`), the platforms (`PLATFORMS = [binary_sensor, sensor]`) and the frontend assets. Setup and reloads never create, rewrite or delete a dashboard, and there is no options update listener, so no options change (the flow's own saves included) can set off dashboard work.

`async_migrate_entry` moves entries from 2.2.5 and earlier (config entry minor version 1) to minor version 2 (`ENTRY_MINOR_VERSION`), before their first setup. It drops the old `auto_create_view` option and records which dashboard the entry owns in `dashboard_id` and `dashboard_url_path`, writing nothing to Lovelace: with that option on (or absent, its old default), `frontend.async_find_legacy_dashboard` returns the id of a row on url path `apollo-mmwave` whose own stored config is exactly `{"strategy": {...}}` with our type (keys the user typed under `strategy` included), and otherwise the entry owns none (both None). A taken-over dashboard, one with more than a `strategy` key, a row with no config and a YAML dashboard on the path are not adopted, and with the option off nothing is, so a strategy dashboard the user built there is left alone (X03). `dashboard_devices` is kept. The migration always returns True. When the dashboards cannot be read (the collection is unreachable or the lookup raised), `async_find_legacy_dashboard` logs a warning and raises `DashboardsUnreadableError`, and the migration returns without updating the entry: it keeps minor version 1 and `auto_create_view`, owns no dashboard meanwhile, and the next setup looks again. Unknown is never recorded as none.

Every teardown is an `entry.async_on_unload` hook. Home Assistant runs the hooks newest first, after `async_unload_entry` returns `True`, and starts a coroutine a hook returns as a task that the unload waits for (up to 10 s). On unload the order is therefore: calibration teardown (which then waits on running jobs), websocket subscriptions closed, zone teardown (service removed, store popped, store flushed), LD2450 pair cache. Because the zone teardown is a hook, a setup that fails after the service was registered (platform forwarding, frontend assets) no longer leaves `update_zone` or a stale store behind: HA runs the hooks for a failed setup and never calls `async_unload_entry` for it. A failed platform unload skips the hooks, so the service and store stay. `async_unload_entry` itself only unloads the platforms. The calibration websocket commands guard on their own keys because the zone store can be gone while the calibration teardown is still waiting on a job. `async_remove_entry` removes the dashboard the entry recorded (`async_remove_dashboard`: by id, and only while its config is still our strategy; an entry that owns none touches no dashboard), then the Lovelace resource rows (`async_remove_lovelace_resources`, skipped while another non-ignored Apollo mmWave entry remains), removes the zone store through the live instance in `hass.data` when there is one (which cancels a pending delayed save that would otherwise write the file back about 2 s later; a fresh `ZoneStore` otherwise), and removes the calibration file through a fresh `CalibrationStore`.

The service side:

- `_device_id_from_call` accepts `device_id` as a string or a one-item list (the shape a `target:` block produces) and refuses multi-device targets. `_device_is_registered` is applied on every path, so an unknown or stale device id never reaches the `store.device()` setdefault.
- `_resolve_target_device`: when a call carries both `device_id` and `location`, `device_id` wins and `location` is ignored without the deprecation warning. The schema comment that says "Exactly one" is inaccurate; the schema requires at least one.
- Deprecated `location`: `_device_id_for_label` slug-matches the value against stored `label` fields first (the first device in store order wins), then against `aliases`, so either name a rename left behind reaches the radar and a device's own label beats another device's alias on a tie. `_device_id_for_deprecated_location` warns once per run via the `hass.data` flag `_DATA_LOCATION_WARNED` and refuses a label whose device has left the registry.
- `display_units` (`m`, `ft` or `auto`) is the unit the zone map card shows one radar's map in, for every viewer. It is display only: geometry stays millimeters and presence never reads it. `auto` removes the stored key, so the card follows Home Assistant's unit system again, and is never stored itself (`DISPLAY_UNITS_AUTO`).
- `_normalize_entities`: an empty `entities` list means "no change", never "erase", because a card calling the service before it had loaded used to wipe people's tracked pairs. `clear_entities: true` is the only way to empty the list, and it takes precedence over `entities` in the same call (`_apply_entity_pairs`).
- Rename: `_update_registry_names` writes the registry `name` as `Zone {n} - {zone_name}` / `Zone {n} presence - {zone_name}` (or the bare base when the name is empty) and only when `_is_generated_name` says the current name is still generated, so user-typed names survive. Both zone entities use `has_entity_name`, so before a rename their friendly names are "<radar name> Zone N" and "<radar name> Zone N presence". The explicit registry name replaces the whole friendly name, so a renamed zone's entities lose the radar prefix ("Zone 1 - Couch"), and a rename to "" writes the bare base, which is still explicit, so the prefix does not come back. A name sent on the call that creates the zone reaches only the store, because the entities do not exist yet; a later rename updates the registry. Delete removes both registry entries via `_remove_zone_entities`.
- Numbers: `_coerce_float` treats inf, nan, ints too large for a float and any magnitude above `_MAX_SAFE_INT` (2**53 - 1, JavaScript's `Number.MAX_SAFE_INTEGER`) as non-numeric. The bound is a serialization limit, not a geometry range: HA writes the store, websocket replies and recorder rows with orjson, which refuses ints outside 64 bits, and one such value used to make every later zone store write fail for every radar. A rect with such a bound clears with `WARN_RECT_NON_NUM`, an ellipse with `WARN_ELLIPSE_INVALID`, and a polygon drops that point. `_sanitize_rotation` goes through `_finite_float` instead: inf and nan are ignored (a rotation-only call then changes nothing), while a huge finite angle still clamps to 180.
- Geometry: each normalizer rebuilds a clean dict, so only the shape's own keys are stored (`x_min`, `x_max`, `y_min`, `y_max` for a rect; `cx`, `cy`, `rx`, `ry` for an ellipse; `points` for a polygon) and extra caller keys in `data` are dropped. Before 711f65b the rect and polygon paths kept them, which let an oversized extra value break every store write. Polygons with more than `POLYGON_MAX_POINTS` points are truncated with `WARN_POLY_TRUNCATING` (the slice runs before malformed points are filtered), not rejected; the card caps them too. A polygon clears with `WARN_POLY_INSUFFICIENT` when fewer than `POLYGON_MIN_POINTS` points arrive or `points` is not a list, and with `WARN_POLY_MALFORMED` when enough arrive but fewer than 3 parse as `{x, y}` numbers (for example `[x, y]` lists). A drawable shape sent with `data` omitted or null is stored as `{shape, data: null}` and logs `WARN_ZONE_NO_GEOMETRY`; `shape: none` is the quiet, documented clear. The warnings name "zone N on device '<device_id>'", and the `_normalize_*` helpers take the device id. There is no branch for an unsupported shape: the schema's `vol.In(list(SUPPORTED_SHAPES))` rejects it first.

The module also holds `_zone_entity_unique_ids` (used by the rename and delete paths) and `get_store`, which `binary_sensor.py`, `sensor.py`, `zone_entities.py` and `websocket.py` import lazily.

### `config_flow.py`

`ApolloMmwaveConfigFlow` has `VERSION = 1` and `MINOR_VERSION = ENTRY_MINOR_VERSION` (2). `async_step_user` shows two boxes, `create_dashboard` and `dashboard_admin_only` (`DEFAULT_CREATE_DASHBOARD` and `DEFAULT_DASHBOARD_ADMIN_ONLY`, both True), with a description that says what the dashboard is, that it is created once (if the first box stays ticked) and is never recreated or changed on its own, that removing the integration removes it unless the user took control of it, and where the Community dashboards picker is. On submit, with the first box ticked, it calls `async_create_dashboard(require_admin=...)` right there, then creates a single entry with `unique_id = "apollo_mmwave"`, empty `data` and `options = {dashboard_id, dashboard_url_path}` (`_ownership`): the new row's id and `apollo-mmwave`, or None for both when the box was unticked or nothing was created. A failed create (collection unreachable, url path taken, a write error) is a warning in the log and never blocks the setup. Neither box is stored. It aborts with `already_configured` when an entry exists (single instance is enforced in code, not through the manifest).

`ApolloMmwaveOptionsFlow.async_step_init` asks `async_dashboard_owned` whether the recorded row is still ours (`_owned`: True, False, or None when the collection cannot be read). It shows a menu: `add_dashboard` and `dashboard_devices` while the entry owns none, `dashboard_devices` and `remove_dashboard` while it owns one. With None it skips the menu and goes to `dashboard_devices`, keeping the recorded ownership. `add_dashboard` is a form with only `dashboard_admin_only` and a description of what it creates; Submit calls `async_create_dashboard` with the stored `dashboard_devices` and records the new row. `remove_dashboard` is a form with no fields that says what will be deleted; Submit calls `async_remove_dashboard` on the recorded row. `dashboard_devices` is a `DeviceSelector` filtered to `integration=esphome`, `manufacturer=ApolloAutomation` and `model in MMWAVE_MODELS`; While the entry owns a dashboard, or might (`_owned` None), Submit writes the selection into that row with `async_set_dashboard_devices` and stores it only if the write lands; owning none, Submit only stores it. `async_set_dashboard_devices` logs a warning when the collection is unreachable, so the form's error has a reason in the log. Each step finishes through `_save`, which keeps the current options, applies the step's change and, when `_owned` is False and a row is recorded, forgets it (both keys None): a dashboard the user deleted or took control of is never recreated or written to. An entry with no record keeps none, so a 2.2.5 entry whose migration could not read the dashboards yet can still adopt its old dashboard at a later start. A failed create, delete or write shows `dashboard_not_created`, `dashboard_not_removed` or `dashboard_not_updated` on the form and changes no option. HA's device filter compares `model` exactly, so `MMWAVE_MODELS` lists every firmware variant and must stay in step with the lower-cased prefixes in `frontend-src/src/profiles.ts` `APOLLO_MODELS`; `tests/test_config_flow.py::test_mmwave_models_match_frontend_prefixes` and `frontend-src/test/registry-detection.test.ts` check both directions. The `update_zone` service's own `device_id` selector stays unfiltered on purpose, so DIY hardware remains selectable. `ApolloMmwaveOptionsFlow` has no constructor and reads the entry through the base `OptionsFlow.config_entry` property; `async_get_options_flow` keeps HA's `config_entry` parameter but does not forward it. The flow does its dashboard work itself, before it saves, and saving the options sets off nothing else.

### `const.py`

The home for shared names: `DOMAIN`, `SERVICE_UPDATE_ZONE`, `EVENT_ZONE_UPDATED`, `SIGNAL_ZONES_UPDATED`, the calibration names (`SERVICE_CALIBRATE_GATES`, `SERVICE_CANCEL_CALIBRATION`, `SERVICE_RESTORE_GATE_THRESHOLDS`, `EVENT_CALIBRATION_STARTED`, `EVENT_CALIBRATION_FINISHED`, `SIGNAL_CALIBRATION_UPDATED`, `DATA_CALIBRATION_STORE`, `DATA_CALIBRATION_JOBS`), most `hass.data` keys, the store keys (including `STORE_ALIASES` and `STORE_DISPLAY_UNITS`), `INPUT_UNIT_FACTORS` and `SENSOR_UNIT_FACTORS`, the map units `DISPLAY_UNITS` (`m`, `ft`) and `DISPLAY_UNITS_AUTO`, shape names and polygon limits, `CARD_TYPE`, options keys, dashboard constants, `STATIC_URL_BASE`, `FRONTEND_DIR` and `JS_BUNDLES`, plus the `WARN_*` log templates (`WARN_POLY_INSUFFICIENT`, `WARN_POLY_MALFORMED`, `WARN_POLY_TRUNCATING`, `WARN_RECT_INVALID`, `WARN_RECT_NON_NUM`, `WARN_ELLIPSE_NON_POSITIVE`, `WARN_ELLIPSE_INVALID`, `WARN_ZONE_NO_GEOMETRY`). Three `hass.data` keys live elsewhere: `_DATA_LOCATION_WARNED = "location_deprecation_warned"` in `__init__.py`, `DATA_SUBSCRIPTIONS = "ws_subscriptions"` in `websocket.py` and `_DATA_CALIBRATION_CLOSING = "calibration_closing"` in `calibration.py`.

### `store.py`

`ZoneStore` wraps a `_MigratingStore` with key `apollo_mmwave.zones` and `STORAGE_VERSION = 2`.

Loading: `async_load` returns `False` when no file exists, and also when the file's `data` is not an object (logged at ERROR with its type); setup then takes the missing-file path and saves over it. Inside a well-formed payload, a `devices` or `orphans` value that is not an object is logged at ERROR and read as empty (`_section`) while the rest still loads; absent or null reads as empty without a log. Each entry goes through `_parse_entry(raw, device_id)`: int zone ids (`_parse_zones`), plus an allow-list of keys (`zones`, `entities`, `rotation_deg`, `label`, `aliases`, `input_units`, `display_units`); anything else is dropped. `aliases` keeps only its string items and is dropped when none are left. `input_units` is restored only when it is a string that is a key of `INPUT_UNIT_FACTORS`; any other value is dropped and the device reads as millimeters. `display_units` is restored only when it is `m` or `ft` (`DISPLAY_UNITS`); any other value is dropped and the card follows Home Assistant's unit system. `entities` (any list) and `rotation_deg` are carried verbatim (a string `'15'` loads as `'15'`). A zone value may be the empty placeholder `{}` from the legacy migration, which means no geometry. Every drop is logged at WARNING with its key: an entry that is not an object, a `zones` value that is not an object (null excepted), a zone key that is not a zone number, and a zone definition that is not an object. The log line is the only trace, because `_data_to_save` dumps the live dicts verbatim and the next save makes every drop permanent. A file that is not valid JSON is handled by HA's `Store`, which renames it to `.corrupt`. `ZoneStore` passes no `max_readable_version`, so HA's `Store` raises `UnsupportedStorageVersionError` for a file whose major version is above 2 before `_async_migrate_func` runs: a downgrade after a future version bump fails entry setup and leaves the file untouched. The `old_major_version > 1` branch only covers a version 2 file with another minor version, whose data passes through unchanged.

Migration: `_async_migrate_func` rekeys v1 `locations` (display names) into v2 `devices` (HA device ids) using `resolve_device_id` (public because `migration.py` shares it: tracked entity first, then the device name slug), retaining unresolvable entries under `orphans`. A v1 payload or `locations` value that is not an object is logged at ERROR and read as empty. When two v1 locations resolve to the same device (a mid-life rename), `_merge_location` folds them first writer wins per zone id and logs a WARNING only for a true id-level conflict; an empty `{}` placeholder does not count as a writer, so a real definition from a later location replaces it silently and a placeholder arriving after a real zone is skipped. Scalars (`entities`, `rotation_deg`) stay first writer. `_record_location` is the one helper all four merge paths use (`_merge_location`, `async_migrate_legacy`, `async_import_zone_mapper`, `_merge_promoted_orphan`): the first name becomes `label` and each later, different name is appended to `aliases`. Like `label`, `aliases` is never used to build an identifier.

Access: `device()` is a `setdefault` and the only accessor that mints an entry; it is for write paths only (the `update_zone` handler calls it after `_call_changes_something`). `zone()` reads through `devices.get()`, so `store.zone()` for an unknown device returns None and stores nothing, and every other reader uses `store.devices.get()`.

### `migration.py`

Three one-way upgrade paths run from setup. `async_migrate_legacy` rebuilds zones from the RestoreEntity attributes of pre-1.2 sensors whose unique id is `apollo_mmwave_<slug>_zone_<n>`, resolving once per location; it keeps an empty placeholder for a zone with no shape so the entity is recreated, puts an unresolvable location in `orphans` with a warning, and skips a restored `rotation_deg` that cannot be rounded (such as `"inf"`) instead of raising out of setup. `async_import_zone_mapper` does the same for the standalone `zone_mapper` platform, except that it skips zones whose restore attributes carry no `shape`, and a location that matches no device is skipped with a warning rather than kept as an orphan; the import is read-only with respect to that integration and counts defined zones (`_defined_zone_count`), so filling a placeholder counts as an import. Neither saves the store; `async_setup_entry` does, after both. Both run only when `ZoneStore.async_load` returns `False`.

`async_migrate_unique_ids` runs on every setup. It promotes orphans that now resolve (`_promote_resolvable_orphans`, folding into an existing entry through `_merge_promoted_orphan`, which also records the orphan's location as label or alias), then builds the slug-to-device bridge first writer wins: every device's `label` in store order, then every device's `aliases` (so a label always wins a tie), then the locations promoted in this run. That is the same precedence as `_device_id_for_label`, so a pre-2.0 entity and a `location:` automation for one name land on one device. It then rewrites pre-2.0 unique ids matching `_OLD_UID` to `<device_id>_zone_<n>[_presence]`. When the new unique id is already taken, the old entity is left in place and a warning names it as stale; that warning repeats on every setup until the stale entity is deleted.

### `zone_entities.py`

`ZoneEntityTracker` keeps exactly one entity per `(device_id, zone_id)` per platform and is built with the config entry. It retries any add the platform refuses (`add_to_platform_abort`, for example an entity id that is still taken) on the next `SIGNAL_ZONES_UPDATED`, and `ZoneEntityMixin.async_will_remove_from_hass` sends one extra signal only while such a refused attempt is pending (`has_aborted`). On the supported Home Assistant versions (2026.8.1 and 2026.10.0) registry removal appears to finish eagerly, so a delete followed by an immediate redraw should cause no refused add and no extra signal (unverified, X58); the module docstring still describes that race. A zone whose entity or device the user disabled is skipped (`is_disabled`) and its earlier aborted attempt is dropped (`ZoneEntityTracker.discard`), so `has_aborted` reports only refusals a retry can still fix. While the entry is `ConfigEntryState.UNLOAD_IN_PROGRESS` (`tracker.unloading`), `_sync_entities` returns early and the removal-time signal is skipped: HA resets the platforms before it runs the entry's on-unload callbacks, so the dispatcher subscription is still live while entities leave, and a re-add then would land on a reset platform bound to the old `ZoneStore`. Only that state counts, because the first sync runs during `SETUP_IN_PROGRESS`. `tests/test_zone_entities.py` pins the real-platform paths.

### `binary_sensor.py`

`ZonePresenceBinarySensor` has unique id `{device_id}_zone_{n}_presence`, name `Zone {n} presence`, device class occupancy, and is linked to the radar's device entry. Shape testers: `_point_in_rect` and `_point_in_ellipse` (inclusive on every boundary) and `_point_in_polygon` (an even-odd ray cast toward +x, at least `POLYGON_MIN_POINTS`; a point exactly on a non-horizontal edge counts as a crossing and one on a horizontal edge does not, so whether a polygon boundary point reads inside depends on the edge). Rotation uses `x' = x cos t + y sin t`, `y' = -x sin t + y cos t`. The module has its own `_coerce_float` without the finite and size guard of the one in `__init__.py`, so `_build_point_rotator` checks finiteness itself.

### `sensor.py`

`ZoneCoordsSensor` has unique id `{device_id}_zone_{n}` and name `Zone {n}`. It exists so automations and the sensor attributes expose the geometry; the card itself reads the websocket instead.

### `ld2450.py`

`resolve_target_pairs`, `effective_target_pairs` and `async_track_target_pairs` as described above. `effective_target_pairs` is the only answer both platforms use, so the sensor's `entities` attribute matches what presence tracks. The `entities` store key is three-valued: absent means auto-detect, `[]` means track nothing, a list means exactly those pairs. Only the two regexes are shared with `ld2450.ts`: the X/Y pairing rule (same target number) and the disabled-entity filter live only in `resolve_target_pairs`, which is authoritative because the presence and geometry sensors and the websocket `suggested_entities` field read it. The frontend never pairs from the registry, and the `hass.entities` it reads already leaves disabled entries out.

### `gates.py`

`resolve_gate_entities` classifies one device's enabled registry entries into `GateEntities`: per-gate `move_threshold`, `still_threshold`, `move_energy` and `still_energy` maps keyed by the digit `GATE_RE` captures (a disabled gate leaves a hole rather than shifting its neighbors), the engineering-mode switch, the LD2410 max move/still gate numbers, the LD2412 min/max gate numbers, the radar-target and moving-target binary sensors, the LD2412 background-correction button and status, and the query-params button of either chip (`_ld2412_query_params` on the R PRO-1, `_query_params` on the MSR firmware) (`_SCALAR_PATTERNS`, first writer wins per slot as in `ld2450.py`). The profile is `ld2412` when any object id contains `_ld2412_`, else `ld2410`; `None` is returned when no gate slot matched (an MTR-1). `number_bounds` reads a number's `min`, `max` and `step` with 0/100/1 fallbacks, `numeric_state` returns a finite float or `None` (through `finite_float`, which `calibration.py` and `calibration_store.py` share), and `is_offline` treats a registered entity with no state object the same as `unavailable`. It is the Python twin of `entities.ts` (see Contracts).

### `calibration.py` and `calibration_math.py`

`calibration.py` holds the algorithm's timing, headroom and verification constants (each a module-level name so tests patch it there; `MIN_SAMPLES`, `SPIKE_ABS` and `SPIKE_RATIO` live in `calibration_math.py` and `MAX_SNAPSHOTS` in `calibration_store.py`, are deliberately not re-exported, and must be patched on those modules), the three service schemas (`CALIBRATE_GATES_SCHEMA`, `CANCEL_CALIBRATION_SCHEMA`, `RESTORE_GATE_THRESHOLDS_SCHEMA`, all `extra=vol.PREVENT_EXTRA`), the pre-flights, `CalibrationJob`, `calibration_payload` and `async_setup_calibration`. Setup loads the store, installs the jobs dict, registers the services with `SupportsResponse.OPTIONAL`, subscribes a synchronous `EVENT_HOMEASSISTANT_STOP` listener that only sets `cancel_requested` (HA core cancels every background task before it fires the event) and returns the `async def` teardown: a closing flag set before its first await (so `calibrate_gates` and `restore_gate_thresholds` are refused as not loaded while it waits, as they are while HA is stopping), cancel requests on every job, a bounded wait for their finally (`asyncio.wait_for` over a `gather`, skipped when no job runs), service removal, listener removal, a final save that logs rather than raises, then the two `hass.data` keys (and the closing flag) are popped last so no job can persist into a store the entry no longer owns. `calibration_math.py` is the pure half: `Bounds`, `Margins`, `ChannelSamples`, `ChannelResult` and `compute_channel` (the peak is the ceiling of the largest tick or event value; the proposal is `peak + max(margin, peak * margin_pct / 100)` rounded up to the step and clamped to the range; `off` at the top of the range; `spike` when the tick maximum is both `SPIKE_ABS` above and `SPIKE_RATIO` times the nearest-rank 95th percentile; `no_data` under `MIN_SAMPLES` ticks, whatever the event peak). It is tested directly with plain tuples.

### `calibration_store.py`

`CalibrationStore` wraps a `Store` with key `apollo_mmwave.calibration`, version 1, as its own file so `store.py` and its allow-list stay untouched and an older build ignores it. Per device it keeps up to `MAX_SNAPSHOTS` snapshots newest first (`add_snapshot`, `discard_snapshot`, `snapshot`, `snapshots_summary`), the `last_result`, and the `interrupted` marker (`set_interrupted`, `clear_interrupted`, `interrupted`). `_parse_device` drops malformed snapshots one at a time and reads a missing `left_on` as `False`; a missing file is empty, an unreadable one logs a warning and starts empty. `async_save` is awaited directly for the snapshot and the marker because both exist to survive a crash, and it raises when the write failed: HA's `Store` catches `WriteError` and `SerializationError` and only logs them, so `_ReportingStore` records the error from `_async_write_data` for `async_save` to raise (during an HA stop the save defers to the final-write stage, still before the process exits, and cannot be checked); results use `async_delay_save`. `snapshot` and `snapshots_summary` skip a snapshot without values, so one can never hide a real one from Undo.

### `websocket.py`

`async_register` registers `apollo_mmwave/zones/get`, `apollo_mmwave/zones/subscribe`, `apollo_mmwave/calibration/get` and `apollo_mmwave/calibration/subscribe` on every config entry setup; registration is a keyed assignment that replaces the previous handlers rather than stacking them, and the commands are never unregistered (HA has no API for it). It returns a teardown that closes this entry's subscriptions, zone and calibration alike (`_subscriptions`); the hook order above runs it before the zone teardown pops the store, and each zone forwarder re-checks `DATA_STORE` as a safety net. Reads are open and writes are admin-only. None of the commands requires admin, and that is deliberate: the Apollo mmWave dashboard is admin-only only when the administrator leaves that box ticked (those made before 2.2.6 are not), the card can sit on any dashboard, the zone card cannot draw without the zone commands, and the same geometry, rotation and tracked pairs are already readable by every user through the zone sensors' attributes. The one zone write, `update_zone`, is an admin service (see below), so a non-admin user sees the zones but cannot change them. It is also why calibration progress goes over a subscription rather than a custom bus event. `tests/test_websocket.py::test_non_admin_users_can_read_and_subscribe` pins it. Zone ids and `peaks` gate keys are stringified in the payloads. The calibration commands use `_calibration_answerable`, built on `_calibration_loaded`, which needs both `calibration_store` and `calibration_jobs` in `hass.data` (`not_loaded` otherwise): the zone teardown can pop the zone store while the calibration teardown is still waiting on a job, and a half-set-up entry can have the reverse. `ws_subscribe_calibration` sends the current payload right after its result, and its forwarder re-checks the keys before every push.

### `frontend.py`

`async_register_frontend_assets` is guarded by `hass.data["apollo_mmwave"]["assets_registered"]`, so it runs once per Home Assistant run; an integration reload skips the resource reconciliation too. It reads the manifest version for the `?v=` cache buster, registers each existing bundle as a static path with `cache_headers=True` (a missing bundle file is a warning; the cache duration itself is Home Assistant's `CACHE_TIME` in `homeassistant/components/http/static.py`, 31 days at the time of writing), adds it as an extra JS URL and reconciles the Lovelace resource collection (`_async_register_lovelace_resources`). The reconciliation keeps exactly one resource row per bundle: rows under `/apollo_mmwave/` are grouped by url with `?v=` stripped (`_base_url`), the row already at the current `?v=` is kept (else the first), it is repointed at the current url with type `module` when its url or type differs (a hand-added classic `js` row would throw on the bundle's top-level `export`), and every other row for that bundle and every row for a bundle no longer in `JS_BUNDLES` is deleted (`_async_remove_stale_resources`, listed under "removed" in the info log). Rows outside `/apollo_mmwave/` are never touched. The storage collection loads lazily, so the function loads it first through `async_get_info()` when its `loaded` attribute is false, as Home Assistant's own resource count does. A YAML-mode resource collection only produces a warning that ends with the urls to add by hand as modules and says to replace each row's url after an upgrade rather than add a second row. On entry removal `async_remove_lovelace_resources` loads the collection the same way and deletes every row under `/apollo_mmwave/` (`_async_remove_stale_resources` with no bundle still shipped), because nothing serves those files after the next restart; in YAML mode it only warns with the rows to delete by hand, and any failure is a warning that never stops the removal. The static paths and extra JS URLs stay registered for the rest of the run, so it sets `hass.data["apollo_mmwave"]["resources_removed"]` before it deletes anything (a delete that fails partway has already taken some rows), and the next `async_register_frontend_assets` in that run recreates the rows from the urls it kept in `resource_urls` before returning on the once-per-run guard.

Nothing in `frontend.py` writes a dashboard at setup. `async_create_dashboard(hass, require_admin, devices)` is called only from the config flow and the options flow's `add_dashboard` step: it creates the storage dashboard at url path `apollo-mmwave` (title, icon, `show_in_sidebar` True and `require_admin` as asked, written once and the user's from then on), saves `_desired_config(devices)`, and returns the row's id. It returns None with a warning that ends with `_PICKER_HINT` (Settings > Dashboards > Add dashboard > Apollo Radar Tuning, and the strategy type) when the collection is unreachable, when any dashboard (YAML or storage) or any row already holds the url path, which is left as it is, or when a write raises; if the row was created and its first `async_save` failed, `_async_roll_back_created_row` deletes it again so a retry starts clean.

Every later touch goes through `_async_our_row(hass, collection, dashboard_id, url_path)`, which returns the recorded row and its stored config only while the row exists under that id with that url path and the config is still ours (`_is_ours`: a `strategy` dict with our type). Lovelace derives a row's id from its url path, so the config check is what keeps a taken-over dashboard, or one the user made on the path after deleting ours, from being written to or deleted. The config is read only from the row's own storage dashboard: `_async_stored_config(hass, item)` returns None, which every caller treats as not ours, unless `hass.data[LOVELACE_DATA].dashboards[item["url_path"]]` has mode `storage` and `config["id"] == item["id"]`, so a stale row under a user's YAML dashboard on the same url path is never written to or deleted (deleting it would make Lovelace drop the YAML panel). `async_dashboard_owned` reports True, False or None (unreadable) for the options flow. `async_set_dashboard_devices` writes `_desired_config(devices, stored)`, which rewrites only `type` and `devices` and carries over any other key under `strategy` that the user typed into the raw config editor (such as `distance_unit`); it saves only when the config changes. `async_remove_dashboard` deletes the row through the collection, which makes Lovelace remove the panel and the stored config; it returns True when nothing of ours is left (deleted, nothing recorded, gone or no longer ours) and False when the collection is unreachable or the delete raised. `async_find_legacy_dashboard` is the read-only lookup `async_migrate_entry` uses (see `__init__.py`). Each of these catches every exception, logs it and returns its failure value, except `async_find_legacy_dashboard`, which raises `DashboardsUnreadableError` so the migration can tell "unknown" from "none". The dashboards collection is borrowed from HA's `lovelace/dashboards/list` handler (`_dashboards_collection`); that is the only working path on the pinned versions (2026.10.0, and 2026.8.1, the HACS floor), which keep the collection in a local inside lovelace's `async_setup`, and the `dashboards_collection` attribute check that runs first is forward compatibility only. `tests/test_frontend.py` covers every warning branch and the ownership checks, `tests/test_config_flow.py` the flows, and `tests/test_init.py` the migration and that setup, reloads and option changes write no dashboard (`record_dashboard_writes` in `tests/conftest.py`).

### `diagnostics.py`

`async_get_config_entry_diagnostics` builds the support file an administrator downloads from Settings > Devices & services > Apollo mmWave > three dots > Download diagnostics (HA's download view is `require_admin`). Home Assistant wraps the result with its own system details, the custom integrations and this manifest. The integration has no `manifest.json` dependency on `diagnostics`: HA finds the platform by its file and preloads it with the package (`loader.BASE_PRELOAD_PLATFORMS`), which is why `tests/test_imports.py` now imports every preloaded platform whose file exists, as HA's import executor does, before it checks that nothing else loads later.

Top level: `versions` (manifest and HA), `unit_system` (`hass.config.units.as_dict()`; a `length` of `mi` means the cards show feet), `entry` (title, state, version, minor version, the whole `options` dict and `dashboard_is_ours` from `async_dashboard_owned`: True, False or None when the dashboards cannot be read), `lovelace` (`resource_mode`, `served_urls` from `DATA_RESOURCE_URLS`, and `resource_rows`: url and type of every row under `/apollo_mmwave/`, or None when the collection has not loaded or cannot be read), `zone_store_loaded`, `calibration_store_loaded`, the zone store's `orphans`, and `devices`. A device gets a section when it is an Apollo radar in the registry (`apollo_radars`: manufacturer ApolloAutomation and a model starting with a `MODEL_RADARS` prefix) or when the zone store, the calibration store or `dashboard_devices` names it, which covers DIY radars and devices that left the registry; sections are sorted by name. Each holds the registry identity (name, name_by_user, manufacturer, model, model_id, sw_version, hw_version, disabled_by, the config entry domains) and `selected_for_dashboard`; `radars` (`expected` from the model, `gate_radar` from `resolve_gate_entities`, `ld2450` from the entities); `firmware` (the Apollo, ESPHome, LD2410, LD2412 and LD2450 version sensors, reported even when disabled, plus every `update` entity with `installed_version`, `latest_version` and `in_progress`); `wifi_signal`; `gate_radar` (profile, gate count, every move and still threshold state by gate); `ld2450` (Zone Type, Multi Target Tracking and `target_pairs` with `source` detected, configured or cleared, `tracked` and `detected`; None on a radar with neither an LD2450 nor configured pairs); `calibration` (exactly `calibration_payload`, what the calibrate card receives); `zone_store` (the store entry with string zone keys); and `zone_entities` (this integration's own entities on the device). Every entity is reported as entity id, state, unit, device class, `registered` and `disabled_by` (`_entity`).

It is read only: no store save, service call, state write, dashboard write or resource write (`tests/test_diagnostics.py` checks each). `_target_pairs` reads `DATA_PAIR_CACHE` the way `effective_target_pairs` answers but never fills it, and the Lovelace resource collection is read only when its `loaded` attribute is true, because its first load can import resources from an old dashboard config and save files. Privacy is two nets. First, only the entities named above are read, and of the registry fields only the ones listed, so the device's `connections` (its MAC), `configuration_url` and identifiers, and the IP address, MAC, BT MAC and SSID sensors never reach the file. Second, `async_redact_data(result, TO_REDACT)` replaces any `access_token`, `bssid`, `bt_mac`, `configuration_url`, `connections`, `host`, `ip`, `ip_address`, `mac`, `mac_address`, `password`, `refresh_token`, `ssid`, `token`, `user_id` or `wifi_ssid` key anywhere in the result with `**REDACTED**`, for a value a later field or a verbatim-stored pair might carry. Device names and entity ids stay, by the owner's decision, although ESPHome's default names end in the last six hex digits of the MAC. `MODEL_RADARS` mirrors `APOLLO_MODELS` in `profiles.ts`; `tests/test_diagnostics.py::test_model_radars_match_the_frontend` keeps the two equal. There is no device-level diagnostics: the radar devices belong to the ESPHome entry, and the zone entities attach through `device_entry` without adding this entry to the device, so HA would never offer a per-device download.

## Frontend modules

### Detection and profiles (`register.ts`, `entities.ts`, `entity-index.ts`, `profiles.ts`, `ld2450.ts`, `ld2450-entities.ts`, `types.ts`, `index.ts`)

`index.ts` is the tuning bundle entry: it exports `CARD_VERSION` and side-effect imports the distance, gate-energy, calibrate and setup cards and the strategy. `registerElement` (`register.ts`) defines an element immediately and re-asserts every pending definition once `home-assistant` or `hc-main` is defined, because HA's scoped-custom-element-registry polyfill replaces `window.customElements` after boot; `safeDefine` swallows any `define()` error without logging. `test/register.test.ts` boots the app through a model of @webcomponents/scoped-custom-element-registry 0.0.10 (the copy in HA frontend 20260930.2): its `define()` throws only on a tag or class collision in its own map and native-defines a stand-in only when the native registry lacks the tag, while `get()` and `whenDefined()` see only its own map. That stand-in is what resolves the native `whenDefined` held from before the swap; re-check the model if HA ships a different polyfill. `register.ts` also exports `registerCustomCard(type, name, description)`, which adds a card picker entry to `window.customCards` once per type with the repository link; the distance, gate-energy and setup cards use it, the calibrate card has its own once-per-type guard, and the zone map card pushes its entry unconditionally.

`profiles.ts` holds the chip tables: `LD2410_PROFILE` (9 gates g0..g8, MSR-2 naming) and `LD2412_PROFILE` (14 gates g00..g13, `ld2412_` naming), each with `maxBarLabels`, optional `maxBarTips` (only the LD2412 sets them, so its Min Gate row reads "gates below this one are ignored"; the default is `rangeLimitTip(label)`), `rangeLabels`, `gateSizeLabel`, `rangeTip`, `gateTip` (one shared `GATE_TIP`), `wikiUrl` and `entityMap(base)`. `rangeTip(gateDepth)` states one gate's depth (`gateDepthTip`; `cardMap` passes the same `aboutDistance` text the help card and the threshold rows use, so the note follows the gate size select when the user enabled it and the user's unit) instead of pointing at the gate size control, which ships disabled on every model, and says which sensor Radar Timeout holds on (`radarTimeoutTip`: Radar Target, or LD2412 Presence). It also holds `APOLLO_MODELS` (model prefix to profile and LD2450 flag), `apolloModelInfo`, `isEsphomeDevice`, `detectProfile` (probes each profile's engineering-mode switch id in `hass.states`) and `LD2410_FACTORY_THRESHOLDS`.

`entity-index.ts` exports `entitiesForDevice(hass.entities, deviceId)`, which groups `hass.entities` by `device_id` in one pass (registry order kept, so first-match-wins and tie-breaks are unchanged) and caches the result in a WeakMap keyed on the `hass.entities` object. `baseNameFromDevice`, `detectProfileFromEntities`, `entityMapFromDevice` (`entities.ts`), `isEsphomeDevice` (`profiles.ts`), `ld2450EntityIds`, `hasLd2450Device` (`ld2450.ts`) and the liveness fallback in `hasLiveRadarEvidence` (`strategy-core.ts`) read their device's list from it, so detection is linear in the registry size (a Proxy guard test in `test/strategy-regen.test.ts` counts enumerations). Like the `cards/resolution.ts` memo, it relies on HA replacing, never mutating, `hass.entities`: code and tests must build a new registry object rather than add, remove or re-home entries of one a helper has already read.

`entities.ts` turns registered entity ids into an `EntityMap` (`types.ts`). `baseNameFromDevice` strips `KNOWN_SUFFIXES` and takes the most common base; the LD2412 and LD2450 entries (`/_ld2412_(?!.*ld2412_).+$/`, `/_ld2450_(?!.*ld2450_).+$/`) strip from the last chip token, so a device named after its chip ("Office LD2412", entities `switch.office_ld2412_ld2412_engineering_mode`) keeps base `office_ld2412`. `classifyObjectId` matches `GATE_PATTERNS` then `SCALAR_PATTERNS` (the entity's domain must match the slot's). `entityMapFromDevice` builds a possibly sparse map, first match wins per slot. Gate arrays are indexed by gate number (0..8 on the LD2410, 0..13 on the LD2412), and on an LD2412 the `max_move_distance` / `max_still_distance` slots hold the max and min distance gate, so consumers label them through `RadarProfile.rangeLabels` / `maxBarLabels`, never by slot name. `resolveEntities` wraps `resolveEntitiesDetailed`, which adds the base-name fallback and the `config.entities` overrides and also returns `fallbackBase`. The fallback picks its chip with `resolveProfile(hass, config) ?? LD2410_PROFILE`, so the map and the card's profile share one precedence: concrete entity markers, then the registry model (`apolloModelInfo`), then `detectProfile(hass, base)`, then the LD2410 default. Overrides go through `withOverrides`: the four gate slots (`GATE_SLOTS`) take an override only when it is an array, so a YAML `move_threshold:` (null) or a single id string keeps the resolved list, while a scalar override applies as given and a null scalar hides that row. The LD2410 map has a `zone_occupancy` slot for the firmware's any-zone sensor (`_radar_zone_occupancy`, "Radar Zone Occupancy"), whose suffix the numbered `_radar_zone_<n>_occupancy` patterns never match and the reverse. `deviceInfoEntities(hass, deviceId)` resolves the Device card's whole-device entities (`DeviceInfoEntities`) from the device's own entities, skipping this integration's: the Apollo firmware version, the LD2410 "Radar Firmware Version" (`_radar_firmware_version`), the LD2412 and LD2450 firmware sensors, the firmware `update` entity, RSSI and ESP Reboot (`DEVICE_INFO_PATTERNS`, first match per slot). Each pattern names its domain, and the update slot takes the `update` domain only, because the firmware's "Firmware Update" template button (`button.<dev>_firmware_update`), which installs with no dialog, ends the same way. `ld2450.ts` exports `ld2450EntityIds`, `hasLd2450Device` and `zoneMapCard` (the zone map card config the strategy emits, with no `grid` or `grid_units`, so its map is fitted and in the viewer's units); it uses the same regexes as the backend for detection only.

`ld2450-entities.ts` resolves the LD2450's settings and live sensors on one device into an `Ld2450Entities` map (`ld2450Entities(hass, deviceId)`): Zone Type, Multi Target Tracking, Timeout, Bluetooth, Restart (R PRO-1 only), Factory Reset, the presence and target-count sensors, each target's distance, direction and speed (`targets`, `LD2450_TARGETS`) and each built-in zone's four corner numbers and three counts (`zones`, `LD2450_ZONES`). The two Apollo firmwares name them differently: the R PRO-1 puts "LD2450 " in front of every name because it also carries an LD2412 (`select.<dev>_ld2450_zone_type`), the MTR-1 mostly does not (`select.<dev>_zone_type`), keeps the prefix on a few ("LD2450 Bluetooth", "LD2450 Presence") and puts it last on one ("Factory Reset LD2450"). `PATTERNS` lists per slot the domain and the spellings in order of preference (`chip`, the prefixed one, first; then `bare`; `exact` for `factory_reset_ld2450`), each allowing HA's `_N` dedup tail, and a slot takes the device's entity whose object id matches the most preferred spelling, in registry order among equals. The base cannot be required, because an entity that is disabled by default keeps the id it was registered with after the device is renamed. The MTR-1's bare names (`timeout`, `zone_type`) are generic, so the lookup reads only the device's own entities (`entitiesForDevice`) and skips entities of this integration's platform. An object id that starts with the device's base (`baseNameFromDevice`) is matched whole after it (`rank` with `whole`: the spelling must match from the name's first character), so nothing in the base is taken for part of a name; matching every id by suffix read an MTR-1 named "Garage Zone 2" as having a `zone_2` token before every bare name, which lost its settings and filed its radar-wide counts as built-in zone 2's. Only an id that matches no pattern that way (one registered under another base, or any id when the base is unknown or wrong) is matched by its suffix, and then a bare match is rejected when the text before it ends in a token its spelling lists in `notAfter`: `ld2410` or `ld2412` for every bare name (`OTHER_CHIP_BEFORE`: `ld2412_timeout` is the R PRO-1's other radar), and also `zone_N` for the radar-wide still and moving counts (`ZONE_BEFORE`, `radarCount`: `zone_1_still_target_count` is a built-in zone's count). The whole-device ESP Reboot and Factory Reset ESP buttons match no spelling, and the chip's firmware version is left to `deviceInfoEntities`. Results are cached per `hass.entities` object and device id, relying on HA replacing the registry as `entity-index.ts` does. `builtInZoneNumberIds` lists the resolved corner numbers. `zonePresenceSensors(hass, deviceId)` lists this integration's zone presence sensors on the device (`ZonePresenceBinarySensor` is attached to the radar's own device entry): `binary_sensor.` entries of platform `apollo_mmwave`, or, when the frontend sends no platform, ids of the shape `binary_sensor.<device>_zone_<n>_presence[_N]`, sorted by zone number with registry order kept for renamed ids.

### Calibrate card (`cards/calibrate-card.ts`, `calibration/api.ts`, `calibration/model.ts`)

`ApolloRadarCalibrateCard` (element `apollo-radar-calibrate-card`, card picker name "Apollo Radar Auto-Calibrate") is a Lit element that takes `device_id`, `device_base_name`, `title` and a `calibration` block (`CalibrateCardConfig` in `types.ts`). It is a view of a backend job, never the job itself: it opens `apollo_mmwave/calibration/subscribe` for one device (`subscribeCalibration`), renders every pushed `CalibrationPayload`, and sends three service calls through one `callService` helper that passes `notifyOnError = false` so a `ServiceValidationError` is rendered once by the card and not again by HA's toast (`startCalibration`, `cancelCalibration`, `restoreThresholds`, plus `turnEngineeringMode` for the interrupted banner). The start call's promise is only watched for rejection; progress arrives over the subscription, which is why the job survives the browser closing. A rejection goes through `describeServiceError`: HA's websocket `call_service` sends a pre-flight `ServiceValidationError` as `{code: "service_validation_error", message: "Validation error: <text without its final period>", translation_domain, translation_key, translation_placeholders}`, so the card loads the exception translations (`hass.loadBackendTranslation("exceptions", domain)`) and renders `component.<domain>.exceptions.<key>.message` in the user's language, falling back to the message with the prefix dropped and the period restored. A `not_found` from a service call means the integration is unloaded (HA cannot find the service); only the subscription's `not_found` means an unknown device. A rejected start or Undo becomes the failed view ("Calibration failed: " / "Restore failed: ", with Try again and Close); a rejected Stop or "Turn it off" is shown inline in the running view or the banner, so it never replaces the running job or its result. For `thresholds_not_numeric` (the refusal's `translation_key`, read by `refusalKey`, or a failed job's `error.code`) the primary button is "Read settings from the radar" instead of Try again when the card knows the query-params button (`entities.query_params_button`, else the resolved map's `query_params`, and only while HA has its state): it calls `button.press` (`pressButton`), waits `READ_SETTINGS_WAIT_MS` (3 s) and then runs the same retry Try again would (same calibration or preview, same restore). Close, a new run, a device change and leaving the page drop a pending retry (`_readSettingsToken`); a rejected press is shown in the view. Without a known button the view keeps Try again and says where the button is. The button label, its progress line and the wait (`READ_SETTINGS_LABEL`, `READING_SETTINGS`, `READ_SETTINGS_WAIT_MS`) live in `calibration/model.ts`, which the calibrate card re-exports, so the gate setup checks share them without importing the card.

Subscription lifecycle: the device id comes from `resolvedDeviceId` (`cards/resolution.ts`: `config.device_id`, else the device of the first resolved entity in `hass.entities`); the card subscribes on the first `hass` with a device id, disposes in `disconnectedCallback`, resubscribes in `connectedCallback`, and on a device change disposes and reopens. Every open is tagged with a serial so a payload or a resolved unsubscribe from a superseded connection is dropped. It also listens to the websocket connection's `ready` and `disconnected` events and re-runs its own subscribe on every `ready`: `home-assistant-js-websocket` re-sends subscriptions on reconnect, but a re-subscribe refused with `not_loaded` (HA restarted and `apollo_mmwave` is not loaded yet, the normal order after the one restart that interrupted a job) is dropped silently. A `not_loaded` rejection is retried with `CALIBRATION_RETRY_DELAYS_MS` (copied from the zone API, not imported) while the card reads "Apollo mmWave is still loading...", then shows the Not loaded copy with a manual Retry (`_failOpen`). Unlike the zone API, it does not treat HA's `unknown_command` as not loaded. Neither `ready` nor `disconnected` fires on an integration reload, which closes the subscription server side without telling the client, so the card also watches `config_entries/subscribe` through `subscribeEntryLoads` (copied into `calibration/api.ts` from the zone API, once per connection) and reopens its subscription when an `apollo_mmwave` entry reports `loaded`. That feed is open to every user; the copy's doc comment still calls it admin-only. The engineering switch and the LD2412 background-correction status are read from live HA state first and from the payload's `entities` only when HA has no state: the backend pushes only from job code, so while no job runs the payload is as old as the last push. `shouldUpdate` re-renders on payload, local state or config changes, registry changes, and state changes of the engineering switch, the threshold numbers, the gate-range numbers, the radar-target sensor and the background-status sensor only.

State selection lives in `model.ts` (`nextLocalState`, `showsResultView`): the Done, Partial, Preview, Cancelled, Failed and Restored views render only while card-local `observedFinish` holds the id of a job this card watched reach a terminal status; a fresh mount with a stored `last_result` renders Idle with the footer and a "Show last result" toggle. Every terminal and failure view has a Close back to Idle, and the interrupted banner renders above all of them. "Try again" repeats the failed job: a calibration with the same `apply` the card saw on the job, a restore with the snapshot it was writing back (`restoreSource`: the result's `restored_from`, else the snapshot older than its redo snapshot), never the newest snapshot, which after the redo snapshot is the very values being undone. Everything else in `model.ts` is pure copy: `phaseLabel`, `phaseHeadline` (the headline's stable phase sentence, the only text in the running view's live region, so the per-second countdown is not announced) and `progress` for the running job, `resultRows`, `unusedFootnote` and `warningLines` for the result, `undoLabel` and `restoredLine` (what the snapshot holds, from `snapshotContents`: a calibrate snapshot holds the values from before it and each restore snapshot above it flips that, so the newest reads "Undo (restore your previous values)" or "Redo (put the calibrated values back)", falling back to the time when the calibrate snapshot has aged out; `undoTitle` keeps the time for the tooltip and `savedLine` shows it as text under the idle footer's button, since a tooltip never shows on a touch screen), `footerLine` (names a preview by the result's `apply`, a `cancelled_by_shutdown` failure as stopped by a restart, and says "Nothing was changed." when `writes_done` is 0), `idleSentence`/`durationText`, `isFactoryThresholds` (the `LD2410_FACTORY_THRESHOLDS` hint) and `canStart`/`canStop`. A gate channel whose threshold sits at its number's `max` (`thresholdMax`, fallback 100) never triggers, so it is off; calibration still sets it. Before a run the idle body names the in-use ones from live state (`liveGateLimits`, `offChannelsBeforeRun`, `offGatesLine`; the gate range mirrors `_gate_unused`, LD2410 G0 and G1 still are skipped as in `gate_off`, and so is a channel that `last_result`, an applied or partial calibration, set to the top itself, by its `gates_off` or a written cell at the max); after one, `resultRows` tags a cell "(was off)" when the result's `old` was at the max and `new` is below it, and `reenabledLines` adds one warning per such channel under applied and preview tables. The interrupted banner composes its lines from the marker's `phase` and `left_on` as independent facts plus the live switch state, so "Turn it off" disappears when the switch reads off without a store write.

Every render helper wraps its template in an element, because happy-dom 14 mis-cloned Lit child-part markers at a template root and inside `<svg>` (see Build, test and CI); the same reason is why `charts/gate-energy-chart.ts` keeps its SVG in a nested template.

### Setup card (`cards/setup-card.ts`, `cards/setup-checks.ts`)

`ApolloRadarSetupCard` (element `apollo-radar-setup-card`, `SETUP_CARD_TAG`, card picker name "Apollo Radar Setup") is a Lit element that takes `device_id`, `title` and `radar` (`SetupCardConfig` and `SetupRadar` in `types.ts`: `ld2450`, the default, or `gate`; the header defaults to "Radar setup" with "LD2450 · <device name>", or "<chip> · <device name>" in gate mode, under it). Without `radar` it checks the two LD2450 settings that decide whether the zone map can show anyone, and offers the fix; gate mode is described at the end of this section. Both are handed straight to the radar chip and Apollo firmware never sets them, so they are whatever the chip holds. Zone Type Detection makes the chip report only people inside its built-in zones (with all of them at 0, nobody, so the map never gets a dot) and Filter reports everyone except them; the zone map replaces those zones, so Disabled is recommended. Multi Target Tracking off tracks one person only.

The checks are pure functions of HA state in `setup-checks.ts`, which also holds every line of the card's copy. `setupStatus(hass, deviceId)` returns `no_device`, `nothing_to_check` (neither setting resolved on the device), `offline` (every checked entity is "unavailable" or has no state), `waiting` (no checked entity has a value other than "unknown", or Zone Type has none and nothing else needs fixing, so "Radar settings look good." always means Zone Type, when the device has it, was read), or `checked` with a list of `SetupProblem`s and `zoneTypeUnread` when those are Multi Target Tracking's while Zone Type is still unread; the card then adds "Waiting for the radar to report its Zone Type." under the warning. Zone Type is a problem whenever it is live and neither "Disabled" nor "unknown": Detection is a warning whose second sentence depends on `builtInZonesEmpty` (all of the resolved corner numbers read 0; false when any is missing or not a number, so the card never says "None are set" without reading them all) and carries a "Zone Type should be Disabled" hint; Filter and any option the card does not know are notes. Multi Target Tracking is a warning only while its switch reads "off": on the R PRO-1 the switch is disabled by default in the registry and so usually absent, and the chip's default is multi target, so there is nothing to say then. Each problem carries one `SettingFix`, `select.select_option {entity_id, option: "Disabled"}` (left out when the select's `options` attribute lacks "Disabled") or `switch.turn_on {entity_id}`. With more than one fix the card shows a single "Use recommended settings" button with a helper line built by `recommendedLine`, otherwise one button per problem.

The card never writes on its own: only a click calls the services, through the calibration `callService` helper with `notifyOnError = false`, every fix of the click at once (`Promise.allSettled`). The buttons are disabled and a progress line shows while the call runs; a rejection becomes the card's own error line (the fix's `failure` lead, else "Could not change <setting>", then ": <reason>" through `describeServiceError`, except that HA's `not_found` reads as "Home Assistant could not find this setting", because these are select and switch calls, not this integration's services). A device change bumps `_serial`, so a call that settles afterward is dropped, and the error line clears once the checks pass. `shouldUpdate` re-renders on config, registry or device changes, and on a `hass` tick only when a state that `watchedSetupIds` names changed (Zone Type, Multi Target Tracking and the corner numbers). `getStubConfig` picks the first device with an LD2450 (`hasLd2450Device`), else the first whose own entities give a gate profile (`detectProfileFromEntities`) with `radar: "gate"`.

Gate mode (`radar: "gate"`) checks the device's gate radar, the LD2410 or LD2412 its profile names, with the checks and copy in `cards/gate-setup-checks.ts`. The card resolves the entity map and profile through `resolveRadar` with `{type, device_id}`, so the MSR-1 and MSR-2 spellings both resolve and one config fits MSR-1, MSR-2 and R PRO-1. `gateSetupStatus(hass, deviceId, map, profile, job)` returns the LD2450 status shapes plus `checking`: `nothing_to_check` without a profile or when none of `gateCheckedIds` resolved, `offline` when none of them is live (`isLive`, exported from `setup-checks.ts` with `isRead`), `waiting` when none has a value yet, else `checked` with these problems, each with `setting`, `level`, `text`, `hint` and an optional `fix`:

- `engineering_mode` (a note) while Radar Engineering Mode reads `on` and `job` is `idle`; the fix is `switch.turn_off`. `job` comes from `CalibrationJobWatch` (`calibration/job-watch.ts`), which opens `apollo_mmwave/calibration/subscribe` with a smaller copy of the calibrate card's recovery (the `not_loaded` backoff with `CALIBRATION_RETRY_DELAYS_MS`, a reopen on the connection's `ready` and on the entry's `loaded` through `subscribeEntryLoads`) and keeps only `jobActivity(payload)`: `unknown` until the feed first answers, `running` while the payload has a job whose result is not stored yet (`last_result.job_id` differs; the job turns the switch back off before it stores the result), and `idle` otherwise, a refused feed included, since no job can run then. While the activity is `unknown` and the switch reads `on` with nothing else to report, the status is `checking`, so "Radar settings look good." never stands over a switch a job may own.
- `settings_unread` (a note) when a threshold, a range gate or the timeout reads `unknown`; the text names the groups ("gate thresholds", "detection range", "timeout"). The fix presses the query-params button only while that button is live, with the calibrate card's `READ_SETTINGS_LABEL` and `READING_SETTINGS` and `settleMs: READ_SETTINGS_WAIT_MS`: the card keeps the progress line (and every button disabled) until the problem clears or the wait runs out, then shows the fix's `noAnswer` line if it is still there. Without a live button the hint says to press Query Params on the device page.
- `zone_order` (a warning, LD2410 only) for zones that can never turn on, by the firmware's rules: Zone 1 counts from Start Zone 1 to End Zone 1, both inclusive, and each later zone from past the previous end to its own. `zone_reach` (a warning when a zone starts past the reach, a note when it only ends past it) uses the larger max gate times the gate size select's value when enabled, else `DEFAULT_GATE_SIZE_M` (0.75 m). Each bound is converted to cm from its own number's unit. Both are report only.
- `gate_range` (a warning, LD2412 only) when Min Gate (`max_still_distance` on the LD2412 map) is at or above Max Gate (`max_move_distance`). Report only.

Gate fixes are never combined into "Use recommended settings": each fixable problem keeps its own button. `shouldUpdate` watches `gateWatchedIds` (the checked ids plus the gate size select), and the job watch re-renders the card when the activity changes. The watch opens in `connectedCallback` and on `willUpdate`, reopens on a device or connection change, and closes in `disconnectedCallback` and outside gate mode.

### Strategy (`strategy.ts`, `strategy-core.ts`, `panels/`)

`strategy.ts` registers `ll-strategy-dashboard-apollo-radar-tuning`, `ll-strategy-view-apollo-radar-tuning` and `ll-strategy-section-apollo-radar-tuning` and pushes a `window.customStrategies` entry once. All three share `shouldRegenerate`. Its fast path returns false when `hass.devices` and `hass.entities` are reference-equal and no entity crossed the live line (`availabilityChanged`, which uses `isLiveState` from `strategy-core.ts`: only "unavailable" or a missing state is offline, "unknown" is live; the device `online` flag uses the same predicate). Otherwise it first unwraps the legacy `{type, options: {...}}` strategy form exactly as HA does before `generate()` (exactly two keys, `options` an object; `isLegacyOptions`), because HA hands the hook the raw strategy object, then compares `radarDeviceKey`: per device a JSON array of device id, profile key, LD2450 flag, online flag, device name and base name, sorted and joined. A `name_by_user` rename or an entity-id rename therefore regenerates an open dashboard. Drawing a zone does not: the zone entities (`sensor.<slug>_zone_N`, `binary_sensor.<slug>_zone_N_presence`, platform `apollo_mmwave`) sit on the radar device, but their ids match no radar entity pattern and the liveness fallback in `hasLiveRadarEvidence` skips entities of that platform, so base, capabilities, liveness and the key are unchanged. `ApolloLd2410DashboardStrategy.generate` has two empty states: `EMPTY_VIEW` ("No Apollo mmWave devices found", auto-detection found nothing) and `STALE_SELECTION_VIEW`, used when the config has a non-empty `devices` list or a `device_id` and `generateViews` returns nothing. A selected device is rendered whenever it is in `hass.devices`, offline or not, so that result means every selected id is missing from the registry. The view and section strategies return empty sections or cards with no message.

`strategy-core.ts` does the work. `strategyDevices` takes `config.device_id` first (when both are set, only it is rendered and `devices` is ignored), then the `config.devices` selection (forced, shown even offline), else `detectRadarDevices`. `deviceFromId` combines the registry match (`apolloModelInfo`, applied only to an ESPHome device per `isEsphomeDevice`), the base name, liveness (`hasLiveRadarEvidence`: a recognized radar entity with a live state; when none is recognized, a registry-matched device falls back to any live entity of the device other than this integration's own), the profile (`detectProfileFromEntities`, then the registry model) and the LD2450 flag. That flag is device-scoped only (`hasLd2450Device` or the registry model's flag), so a gate-only MSR renamed to the same name as an R PRO-1 or MTR-1 never gets a zone map. `cardMap` builds entities cards from `panels/entity-rows.ts` (each filtered through `presentRows`), one history graph per tab (`historyCard`, rows from `panels/history.ts`), the two custom chart cards, the gate radar's Radar setup card and the calibrate card (both for every device with a gate-radar profile, online or not; the calibrate card gets `config.calibration` as its `calibration` block), a "Start here" help card, the zone map card, the LD2450 cards below and the Device card. The gate setup card is `{type: "custom:apollo-radar-setup-card", device_id, radar: "gate"}` (see Setup card), left out when none of `gateCheckedIds(m, profile)` exists in `hass.states`, as on an R PRO-1 built without the LD2412.

The help card (`helpCard`, `helpCardBody`) gives each kind of tab its own "Start here" list, and every kind, the "no radar data" card included, ends with `deviceLink`, a markdown link to `/config/devices/device/<device_id>` ("All settings for this device →"). A gate radar alone gets `gateSteps`: "Fix anything the Radar setup card flags." when the tab has the gate setup card (`HelpContext.gateSetup`), then calibrate, the two range gates on the Detection Range card with one gate's depth in the user's unit, Radar Timeout and the Gate Energy walk, then the wiki link. The depth is `aboutDistance(gateSizeMeters(...))`: the gate size select's value when the user enabled it, else `DEFAULT_GATE_SIZE_M` (0.75), in feet when `hass.config.unit_system.length` is `mi` (`lengthUnit`). An R PRO-1 gets a sentence on what each radar is for, the same steps naming the chip ("the LD2412's Radar setup card"), a last step for the LD2450 that names its own setup card when the tab has one (`ld2450Setup`), and an "In automations" line that recommends LD2412 Presence while its `radar_target` exists, else `LD2450_AUTOMATIONS`. An MTR-1, online or not, gets three steps (two without the LD2450 setup card), the last of which says to reload the page before watching Zone presence, and `LD2450_AUTOMATIONS`. So does an R PRO-1 with none of the gate radar's entities (`HelpContext.gateRadar` false: no gate setup card and no `radar_target`), which keeps the LD2412 profile from its registry model (see Known limitations). No step names Gate Size, which ships disabled on every model. The device name goes through `markdownText`, which backslash-escapes every ASCII punctuation character, because Home Assistant renders markdown card content as a template first, so a name with `{{`, `{%` or `{#` would be evaluated and `*` or `[` would change the formatting. `OFFLINE_NOTE` follows for an offline device with a profile or an LD2450.

Gate-radar rows: `controlRows` lists Radar Engineering Mode, the LD2412 background correction pair, `RADAR_BLUETOOTH` ("Radar Bluetooth (HLK app)", the chip's own Bluetooth, not the device's proxy), `restartRadarRow` and `factoryResetRow`. The whole-device ESP Reboot is no longer on it. Both buttons come from `confirmRow`, whose `Row.confirm` makes `entityRow` build HA's special `button` row with `action_name` (the button text, "Restart" or "Reset") and a `perform-action` `button.press` tap action that carries a `confirmation`, so HA asks "Restart the <chip> radar? It stops detecting for a few seconds while it starts up." or "Reset the <chip> radar to its factory settings?" before pressing. Threshold rows are named by `gateName` ("G0 (at the sensor)", "G4 (about 3 m)", "G4 (about 10 ft)"; below 1 m two decimals, below 3 ft one), fixed when the dashboard is generated, so a changed gate size shows after a reload. Notes follow three cards: the profile's `rangeTip` under Detection Range, `zoneConfigNote(unit, anyZone)` under the LD2410 Zone Config (the boxes are template numbers in cm, which HA never converts; the back-to-back zones; "Any zone" for automations when `zone_occupancy` exists) and `GATE_TIP` under the thresholds. Target / Occupancy (`occupancyRows`, ending with "Any zone") sets `state_color: true`.

Slider rows: `sliderRow` (`panels/entity-rows.ts`) builds a row with `slider: true`. `rangeRows` uses it for the two range gates (`max_move_distance` and `max_still_distance`: Max Move Gate and Max Still Gate on the LD2410, Max Gate and Min Gate on the LD2412) and `moveThresholdRows` and `stillThresholdRows` for every gate; Radar Timeout (0 to 900 s, which HA draws as a box) and the gate size select stay plain `row()`s. `cardMap` passes the Detection Range, Move Thresholds and Still Thresholds rows through `unlockBoxes(hass, presentRows(...))`, which drops the flag from a number whose state has a `mode` and is not a slider (`showsSlider`; a state without a mode keeps it, the safe side), and hands `entitiesCard` the device id. `entityRows(rows, lockDevice)` then writes each flagged row as `{type: "custom:apollo-radar-slider-row", entity, name, device_id}` and puts one `{type: "custom:apollo-radar-slider-lock-row", device_id}` right above the first of them, so Radar Timeout and Gate Size sit above the lock row and read as unlocked. The three cards stay `entities` cards with the same titles and columns. No other card (Controls, Zone Config, Target / Occupancy, the LD2450 cards, the Device card, anything on an MTR-1 tab) gets a slider row, and DIY LD2410 and LD2412 devices take the same path. `GATE_TIP` says the sliders start locked and where Unlock is.

`historyCard` makes one `history-graph` per tab with `hours_to_show: 24`, left out with no rows. `historyEntities(m, chip)` gives the gate radar's lines ("Detected", "Moving", "Still", "Any zone", "Zone 1" to "Zone 3"; "<chip> Presence", "<chip> Moving" and "<chip> Still" on a tab with two radars), and `ld2450HistoryEntities(l, zones, chip)` adds the LD2450's Presence ("LD2450 Presence" beside a gate radar) and each `zonePresenceSensors` id with no name, so HA shows the zone's own name. `HistoryRow` is its own type (`entity`, optional `name`). The graph is "<chip> Occupancy History" on a gate radar alone and "Occupancy History" otherwise. Like Zone presence, a zone drawn since the page loaded joins it after a reload.

The Device card (`deviceCard`, `DEVICE_TITLE`) ends every tab. `deviceRows` (`panels/device-rows.ts`) turns `deviceInfoEntities` into rows: "Apollo firmware", "LD2410 firmware", "LD2412 firmware", "LD2450 firmware", "Firmware update" (a plain row, whose tap opens HA's own update dialog; the card never installs anything) and the restart, a `confirmRow` that `deviceRestart` names after what it takes down ("Restart device", "Restart device (both radars)" on an R PRO-1 with gate radar entities, "Restart device (also restarts the radar)" on an MTR-1 and on an R PRO-1 without the LD2412). A native `conditional` card with a `numeric_state` condition below `WEAK_WIFI_DBM` (-75) shows `WEAK_WIFI_NOTE`; an unavailable RSSI is not numeric, so the note stays hidden offline and follows the live signal without a regeneration. A markdown card with `deviceLink` and `SUPPORT_FILE_NOTE` (a link to `/config/integrations/integration/apollo_mmwave` and the Download diagnostics menu item) closes it, titled "Device" itself when no row resolved; more than one card goes in a `vertical-stack`.

`buildDeviceSections`, `deviceView` and `generateViews` lay the cards out as one sections view per device. Column 1 of a gate-radar tab is the help card, the gate setup card, the calibrate card, Controls, and the LD2410 Zone Config with its note, so the help's steps come before the cards they point at; then Distances, Detection Range and its tip; then Gate Energy, Move Thresholds and the gate tip; then the history and Still Thresholds. Target / Occupancy goes in column 2, or in column 1 when there is no Zone Config (the LD2412). `buildDeviceCards`, the flat list the section strategy uses, starts the same way. The Device card is appended to the last section, so it ends every tab. A device without a gate-radar profile but with a zone map leads with [help, setup, zone map], online or not, so an offline MTR-1 shows the "Offline right now" note above its map; a forced device with nothing detectable gets only the "no radar data available right now" help card and the Device card instead of an empty tab.

For a device with an LD2450, `cardMap` resolves `ld2450Entities` for that device only and adds, besides the zone map: the Radar setup card (`{type: "custom:apollo-radar-setup-card", device_id}`, online or not like the calibrate card, and left out when neither Zone Type nor Multi Target Tracking exists in `hass.states`), "Zone presence" (`zonePresenceCard`: an entities card of the device's `zonePresenceSensors` with no row names, so HA shows each sensor's own name, which follows a zone rename; each row is a `conditional` row with `state_not: "unavailable"`, because a conditional reads a missing entity as "unavailable" and a deleted zone's sensor leaves `hass.states`, where a plain row would show HA's "Entity not available" warning until a reload; the inner row repeats `state_color: true`, since the conditional row builds it from `row` alone; with no sensors, a markdown card that says to draw a zone and reload), "LD2450 Live" (`ld2450LiveRows`: Presence, Moving Target, Still Target, Target Count and each target's distance and direction), "LD2450 Controls" (`ld2450ControlRows`: Zone Type, Multi Target Tracking, Radar Timeout, Radar Bluetooth (HLK app), Restart Radar and Factory Reset Radar, named like the gate radars' Controls rows and asking first the same way; the firmware version is on the Device card), `LD2450_TIMEOUT_NOTE` under it while the LD2450 timeout exists (it holds LD2450 Presence, not the drawn zones, which turn off as soon as nobody is in them), and the built-in zones card (`builtInZonesCard`). Its Presence and the zone presence sensors also go to the tab's history. Rows go through `presentRows` like every other entities card, and Zone presence and LD2450 Live set `state_color: true`. The built-in zones card is a native `conditional` card on the Zone Type entity with `state_not: ["Disabled", "unavailable", "unknown"]`, wrapping a `vertical-stack` of a markdown note titled "Radar's built-in zones" and an entities card with a `section` row per zone (`builtInZoneRows`: X1, Y1, X2, Y2 and the three counts), so it appears and goes with the live state without a regeneration; it is left out when Zone Type or every zone row is missing. `buildDeviceCards` order ends with the zone heading, setup, zone map, zone presence, LD2450 Live, the history, LD2450 Controls, its note, built-in zones and the Device card. In `buildDeviceSections` the LD2450 setup card sits right above the zone map in the map's section. An R PRO-1 gets column 1, then [heading "Zone Map", LD2450 setup, zone map] and [zone presence, LD2450 Live, LD2450 Controls, its note, built-in zones], then its other three tuning columns, six in all, with one Radar setup card per radar. An MTR-1, online or not, gets [help, setup, zone map], [zone presence, LD2450 Live, history] and [LD2450 Controls, its note, built-in zones, Device]. Section order is also the phone's reading order, which is why help, setup and the map lead. These cards are built once per generation: drawing a zone or enabling a disabled entity leaves `radarDeviceKey` unchanged (see `shouldRegenerate` above), so a new zone's presence sensor or a newly enabled Multi Target Tracking row appears after a page reload, while the setup card and the conditional card follow live state. `generateViews` appends the device id to the view path when two devices share a base name, because HA opens the first view matching the URL.

### Tuning cards and charts (`cards/`, `charts/`)

`ApolloLd2410DistanceCard` (`cards/distance-card.ts`, element `apollo-radar-distance-card`) and `ApolloLd2410GateEnergyCard` (`cards/gate-energy-card.ts`, element `apollo-radar-gate-energy-card`) are Lit elements that take `device_id`, `device_base_name`, `entities`, `title` and `distance_unit` (`types.ts`; `distance_unit` is typed as `Uom`). Without a `title` they are titled after the resolved chip ("LD2412 Distances" / "LD2412 Gate Energy" on an R PRO-1, "LD2410 ..." on an MSR, matching the strategy's titles), and a device with no resolved profile keeps the LD2410 wording; the chart SVG aria-labels follow the same chip through the trailing `label` argument of `renderDistanceChart` and `renderGateEnergyChart`. `cards/resolution.ts` memoizes entity resolution (`resolveRadar`). `ResolvedRadar` carries `ids` (every resolved id, which drives a recomputed resolution's re-render check) and `radarIds` (`radarEntityIds`: the same minus the ESP Reboot button). Both cards decide "device not found" with `anyResolved(hass, radarIds)`, so a card pointed at a device with no gate radar (an AIR-1, an MTR-1, any ESPHome board whose only classified entity is ESP Reboot) says "Apollo mmWave: device not found. Check the card's device configuration." instead of rendering blank. Each card watches only the slots its chart reads: the distance card `DISTANCE_CHART_SLOTS` and the gate-energy card `GATE_ENERGY_CHART_SLOTS` (exported next to each renderer), flattened by `watchedIds` and cached per resolution by `watchResolved`. The gate is `drawnStatesChanged`: a resolution recomputed on the tick checks every id, a tick that flips the "device not found" decision re-renders, and otherwise only the watched ids count, so a gate-energy tick no longer redraws the distance card and the reverse. Registry replacements (and `hass.config` for the distance card) always re-render. A chart that starts reading a new slot must add it to its list; a Proxy guard test in `test/cards.test.ts` fails otherwise.

Both charts take the gate count from `gateRegisterCount` (`charts/geometry.ts`), the longest of the four gate arrays, so a disabled top-gate threshold entity (HA leaves disabled entities out of `hass.entities`, which shortens that one array) no longer drops a gate. `charts/distance-chart.ts` renders zones, detection/moving/still bars, gate bands and max-gate bars scaled to gate size times gate count; the two max rows take their tooltips from the profile's `maxBarTips` (the trailing `maxTips` argument of `renderDistanceChart`), `maxLabels` defaults to `LD2410_PROFILE.maxBarLabels`, and a max row is drawn only when its gate state is numeric. The distance chart renders nothing when `move_threshold` is empty. `charts/gate-energy-chart.ts` renders per-gate move/still energy with threshold markers, visible only while the engineering-mode switch is on. `GateEnergyModel.unavailable` is true only when that switch reads "unavailable": the dimmed plot then says "Radar unavailable / Waiting for the device to reconnect" and shows no button. While the switch reads off and `hass.callService` exists, the chart places a real HTML `<button class="overlay">` ("Turn on Radar Engineering Mode") over the plot area, inside a `position: relative` wrapper, which calls `switch.turn_on` through the calibration `callService` helper with HA's own error toast left on (the chart has nowhere else to show a failure) and catches the rejection; a real button is focusable and announced where an SVG element with an ARIA role inside `role="img"` is not. A bar whose energy exceeds its threshold is outlined in the threshold color (`stroke-width="2"`) and the legend explains it. There is deliberately no "turn it off" line or button on the chart: the calibration job turns the mode on for its listen, and that line would invite a click mid-run. The `.chart-legend` styles are exported as `chartLegendStyles` from `charts/gate-energy-chart.ts` and composed into the gate-energy card's `static styles`. `panels/entity-rows.ts` `controlRows` adds the LD2412's Start Dynamic Background Correction button and Background Correction Running status right after the engineering-mode row when the slots resolve. `charts/geometry.ts`, `charts/entity-read.ts` and `charts/unit-convert.ts` are pure helpers.

### Slider lock (`cards/slider-lock.ts`, `cards/slider-lock-rows.ts`)

HA's number row draws its slider with `ha-slider`, a Web Awesome slider (3.7 in HA 2026.8 to 2026.10) whose `#slider` is `touch-action: none` and sets the value on touch down. On a phone, a scroll that starts on a slider therefore changes the threshold instead of scrolling the page. The slider lock puts the gate radar's sliders behind a per-radar lock while keeping HA's own row.

The store, `slider-lock.ts`, is pure (it defines no element), so `strategy-core.ts` can import `SLIDER_ROW_TAG`, `SLIDER_LOCK_ROW_TAG` and `showsSlider`, a copy of HA's `showNumberSlider` (mode `slider`, or `auto` with (max - min) / step <= 256; the same in both supported frontends). It keeps one `RadarLock` per `device_id` in a module `Map` and saves nothing, so every page load starts locked (the zone map's Locked button, by contrast, is in localStorage). `setUnlocked(id, true)` does nothing for a radar no row watches (a stale toast action), resets the try counter and arms the relock timer, `RELOCK_AFTER_MS` (5 minutes); `noteSliderChange` arms it again. `expire` re-arms for the time left when a change moved the deadline, and returns without locking while `drags` holds a pointer (`dragStarted`, from the row's capture-phase pointerdown on an unlocked slider with the primary pointer's main button, the button Web Awesome drags with; `drags` maps each pointerId to its pointerType). Global listeners go in on the first watch or drag: window `pointerup` and `pointercancel` (capture) end a drag and, when the deadline passed during it, call `expire` one tick later, after Web Awesome's `change` (sent from its pointerup handler once `updateComplete` resolves) has re-armed the timer, so a drag that set a value never ends in a relock; window `contextmenu` (capture) ends every drag but a touch's the same way, because a context menu can take the mouse's pointerup (macOS opens it on the press of a ctrl-click, which Web Awesome takes for a drag), while a long press on a touch screen can open one under a finger that goes on dragging; document `visibilitychange` clears `drags` when hidden and runs `expire` on every radar when visible, as window `pageshow` does, because phone timers sleep in the background; window `scroll` stamps the time for `recentScroll` (HA dashboards scroll the window). `watchSliderLock` returns an unwatch. When a radar's last watcher leaves, the radar locks after `LEAVE_GRACE_MS` (2 s) and its entry is dropped, so leaving the tab or the dashboard locks it, while a strategy regeneration, which puts new rows in within milliseconds, keeps the state. `hui-root` keeps each tab's view and reattaches the same rows when the user comes back, so both rows `requestUpdate()` on every connect.

`ApolloRadarSliderRow` takes `entity`, `device_id` and any option of HA's number row (`SliderRowConfig`); `setConfig` throws without `entity` or `device_id`. It builds HA's row with `window.loadCardHelpers().createRowElement({color: "state", ...config})`, less `type` and `device_id` (`color: "state"` is what the entities card adds to a plain row; it leaves custom rows alone), hands it every `hass` in `shouldUpdate`, and re-renders itself only for its entity's state or `localize`. Without `loadCardHelpers`, or when it throws, the row shows a read-only name and value and nothing is locked. Locked means the radar is locked, HA's row is built and `showsSlider` holds for the state; an unavailable number keeps its range and mode, so it stays locked. The row then gets `.locked`: `.native { pointer-events: none }`, `--ha-slider-thumb-color` and `--ha-slider-indicator-color` set to `--secondary-text-color` (the track keeps its color, so the position stays readable), and an `aria-hidden` `.shield` over the whole row with `touch-action: pan-y` (then `pan-y pinch-zoom` where known) and explicit sides rather than `inset` for iOS 14. A vertical swipe that starts on the shield scrolls the page natively, the browser sends `pointercancel` and no click, and Web Awesome's own pointer and touch listeners never see it.

A try on a locked slider: pointerdown (primary, main button) records whether it landed in the slider zone (`_inSliderZone`: from 8 px before the `ha-slider`'s left edge, its right edge in a right-to-left language, read through HA's row's open shadow root; with no slider to measure the whole row counts, so the row stays locked and only the name tap is lost). A move of `DRAG_PX` (10 px) either way marks the gesture moved, and a mostly horizontal one in the slider zone is a try; a moved gesture never counts its click, and a mouse or pen move with no button down drops a gesture released elsewhere. A click in the name zone fires `hass-more-info`, as HA's row does; in the slider zone it is a try unless the window scrolled within `SCROLL_GUARD_MS` (300 ms). `_try` does nothing for a missing or unavailable entity. Otherwise `noteTry` answers `nudge` or `remind`: a second try within `REMIND_WITHIN_MS` (10 s), or any key press, reminds, at most once per `REMINDER_GAP_MS` (4 s, HA's shortest toast). The thumb and fill take `--warning-color` for `NUDGE_MS` (1.2 s), a bubbling `haptic` event ("light", or "warning" for a reminder) reaches the window, where HA's haptic mixin vibrates only while the user's Vibrate setting is on, and a reminder fires `hass-notification` with `REMINDER_TOAST`, `duration: 6000` and an Unlock action. Toast ids are `apollo-mmwave-sliders-<device_id>`, so an unlock, a lock and a reminder replace each other in place. Every watcher hears "try", so the radar's lock rows flash.

The keyboard and change checks are capture-phase listeners on the row's own `.row`, so they run before anything inside HA's row. While locked, a value key (arrows, Home, End, Page Up, Page Down) from a slider (an `ha-slider`, a `role="slider"` element or a range input in the composed path) is prevented and stopped before Web Awesome's keydown on `#slider`, and a non-repeat press is a keyboard try; Tab, Enter and Space pass, so focus moves and Enter on the name opens more-info. A `change` from a slider while locked stops before HA's row's `@change`, which calls `number.set_value`, and the row is built again so it shows the real value: whatever moved the slider, nothing is written. Unlocked, a slider's `change` calls `noteSliderChange`.

`ApolloRadarSliderLockRow` takes `device_id` and is laid out like an HA row: a lock icon (`--state-icon-color`, `--primary-color` when unlocked), "Sliders locked" over "A scroll cannot move them." or "Sliders unlocked" over "They lock again after 5 minutes without a change.", and an Unlock or Lock button whose `aria-describedby` points at that text (no `aria-pressed`, since the label names the action, and no live region, since three lock rows per radar would all speak). Unlock toasts `UNLOCKED_TOAST` and Lock `LOCKED_TOAST`; a relock after 5 idle minutes or after leaving is silent. A try flashes the button with a warning-colored ring (`flash-a` and `flash-b` alternate so the animation starts again; a steady ring with `prefers-reduced-motion`). It skips renders for `hass` alone.

What the rows rely on from HA, and what happens without it: `loadCardHelpers().createRowElement` (`ha-panel-lovelace.ts`; without it, the read-only fallback), the `ha-slider` tag (the name and slider split only), `--ha-slider-thumb-color` and `--ha-slider-indicator-color` (the gray look only), and the `hass-more-info`, `hass-notification` and `haptic` events. The lock itself, the shield and the capture checks, depends on none of them. Neither row calls `registerCustomCard`, so the card picker still lists four cards from this bundle.

### Zone map (`zone-map/card.ts`, `editor.ts`, `api.ts`)

`ZoneMapCard` (element `apollo-radar-zone-map-card`) is a plain `HTMLElement` with a canvas 800 px wide (`CANVAS_WIDTH_PX`, `setupCanvas`, sized by `_sizeCanvas`). It draws rect, ellipse and polygon zones in millimeters, Y-down, over live targets and a device cone, with a rotation slider (`_persistRotation`), an m / ft switch, a per-radar lock persisted in `localStorage` (`readStoredLock`), a single-level undo and a zone manager for rename, delete and add (`_renderZoneManager`, `_handleAddZone`). Lock precedence: `_applyAutoLock` runs once per page load (and again after `start_locked` is removed from a live config) and uses the `start_locked` config first, then the stored `localStorage` value, then "locked if the radar already has zones". `setConfig` derives every field from the defaults plus the keys present, so removing `grid`, `cone`, `show_undo`, `unit_label_size` or `start_locked` (or a sub-key of `cone`) from a live card reverts it to what a freshly added card uses (the fitted grid, `DEFAULT_CONE`, `DEFAULT_SHOW_UNDO`, `DEFAULT_UNIT_LABEL_SIZE`); a sub-key dropped from a YAML `grid` that still has a usable extent falls back to `DEFAULT_GRID` for that edge. The file is `@ts-nocheck` by design (see its header comment), so `tsc` does not check it.

Map unit: `_displayUnit` returns, in order, the unit this page's viewer picked on the switch (`_viewDisplayUnits`), the unit saved for the radar (`_storedDisplayUnits`, from the payload's `display_units`), a YAML `grid_units` the card knows (`_gridUnitsConfigured`, returned as written, so a hand-written card in mm or in draws as it did before the switch existed; a misspelled unit counts as absent), and last Home Assistant's unit system (`hass.config.unit_system.length === "mi"` gives `ft`, else `m`, the distance card's rule). Grid steps, labels, the help line and the cache keys all read it, and `set hass` calls `_displayUnitChanged` when it changes. The switch (`_chooseDisplayUnit`) sets the page's pick and saves it for the radar only for an administrator (see Runtime data flow), and its tooltips say so (`UNIT_SWITCH_TITLES`, set by `_renderUnitSwitch`, which `set hass` also calls when the viewer's admin flag changes): "Show this radar's map in feet for everyone" for an administrator, "Show the map in feet" for anyone else; the pick then stays the page's, for an administrator too, so a save from another page does not flip the map under someone who just chose. A device change forgets both the pick and the saved unit (`_resetDeviceState`). Feet labels read "4 ft" with a space; meters keep "2m".

Fitted grid: a card whose YAML has no `grid` with a usable extent (`_gridFromConfig` false) fits its extents to the radar's field of view as currently rotated (`_refitGrid`, `_fittedGrid`). `_sectorBox` takes the box around the cone with the arc pushed out by `FIT_MARGIN_FRACTION` of its range (the apex gets no margin: behind the radar is its wall), the box grows to take in every stored zone (`_zonePoints`), `_roundOut` moves each edge out to a whole grid step of the map's unit (1 m, or 2 ft at the 6 m range), leaving an edge within `FIT_EDGE_SLACK_MM` of a step on that step: the card saves zones in whole mm and a feet edge rarely is one (22 ft is 6705.6 mm), so without the slack a zone drawn to the edge grew the map a step when its save echoed back. The step depends on the span, so the rounding repeats until the step settles; when two steps take turns (rounding out to the larger can leave a span narrow enough for the smaller), the larger is used. `_fittedGrid` returns that step, `_refitGrid` keeps it with its unit in `_fitStep`, and `_computeGridMetrics` draws both axes at it (`_fittedStep`; a YAML grid, or a unit changed since the fit, picks a step per axis), so every edge lands on a grid line and X and Y never differ where float error put a step at exactly 40 px. Then `_shapeFit` grows the short side in whole steps until the height is between `FIT_MIN_ASPECT` (0.75) of the width and the width, toward the side the radar faces along that axis (so a wall-mounted radar stays on the edge it is mounted on) or evenly when it faces neither way. Facing ahead, a 120 degree, 6 m cone fits a grid about 12 m wide by 9 m deep. `_sizeCanvas` then gives a fitted grid a canvas 800 px wide and as tall as the grid's own shape, and sets the same `aspect-ratio` on `.canvas-container`, so a meter is as long across as down; a YAML grid keeps the square 800 by 800 canvas. The grid refits when a payload arrives (`_applyZoneConfig`), when the rotation slider is released or reset (`_refitAndDraw` on `change` and double-click, never on every `input` step, which would resize the canvas under the dragging finger), and when the map's unit changes; it never refits while a shape is being drawn (`isDrawing`), because a drag holds its start point in canvas pixels. Every path that ends or drops a gesture calls `_refitAndDraw` (a rect or ellipse save in `endDrawing`, `finishPolygon` whether or not it saves, Escape, `cancelDrawing`, which the outside press, `mouseleave` and `touchcancel` reach, and a mode change in `_setDrawMode`), so a payload or unit change that arrived mid-gesture is fitted once it ends; the save's echo fits again too. The fitted canvas can be shorter than the five polygon buttons on a phone, so `#modeGroup` wraps into a second column through a CSS container query (`container-type: size` on `.canvas-container`, `max-height: calc(100cqh - 44px)`); browsers without container queries keep the single column.

Captions: with `unit_display` on, `_rangeLabel` draws "Radar range 6 m (20 ft), 120°" (`_rangeText`; feet first in feet mode) centered just past the arc on the line the radar faces, or just inside it, and leaves it out when it fits in neither place, as on a YAML grid that cuts the arc off. The help line under the map (`_renderInfo`, `#gridInfo`) gives the grid extents in the map's unit and ends with "Radar range: ..."; it is rewritten without rebuilding the card when the unit or the fit changes. Cone rings stay 1 m apart in meters and 4 ft apart in feet.

`getStubConfig` seeds no `grid` and no `grid_units` and sets `unit_display: true`, so a card added from the picker is fitted and in the viewer's units like the dashboard's cards (X42).

Drawing: only the primary mouse button and touch draw (`startDrawing` and `endDrawing` return when `e.button !== 0`). A touch gesture follows the finger that started it: `startDrawing` ignores a touchstart with more than one touch and records `changedTouches[0].identifier` as `_activeTouchId`; `_getPointFromEvent(e, touchId = this._activeTouchId)` reads that finger from `touches`, then `changedTouches` (a lifted finger is only there), and returns null when the finger is absent, the canvas has no layout box, or the point is not finite. `draw` and `endDrawing` ignore touch events whose `changedTouches` lack the tracked finger (`_carriesTrackedTouch`). Pointer moves only record `_cursorPoint` and call `drawGrid()`, which rebuilds every preview from state. A rect or ellipse drag is canceled by leaving `.canvas-container` (mouseleave), by a `touchcancel` that includes the tracked finger (`_cancelTouch`), by a press elsewhere in the card, and by an end point that is null; the rect branch of `endDrawing` also cancels when the rounded bounds have no area, mirroring the backend's strict `<` check in `_normalize_rect`. A polygon is a multi-click session: leaving the canvas or a `touchcancel` only drops the rubber-band line and keeps the placed vertices. It is canceled by Escape, by a mousedown or touchstart elsewhere in the card (`_outsideClickHandler`, a document capture listener added in `_attachGlobalListeners`), by locking the grid and by a real draw-mode change; Backspace and the Undo point button remove the last vertex (`_popPolyPoint`). `_outsideClickHandler` and the window `keydown` listener (`_onKeyDown`) read `event.composedPath()` because a document or window listener sees the target retargeted to the outermost shadow host; presses on the overlay buttons inside `.canvas-container` (Finish, Undo point, mode menu, lock, undo) do not cancel, and keys whose origin is an input, textarea, select or contenteditable element are left to that field. A double-click or double-tap finishes the polygon only when the second tap lands within `POLY_DOUBLE_TAP_SLOP_PX` (24 CSS px) of the last vertex and within 350 ms of it (`_isPolyFinishTap`); the finishing tap is never stored, and `finishPolygon` drops consecutive identical vertices, so a polygon with fewer than 3 distinct vertices is not saved. `_setDrawMode` with the mode already active (including the call at the end of every `render()`: a theme flip, a same-radar `setConfig`, load-error recovery) leaves a shape in progress alone; only a real mode change (`_resetDrawingState`) or a retarget to another radar drops it. A gesture whose selected zone disappears mid-drag is dropped, and ellipse corners are clamped to the grid before the radii are derived.

Zone manager: `_renderZoneManager` rebuilds every row on each payload, but first `_captureZoneNameDrafts` records each input whose value differs from the name its row was built with (`data-stored-name`, keyed by `data-zone-id`) and the focused input's selection; after the rebuild `_restoreZoneNameDrafts` puts those values back on the rows of zones still listed and restores focus (`preventScroll`) and `setSelectionRange`. Save looks the zone up in `zoneConfig` by id at click time. When `_zoneIsUnsaved(zoneId)` holds (a payload has arrived, its `zones` lacks the id, and `this.zones` holds no local geometry for it) Save sends `{device_id, zone_id, shape: "none", data: null, name}`, which creates a zone only the YAML named; otherwise, and always before the first payload, it sends the name-only `{device_id, zone_id, name}`. Delete is not undoable: it drops that zone's entries from the undo snapshot, so Undo cannot re-create the deleted zone or overwrite a zone added later under the freed id, while entries for other zones stay undoable. Add Zone takes the next free id and sends `{device_id, zone_id, shape: "none", data: null, name}`.

`ZoneMapCardEditor` (`editor.ts`, element `apollo-radar-zone-map-card-editor`) edits `device_id`, `title`, `dark_mode` and `start_locked` using `ha-device-picker`, `ha-textfield` and `ha-selector`; `firstLd2450DeviceId` fills the `device_id` of `getStubConfig`. `api.ts` is the typed websocket client described under Runtime data flow.

## Contracts between frontend and backend

**Websocket commands** (`websocket.py`, `api.ts`): `apollo_mmwave/zones/get {device_id}` returns one payload; `apollo_mmwave/zones/subscribe {device_id}` returns null then pushes the same payload on every change (one push per zone edit). Error codes: `not_loaded` and HA's `unknown_command` (both retried by the zone card; `api.ts` exports `ERR_UNKNOWN_COMMAND`) and HA's `not_found` (terminal). The card's reload recovery also uses HA's `config_entries/subscribe`, which is not admin-gated in any supported version. None of the four commands requires admin.

**Calibration websocket commands** (`calibration/api.ts`): `apollo_mmwave/calibration/get {device_id}` returns one payload; `apollo_mmwave/calibration/subscribe {device_id}` returns null, then immediately pushes the current payload, then every change. Error codes: `not_loaded` (retried by the calibrate card) and `not_found`; the calibrate card does not retry `unknown_command`. The payload (`CalibrationPayload`) is `{job: JobState | null, snapshots: [{id, taken_at, reason, count}], last_result: CalibrationResult | null, interrupted: InterruptedMarker | null, entities: EntitiesInfo | null}`, where `EntitiesInfo` names the radar's `query_params_button` (null when it has none); `JobState` carries `job_id`, `kind`, `status`, `sub_phase`, `elapsed_s`, `remaining_s`, `duration_s`, `settle_s`, `samples`, `peaks` (gate keys are strings on the wire), `writes_done`, `writes_total`, `apply`, `cancel_requested` and `engineering_mode_turned_on`; `CalibrationResult` is the backend's result payload (per-gate `move`/`still` channel results with `peak`, `p95`, `old`, `new`, `samples`, `written`, `confirmed`, `actual`, `flags`, `skipped`, plus `apply` (false for a preview, null on a restore), `changed`, `unchanged`, `writes_done`, `writes_total`, `unverified`, `gates_off`, `warnings` and `error`; a restore result has `gates: []` and adds `restored`, `missing` and `restored_from: {id, taken_at}`); `InterruptedMarker` carries `phase` and `left_on` as independent facts. `warnings`, `flags` and `error.code` are codes; `calibration/model.ts` owns every sentence. The card calls `apollo_mmwave.calibrate_gates` with `{device_id, ...calibration block, apply?: false}`, `apollo_mmwave.cancel_calibration {device_id}` and `apollo_mmwave.restore_gate_thresholds {device_id, snapshot_id?}` (without `snapshot_id` from every Undo button, because the newest snapshot is the one its label names; only "Try again" on a failed restore passes the id of the snapshot it was restoring), `switch.turn_on` / `switch.turn_off {entity_id}` for the chart overlay and the interrupted banner, and `button.press {entity_id}` on the query-params button for "Read settings from the radar". The setup card in gate mode opens the same subscription (`CalibrationJobWatch`, with the same `not_loaded` retry) and reads only whether a job runs; its own writes are `switch.turn_off` on Radar Engineering Mode and that `button.press`. The service schemas, the bus events, the `apollo_mmwave.calibration` storage file and the backend side of these commands are documented with the backend modules.

**Calibration services** (`calibration.py`, `services.yaml`; all `extra=vol.PREVENT_EXTRA`, all registered with `SupportsResponse.OPTIONAL`, all plain services rather than admin ones because each checks `POLICY_CONTROL` for the calling user on the entities the job writes): `apollo_mmwave.calibrate_gates {device_id: str | [str], duration_s?: 15..600 = 60, settle_s?: 0..120 = 15, margin?: 0..50 = 15, margin_pct?: 0..100 = 35, kind?: both | move | still = both, apply?: bool = true, wait?: bool = false}` returns `job.public_state()` when the job starts, or the result payload with `wait: true`; `apollo_mmwave.cancel_calibration {device_id}` returns `{cancelled: bool}` and is a no-op without a job; with one, the caller must be allowed to control every entity the job writes (`_job_entities`: the engineering mode switch and the planned thresholds, or a restore's targets), the check that job's pre-flight ran, or the call is refused with `not_allowed`; `apollo_mmwave.restore_gate_thresholds {device_id, snapshot_id?, wait?}`. `margin` and `margin_pct` may not both be 0 (checked in the pre-flight, not the schema). Pre-flight refusals are `ServiceValidationError`s with the translation keys `unknown_device`, `multiple_devices`, `calibration_running`, `no_gate_entities`, `engineering_mode_missing`, `device_offline`, `background_correction_running`, `thresholds_not_numeric`, `margin_zero`, `not_allowed` and `no_snapshot` (`translations/en.json` `exceptions`). Job failures are codes on `result.error` (`engineering_mode_not_confirmed`, `no_energy_data`, `engineering_mode_lost`, `background_correction_started`, `thresholds_not_numeric`, `snapshot_failed`, `device_offline`, `write_failed`, `not_allowed`, `cancelled_by_shutdown`, `unexpected`, and `no_gate_data`, which the original calibration spec did not list) with the sentences in `ERROR_MESSAGES` (`device_offline` and `write_failed` have reworded zero-write forms without the Undo clause), which the card shows verbatim after "Calibration failed: ".

**Calibration bus events and signal**: `apollo_mmwave_calibration_started {device_id, job_id, kind}` and `apollo_mmwave_calibration_finished {device_id, job_id, kind, status, outcome, changed, snapshot_id}` (`EVENT_CALIBRATION_STARTED`, `EVENT_CALIBRATION_FINISHED`). The internal dispatcher signal `apollo_mmwave_calibration_updated` (`SIGNAL_CALIBRATION_UPDATED`) carries the device id as its only positional argument and fires on every status or sub-phase change and once per tick, never more often.

**Calibration storage schema** (`calibration_store.py`): key `apollo_mmwave.calibration`, version 1, shape `{"devices": {<device_id>: {"snapshots": [{"id", "taken_at", "reason": "calibrate" | "restore", "job_id", "values": {<entity_id>: {"value", "unique_id", "platform"}}}], "last_result": <result payload> | null, "interrupted": {"job_id", "kind", "phase": "engineering" | "applying" | null, "started_at", "engineering_mode_turned_on", "snapshot_id", "left_on"} | null}}}`. Snapshots are newest first and capped at `MAX_SNAPSHOTS`; `unique_id` and `platform` let a restore re-resolve a renamed entity. `apollo_mmwave.zones` and `store.py` are untouched by the calibration feature.

**Payload** (`websocket.py` `_payload`, `api.ts` `ZoneConfig`): `{zones: {"<id>": {shape, data, name?} | {}}, entities: [{x, y}] | null, rotation_deg: number | null, label: string | null, input_units: string | null, display_units: string | null, suggested_entities: [{x, y}]}`. The server always sends `input_units` (null means millimeters), the unit for target sensors that have no length unit of their own, and `display_units` (`"m"`, `"ft"`, or null when no unit is saved and the card follows Home Assistant's unit system); the TypeScript interface declares both optional (`display_units?: DisplayUnits | null`). Zone ids are ints in the store and strings on the wire. A zone value of `{}` is the placeholder `migration._legacy_zone_definition` stores for a pre-1.2 zone whose restore data was lost; it means no geometry, `api.ts` `ZoneDef` declares `shape?` and `data?` optional to match, and the card lists such a zone (as `Zone N` or its YAML name) and draws nothing for it. `entities: null` means never configured (the card uses `suggested_entities`); `[]` means cleared.

**Service** `apollo_mmwave.update_zone` (`UPDATE_ZONE_SERVICE_SCHEMA` in `__init__.py`, `services.yaml`): registered with `async_register_admin_service`, so a call from a user who is not an administrator raises `Unauthorized` before anything is written (the card shows it as its "Could not save" toast), and calls with no user, such as automations, run (`tests/test_init.py::test_update_zone_is_admin_only`). at least one of `device_id` (str or one-item list) or deprecated `location`; when both are given, `device_id` wins and `location` is ignored without the deprecation warning. `zone_id` is an integer from 1 to 2**53 - 1 (`vol.All(vol.Coerce(int), vol.Range(min=1, max=_MAX_SAFE_INT))`), so 0 is refused, matching `services.yaml` ("1..N", selector min 1) and the card; a float is truncated (1.9 becomes 1). `shape` in `none`, `rect`, `ellipse`, `polygon`; `data` dict or null, read only together with `shape`. To clear a zone send `shape: none` (`data` omitted or null); `data: null` without a shape never cleared anything. `name`; `delete`; `rotation_deg` (coerced to float, then rounded and clamped to [-180, 180] by `_sanitize_rotation`; inf and nan are ignored, so the call carries no rotation); `input_units` in `INPUT_UNIT_FACTORS`; `display_units` in `m`, `ft` or `auto` (`m` and `ft` always count as a change, `auto` removes the saved unit and counts only while one is saved, so an `auto` with nothing saved is refused as "carried nothing to change" and creates no store entry); `entities` as `[{x: entity_id, y: entity_id}]`, where an empty list means no change; `clear_entities`, which wins over `entities`. Extra top-level keys are rejected. Coordinates that are not finite or exceed `_MAX_SAFE_INT` are treated as non-numeric (see `__init__.py`). Calls that would change nothing are refused with a warning and write, signal and fire nothing (`_call_changes_something`). The card sends: `{device_id, zone_id, shape, data}` for geometry (`updateHomeAssistantShape`), `{device_id, zone_id, name}` for rename of a stored zone, `{device_id, zone_id, shape: "none", data: null, name}` for a new zone and for the rename of a zone only its YAML names, `{device_id, zone_id, delete: true}` for delete, `{device_id, rotation_deg}` for rotation (`_persistRotation`), `{device_id, display_units}` with `m` or `ft` from the unit switch, and only for an administrator (`_chooseDisplayUnit`), and always adds `input_units` (`_saveZoneUpdate`). It never sends `entities`, `clear_entities`, `location` or `display_units: auto`.

**Geometry**: integer millimeters, X to the radar's right, Y away from the radar. `rect {x_min, x_max, y_min, y_max}` with strict `x_min < x_max` and `y_min < y_max`; `ellipse {cx, cy, rx, ry}` with radii floored at 1 mm; `polygon {points: [{x, y}]}` with `POLYGON_MIN_POINTS` to `POLYGON_MAX_POINTS` points (`const.py`). The rotation formula is the same in `binary_sensor.py` (`_build_point_rotator`) and `card.ts` (`_drawTrackedTargets`). Positive `rotation_deg` swings the device's facing direction toward its right (+X): 90 maps (x, y) to (y, -x), so a target straight ahead at (0, d) lands at (d, 0), and `drawDeviceCone` uses the same sign (the cone at +90 points to +X). Do not call it "clockwise": the card's canvas is Y-down, so on screen the motion looks counterclockwise. `services.yaml` `rotation_deg` and the `_build_point_rotator` docstring carry the same sentence.

**Bus event** `apollo_mmwave_zone_updated` with data `{"device_id": "<ha device id>"}` (`EVENT_ZONE_UPDATED`, fired from `_notify_zones_updated`), only for `update_zone` calls that changed something. The internal dispatcher signal `apollo_mmwave_zones_updated` (`SIGNAL_ZONES_UPDATED`) carries the device id as its only positional argument; the LD2450 cache invalidation sends the signal without the bus event.

**Storage schema** (`store.py`): key `apollo_mmwave.zones`, version 2, shape `{"devices": {<device_id>: {"zones": {"<n>": {shape, data, name?} | {}}, "entities"?: [...], "rotation_deg"?: int, "label"?: str, "aliases"?: [str], "input_units"?: str, "display_units"?: "m" | "ft"}}, "orphans": {<v1 location>: same}}`. `aliases` holds every other v1 or legacy location name that merged onto the device (the first name stays `label`). `input_units` is absent for millimeters and is restored on load only when it is a key of `INPUT_UNIT_FACTORS`. It only scales readings from target sensors with no length unit of their own; a sensor's own unit wins. `display_units` is absent when the card follows Home Assistant's unit system and is restored only when it is `m` or `ft`; it is display only, so presence detection and the zone sensors never read it. Version 1 files have `{"locations": {<display name>: {zones, entities, rotation_deg}}}`.

**Entity unique ids**: `{device_id}_zone_{n}` and `{device_id}_zone_{n}_presence`. The formats are spelled out in each module that needs them: `_zone_entity_unique_ids` in `__init__.py` (used by `_update_registry_names` and `_remove_zone_entities`), the `_attr_unique_id` lines in `sensor.py` and `binary_sensor.py`, and `new_uid` in `migration.py`. Likewise the base names `Zone {n}` and `Zone {n} presence` appear in `_update_registry_names` and the platforms' `_attr_name`. `tests/test_zone_entities.py::test_platform_unique_ids_match_the_service_lookup`, `tests/test_migration.py` and `tests/test_sensor.py` pin them.

**Custom element names**: `apollo-radar-zone-map-card` (`card.ts`, `const.py` `CARD_TYPE` as `custom:apollo-radar-zone-map-card`, `editor.ts` `ZONE_MAP_CARD_TYPE`), `apollo-radar-zone-map-card-editor` (`editor.ts`), `apollo-radar-distance-card` (`distance-card.ts`), `apollo-radar-gate-energy-card` (`gate-energy-card.ts`), `apollo-radar-calibrate-card` (`calibrate-card.ts`, `CALIBRATE_CARD_TAG`), `apollo-radar-setup-card` (`setup-card.ts`, `SETUP_CARD_TAG`; the strategy writes `custom:apollo-radar-setup-card` in `strategy-core.ts`, with `radar: "gate"` for the gate radar's copy), `apollo-radar-slider-row` and `apollo-radar-slider-lock-row` (entities card rows defined in `slider-lock-rows.ts`, `SLIDER_ROW_TAG` and `SLIDER_LOCK_ROW_TAG` in `slider-lock.ts`; the strategy writes them as `custom:` rows in `strategy-core.ts`), `ll-strategy-{dashboard,view,section}-apollo-radar-tuning` (`strategy.ts`) for strategy type `custom:apollo-radar-tuning` (`const.py` `DASHBOARD_STRATEGY_TYPE`).

**Static URL paths**: `/apollo_mmwave/apollo-radar-tuning.js` and `/apollo_mmwave/apollo-radar-zone-map-card.js` (`const.py` `STATIC_URL_BASE`, `JS_BUNDLES`), served from `custom_components/apollo_mmwave/www` with `?v=<manifest version>` (`frontend.py`). Bundle names must match `frontend-src/vite.config.ts` and `vite.zone-map.config.ts`.

**Dashboard strategy config**: `{"strategy": {"type": "custom:apollo-radar-tuning", "devices"?: [device ids], ...user keys}}` written by `frontend.py` `_desired_config` from the `dashboard_devices` option, when the dashboard is created and when an administrator saves a new selection in the options flow, and it rewrites only `type` and `devices`; read by `StrategyConfig` (`strategy-core.ts`: `device_id`, which takes precedence over `devices`; `devices`; `distance_unit`, passed only to each device's distance card; `calibration` with `duration_s`, `settle_s`, `margin`, `margin_pct`, copied onto every generated calibrate card). `distance_unit` accepts exactly the lowercase tokens `mm`, `cm`, `m`, `in`, `ft` and `yd` (`isValidUom`); any other value is ignored without a warning and the card follows HA's unit system (`defaultDistanceUnit`). A `device_id` typed into the raw config of the integration's own dashboard survives a new selection and overrides the "Dashboard devices" option.

**Gate entity naming regexes**: `entities.ts` `GATE_PATTERNS` (`_g(\d+)_(move|still)_(threshold|energy)(?:_\d+)?$` per slot) and the `SCALAR_PATTERNS` suffixes for the engineering-mode switch, the LD2410 max move/still gate numbers, the LD2412 min/max gate numbers, the radar-target and moving-target binary sensors, and the LD2412 `_ld2412_start_dynamic_background_correction` button, `_ld2412_dynamic_background_correction_status` binary sensor, and the `_ld2412_query_params` and MSR `_query_params` buttons have a Python twin in the backend's `gates.py`; change both together, as with the LD2450 regexes.

**LD2450 naming regex**: `(?:_ld2450)?_target_(\d+)_x(?:_\d+)?$` and the `_y` twin must stay identical in `ld2450.py` (`TARGET_X`, `TARGET_Y`) and `ld2450.ts`. Only the regexes are shared; pairing and the disabled filter are backend-only (see `ld2450.py`).

**Tests that pin these contracts**: `tests/test_contracts.py` reads files from the repository root and checks that the `TARGET_X` / `TARGET_Y` literals in `frontend-src/src/ld2450.ts` equal the Python patterns, that the committed `www/apollo-radar-tuning.js` registers `ll-strategy-dashboard-` plus `DASHBOARD_STRATEGY_TYPE` without its `custom:` prefix, that `www/apollo-radar-zone-map-card.js` registers `CARD_TYPE` without the prefix, that `ZONE_MAP_CARD_TYPE` in `editor.ts` equals `CARD_TYPE`, and that the `SENSOR_LENGTH_UNITS` table in `zone-map/card.ts` equals `SENSOR_UNIT_FACTORS`. The element checks read the committed bundles because those are what HA serves. `frontend-src/test/bundle-tuning.test.ts` and `bundle-zone-map.test.ts` go further and run the committed bundles in happy-dom, one bundle per file so their registrations never share a window: each bundle must parse as one module with no import, define every tag that `registerElement` or `customElements.define` gives it in the sources (`test/bundle-sources.ts` follows the imports from each entry), add its `window.customCards` entries once (the tuning bundle also its `customStrategies` entry), and leave the other bundle's tags undefined. The calibrate, gate energy, distance, setup and zone map cards must render and repaint after a new `hass`, a pushed payload, a new config or (the setup card) a button press, and no Lit card may hold a reactive property as an own instance property. That last check fails on a build whose TypeScript transform emits class fields (`useDefineForClassFields: true`), which shadow Lit's accessors so the cards stop updating. Each bundle must also define its tags again through a model of HA's registry polyfill once `<home-assistant>` is defined (`test/registry-polyfill.ts`, shared with `test/register.test.ts`), and a second evaluation of the tuning bundle must leave one picker entry per card and strategy and the first copy's elements. Those checks stay narrow, so `npm run test:bundles` (`vitest.bundles.config.ts`) also runs every suite that imports a card, strategy or zone map module against the committed bundles; see "Build, test and CI". `tests/test_bundles_exist.py` fails when a name in `JS_BUNDLES` is not a file under `www/` (at runtime a missing bundle is only a warning). The model list is pinned in both directions (see `config_flow.py`), and the version copies by `frontend-src/test/build.test.ts` and `tests/test_versions.py`.

## Build, test and CI

The frontend is built and tested from `frontend-src/` (`frontend-src/package.json`):

```sh
cd frontend-src
npm ci              # installs exactly the lockfile, as CI does
npx tsc --noEmit    # type check src and test (tsconfig.json); zone-map/card.ts is @ts-nocheck
npm test            # vitest run (vitest.config.ts)
npm run test:bundles # the card, strategy and zone map suites against www/ (vitest.bundles.config.ts)
npm run build       # vite build && vite build --config vite.zone-map.config.ts
npm run watch       # watch:tuning and watch:zone-map side by side (Ctrl+C stops both)
```

The toolchain is Vite 8.3 (Rolldown bundles, Oxc transforms TypeScript), vitest 5, happy-dom 21, TypeScript 7.0 (the native `tsc`, used only to type check) and terser 5.51, all dev dependencies; `lit` (3.3) is the only runtime dependency and the only one that reaches the shipped bundles. CI builds on Node 22, so rebuild `www/` with a Node 22 toolchain to match the committed output. `npm run build` runs Vite twice on purpose (`vite.config.ts`): a single multi-entry build would hoist `src/register.ts` into a shared chunk that HA never fetches, so each bundle is built standalone and written to `../custom_components/apollo_mmwave/www/<name>.js` with `emptyOutDir: false`, `minify: "terser"` and `rolldownOptions.output.codeSplitting: false` (Rolldown's name for `inlineDynamicImports`). `npm run watch` keeps two separate Vite processes for the same reason; it uses POSIX shell job control (`a & b & wait`), so on Windows with npm's default `cmd.exe` run `npm run watch:tuning` and `npm run watch:zone-map` in two terminals. `build.target` is pinned to Vite 6's old default (`es2020`, `edge88`, `firefox78`, `chrome87`, `safari14`), because Vite 8's default (Safari 16.4, Chrome 111) leaves class static blocks in the output that iOS 15 Safari cannot parse. Oxc reads `experimentalDecorators` and `useDefineForClassFields: false` from `tsconfig.json`, so Lit's decorators compile to legacy `__decorate([...], Card.prototype, "hass", void 0)` calls and field initializers to constructor assignments, with no class field that would hide Lit's accessors. The two outputs, `apollo-radar-tuning.js` (from `src/index.ts`) and `apollo-radar-zone-map-card.js` (from `src/zone-map/card.ts`), are committed because the Python side serves exactly those filenames (`const.py` `JS_BUNDLES`) and HACS users never run npm. Any change under `frontend-src/src` must therefore be followed by a rebuild and a commit of `www/`. Up to 2.2.2 the bundles shipped unminified, comments included, because Vite 6's terser plugin skipped ES library output. Vite 8 runs terser on it, keeping `/* @__PURE__ */` annotations, and strips comments except lit's `@license` notices (kept by `rolldownOptions.output.comments: { legal: true }`) and comments inside template strings (CSS in the card styles), so most comment-only edits no longer change a bundle; rebuild anyway and let the bundle-sync step decide.

`vitest.config.ts` runs `test/**/*.test.ts` in happy-dom with `TZ=UTC` and `test/setup-canvas.ts` as a setup file, and allows `../custom_components/apollo_mmwave` in `server.fs.allow` because `test/registry-detection.test.ts` imports `config_flow.py` with `?raw` to check `MMWAVE_MODELS` and the `test/bundle-*.test.ts` files import the committed bundles from `www/`. Two Lit problems seen on happy-dom 14 shaped the tests: child-part markers at a template root and inside `<svg>` were mis-cloned, and a `<button>` reported `tabIndex` -1 unless it carried `tabindex="0"`. So render helpers keep their bindings inside an element, `charts/gate-energy-chart.ts` keeps its SVG in a nested template, the chart's overlay button carries `tabindex="0"`, and both chart renderers are asserted on their `TemplateResult` through `flat` in `test/template-markup.ts` rather than on the DOM (`test/distance-chart.test.ts`, `test/gate-energy-chart.test.ts`). `vitest.config.ts` notes that the problems were not re-checked after the move to happy-dom 20. A probe during the audit's documentation pass (happy-dom 20.14.6) rendered both charts' SVG children and a root-level child part into the DOM and gave a plain `<button>` `tabIndex` 0, so the workarounds look unnecessary now; they still work. Frontend coverage is not configured.

`vitest.bundles.config.ts` reuses that config for the suites that import `../src/cards/calibrate-card`, `distance-card`, `gate-energy-card`, `setup-card`, `slider-lock-rows`, `../src/strategy`, `../src/zone-map/card` or `editor` (it reads `test/` to find them, leaving out `test/bundle-*.test.ts`). An alias swaps each of those modules for the file at the same path under `test/bundle-shims/`, which exports the class the committed bundle defined (`shouldRegenerate` for the strategy), plus the source module's other exports for `calibrate-card`, `setup-card`, `slider-lock-rows` and `editor`. The setup file `test/bundle-shims/load-bundles.ts` loads both bundles into each suite's window before the suite imports anything and records the class each defined per tag, so a shim throws for a tag its bundle lost instead of handing out the class the source module registered in its place. Two tests compare against a source module's own object and are skipped there by `testNamePattern`: `cards.test.ts` "styles the gate-energy chart's legend from the chart module" and `strategy.test.ts` "stays one entry when the bundle is evaluated again" (`bundle-tuning.test.ts` evaluates the bundle twice instead). Helpers that only the sources export, such as the chart renderers in `charts/`, are still tested from the sources alone, and so is the slider lock store: `test/slider-lock.test.ts` imports only `cards/slider-lock.ts`, which defines no element, while `test/slider-lock-rows.test.ts` runs in both modes and, since the bundle's rows use the bundle's own copy of the store, drives the lock only through the rows. If a bundle test misses a file just added under `src/` (`test/bundle-sources.ts` reads the sources through `import.meta.glob`), delete `frontend-src/node_modules/.vitest-cache` and run it again.

The Python suite (`tests/`) needs Python >= 3.14.2. Locally, after `scripts/bootstrap`:

```sh
uv pip install -r requirements-test.txt   # test harness into the .venv bootstrap made
uv run --no-project pytest tests/         # or .venv/bin/python -m pytest tests/
```

Do not run `uv venv` after `scripts/bootstrap`: uv refuses an existing `.venv`, and `--clear` would discard ruff and pre-commit. `uv venv && uv pip install -r requirements-test.txt` is the clean-checkout form CI uses, and it installs no ruff. Coverage needs no extra install, because `pytest-homeassistant-custom-component` pins `pytest-cov` and `coverage`: append `--cov=custom_components/apollo_mmwave --cov-report=term-missing` (the `.coverage` file is gitignored). `requirements-test.txt` pins `pytest-homeassistant-custom-component` (which pins a matching `homeassistant`, 2026.10.0 at the time of writing) and `home-assistant-frontend`, needed because `manifest.json` depends on `frontend`. Keep the frontend's YYYYMMDD prefix aligned with the HA release; an exact match is not required, because the harness sets `skip_pip` and HA never checks the frontend requirement under test. A `.venv` created before a pin change keeps the old harness until `uv pip install -r requirements-test.txt` runs again (`scripts/bootstrap` alone does not upgrade it), so check `homeassistant` in `.venv` before trusting a local backend run. CI tests only 2026.10.0, and no job tests the `hacs.json` floor (2026.8.1). During the audit the local `.venv` happened to hold 2026.8.1 (REVIEW_REPORT X56), which is where the HA APIs the calibration feature relies on were checked against the floor. `pyproject.toml` sets `testpaths = ["tests"]` and `asyncio_mode = "auto"`. `tests/conftest.py` auto-enables custom integrations; fixtures register an ESPHome radar device with three target pairs, plus gate-radar fixtures for the calibration tests.

The copy style for user-facing text (no em dash, "R PRO-1") is enforced by `tests/test_translations.py` for `translations/en.json` and `services.yaml` and by `frontend-src/test/copy.test.ts` for the frontend's profile tips, help cards, empty dashboards, card picker entries, the setup card's lines and the slider lock's copy.

CI (`.github/workflows/`):

- `lint.yml`: Python 3.14, uv, `uv venv` plus `uv pip install "$(grep -E '^ruff==' requirements.txt)"` (ruff only; the Home Assistant pin is exercised by the pytest job), then `scripts/lint-check`.
- `test.yml` job `pytest`: `uv venv`, `uv pip install -r requirements-test.txt`, `uv run --no-project pytest tests/ -q --cov=custom_components/apollo_mmwave --cov-report=term-missing`. The log ends with a per-module coverage table listing missed lines; no threshold is enforced, so a coverage drop never fails CI.
- `test.yml` job `frontend` (working directory `frontend-src`): `actions/setup-node` with Node 22 (npm cache keyed on `frontend-src/package-lock.json`), `npm ci`, `npx tsc --noEmit`, `npm test`, `npm run test:bundles`, then `npm run build` followed by `git status --porcelain -- ../custom_components/apollo_mmwave/www` and `test -z` on that output. The step fails when a fresh build modifies, deletes or adds any file under `www/`, including an untracked bundle a rename leaves behind (with `emptyOutDir: false`, `git diff` alone would not see it); the status lines are printed first so the log names the files out of sync.
- `validate.yml`: hassfest and HACS validation (`category: integration`, no checks ignored) on push to `main`, pull request, daily cron and manual dispatch. The HACS brands check passes on the local `custom_components/apollo_mmwave/brand/icon.png`; the action falls back to the home-assistant/brands list only when that file is missing.

`.github/dependabot.yml` asks for daily version updates for devcontainers (Features only, never the base image), GitHub Actions, pip and npm in `/frontend-src`. It ignores `homeassistant`, `pytest-homeassistant-custom-component` and `home-assistant-frontend`, which are bumped by hand in one commit (`homeassistant==` in `requirements.txt`, the harness release that pins the same HA, and a matching frontend); that also suppresses Dependabot security-update PRs for the two test pins, though alerts still appear in the Security tab. An npm bump that changes the built output (lit, vite, terser) fails the frontend job's bundle-sync step until `npm run build` is run and `www/` is committed on that PR, which is expected. A bundle change also needs a version bump (the `?v=` cache buster), so such a bump ships as a release: the Vite 8, TypeScript 7 and terser 5.51 bumps went out in 2.2.3, together with the setup-uv bump.

Local development uses `scripts/develop`, which sources `./.venv/bin/activate` when it exists (so the pinned `hass` runs from a plain shell; without a `.venv` it falls back to whatever `hass` is on `PATH`), creates `config/` with `hass --script ensure_config` when it is missing, and runs `hass --config config --debug` with `./custom_components` on `PYTHONPATH` and `config/configuration.yaml` (debug logging for `custom_components.apollo_mmwave`). The devcontainer (`.devcontainer.json`) uses the `mcr.microsoft.com/devcontainers/python:3.14` image, runs `scripts/setup` (bootstrap into `./.venv`) as its `postCreateCommand` and `scripts/motd` on start, and points VS Code's interpreter at `${containerWorkspaceFolder}/.venv/bin/python`, so `hass`, `ruff` and `pre-commit` come from that venv. `scripts/help` (printed by `scripts/motd`) lists each script with the text of its `# script/<name>:` header, so a new script needs that header (60 characters or fewer, or it is truncated).

## Known limitations

These were checked against the code at the end of the full audit (October 2026). `CHANGELOG.md` lists the user-facing ones under "Known limitations" in its "Upgrading to 2.0" notes, and `docs/configuration.md` mentions more of them next to the feature they affect. `REVIEW_REPORT.md` at the repository root records what the audit fixed and, under "Flagged and left alone", every item it deliberately did not fix (X01 to X61), each with a recommendation. Most flagged items also carry a `TODO(REVIEW_REPORT.md <id>)` comment at their code site (Python ones end the first line with `# noqa: FIX002, TD003`, because ruff `select = ["ALL"]` reports every TODO), and `grep -rn --exclude-dir=www "TODO(REVIEW_REPORT.md" custom_components frontend-src/src .github .pre-commit-config.yaml` lists them. The list below is the subset a maintainer is most likely to run into; the ids point at the full entries.

Zones, the store and `update_zone`:

- The card owns `input_units` in practice: `_saveZoneUpdate` sends its own YAML value on every zone and rotation write and the card never reads the payload's `input_units`, so a unit set through the service is overwritten by the next card save. Since 2.2.7 it only applies to target sensors with no length unit of their own, so this matters for DIY sensors only. `yd` is accepted by the backend (`INPUT_UNIT_FACTORS`) but absent from the card's `LENGTH_UNITS`, which normalizes unknown units to `mm` (X04). The store itself now keeps `input_units` across restarts and reloads.
- `zone_id: .inf` and a `rotation_deg` integer too large for a float raise `OverflowError` out of the service call instead of a validation error, because `vol.Coerce` catches neither; no state changes.
- A zone 0 created before `zone_id` gained its lower bound still loads and has entities, but neither the service nor the card can address it; remove it by editing `.storage/apollo_mmwave.zones` with Home Assistant stopped.
- Zones stored under a device id that left the registry for good (replaced hardware, or a radar re-added after HA's 30-day deleted-device retention) cannot be removed through `update_zone`, and their device-less entities are re-created with a warning on every setup (X08).
- `delete: true` for a zone the store does not hold still mints an empty store entry, saves, and fires the event (X15). A blank `name` is stored and pins the bare base as the registry name (X14). A name sent on the call that creates a zone never reaches the registry (X01). `location` is ignored silently when `device_id` is also given (X12), and labels that slugify alike resolve by store order with no warning (X16).
- The stored `label` is a one-time copy of the v1 display name: it is never refreshed after a device rename and is absent for devices first configured on 2.x, yet the payload sends it and the zone card uses it as its heading when the card has no `title` (X27).
- Configured `entities` pairs do not follow an entity id rename; presence then reads off with no log (X07). Zone presence reads `off`, not `unavailable`, while the radar is offline (X09).
- A pre-2.0 zone entity that cannot move to its new unique id logs the "is stale and can be deleted" warning on every setup and reload until it is deleted (X29).
- The retry details of `zone_entities.py` were flagged but not verified: a disabled entity is constructed on every signal before it is skipped, an add that raises inside HA instead of aborting is never retried, the removal nudge fires before HA frees the old state so a retry could get a `_2` entity id, and the module docstring describes a race the pinned HA cannot produce (X58).

Frontend registration and the dashboard:

- JS cache busting uses only the `manifest.json` `version` for the `?v=` query, with Home Assistant's long-lived cache header on the static path. A `www/` rebuild without a version bump is invisible to browsers that cached the old module.
- Ownership is the recorded id and url path plus a config that is still this strategy. Lovelace derives a row's id from its url path, so if the user deletes the integration's dashboard and builds a new one on `apollo-mmwave` whose config is exactly this strategy, the integration cannot tell it apart from its own: a device selection is written into it, and removing the entry, or the options flow's remove step, deletes it. Any other dashboard on that path is left alone.
- A dashboard made by 2.2.5 or earlier keeps `require_admin` False after the upgrade: adoption writes nothing, so it stays visible to every user until an administrator changes it in Settings > Dashboards.
- A deleted `/apollo_mmwave/` Lovelace resource row comes back only at the next Home Assistant restart, not on an integration reload, because the once-per-run asset guard also skips the resource reconciliation (X28).
- Editing a strategy view in the Home Assistant UI discards its cards; that is how Home Assistant treats strategy views. Use "take control" on the dashboard instead.
- Entities registered after the first detection do not add rows to an open dashboard, because they do not change `radarDeviceKey`. That includes a zone drawn since the page loaded, whose presence sensor joins the Zone presence card only after a reload (the empty card says so); a deleted zone's row hides itself at once, but once every listed zone is deleted the card shows its title over no rows, not the draw-a-zone hint, until a reload; and an entity enabled since then, such as the R PRO-1's Multi Target Tracking switch, which joins LD2450 Controls after a reload, or its chip firmware sensors, which join the Device card. The history's zone lines follow the same rule. The Radar setup cards, the built-in zones conditional card and the weak Wi-Fi note read live state and need no reload. Conversely, any radar's online/offline flip changes the key and rebuilds every tab, which drops an unfinished zone drawing on any tab (X31).
- The view and section strategies render nothing, with no message, when no device matches (X30); with several devices the view strategy runs their sections together with no separator (X38). An R PRO-1's six sections (four tuning, the zone map with its setup card, and the LD2450 status and controls) exceed HA's default of four columns, so the Zone Map and the LD2450 column wrap to a second row (X36).
- The MTR-1 firmware leaves most LD2450 names unprefixed ("Timeout", "Zone Type"), so `ld2450-entities.ts` reads them on the radar's own device only, after its base name, or by suffix for an id under another base. A second entity on the same device with such a name would be ambiguous, and the first in registry order wins. The base comes from `baseNameFromDevice`, the most common base among the device's entity ids; a device whose ids were renamed one by one to different bases falls back to suffix matching for the ids outside that base.
- The slider lock (see Slider lock) covers locked sliders only. Unlocked sliders behave like HA's own: a touch sets the value where it lands and cannot start a scroll, until the radar locks again (5 minutes without a change, or leaving the tab). On a locked slider, a gesture that starts sideways does not scroll the page (the shield is `pan-y`) and counts as a try. The lock is per page, not per user: every browser tab and device has its own, and a reload locks. A dashboard taken control of before 2.3.0 keeps plain number rows with no lock until the rows are added by hand (`docs/configuration.md` Card options). Locked sliders stay in the Tab order; their value keys go to the reminder toast. The gate tip under Move Thresholds says the sliders start locked even on a DIY build whose thresholds are all boxes.
- Restart Radar, Factory Reset Radar and the Device card's restart ask first through HA's button row (see Strategy). The LD2412's Start Dynamic Background Correction is still a plain button row that presses on one tap.
- The gate distances in the threshold row labels and the help card follow Home Assistant's unit system, not the strategy's `distance_unit` (which only the distance cards read), and are fixed when the dashboard is generated, so a gate size changed on the device shows after a reload.
- After a Home Assistant restart that interrupted a calibration, the calibrate card's interrupted banner can offer its own "Turn it off" beside the gate setup card's "Turn off Radar Engineering Mode". Both turn the same switch off; they were left separate.
- On an R PRO-1 tab both setup cards are titled "Radar setup"; only the line under the title ("LD2412 · <name>" or "LD2450 · <name>") and their place tell them apart.
- An invalid `distance_unit` ("CM", "feet") is ignored without a warning (X50).
- An R PRO-1 without the optional LD2412 still gets the LD2412 tuning cards. `APOLLO_MODELS` in `profiles.ts` maps every `r-pro-1` model to `LD2412_PROFILE`, and `deviceFromId` in `strategy-core.ts` falls back to that registry profile when `detectProfileFromEntities` finds no LD2412 entity. The help card and the Device card's restart follow the LD2450-only wording (`gateRadar` in `cardMap`), but the tab still shows an Auto-calibrate card that says the radar is offline with its buttons disabled (the backend's payload has `entities: null` because `resolve_gate_entities` finds no gate), "device not found" on both charts and no Controls card (ESP Reboot is on the Device card now), above a working zone map. The gate setup card is left out, because none of the settings it checks exists. `docs/configuration.md` tells users to use the zone map.

Zone map card:

- Reload recovery uses `config_entries/subscribe`, which every user can open. The bounded `RETRY_DELAYS_MS` retry covers a card that misses the entry's `loaded` event (for example when the entry finishes loading between the failed open and the feed subscribe, or when the feed is refused); once the retries run out without that event, the card stays on the "still not loaded" message until a page reload. The re-subscribe `home-assistant-js-websocket` sends after a websocket reconnect can be refused silently, leaving the card on stale zones (X48).
- The lock gates only drawing: chip double-click clear, Clear All, Undo, the manager's Delete, Add and rename, and rotation still write while the card says Locked (X06). A locked canvas still prevents default on every touch, so a phone cannot scroll the page past the map (X46).
- The canvas backing store is a fixed 800 px wide with no `devicePixelRatio` scaling (blurry on HiDPI screens). A fitted grid gets a canvas of its own shape, but a YAML `grid` keeps the square canvas, so one whose X span differs from its Y span is drawn stretched (X39).
- Zone map cards added from the card picker before 2.3.0 carry the old stub's `grid` (-6000..6000 by 0..12000 mm) and `grid_units: mm` in their YAML, so they keep that square map until the user deletes both keys; an administrator's saved unit still wins over their `grid_units`.
- A non-administrator's m / ft pick is saved nowhere: it lasts until the card is rebuilt (a page reload or a dashboard regeneration).
- Clear All, and undo of a first draw, write `shape: none` for YAML-seeded ids the store never held, which creates entities for them (X43). A polygon finished with fewer than 3 distinct points, or with no zone selected, is dropped without a message (X44).
- In ellipse mode a click, a tap or a perfectly straight drag still saves an ellipse with a 1 mm radius over the zone: the ellipse branch of `endDrawing` floors each radius at 1 (`Math.max(1, ...)`), while the rect branch drops a box with no area (F21). The fix agents reported it but left it out of scope; see REVIEW_REPORT.md "Recommended next steps".
- Before the first payload arrives, the cone is drawn at the YAML `cone.angle_deg` and then snaps to the stored rotation (cosmetic; the sensors are unaffected).
- The card picker entry is pushed without a once-per-type guard, so evaluating the zone-map bundle twice lists "Apollo Zone Map" twice.

Tuning cards and detection:

- If all four top-gate entities of a device are disabled, the longest gate array is still one short and the charts show one gate fewer; only the profile's register count could hold the axis, which was left out so DIY firmware with fewer gates keeps its own count.
- A resolved device with no gate entities renders nothing (X20). An offline device shows "0.0" distance bars on the 0.75 m default axis, and unavailable max and zone rows drop out and shrink the chart (X21).
- The chip markers stay unanchored: `/_ld2410_/` in `LD2410_MARKERS` and the inline `/_ld2412_/` in `detectProfileFromEntities` match any entity whose base holds the token, so a device named "My LD2410 Bench" counts its non-radar entities as LD2410 evidence. No tab or card comes from that alone, because liveness needs classified radar entities.
- `resolveProfile` calls `apolloModelInfo` without the `isEsphomeDevice` gate the strategy applies, so a hand-written card pointed at a network integration's copy of the radar device resolves a profile the strategy would reject.
- A `device_base_name`-only distance card on an MSR-1 builds MSR-2 entity ids for Bluetooth and Gate Size, so it draws gates at the 0.75 m default; `device_id` (which the generated dashboard always sets) avoids this (X24).

Calibration:

- The chart's one-click engineering mode and every calibrate card action need `hass.callService`, which every current HA frontend provides; without it the chart shows only the SVG text and the card's buttons stay disabled.
- Snapshot history lives for the integration's lifetime: `async_remove_entry` deletes `apollo_mmwave.calibration` along with the zone store, and only `MAX_SNAPSHOTS` are kept per device.
- The numeric pre-flight sees only enabled gate entities and Home Assistant's copy of their state; the LD2412 refresh before the capture, the read-back verification and Undo are the backstop for what it cannot see.
- The calibrate card offers only the newest snapshot as Undo (`undoLabel` names `snapshots[0]`, which is what `restore_gate_thresholds` picks without a `snapshot_id`); older snapshots are reachable through the service.
- `snapshotContents` tells Undo from Redo by assuming every restore wrote back the newest snapshot, which every card Undo and Redo does. A restore of an older `snapshot_id` through the service, a failed restore and its retry, or a hand edit between runs can make the label describe the wrong values; the button still restores exactly `snapshots[0]`.
- The "Restored the thresholds from 14:31" line names the result's `restored_from`; for a stored result without it, it infers the restored snapshot as the entry older than the redo snapshot in the payload's list, and drops the time when that entry is missing.
- The calibrate card does not treat HA's `unknown_command` as not loaded, so on a fresh boot it can show that error instead of the loading state until the entry's `loaded` event reopens the subscription; the zone API's handling of that code was not copied over.

Tooling:

- The pre-commit hooks use `language: system`, so a commit made without `.venv` active fails with "Executable ruff not found" or runs an unpinned ruff (X05).
- The integration ships only `brand/icon.png` and `brand/icon@2x.png` (HA 2026.3+ local brand images, pinned by `tests/test_brand.py`), with no logo or dark variants. They resolved X54, so the HACS brands check runs again.

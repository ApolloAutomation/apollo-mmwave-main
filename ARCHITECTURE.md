# Architecture

This document is for a maintainer new to the `apollo_mmwave` repository. It describes what the integration is, how the Python and TypeScript halves fit together, where data flows at runtime, and which values are tuning knobs. Line numbers refer to the tree this document was written against and drift as files change; function names are the stable reference.

## Overview

`apollo_mmwave` is a Home Assistant custom integration (installed through HACS, `hacs.json`) for Apollo Automation mmWave radars: MSR-1 and MSR-2 (LD2410 chip), R-PRO-1 (LD2412 plus LD2450) and MTR-1 (LD2450 only). It does not talk to hardware. The ESPHome integration already exposes the radar's sensors; this integration adds drawn occupancy zones on top of the LD2450 X/Y target sensors and a tuning dashboard for the gate radars.

It has two halves that ship as one HACS package:

- The Python backend in `custom_components/apollo_mmwave/`. It owns a config entry, a persisted zone store (`.storage/apollo_mmwave.zones`), a persisted calibration store (`.storage/apollo_mmwave.calibration`), the `apollo_mmwave.update_zone` service and the three gate-calibration services (`calibrate_gates`, `cancel_calibration`, `restore_gate_thresholds`), one `sensor` and one `binary_sensor` entity per zone, four websocket commands, and the Lovelace resource and dashboard registration.
- The TypeScript/Lit frontend in `frontend-src/`. Vite compiles it into two self-contained ES module bundles that are committed under `custom_components/apollo_mmwave/www/` (`apollo-radar-tuning.js` and `apollo-radar-zone-map-card.js`, `const.py` `JS_BUNDLES`).

The backend serves the committed bundles itself at `/apollo_mmwave/<bundle>?v=<manifest version>` and registers them as Lovelace module resources and extra JS URLs (`frontend.py` `async_register_frontend_assets`). Users therefore install one repository and get the cards, the strategy and the backend together. The `www/` folder is a committed build output, not a scratch directory (`frontend-src/vite.config.ts`), and CI fails if it is stale (see Build, test and CI).

## Runtime data flow

### Device entity to integration to storage to presence sensors

1. The ESPHome device exposes LD2450 target sensors named `sensor.<base>_ld2450_target_<n>_x` / `_y` (R-PRO-1) or `sensor.<base>_target_<n>_x` / `_y` (MTR-1). `resolve_target_pairs` (`ld2450.py`) scans the entity registry for one device, matches `TARGET_X` / `TARGET_Y` and returns `[{x, y}]` pairs sorted by target number, skipping disabled entities. `async_track_target_pairs` (`ld2450.py`) installs a per-device cache in `hass.data["apollo_mmwave"]["ld2450_pair_cache"]` and invalidates it on entity registry events, firing `SIGNAL_ZONES_UPDATED`. When setup runs before Home Assistant has finished starting, a one-shot `EVENT_HOMEASSISTANT_STARTED` listener invalidates every cached device and re-fires the signal for each, so pairs resolved before ESPHome registered its entities are resolved again.
2. At setup, zones can enter the store from the migration paths (`async_migrate_legacy`, `async_import_zone_mapper`, `_promote_resolvable_orphans` in `migration.py`, and the v1 to v2 rekey in `store.py`). After setup, zones enter the store only through the service. `handle_update_zone` (`__init__.py`) resolves the device via `_resolve_target_device`, refuses no-op calls in `_call_changes_something`, fetches `store.device(device_id)` (`store.py`), applies `rotation_deg` and `input_units` (`_apply_device_settings`), applies tracked pairs (`_apply_entity_pairs`), then either deletes, renames, or normalises geometry through `_normalize_zone_payload` into whole millimetres. Every mutating path ends in `_notify_zones_updated`, which schedules a debounced write (`ZoneStore.async_delay_save`, `SAVE_DELAY_SECONDS` in `store.py`), sends the dispatcher signal `SIGNAL_ZONES_UPDATED` with the device id, and fires the public bus event `apollo_mmwave_zone_updated`.
3. `async_setup_zone_platform` (`zone_entities.py`) runs `_sync_entities` once at platform setup and again on every `SIGNAL_ZONES_UPDATED`. It diffs `store.devices[*]["zones"]` against a `ZoneEntityTracker` and creates a `ZonePresenceBinarySensor` (`binary_sensor.py`) and a `ZoneCoordsSensor` (`sensor.py`) for each missing `(device_id, zone_id)`.
4. `ZonePresenceBinarySensor.async_added_to_hass` calls `_track_coordinate_entities`, which resolves pairs via `effective_target_pairs` (`ld2450.py`: the stored `entities` list if the key is present, else the cached auto-detected pairs) and subscribes `async_track_state_change_event` on every X/Y entity id. Each state change runs `_handle_coordinate_update` then `_evaluate_presence`: read the zone from `store.zone()`, pick a tester from `_SHAPE_TESTERS`, build a rotator from the device's `rotation_deg` (`_build_point_rotator`), and iterate `_iter_rotated_coordinates`. `_get_coordinate_pair` parses both states, drops `unknown`/`unavailable`, drops the exact `(0, 0)` idle-slot sentinel and multiplies by `INPUT_UNIT_FACTORS[input_units]` (default 1.0). Any rotated point inside the shape sets `is_on`.
5. `ZoneCoordsSensor.extra_state_attributes` (`sensor.py`) publishes `shape`, `data`, the effective `entities` list, `rotation_deg` and `name`; its state is the zone id. Both entities rewrite state on `SIGNAL_ZONES_UPDATED` for their device.

### Device entity to websocket to cards

1. The zone map card's `setConfig` (`frontend-src/src/zone-map/card.ts`) requires `device_id` and calls `_connectZones`, which hands off to `connectZones` (`frontend-src/src/zone-map/api.ts`). That subscribes first (`subscribeZones`, command `apollo_mmwave/zones/subscribe`), then reads once (`fetchZones`, command `apollo_mmwave/zones/get`), drops the read if a push already arrived, retries `not_loaded` with `RETRY_DELAYS_MS`, and re-opens both when `subscribeEntryLoads` sees this domain's config entry reach state `loaded`. `connectZones` serialises overlapping opens through a promise queue (`requestOpen`), so a reload burst or a retry landing on an entry update cannot leave an orphan server-side subscription. When `setConfig` is called with a different `device_id`, `_resetDeviceState` disposes the subscription and clears zones, tracked entities, the undo snapshot, cone angle and lock; `_connectZones` tags each connection so payloads from a superseded connection are dropped.
2. On the server, `ws_get_zones` and `ws_subscribe_zones` (`websocket.py`) both pass `_answerable` (`not_loaded` if the store is gone, `not_found` if the device id is not in the device registry) and answer with `_payload`, built from `store.devices.get(device_id)` plus fresh `resolve_target_pairs` as `suggested_entities`. The subscription's `_forward` listens to `SIGNAL_ZONES_UPDATED` and pushes a new payload for the matching device.
3. The card applies each payload in `_applyZoneConfig` (`card.ts`): `_applyZones` splits drawable zones from the name list, `_applyRotation` sets the cone angle and slider, `_applyTrackedEntities` uses `entities` when it is an array and `suggested_entities` when it is null.
4. Live targets are drawn on every `hass` assignment: `set hass` calls `drawGrid`, which calls `_drawTrackedTargets` to read `hass.states[pair.x].state` and `hass.states[pair.y].state`, scale by the card's `input_units` multiplier, rotate by the cone angle and skip near-zero readings.
5. Writes go the other way: `endDrawing` or `finishPolygon` produce a payload, `updateHomeAssistantShape` wraps it, and `_saveZoneUpdate` appends `input_units` and calls `hass.callService("apollo_mmwave", "update_zone", ...)`. The backend path above then pushes the result back over the subscription.
6. The tuning cards do not use the websocket. `ApolloLd2410DistanceCard.shouldUpdate` (`frontend-src/src/cards/distance-card.ts`) calls `resolveRadar` (`frontend-src/src/cards/resolution.ts`), memoised on `config`, `hass.entities` and `hass.devices`, which calls `resolveEntities` and `resolveProfile` (`frontend-src/src/entities.ts`). `render` then reads `hass.states` through `distanceModel` (`frontend-src/src/charts/distance-chart.ts`) or `gateEnergyModel` (`frontend-src/src/charts/gate-energy-chart.ts`).

### Card to service to job to websocket

1. The calibrate card (`frontend-src/src/cards/calibrate-card.ts`) subscribes to `apollo_mmwave/calibration/subscribe` for its device and calls `apollo_mmwave.calibrate_gates` with `{device_id}` plus its `calibration` block (`startCalibration` in `calibration/api.ts`). It never awaits that call for its UI: progress arrives over the subscription, which is why a job survives the browser closing.
2. `handle_calibrate_gates` (`calibration.py`) looks the calling user up (the only await of the pre-flight), then runs every check and the registration with no await between them, so two calls cannot both register a job for one device: `_single_device_id`, `_preflight_calibrate` (`calibration_running`, `no_gate_entities`, `engineering_mode_missing`, `device_offline`, `background_correction_running`, `thresholds_not_numeric` over every threshold the chip is sent with the writes, which is all 28 on the LD2412 and both numbers of every written gate on the LD2410, `margin_zero`, `not_allowed`; each a `ServiceValidationError` whose translation key is in `translations/en.json`), then `_launch` registers the `CalibrationJob` in `hass.data["apollo_mmwave"]["calibration_jobs"]` keyed by device id, starts `job.run()` as an entry background task, fires `apollo_mmwave_calibration_started` and returns `job.public_state()`, or, with `wait: true`, shields `job.done.wait()` and returns `job.result_payload()`.
3. `CalibrationJob.run()` delegates to `_prepare`, `_sample`, `_compute`, `_apply` and `_verify`, with `_finish` as the finally. Every timed phase is driven by one `async_track_time_interval(TICK_S)` tick and `asyncio.Event`s the tick sets, so tests drive it with `async_fire_time_changed`; the only `asyncio.sleep` calls are `WRITE_SPACING_S`, `VERIFY_SETTLE_S` and `RESTORE_READBACK_S`. `_prepare` hard-saves the `interrupted` marker (phase `engineering`) before `switch.turn_on` when the switch is off, waits for it to read `on` within `ENGINEERING_CONFIRM_TIMEOUT_S` (`engineering_mode_not_confirmed`), then runs the settle countdown and the energy warmup side by side; sampling starts on the first tick at which both hold, and `no_energy_data` fires `ENERGY_WARMUP_TIMEOUT_S` after the switch read `on` even mid-countdown. `_sample` takes one read of every energy sensor per tick (`samples` counts ticks; a state-change listener only raises the per-entity `event_peak`), counts ticks with the radar-target and moving-target sensors on, and the liveness guards fail the job with `engineering_mode_lost` (switch `off` for `ENGINEERING_LOST_TICKS` ticks) or `background_correction_started`. `_compute` runs `calibration_math.compute_channel` per gate channel and adds the `unused`, `skipped`, `off` and `gates_off` rules. `_apply` fails `no_gate_data` before touching the device when no gate collected `MIN_SAMPLES` readings, presses the LD2412 query-params button (`sub_phase: "refresh"`), re-checks that every threshold the chip will be sent is numeric, captures the current values (the snapshot, every `old` and the skip rule all come from this one read, and a cell's `unchanged` is recomputed from it), pushes once the plan and `writes_total` are known, takes no snapshot or marker at all when every value is already within tolerance, otherwise hard-saves the snapshot (`snapshot_failed` otherwise, and nothing is written), hard-saves the marker with phase `applying`, then writes gate by gate, move then still, skipping values within `VERIFY_TOLERANCE` of the capture, `WRITE_SPACING_S` apart; `device_offline`, `write_failed` and `not_allowed` stop it while keeping `writes_done`, `writes_total` and `snapshot_id` so the card can offer Undo. `_verify` presses the LD2412 button again, waits `VERIFY_SETTLE_S` and compares every written number numerically; mismatches and unreadable states go to `unverified` and the outcome becomes `partial`.
4. `_finish` runs on every exit path, including task cancellation from an unload or HA stop (`asyncio.CancelledError` is mapped to `cancelled_by_shutdown` and re-raised only after the restore attempt; a second cancellation during the restore is tolerated). It removes the tick and the listener, turns the switch off only if the job turned it on (bounded by `SHUTDOWN_RESTORE_TIMEOUT_S`, every exception logged at warning), reads the switch back, settles the marker (`_settle_marker`: everything is cleared when the switch reads `off`; a shutdown keeps the phase it was in so the banner can offer Undo after the restart; a finish the job reached itself clears the write phase and keeps the engineering fact, with `left_on` set when the turn-off was not echoed), persists `last_result` with a delayed save when the store is still in `hass.data`, removes the job from the registry, dispatches `SIGNAL_CALIBRATION_UPDATED`, fires `apollo_mmwave_calibration_finished` and sets `job.done`.
5. Only three device write shapes exist, all `blocking=True` with the service call's context: `number.set_value {entity_id, value}`, `switch.turn_on` / `turn_off {entity_id}` and `button.press {entity_id}`.
6. `ws_subscribe_calibration` (`websocket.py`) answers null, pushes `calibration_payload(hass, device_id)` at once, then forwards every `SIGNAL_CALIBRATION_UPDATED` for the device; `_calibration_answerable` requires both calibration keys in `hass.data` (`not_loaded` otherwise) and the forwarder re-checks them before every push. `restore_gate_thresholds` reuses the same job with `kind: "restore"`: the shared pre-flight plus snapshot resolution (ids re-resolved through `unique_id`, ids that left the registry or are disabled reported in `missing` and left out of the offline, numeric and permission checks), a redo snapshot with reason `restore`, the same paced writer and verification, and no engineering-mode touch.

## Backend modules

### `__init__.py`

`async_setup_entry` loads or migrates the store, runs `async_migrate_unique_ids`, stores the `ZoneStore` at `hass.data["apollo_mmwave"]["store"]`, installs the LD2450 pair cache, registers the service with `UPDATE_ZONE_SERVICE_SCHEMA`, registers the websocket commands, hands `entry.async_on_unload` the `async def` teardown returned by `async_setup_calibration` (`calibration.py`), forwards `PLATFORMS = [binary_sensor, sensor]`, registers frontend assets, applies the dashboard option and adds an options update listener. `async_unload_entry` unloads platforms, removes the service, pops the store and flushes it; it pops the zone store before the on_unload hooks run, which is why the calibration websocket commands guard on their own keys. `async_remove_entry` removes the dashboard and deletes both storage files.

The service side:

- `_device_id_from_call` accepts `device_id` as a string or a one-item list (the shape a `target:` block produces) and refuses multi-device targets. `_device_is_registered` is applied on every path, so an unknown or stale device id never reaches the `store.device()` setdefault.
- Deprecated `location`: `_device_id_for_label` slug-matches the value against stored `label` fields only; `_device_id_for_deprecated_location` warns once per run via the `hass.data` flag `_DATA_LOCATION_WARNED` and refuses a label whose device has left the registry.
- `_normalize_entities`: an empty `entities` list means "no change", never "erase", because a card calling the service before it had loaded used to wipe people's tracked pairs. `clear_entities: true` is the only way to empty the list, and it takes precedence over `entities` in the same call (`_apply_entity_pairs`).
- Rename: `_update_registry_names` writes the registry `name` as `Zone {n} - {zone_name}` (or the bare base when the name is empty) and only when `_is_generated_name` says the current name is still generated, so user-typed names survive. Delete removes both registry entries via `_remove_zone_entities`.
- Geometry: `_normalize_rect` and `_normalize_polygon` return `{**data, ...}` and therefore persist any extra keys the caller put in `data`, while `_normalize_ellipse` rebuilds a clean dict. Polygons with more than `POLYGON_MAX_POINTS` points are truncated with a warning, not rejected (mirrored by the card).

The module also holds the unique-id contract `_zone_entity_unique_ids` and `get_store`, which `binary_sensor.py`, `sensor.py`, `zone_entities.py` and `websocket.py` import lazily.

### `config_flow.py`

`ApolloMmwaveConfigFlow.async_step_user` creates a single entry with `unique_id = "apollo_mmwave"`, empty `data` and `options = {auto_create_view}`. `ApolloMmwaveOptionsFlow.async_step_init` shows an `auto_create_view` toggle and a `dashboard_devices` `DeviceSelector` filtered to `integration=esphome`, `manufacturer=ApolloAutomation` and `model in MMWAVE_MODELS`. Option changes are applied without a reload by `_async_options_updated` (`__init__.py`).

### `const.py`

The home for shared names: `DOMAIN`, `SERVICE_UPDATE_ZONE`, `EVENT_ZONE_UPDATED`, `SIGNAL_ZONES_UPDATED`, the calibration names (`SERVICE_CALIBRATE_GATES`, `SERVICE_CANCEL_CALIBRATION`, `SERVICE_RESTORE_GATE_THRESHOLDS`, `EVENT_CALIBRATION_STARTED`, `EVENT_CALIBRATION_FINISHED`, `SIGNAL_CALIBRATION_UPDATED`, `DATA_CALIBRATION_STORE`, `DATA_CALIBRATION_JOBS`), most `hass.data` keys, store keys and `INPUT_UNIT_FACTORS`, shape names and polygon limits, `CARD_TYPE`, options keys, dashboard constants, `STATIC_URL_BASE`, `FRONTEND_DIR` and `JS_BUNDLES`, plus the `WARN_*` log templates. Two `hass.data` keys live elsewhere: `_DATA_LOCATION_WARNED = "location_deprecation_warned"` in `__init__.py` and `DATA_SUBSCRIPTIONS = "ws_subscriptions"` in `websocket.py`.

### `store.py`

`ZoneStore` wraps a `_MigratingStore` with key `apollo_mmwave.zones` and `STORAGE_VERSION = 2`. `async_load` returns `False` when no file exists. `_async_migrate_func` rekeys v1 `locations` (display names) into v2 `devices` (HA device ids) using `_resolve_device_id`, retaining unresolvable entries under `orphans`. `_parse_entry` normalises each loaded entry: int zone ids and an allow-list of keys (see Known limitations for what that allow-list drops). `device()` is a `setdefault`, so readers use `store.devices.get()` to avoid minting entries. `_data_to_save` dumps the live dicts verbatim.

### `migration.py`

Three one-way upgrade paths run from setup. `async_migrate_legacy` rebuilds zones from the RestoreEntity attributes of pre-1.2 sensors whose unique id is `apollo_mmwave_<slug>_zone_<n>`; it keeps an empty placeholder for a zone with no shape so the entity is recreated. `async_import_zone_mapper` does the same for the standalone `zone_mapper` platform, except that it skips zones whose restore attributes carry no `shape`; the import is read-only with respect to that integration. Both run only when no store file exists. `async_migrate_unique_ids` runs on every setup: it promotes orphans that now resolve (`_promote_resolvable_orphans`) and rewrites pre-2.0 unique ids matching `_OLD_UID` to `<device_id>_zone_<n>[_presence]`.

### `zone_entities.py`

`ZoneEntityTracker` keeps exactly one entity per `(device_id, zone_id)` per platform, remembers refused adds (`add_to_platform_abort`) and skips user-disabled registry entries (`is_disabled`). `ZoneEntityMixin.async_will_remove_from_hass` re-dispatches `SIGNAL_ZONES_UPDATED` when an aborted add is pending, so a delete followed by an immediate redraw still ends with one entity.

### `binary_sensor.py`

`ZonePresenceBinarySensor` has unique id `{device_id}_zone_{n}_presence`, name `Zone {n} presence`, device class occupancy, and is linked to the radar's device entry. Shape testers: `_point_in_rect` (inclusive bounds), `_point_in_ellipse`, `_point_in_polygon` (even-odd ray cast, at least `POLYGON_MIN_POINTS`). Rotation uses `x' = x cos t + y sin t`, `y' = -x sin t + y cos t`.

### `sensor.py`

`ZoneCoordsSensor` has unique id `{device_id}_zone_{n}` and name `Zone {n}`. It exists so automations and the sensor attributes expose the geometry; the card itself reads the websocket instead.

### `ld2450.py`

`resolve_target_pairs`, `effective_target_pairs` and `async_track_target_pairs` as described above. `effective_target_pairs` is the only answer both platforms use, so the sensor's `entities` attribute matches what presence tracks. The `entities` store key is three-valued: absent means auto-detect, `[]` means track nothing, a list means exactly those pairs. The registry listener invalidates the changed entity's device when that device is cached; otherwise it scans every cached device whose pairs reference the entity id and invalidates those, which covers an entity moved away from a cached device.

### `gates.py`

`resolve_gate_entities` classifies one device's enabled registry entries into `GateEntities`: per-gate `move_threshold`, `still_threshold`, `move_energy` and `still_energy` maps keyed by the digit `GATE_RE` captures (a disabled gate leaves a hole rather than shifting its neighbours), the engineering-mode switch, the LD2410 max move/still gate numbers, the LD2412 min/max gate numbers, the radar-target and moving-target binary sensors, and the LD2412 background-correction button and status and query-params button (`_SCALAR_PATTERNS`, first writer wins per slot as in `ld2450.py`). The profile is `ld2412` when any object id contains `_ld2412_`, else `ld2410`; `None` is returned when no gate slot matched (an MTR-1). `number_bounds` reads a number's `min`, `max` and `step` with 0/100/1 fallbacks, `numeric_state` returns a finite float or `None` (through `finite_float`, which `calibration.py` and `calibration_store.py` share), and `is_offline` treats a registered entity with no state object the same as `unavailable`. It is the Python twin of `entities.ts` (see Contracts).

### `calibration.py` and `calibration_math.py`

`calibration.py` holds the algorithm's timing, headroom and verification constants (each a module-level name so tests patch it there; `MIN_SAMPLES`, `SPIKE_ABS` and `SPIKE_RATIO` live in `calibration_math.py` and `MAX_SNAPSHOTS` in `calibration_store.py`, are deliberately not re-exported, and must be patched on those modules), the three service schemas (`CALIBRATE_GATES_SCHEMA`, `CANCEL_CALIBRATION_SCHEMA`, `RESTORE_GATE_THRESHOLDS_SCHEMA`, all `extra=vol.PREVENT_EXTRA`), the pre-flights, `CalibrationJob`, `calibration_payload` and `async_setup_calibration`. Setup loads the store, installs the jobs dict, registers the services with `SupportsResponse.OPTIONAL`, subscribes a synchronous `EVENT_HOMEASSISTANT_STOP` listener that only sets `cancel_requested` (HA core cancels every background task before it fires the event) and returns the `async def` teardown: a closing flag set before its first await (so `calibrate_gates` and `restore_gate_thresholds` are refused as not loaded while it waits, as they are while HA is stopping), cancel requests on every job, a bounded wait for their finally (`asyncio.wait_for` over a `gather`, skipped when no job runs), service removal, listener removal, a final save that logs rather than raises, then the two `hass.data` keys (and the closing flag) are popped last so no job can persist into a store the entry no longer owns. `calibration_math.py` is the pure half: `Bounds`, `Margins`, `ChannelSamples`, `ChannelResult` and `compute_channel` (the peak is the ceiling of the largest tick or event value; the proposal is `peak + max(margin, peak * margin_pct / 100)` rounded up to the step and clamped to the range; `off` at the top of the range; `spike` when the tick maximum is both `SPIKE_ABS` above and `SPIKE_RATIO` times the nearest-rank 95th percentile; `no_data` under `MIN_SAMPLES` ticks, whatever the event peak). It is tested directly with plain tuples.

### `calibration_store.py`

`CalibrationStore` wraps a `Store` with key `apollo_mmwave.calibration`, version 1, as its own file so `store.py` and its allow-list stay untouched and an older build simply ignores it. Per device it keeps up to `MAX_SNAPSHOTS` snapshots newest first (`add_snapshot`, `discard_snapshot`, `snapshot`, `snapshots_summary`), the `last_result`, and the `interrupted` marker (`set_interrupted`, `clear_interrupted`, `interrupted`). `_parse_device` drops malformed snapshots one at a time and reads a missing `left_on` as `False`; a missing file is empty, an unreadable one logs a warning and starts empty. `async_save` is awaited directly for the snapshot and the marker because both exist to survive a crash, and it raises when the write failed: HA's `Store` catches `WriteError` and `SerializationError` and only logs them, so `_ReportingStore` records the error from `_async_write_data` for `async_save` to raise (during an HA stop the save defers to the final-write stage, still before the process exits, and cannot be checked); results use `async_delay_save`. `snapshot` and `snapshots_summary` skip a snapshot without values, so one can never hide a real one from Undo.

### `websocket.py`

`async_register` registers `apollo_mmwave/zones/get`, `apollo_mmwave/zones/subscribe`, `apollo_mmwave/calibration/get` and `apollo_mmwave/calibration/subscribe` on every config entry setup; registration is a keyed assignment that replaces the previous handlers rather than stacking them, and the commands are never unregistered. It returns a teardown that closes this entry's subscriptions (zone and calibration alike, through `_subscriptions`) on unload. None of the commands requires admin, which is why calibration progress goes over a subscription rather than a custom bus event. Zone ids and `peaks` gate keys are stringified in the payloads. The calibration commands use `_calibration_answerable`, which needs both `calibration_store` and `calibration_jobs` in `hass.data` (`not_loaded` otherwise), because `async_unload_entry` pops the zone store before the on_unload hooks run and a half-set-up entry can have the reverse; `ws_subscribe_calibration` sends the current payload right after its result and its forwarder re-checks the keys before every push.

### `frontend.py`

`async_register_frontend_assets` is guarded by `hass.data["apollo_mmwave"]["assets_registered"]`, reads the manifest version for the `?v=` cache buster, registers each existing bundle as a static path with `cache_headers=True` (the cache duration itself is Home Assistant's `CACHE_TIME` in `homeassistant/components/http/static.py`, 31 days at the time of writing), adds it as an extra JS URL and reconciles the Lovelace resource collection (`_async_register_lovelace_resources`): an existing row with an older `?v=` is updated in place rather than duplicated, stale `/apollo_mmwave/` rows are deleted, and a YAML-mode resource collection only produces a warning listing the URLs to add by hand. `async_register_dashboard` creates the storage dashboard at url path `apollo-mmwave` once and keeps its config at `{"strategy": {"type": "custom:apollo-radar-tuning", "devices": [...]?}}` (`_desired_config`), only when `_is_ours` agrees; a YAML dashboard already holding the `apollo-mmwave` url path is left alone. The dashboards collection is borrowed from HA's `lovelace/dashboards/list` handler. `async_remove_dashboard` deletes it only if still ours.

### `services.yaml`, `translations/en.json`, `manifest.json`

`services.yaml` documents `update_zone`: `device_id`, deprecated `location`, `zone_id`, `shape`, `data`, `name`, `delete`, `input_units`, `rotation_deg`, `entities`, `clear_entities`; and the three calibration services with their fields, defaults and selector ranges (which mirror the voluptuous schemas in `calibration.py`). `translations/en.json` carries the config and options flow strings and the `exceptions` block whose keys are the calibration pre-flight refusals. `manifest.json` declares `config_flow: true`, dependencies `frontend`, `http`, `lovelace`, `websocket_api`, `integration_type: service`, `iot_class: local_push`, and the version.

## Frontend modules

### Detection and profiles (`register.ts`, `entities.ts`, `profiles.ts`, `ld2450.ts`, `types.ts`, `index.ts`)

`index.ts` is the tuning bundle entry: it exports `CARD_VERSION` and side-effect imports the two cards and the strategy. `registerElement` (`register.ts`) defines an element immediately and re-asserts every pending definition once `home-assistant` or `hc-main` is defined, because HA's scoped-custom-element-registry polyfill replaces `window.customElements` after boot. `profiles.ts` holds the chip tables: `LD2410_PROFILE` (9 gates g0..g8, MSR-2 naming) and `LD2412_PROFILE` (14 gates g00..g13, `ld2412_` naming), `APOLLO_MODELS` (model prefix to profile and LD2450 flag), `apolloModelInfo` and `isEsphomeDevice`. `entities.ts` turns registered entity ids into an `EntityMap` (`types.ts`): `baseNameFromDevice` strips `KNOWN_SUFFIXES`, `classifyObjectId` matches `GATE_PATTERNS` then `SCALAR_PATTERNS`, `entityMapFromDevice` builds a possibly sparse map, and `resolveEntities` / `resolveProfile` add the base-name fallback and `config.entities` overrides. `ld2450.ts` detects LD2450 target sensors with the same regexes as the backend and emits the zone map card config (`zoneMapCard`).

### Calibrate card (`cards/calibrate-card.ts`, `calibration/api.ts`, `calibration/model.ts`)

`ApolloRadarCalibrateCard` (element `apollo-radar-calibrate-card`, card picker name "Apollo Radar Auto-Calibrate") is a Lit element that takes `device_id`, `device_base_name`, `title` and a `calibration` block (`CalibrateCardConfig` in `types.ts`). It is a view of a backend job, never the job itself: it opens `apollo_mmwave/calibration/subscribe` for one device (`subscribeCalibration`), renders every pushed `CalibrationPayload`, and sends three service calls through one `callService` helper that passes `notifyOnError = false` so a `ServiceValidationError` is rendered once by the card and not again by HA's toast (`startCalibration`, `cancelCalibration`, `restoreThresholds`, plus `turnEngineeringMode` for the interrupted banner). The start call's promise is only watched for rejection; progress arrives over the subscription, which is why the job survives the browser closing. A rejection goes through `describeServiceError`: HA's websocket `call_service` sends a pre-flight `ServiceValidationError` as `{code: "service_validation_error", message: "Validation error: <text without its final period>", translation_domain, translation_key, translation_placeholders}`, so the card loads the exception translations (`hass.loadBackendTranslation("exceptions", domain)`) and renders `component.<domain>.exceptions.<key>.message` in the user's language, falling back to the message with the prefix dropped and the period restored. A `not_found` from a service call means the integration is unloaded (HA cannot find the service); only the subscription's `not_found` means an unknown device. A rejected start or Undo becomes the failed view ("Calibration failed: " / "Restore failed: ", with Try again and Close); a rejected Stop or "Turn it off" is shown inline in the running view or the banner, so it never replaces the running job or its result.

Subscription lifecycle: the device id comes from `resolvedDeviceId` (`cards/resolution.ts`: `config.device_id`, else the device of the first resolved entity in `hass.entities`); the card subscribes on the first `hass` with a device id, disposes in `disconnectedCallback`, resubscribes in `connectedCallback`, and on a device change disposes and reopens. Every open is tagged with a serial so a payload or a resolved unsubscribe from a superseded connection is dropped. It also listens to the websocket connection's `ready` and `disconnected` events and re-runs its own subscribe on every `ready`: `home-assistant-js-websocket` re-sends subscriptions on reconnect, but a re-subscribe refused with `not_loaded` (HA restarted and `apollo_mmwave` is not loaded yet, the normal order after the one restart that interrupted a job) is dropped silently. A `not_loaded` rejection is retried with `CALIBRATION_RETRY_DELAYS_MS` (copied from the zone API, not imported, so `zone-map/api.ts` stays untouched) while the card reads "Apollo mmWave is still loading...", then shows the Not loaded copy with a manual Retry. Neither `ready` nor `disconnected` fires on an integration reload, which closes the subscription server side without telling the client, so the card also watches `config_entries/subscribe` through `subscribeEntryLoads` (copied into `calibration/api.ts` from the zone API, once per connection, admin-only like the zone card's) and reopens its subscription when an `apollo_mmwave` entry reports `loaded`. The engineering switch and the LD2412 background-correction status are read from live HA state first and from the payload's `entities` only when HA has no state: the backend pushes only from job code, so while no job runs the payload is as old as the last push. `shouldUpdate` re-renders on payload, local state or config changes, registry changes, and state changes of the engineering switch, the threshold numbers, the radar-target sensor and the background-status sensor only.

State selection lives in `model.ts` (`nextLocalState`, `showsResultView`): the Done, Partial, Preview, Cancelled, Failed and Restored views render only while card-local `observedFinish` holds the id of a job this card watched reach a terminal status; a fresh mount with a stored `last_result` renders Idle with the footer and a "Show last result" toggle. Every terminal and failure view has a Close back to Idle, and the interrupted banner renders above all of them. "Try again" repeats the failed job: a calibration with the same `apply` the card saw on the job, a restore with the snapshot it was writing back (`restoreSource`: the result's `restored_from`, else the snapshot older than its redo snapshot), never the newest snapshot, which after the redo snapshot is the very values being undone. Everything else in `model.ts` is pure copy: `phaseLabel`, `phaseHeadline` (the headline's stable phase sentence, the only text in the running view's live region, so the per-second countdown is not announced) and `progress` for the running job, `resultRows`, `unusedFootnote` and `warningLines` for the result, `undoLabel` (snapshot time, with the day when not today), `idleSentence`/`durationText`, `isFactoryThresholds` (the `LD2410_FACTORY_THRESHOLDS` hint) and `canStart`/`canStop`. The interrupted banner composes its lines from the marker's `phase` and `left_on` as independent facts plus the live switch state, so "Turn it off" disappears when the switch reads off without a store write.

Every render helper wraps its template in an element: happy-dom (the test DOM) mis-clones Lit child-part markers at a template root and inside `<svg>`, which is also why `charts/gate-energy-chart.ts` keeps its SVG in a nested template.

### Strategy (`strategy.ts`, `strategy-core.ts`, `panels/`)

`strategy.ts` registers `ll-strategy-dashboard-apollo-radar-tuning`, `ll-strategy-view-apollo-radar-tuning` and `ll-strategy-section-apollo-radar-tuning` and pushes a `window.customStrategies` entry. All three share `shouldRegenerate`, which returns false when `hass.devices` and `hass.entities` are reference-equal and no entity crossed the `unavailable` line, and otherwise compares `radarDeviceKey` (device id, profile key, LD2450 flag, online flag). `strategy-core.ts` does the work: `strategyDevices` picks `config.device_id`, `config.devices` or `detectRadarDevices`; `deviceFromId` combines registry match, base name, liveness and profile; `cardMap` builds entities cards from `panels/entity-rows.ts`, a history graph from `panels/history.ts`, the two custom chart cards, the calibrate card (for every device with a gate-radar profile, online or not, with `config.calibration` passed through as its `calibration` block), a "Start here" help card (`helpCardBody`: four numbered steps and the wiki link) and the zone map card; `buildDeviceSections`, `deviceView` and `generateViews` lay them out as one sections view per device, with the calibrate card first in column 1 and `buildDeviceCards` placing it right after the help card. `generateViews` appends the device id to the view path when two devices share a base name, because HA opens the first view matching the URL.

### Tuning cards and charts (`cards/`, `charts/`)

`ApolloLd2410DistanceCard` (`cards/distance-card.ts`, element `apollo-radar-distance-card`) and `ApolloLd2410GateEnergyCard` (`cards/gate-energy-card.ts`, element `apollo-radar-gate-energy-card`) are Lit elements that take `device_id`, `device_base_name`, `entities`, `title` and `distance_unit` (`types.ts`). `cards/resolution.ts` memoises entity resolution and gates re-renders to ticks that changed a resolved entity's state (`resolvedStatesChanged`). `charts/distance-chart.ts` renders zones, detection/moving/still bars, gate bands and max-gate bars scaled to gate size times gate count; `charts/gate-energy-chart.ts` renders per-gate move/still energy with threshold markers, visible only while the engineering-mode switch is on. While the switch reads off (not unavailable or missing) and `hass.callService` exists, the chart places a real HTML `<button class="overlay">` ("Turn on Radar Engineering Mode") over the plot area, inside a `position: relative` wrapper, which calls `switch.turn_on` through the calibration `callService` helper with HA's own error toast left on (the chart has nowhere else to show a failure) and catches the rejection; a real button is focusable and announced where an SVG element with an ARIA role inside `role="img"` is not. A bar whose energy exceeds its threshold is outlined in the threshold colour (`stroke-width="2"`) and the legend explains it. There is deliberately no "turn it off" line or button on the chart: the calibration job turns the mode on for its listen and that line would invite a click mid-run (follow-up F10). `panels/entity-rows.ts` `controlRows` adds the LD2412's Start Dynamic Background Correction button and Background Correction Running status right after the engineering-mode row when the slots resolve. `charts/geometry.ts`, `charts/entity-read.ts` and `charts/unit-convert.ts` are pure helpers.

### Zone map (`zone-map/card.ts`, `editor.ts`, `api.ts`)

`ZoneMapCard` (element `apollo-radar-zone-map-card`) is a plain `HTMLElement` with an 800 by 800 canvas (`setupCanvas`). It draws rect, ellipse and polygon zones in millimetres, Y-down, over live targets and a device cone, with a rotation slider (`_persistRotation`), per-radar lock persisted in `localStorage` (`readStoredLock`), a single-level undo and a zone manager for rename, delete and add (`_renderZoneManager`, `_handleAddZone`). Lock precedence: `_applyAutoLock` runs once per page load and uses the `start_locked` config first, then the stored `localStorage` value, then "locked if the radar already has zones". The file is `@ts-nocheck` by design (see its header comment). `ZoneMapCardEditor` (`editor.ts`, element `apollo-radar-zone-map-card-editor`) edits `device_id`, `title`, `dark_mode` and `start_locked` using `ha-device-picker`, `ha-textfield` and `ha-selector`. `api.ts` is the typed websocket client described under Runtime data flow.

## Contracts between frontend and backend

**Websocket commands** (`websocket.py`, `api.ts`): `apollo_mmwave/zones/get {device_id}` returns one payload; `apollo_mmwave/zones/subscribe {device_id}` returns null then pushes the same payload on every change. Error codes: `not_loaded` (retried by the card) and HA's `not_found` (terminal). The card's reload recovery also uses HA's admin-only `config_entries/subscribe`.

**Calibration websocket commands** (`calibration/api.ts`): `apollo_mmwave/calibration/get {device_id}` returns one payload; `apollo_mmwave/calibration/subscribe {device_id}` returns null, then immediately pushes the current payload, then every change. Same error codes as the zone commands. The payload (`CalibrationPayload`) is `{job: JobState | null, snapshots: [{id, taken_at, reason, count}], last_result: CalibrationResult | null, interrupted: InterruptedMarker | null, entities: EntitiesInfo | null}`; `JobState` carries `job_id`, `kind`, `status`, `sub_phase`, `elapsed_s`, `remaining_s`, `duration_s`, `settle_s`, `samples`, `peaks` (gate keys are strings on the wire), `writes_done`, `writes_total`, `apply`, `cancel_requested` and `engineering_mode_turned_on`; `CalibrationResult` is the backend's result payload (per-gate `move`/`still` channel results with `peak`, `p95`, `old`, `new`, `samples`, `written`, `confirmed`, `actual`, `flags`, `skipped`, plus `changed`, `unchanged`, `writes_done`, `writes_total`, `unverified`, `gates_off`, `warnings` and `error`; a restore result has `gates: []` and adds `restored`, `missing` and `restored_from: {id, taken_at}`); `InterruptedMarker` carries `phase` and `left_on` as independent facts. `warnings`, `flags` and `error.code` are codes; `calibration/model.ts` owns every sentence. The card calls `apollo_mmwave.calibrate_gates` with `{device_id, ...calibration block, apply?: false}`, `apollo_mmwave.cancel_calibration {device_id}` and `apollo_mmwave.restore_gate_thresholds {device_id, snapshot_id?}` (without `snapshot_id` from every Undo button, because the newest snapshot is the one its label names; only "Try again" on a failed restore passes the id of the snapshot it was restoring), and `switch.turn_on` / `switch.turn_off {entity_id}` for the chart overlay and the interrupted banner. The service schemas, the bus events, the `apollo_mmwave.calibration` storage file and the backend side of these commands are documented with the backend modules.

**Calibration services** (`calibration.py`, `services.yaml`; all `extra=vol.PREVENT_EXTRA`, all registered with `SupportsResponse.OPTIONAL`): `apollo_mmwave.calibrate_gates {device_id: str | [str], duration_s?: 15..600 = 60, settle_s?: 0..120 = 15, margin?: 0..50 = 10, margin_pct?: 0..100 = 25, kind?: both | move | still = both, apply?: bool = true, wait?: bool = false}` returns `job.public_state()` when the job starts, or the result payload with `wait: true`; `apollo_mmwave.cancel_calibration {device_id}` returns `{cancelled: bool}` and is a no-op without a job; `apollo_mmwave.restore_gate_thresholds {device_id, snapshot_id?, wait?}`. `margin` and `margin_pct` may not both be 0 (checked in the pre-flight, not the schema). Pre-flight refusals are `ServiceValidationError`s with the translation keys `unknown_device`, `multiple_devices`, `calibration_running`, `no_gate_entities`, `engineering_mode_missing`, `device_offline`, `background_correction_running`, `thresholds_not_numeric`, `margin_zero`, `not_allowed` and `no_snapshot` (`translations/en.json` `exceptions`). Job failures are codes on `result.error` (`engineering_mode_not_confirmed`, `no_energy_data`, `engineering_mode_lost`, `background_correction_started`, `thresholds_not_numeric`, `snapshot_failed`, `device_offline`, `write_failed`, `not_allowed`, `cancelled_by_shutdown`, `unexpected`, and `no_gate_data`, which the spec does not list) with the sentences in `ERROR_MESSAGES` (`device_offline` and `write_failed` have reworded zero-write forms without the Undo clause), which the card shows verbatim after "Calibration failed: ".

**Calibration bus events and signal**: `apollo_mmwave_calibration_started {device_id, job_id, kind}` and `apollo_mmwave_calibration_finished {device_id, job_id, kind, status, outcome, changed, snapshot_id}` (`EVENT_CALIBRATION_STARTED`, `EVENT_CALIBRATION_FINISHED`). The internal dispatcher signal `apollo_mmwave_calibration_updated` (`SIGNAL_CALIBRATION_UPDATED`) carries the device id as its only positional argument and fires on every status or sub-phase change and once per tick, never more often.

**Calibration storage schema** (`calibration_store.py`): key `apollo_mmwave.calibration`, version 1, shape `{"devices": {<device_id>: {"snapshots": [{"id", "taken_at", "reason": "calibrate" | "restore", "job_id", "values": {<entity_id>: {"value", "unique_id", "platform"}}}], "last_result": <result payload> | null, "interrupted": {"job_id", "kind", "phase": "engineering" | "applying" | null, "started_at", "engineering_mode_turned_on", "snapshot_id", "left_on"} | null}}}`. Snapshots are newest first and capped at `MAX_SNAPSHOTS`; `unique_id` and `platform` let a restore re-resolve a renamed entity. `apollo_mmwave.zones` and `store.py` are untouched by the calibration feature.

**Payload** (`websocket.py` `_payload`, `api.ts` `ZoneConfig`): `{zones: {"<id>": {shape, data, name?}}, entities: [{x, y}] | null, rotation_deg: number | null, label: string | null, input_units: string | null, suggested_entities: [{x, y}]}`. The server always sends `input_units`; the TypeScript interface declares it optional. Zone ids are ints in the store and strings on the wire. `entities: null` means never configured (the card uses `suggested_entities`); `[]` means cleared.

**Service** `apollo_mmwave.update_zone` (`UPDATE_ZONE_SERVICE_SCHEMA` in `__init__.py`, `services.yaml`): at least one of `device_id` (str or one-item list) or deprecated `location`; `zone_id` (`cv.positive_int`); `shape` in `none`, `rect`, `ellipse`, `polygon`; `data` dict or null; `name`; `delete`; `rotation_deg` (coerced to float, then rounded and clamped to [-180, 180] by `_sanitize_rotation`); `input_units` in `INPUT_UNIT_FACTORS`; `entities` as `[{x: entity_id, y: entity_id}]`, where an empty list means no change; `clear_entities`, which wins over `entities`. Extra top-level keys are rejected. The card sends: `{device_id, zone_id, shape, data}` for geometry (`updateHomeAssistantShape`), `{device_id, zone_id, name}` for rename, `{device_id, zone_id, delete: true}` for delete, `{device_id, rotation_deg}` for rotation (`_persistRotation`), `{device_id, zone_id, shape: "none", data: null, name}` for a new zone, and always adds `input_units` (`_saveZoneUpdate`). It never sends `entities`, `clear_entities` or `location`.

**Geometry**: integer millimetres, X to the radar's right, Y away from the radar. `rect {x_min, x_max, y_min, y_max}` with strict `x_min < x_max` and `y_min < y_max`; `ellipse {cx, cy, rx, ry}` with radii floored at 1 mm; `polygon {points: [{x, y}]}` with `POLYGON_MIN_POINTS` to `POLYGON_MAX_POINTS` points (`const.py`). The rotation formula is the same in `binary_sensor.py` (`_build_point_rotator`) and `card.ts` (`_drawTrackedTargets`).

**Bus event** `apollo_mmwave_zone_updated` with data `{"device_id": "<ha device id>"}` (`EVENT_ZONE_UPDATED`, fired from `_notify_zones_updated`). The internal dispatcher signal `apollo_mmwave_zones_updated` (`SIGNAL_ZONES_UPDATED`) carries the device id as its only positional argument.

**Storage schema** (`store.py`): key `apollo_mmwave.zones`, version 2, shape `{"devices": {<device_id>: {"zones": {"<n>": {shape, data, name?}}, "entities"?: [...], "rotation_deg"?: int, "label"?: str, "input_units"?: str}}, "orphans": {<v1 location>: same}}`. Version 1 files have `{"locations": {<display name>: {zones, entities, rotation_deg}}}`.

**Entity unique ids**: `{device_id}_zone_{n}` and `{device_id}_zone_{n}_presence` (`_zone_entity_unique_ids` in `__init__.py`, used by `sensor.py`, `binary_sensor.py`, `migration.py`). Registry base names `Zone {n}` and `Zone {n} presence` (`_update_registry_names`) must match `_attr_name` on the platforms.

**Custom element names**: `apollo-radar-zone-map-card` (`card.ts`, `const.py` `CARD_TYPE` as `custom:apollo-radar-zone-map-card`), `apollo-radar-zone-map-card-editor` (`editor.ts`), `apollo-radar-distance-card` (`distance-card.ts`), `apollo-radar-gate-energy-card` (`gate-energy-card.ts`), `apollo-radar-calibrate-card` (`calibrate-card.ts`, `CALIBRATE_CARD_TAG`), `ll-strategy-{dashboard,view,section}-apollo-radar-tuning` (`strategy.ts`) for strategy type `custom:apollo-radar-tuning` (`const.py` `DASHBOARD_STRATEGY_TYPE`).

**Static URL paths**: `/apollo_mmwave/apollo-radar-tuning.js` and `/apollo_mmwave/apollo-radar-zone-map-card.js` (`const.py` `STATIC_URL_BASE`, `JS_BUNDLES`), served from `custom_components/apollo_mmwave/www` with `?v=<manifest version>` (`frontend.py`). Bundle names must match `frontend-src/vite.config.ts` and `vite.zone-map.config.ts`.

**Dashboard strategy config**: `{"strategy": {"type": "custom:apollo-radar-tuning", "devices"?: [device ids], ...user keys}}` written by `frontend.py` `_desired_config` from the `dashboard_devices` option; read by `StrategyConfig` (`strategy-core.ts`: `device_id`, `devices`, `distance_unit`, `calibration` with `duration_s`, `settle_s`, `margin`, `margin_pct`, copied onto every generated calibrate card).

**Gate entity naming regexes**: `entities.ts` `GATE_PATTERNS` (`_g(\d+)_(move|still)_(threshold|energy)(?:_\d+)?$` per slot) and the `SCALAR_PATTERNS` suffixes for the engineering-mode switch, the LD2410 max move/still gate numbers, the LD2412 min/max gate numbers, the radar-target and moving-target binary sensors, and the LD2412 `_ld2412_start_dynamic_background_correction` button, `_ld2412_dynamic_background_correction_status` binary sensor and `_ld2412_query_params` button have a Python twin in the backend's `gates.py`; change both together, as with the LD2450 regexes.

**LD2450 naming regex**: `(?:_ld2450)?_target_(\d+)_x(?:_\d+)?$` and the `_y` twin must stay identical in `ld2450.py` (`TARGET_X`, `TARGET_Y`) and `ld2450.ts`.

## Build, test and CI

The frontend is built and tested from `frontend-src/` (`frontend-src/package.json`):

```sh
cd frontend-src
npm ci              # CI uses npm ci
npx tsc --noEmit    # type check src and test (tsconfig.json)
npm test            # vitest run (vitest.config.ts: happy-dom, test/**/*.test.ts, test/setup-canvas.ts)
npm run build       # vite build && vite build --config vite.zone-map.config.ts
```

`npm run build` runs Vite twice on purpose (`vite.config.ts`): a single multi-entry build would hoist `src/register.ts` into a shared chunk that HA never fetches, so each bundle is built standalone and written to `../custom_components/apollo_mmwave/www/<name>.js` with `emptyOutDir: false` and terser minification. The two outputs, `apollo-radar-tuning.js` (from `src/index.ts`) and `apollo-radar-zone-map-card.js` (from `src/zone-map/card.ts`), are committed because the Python side serves exactly those filenames (`const.py` `JS_BUNDLES`) and HACS users never run npm. Any change under `frontend-src/src` must therefore be followed by a rebuild and a commit of `www/`.

The Python suite (`tests/`):

```sh
uv venv && uv pip install -r requirements-test.txt
uv run --no-project pytest tests/
```

`requirements-test.txt` pins `pytest-homeassistant-custom-component` (which pins a matching `homeassistant`, 2026.10.0 at the time of writing) and `home-assistant-frontend`, needed because `manifest.json` depends on `frontend`. CI therefore exercises only the top of the supported range; the `hacs.json` floor, 2026.8.1, is verified locally against a venv holding that version, which is also where the HA APIs the calibration feature relies on were checked. `pyproject.toml` sets `testpaths = ["tests"]` and `asyncio_mode = "auto"`. `tests/conftest.py` auto-enables custom integrations; fixtures register an ESPHome radar device with three target pairs.

Linting:

```sh
scripts/bootstrap     # venv + pip install -r requirements.txt + pre-commit install
scripts/lint-check    # uv run ruff format . --check && uv run ruff check .
scripts/lint          # same, with --fix
```

Ruff is configured in `pyproject.toml` (`select = ["ALL"]`, target py314, test exemptions). `.pre-commit-config.yaml` runs `ruff check --fix` and `ruff format` on staged Python files.

CI (`.github/workflows/`):

- `lint.yml`: Python 3.14, uv, `scripts/bootstrap`, `scripts/lint-check`.
- `test.yml` job `pytest`: `uv venv`, `uv pip install -r requirements-test.txt`, `uv run --no-project pytest tests/ -q`.
- `test.yml` job `frontend` (working directory `frontend-src`): `npm ci`, `npx tsc --noEmit`, `npm test`, then `npm run build` followed by `git diff --exit-code ../custom_components/apollo_mmwave/www`. The diff fails the job when the committed bundles do not match a fresh build, which is how stale `www/` output is caught.

The vitest suite runs in happy-dom 14, which has two Lit limitations worth knowing before writing a card test: child-part markers at the root of a template and inside `<svg>` are mis-cloned, so templates keep their bindings inside an element and the gate-energy chart's SVG is a nested template whose bars are asserted on the template (`test/gate-energy-chart.test.ts` `flat`) rather than the DOM; and a `<button>` reports `tabIndex` -1 unless it carries `tabindex="0"`.
- `validate.yml`: hassfest and HACS validation (`category: integration`, `ignore: brands`) on push, pull request, daily cron and manual dispatch.

Local development uses `scripts/develop`, which runs `hass --config config --debug` with `./custom_components` on `PYTHONPATH` and `config/configuration.yaml` (debug logging for `custom_components.apollo_mmwave`). The devcontainer (`.devcontainer.json`) runs `scripts/motd` on start.

## Known limitations

These were confirmed against the code when this document was written. `README.md` lists the user-facing ones under "Known limitations". Items fixed by the full audit are recorded in `REVIEW_REPORT.md`; the list below describes behavior that is still present.

- The card overwrites `input_units` on every write with its own YAML value (`_saveZoneUpdate`) and never reads the payload's `input_units`. `yd` is accepted by the backend (`INPUT_UNIT_FACTORS`) but absent from the card's `LENGTH_UNITS`, which normalises unknown units to `mm`.
- The LD2450 registry listener has no event filter and reacts to this integration's own zone entities as well as the radar's.
- JS cache busting uses only the `manifest.json` `version` for the `?v=` query, with Home Assistant's long-lived cache header on the static path. A `www/` rebuild without a version bump is invisible to browsers that cached the old module.
- `radarDeviceKey` (`strategy.ts`) omits the device name and base name, so a device rename does not refresh the tab title or path until a page reload; entities registered after the first detection do not add rows either.
- Zone card reload recovery depends on the admin-only `config_entries/subscribe` feed; non-admin viewers recover only through the bounded `not_loaded` retry or a page reload.
- Editing a strategy view in the Home Assistant UI discards its cards; that is how Home Assistant treats strategy views. Use "take control" on the dashboard instead.
- The chart's one-click engineering mode and every calibrate card action need `hass.callService`, which every current HA frontend provides; without it the chart shows only the SVG text and the card's buttons stay disabled.
- Snapshot history lives for the integration's lifetime: `async_remove_entry` deletes `apollo_mmwave.calibration` along with the zone store, and only `MAX_SNAPSHOTS` are kept per device.
- The numeric pre-flight sees only enabled gate entities and Home Assistant's copy of their state; the LD2412 refresh before the capture, the read-back verification and Undo are the backstop for what it cannot see.
- The calibrate card offers only the newest snapshot as Undo (`undoLabel` names `snapshots[0]`, which is what `restore_gate_thresholds` picks without a `snapshot_id`); older snapshots are reachable through the service.
- The "Restored the thresholds from 14:31" line names the result's `restored_from`; for a stored result without it, it infers the restored snapshot as the entry older than the redo snapshot in the payload's list, and drops the time when that entry is missing.
